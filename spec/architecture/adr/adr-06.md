### ADR-06: `chat_notification_preferences` is a new table, not a column on `notification_preferences` (Chunk 05)

**Decision:** Chat per-channel + per-kind preferences live in a dedicated table `chat_notification_preferences (user_id, chapter_id, scope text in ('channel','kind'), scope_id uuid|null, scope_kind text|null, level text in ('all','mentions','off'), updated_at)` with a unique index over `(user_id, chapter_id, scope, coalesce(scope_id::text, scope_kind))`.

**Rationale:** The existing `notification_preferences` table is boolean (`is_enabled`) and category-keyed. Chat needs a tri-state level (`all` / `mentions` / `off`) and two scope arms: per-channel (default for muting one channel) and per-kind (default for muting all `system_audit` messages globally). Squatting on `category` to encode `channel:<uuid>` or `kind:system_audit` loses type safety, complicates indexes, and would force a brittle string-parsing layer in the worker. **Alternatives considered:** (a) extend `notification_preferences` with a level column — would orphan every existing row's semantics; (b) inline preferences in `users.metadata` JSON — no DB-enforced uniqueness, hard to query at scale. Migration path: when chat is the last preference producer, a follow-up PR consolidates both tables behind a single view.

**Consequences:** Two preference tables until consolidation. The push worker queries both arms in a single `eq(user_id).eq(chapter_id)` load per recipient and resolves precedence locally (channel-pref ▶ kind-pref ▶ channel-name default). The defaults live in `apps/api/src/modules/chat-push-worker/push-rules.ts:defaultLevelFor` so the rule chain is unit-testable without DB seeds; [`spec/behavior/notifications.md`](../../behavior/notifications.md#chat-notification-preferences) § Chat notification preferences is the doc that states them. *(2026-09-05: an inline copy of the defaults stood here and had already drifted — it named four arms and omitted `imported`. Deleted rather than corrected, per [`DOCUMENTATION_CONVENTIONS.md`](../../../docs/internal/DOCUMENTATION_CONVENTIONS.md#where-a-fact-lives) § Where a fact lives. The decision recorded above is unchanged.)*

- **Amendment (2026-09-05) — the per-recipient load is now batched ([#552](https://github.com/pdcarlson/Frapp/issues/552)).** The consequence above described one load *per recipient*, awaited inside the worker's recipient loop; a 150-member channel therefore issued about that many preference queries per message, on a Realtime handler with no backpressure. `findForUsers(userIds, chapterId)` now reads the whole audience with `in(user_id).eq(chapter_id)` and groups the rows by user, so the count is one query per 100-member chunk (`ID_CHUNK_SIZE`, the 414 bound measured in `apps/api/src/domain/utils/chunk-ids.ts`) plus the terminating empty page each chunk pays under the #686 paging rule. Precedence resolution is unchanged, and a user absent from the returned map means "no stored preferences", exactly as the per-user empty array did. A chunk whose read fails is dropped whole rather than returned half-populated: an incomplete row set resolves to a *different* level than the default, where an absent one resolves to the default the old failure path produced.

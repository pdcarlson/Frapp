# Mobile Interaction Patterns

> Client-side mechanics behind the screens: bottom sheets, QR check-in, study sessions, dues payment, chat, and push notifications. Server-side rules stay in [`../../behavior/`](../../behavior/README.md) — this doc links, never restates.

Screen ids reference [`screens.md`](screens.md); surface rules (native-feel, Expo Go isolation, styling) are in [`README.md`](README.md).

## Bottom sheets

Creation flows are sheets (s19 new task, s20 log service hours, s21 upload document, s23 adjust points, and the s17 Ask presentation). One-tap actions never are — see [`README.md`](README.md).

- Library: `@gorhom/bottom-sheet` **v5**. Sheets are components hosted by their parent screen, not routes.
- Detents: snap to content height (`enableDynamicSizing`) for a sheet whose body is bounded. **A sheet with a scrollable body takes a fixed detent instead** — dynamic sizing plus `maxDynamicContentSize` is exactly the combination that breaks a nested scrollable (see the bullet on sheet-aware scrollables below, and the note at the second modal in `apps/mobile/components/tasks/new-task-sheet.tsx`). s17 is the worked case: its body grows without bound as answers land, so it ships the drawn cap as a fixed `["78%"]` snap point rather than a dynamic sheet that would resize under every answer. **The 78% is the cap the reference draws** (`max-height:78%` on s17, `canvas-screens.dc.html`); this bullet used to read "snap to content height; tall sheets (s17, s20) cap at roughly 78%", which taken literally prescribes the one combination that cannot work here.
- Sheet chrome uses the sheet radius and elevated surface from [`../design-system/foundations.md`](../design-system/foundations.md), with a drag handle and title row. A **trailing Cancel where the reference draws one** — s19, s20, s21, s23 do; **s17 does not**, and the reference wins: its header row is ✦ + "Ask Signet" with a trailing caption where Cancel would sit, and the grabber and scrim are the dismissal ([`../design-system/components.md`](../design-system/components.md) §9).
- **Scrim.** A presented sheet draws a `BottomSheetBackdrop` at `rgba(0,0,0,.55)` as drawn, appearing at the first detent and gone at dismissal (`appearsOnIndex={0}` / `disappearsOnIndex={-1}`), so nothing dims a screen with no sheet over it. s17 (`apps/mobile/components/ask/ask-sheet.tsx`) is the first sheet in the app to draw it; the sheets that predate it are tracked with the rest of their chrome drift.
- Text fields inside a sheet MUST use `BottomSheetTextInput` (plain `TextInput` breaks the sheet's keyboard coordination), with `keyboardBehavior="interactive"` on the sheet.
- `react-native-keyboard-controller` does not run in Expo Go. It lives behind an execution-environment check (isolation module per [`README.md`](README.md)); Expo Go falls back to `KeyboardAvoidingView`.
- Sheet chrome is styled with typed `StyleSheet` token factories. **NativeWind on sheet chrome is a hard ban** (research-derived; the full ban list is §2 "De-Google guardrails" in [`../design-system/README.md`](../design-system/README.md)).
- **The shared chrome implementation is `apps/mobile/components/sheet-scaffold.tsx`** — `SheetGrabber`, `SheetHeader`, `SheetPrimaryButton`, `useSheetBackgroundStyle`. Reach for it rather than hand-rolling a grabber, title/Cancel row, or CTA; the sheets predating it (`service-hours.tsx`, `sheet-demo.tsx`) still carry their own copies, tracked separately. Same relationship `state-block.tsx` has to the state family.
- A list inside a sheet MUST use the sheet-aware scrollables (`BottomSheetFlatList`, `BottomSheetScrollView`) **as a direct child of the sheet**, with fixed snap points. Nested inside a `BottomSheetView` under `enableDynamicSizing`, the view writes its frame height and the scrollable writes its content height to the same animated value, so a long list snaps the sheet to full screen and then jumps back. A roster-sized picker therefore gets its own stacked sheet rather than expanding inline (s19).

## QR check-in (s18 member scanner, s22 host display)

- **Token design:** the host screen renders a server-signed rotating token — HMAC-signed, ~30-second TTL. The server accepts the current and the immediately previous window, so a scan racing a rotation still lands. This is a signed nonce scheme, **not TOTP** — there is no shared secret on member devices to leak.
- **"Single-use" is per member, not per code.** This bullet used to read "single-use on redemption", which cannot be literally true: one host code is scanned by everyone in the room inside the same 30-second window, so a globally single-use token would admit exactly one member. What is enforced is one check-in per member, by the unique `(event_id, user_id)` index inside `check_in_event` — there is no redemption ledger over tokens, deliberately. Server rules: [`../../behavior/events.md`](../../behavior/events.md).
- **The token is verified when supplied, never required.** The chat event card checks in with no token, by design (`../../behavior/events.md` § Chat Integration). So the rotating code raises the effort of passing a code around; it is not an access control, and the geofence below is what actually gates presence.
- **Geofence is the real anti-proxy layer.** Any displayed code can be screenshotted and forwarded; the check that defeats proxy check-ins is the server's zone check on the scanner's location. The rotating code raises effort; the geofence enforces presence.
- **The zone is per event and opt-in** (`events.check_in_zone`), so s18 must only claim a location check when the event actually carries one — an unconditional "the geofence is the real check" line would be a security claim about something not running. The screen requests location only for a zoned event, and names the zone from `check_in_zone_name` ("Inside the Great Hall zone"). Foreground permission only; the "no background location" ban below is binding here too.
- **Scanner:** `expo-camera`'s `CameraView`. `onBarcodeScanned` fires repeatedly for one physical code — the client MUST latch the first read and debounce until the server responds, or one scan becomes N redemption attempts.
- **QR rendering is always dark-on-white** (s22: white card on the dark screen), even in dark UI. Scan reliability beats theme purity.
- **Fallbacks:** a short manual rotating code on the host screen (s22 "Show code") for members whose camera fails, and an officer manual override — every override is audit-logged.
- Check-in window, role gates, and the atomic attendance-plus-points award are server rules: [`../../behavior/events.md`](../../behavior/events.md) and [`../../behavior/points.md`](../../behavior/points.md).

## Study sessions (s10)

Client obligations for the geofenced study timer. The session state machine, pause/grace semantics, and expiry rules are owned by [`../../behavior/study-sessions.md`](../../behavior/study-sessions.md).

- **Foreground-only.** The app never requests background location and never the "Always" permission — While Using only. "No background location" is a binding ban, not an optimization.
- **Wall-clock timestamps.** Credited time derives from server-recorded timestamps, never an accumulated client-side timer — a clock the client owns is a clock the client can inflate. Concretely: the displayed figure is `total_foreground_minutes` plus the gap since `last_heartbeat_at`, which is the same span the next heartbeat converts into whole minutes, so the number never runs ahead of what the member will be paid for. `apps/mobile/lib/study/session.ts` owns that derivation.
- **AppState pause/resume:** backgrounding triggers the pause call; returning within the grace window (default 5 minutes, chapter-configurable per zone — s10 surfaces it as "a 5-min grace window", reading the number off the selected zone rather than hard-coding the drawn five) resumes without losing time. The client tracks the last foreground state it *reported*, and rolls that back when a pause or resume call fails, so a dropped call is retried instead of silently permitting background accrual. Exact semantics: behavior spec above.
- **Heartbeat:** every 5 minutes in the foreground, at `Location.Accuracy.Balanced` — precise enough for a building-scale polygon, cheap enough to not drain the battery.
- **Stale sessions die server-side.** A client that crashes or goes silent cannot bank time: the server voids sessions via its stale-heartbeat rule and resolves lapsed pauses on every entry point. The client never needs cleanup logic of its own — but it does need to *read* the outcome: a session ends by **returning 200**, not by throwing, so pause, resume, heartbeat and stop each have to be checked for a terminal status. A client that only inspects its `catch` block keeps a dead session ticking on screen.
- **Permission primer:** the location primer is contextual — shown on the first Start-session tap, explaining the zone check, never at app launch.

## Dues payment (s11)

- Payment runs through **Stripe PaymentSheet** confirming the existing PaymentIntent flow (`POST /v1/invoices/:id/payment-intent` returns the client secret). No new payment backend for mobile. A PaymentIntent is per invoice, so the CTA settles **one** invoice — the earliest due — and says which when more than one is open.
- **The webhook is the source of truth.** PaymentSheet success is provisional: the client shows the invoice as processing and flips it to Paid only when the server (webhook-driven) says so. Idempotency, reconciliation, and invoice states: [`../../behavior/billing.md`](../../behavior/billing.md).
- **Copy says "chapter dues", never "subscription".** Member dues and the chapter's own Signet subscription are different billing concepts; the UI must never blur them. General copy rules: [`../design-system/writing.md`](../design-system/writing.md).
- The whole payment path sits behind a runtime `isStripeAvailable` guard (Stripe RN does not run in Expo Go — isolation module at `apps/mobile/lib/payments/stripe.ts`, per [`README.md`](README.md)). The guard folds in the publishable key (`EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY`), because a member cannot tell a missing native module from a missing key and neither one lets them pay. When unavailable, the screen still renders balance and history; the pay CTA is **disabled with the reason stated**, not hidden — the two causes get different sentences, since one is fixed by an installed build and the other is a deployment setting the member cannot change.

## Chat (s04 list, s05 thread)

Message semantics, read receipts, unread, and mention resolution are owned by [`../../behavior/chat/README.md`](../../behavior/chat/README.md). The hot path itself is shared code — `@repo/chat-core`, which web consumes too — reached through three injected platform ports. Client rules:

- **Inject `NetworkState`. Always.** It is _optional_ on both `ManagerContext` and `ChatActionContext`, and omitting it falls back to the browser implementation, whose probe is `navigator.onLine === false`. React Native defines `navigator` but never sets `onLine`, so that evaluates `undefined === false` and the adapter reports **permanently online** — every offline gate stops queueing and sends are attempted against a dead network. The fallback is silent, so a missed injection throws nothing; `lib/chat/adapters.spec.ts` pins it.
- **Inject `KeyValueStore` too, and respect its seam.** The port is synchronous while AsyncStorage is not, so the mobile adapter serves reads from a boot-hydrated in-memory mirror and persists behind them. That is only sound because its sole consumer is the `chat:lastSeen:<channelId>` backfill cursor, where a miss widens the backfill rather than losing a message. A consumer needing real durability needs a different port.
- **`OutboxStore` has no default, by design.** Constructing a `ChatActionContext` without one is a compile error rather than a silent no-op, because dropping queued sends is the failure it exists to prevent.
- **Await the adapter boot before first read.** Both the mirror and the connectivity cache are synchronous ports over asynchronous platform APIs, so they need one hydrate/prime pass before the manager subscribes.
- **The viewer id is `users.id`, not the auth uid.** `chat_messages.sender_id` references `users(id)`, so it comes from `useCurrentUser()` — not the Supabase auth uid in `lib/auth-session.tsx`. The wrong id renders and sends without error but breaks own-message styling and the RLS-scoped delete behind `unreact`.
- **Wire chat from a hook, not a provider.** `app/_layout.tsx` is frozen ([`navigation.md`](navigation.md) § Hotspot freeze), so the runtime is a hook the chat screens call. `chatRealtime` is a module singleton that already refcounts per channel, so `configure` is an idempotent rebind and no screen calls `destroy()` — with no single owning provider, one screen unmounting must not tear the manager out from under another.
- **Never re-derive unread.** Counts come from `GET /v1/channels/unread`; [`../../behavior/chat/README.md`](../../behavior/chat/README.md) § Read Receipts is explicit that clients MUST NOT compute them.
- **Import `@repo/chat-core` by subpath.** The barrel additionally re-exports `./dispatch` → `@repo/chat-integrations`, whose `types` and `require` conditions point at a `dist/` that is never built (#989). It resolves today, but slash commands are not wired on mobile and the subpaths are the narrower contract.
- **There is no `crypto` global in React Native — never call `crypto.randomUUID()`.** No JS-level polyfill exists in the graph this app bundles: Expo's WinterCG runtime (`node_modules/expo/src/winter/runtime.native.ts`) installs `TextDecoder`, `URL`, `DOMException`, `structuredClone`, and `fetch` but _not_ `crypto`; `react-native` installs none; and neither `expo-crypto` nor `react-native-get-random-values` is a dependency. (That Hermes itself exposes no `crypto` is a documented engine property, not something this repo has executed — nothing has run on a device, #938.) `client_message_id` therefore comes from `randomClientId()` (`@repo/chat-core/random-id`), which prefers `crypto.randomUUID`, then `crypto.getRandomValues`, then `Math.random`, so it upgrades itself automatically if `expo-crypto` is ever added. This is the class of defect neither test suite can catch: vitest runs on Node, where `crypto.randomUUID` exists, _and_ aliases `react-native` to `react-native-web`. Grepping an exported bundle is not a valid re-check — globals come from the native VM, not the bundle.
- **The thread must not use `ScreenShell`.** The shell wraps its children in a `ScrollView` (`components/screen-shell.tsx`), and a `FlatList` nested in a `ScrollView` loses windowing entirely — every message ever loaded mounts at once. s05 hand-rolls `SafeAreaView` + `FlatList` + `KeyboardAvoidingView`; `app/(auth)/chapter-picker.tsx` is the other screen that opts out. s04 legitimately keeps the shell: a channel list is tens of rows, and the shell owns the `headerAction` slot the ✦ Ask pill needs.
- **Key the list by `client_message_id`, not `id`.** It is always present and is stable across the optimistic → confirmed transition; the server id is not, so keying on it remounts every row the moment a send confirms.
- **Opening a channel marks it read.** `POST /v1/channels/{id}/read` stamps the cursor to server `now()` — there is no mark-read-to-a-message API, so this fires on channel entry, not on scroll. Its invalidation of `["channels"]` prefix-matches the `["channels", "unread"]` key, so the s04 badges refresh without a second call.
- **Drafts are AsyncStorage, not the `KeyValueStore` port.** `OutboxStore.clearDraft` removes `chat:draft:<channelId>`; the write half is `lib/chat/draft-store.ts` against the same key. It deliberately does not ride the KV mirror, whose synchronous-read seam is sound only for the `chat:lastSeen:` cursor.
- **`ctx.toast` is undefined on mobile**, so every failure toast inside chat-core is a silent no-op. For `sendMessage` that is recoverable: a terminal 4xx also lands as `_status: "failed"` plus `_error` on the cached message, and the thread renders that inline with retry and discard. `react` and `unreact` have no such cache-row fallback — the optimistic-toggle rollback carries no explanation on its own — so `ChatActionContext.onError` (#999) is the platform-neutral sink `chat-client.ts` fires alongside `toast` on a rejected reaction. `use-chat-channel.ts` wires it per call into `reactionError`, mirroring `sendError`; `chat-thread.tsx` renders it as a dismissible banner above the composer, since a reaction failure has no bubble to attach retry/discard to. Do not add a second `onError`-shaped sink for a future failure class without checking whether this one already fits — it exists precisely because mobile has no toast at all, not because reactions are special.
- **Resolve display names from the roster projection, never per message.** Both the s05 author labels and the s04 DM row titles go through `useMemberDisplayNames()` (`@repo/hooks`) — one cached `GET /v1/members/roster` per chapter — with the shared rule in `packages/hooks/src/display-names.ts` so web resolves identically instead of growing a second copy. Do **not** reach for `useMembers()`: it returns the full profile, and putting every member's email, bio and city on the device to draw a name is the over-fetch #986 objects to. Resolving by `sender_id` rather than joining onto the message is not a preference — `spec/behavior/chat/README.md` records why no join can reach the live delivery path. Two mobile specifics: `users.display_name` is `NOT NULL DEFAULT ''`, so treat `''` exactly like a missing id, and the id subtracted from a DM's `member_ids` is `users.id` per the viewer-id rule above.

## Push notifications

Server-side routing, preferences, and delivery are owned by [`../../behavior/notifications.md`](../../behavior/notifications.md). Client rules:

- **Android channel before permission.** Create the Android notification channel _before_ requesting permission — on Android 13+ the prompt and delivery behave correctly only when the channel already exists.
- **Contextual primer, never at launch.** The opt-in primer appears at the first moment push has obvious value — first RSVP or first chat open — and on the first-run screen (s03) as a card, never as a cold launch-time OS prompt. Declining is a quiet "Not now"; the OS prompt fires only after the user accepts the primer.
- **Cold-start dedup.** A notification tap that launches the app is read via `getLastNotificationResponse()`, then cleared with `clearLastNotificationResponse()` — otherwise the same tap re-navigates on every remount of the handler. **These are the synchronous pair.** This bullet named `getLastNotificationResponseAsync` / `clearLastNotificationResponseAsync` while the epic still targeted SDK 56; SDK 57 deprecated both, and the app runs `expo-notifications@57`. Verified against the installed type declarations, not from memory.
- **Token lifecycle follows auth.** Register the push token on sign-in, deregister it on sign-out; a token MUST NOT outlive the session that created it.
- **Never call `getDevicePushTokenAsync` inside the token listener.** The listener fires on token changes; fetching a token from inside it can re-trigger the listener and loop. **The stronger form ships:** the function is *absent from the structural type* the app declares for the package (`lib/notifications/push-types.ts`), so the call is unwriteable rather than merely discouraged — nothing in the app can reach it, because that type is the app's only handle on the package. `push.spec.ts` pins its absence. Delivery uses Expo push tokens regardless (`Expo.isExpoPushToken` filters them server-side), so the raw APNs/FCM token has no caller here.
- Remote push does not run in Expo Go — it lives behind an isolation module ([`README.md`](README.md)); in Go, notification UI renders from in-app data only. `expo-notifications` needed the **platform split**, not a bare lazy require: it links native modules at import, so the web/SSR half (`lib/notifications/push-module.ts`) contains no specifier for the package at all and only `push-module.native.ts` requires it. ESLint bans a direct `import` of it **anywhere** in `apps/mobile` — including inside `lib/notifications/`, which is why the native half reaches it through a `require` with an inline `no-require-imports` disable — and the message names `@/lib/notifications/push` as the way in. A dynamic `import()` is banned by the same pair of rules: it is still an import.
- **Push is unavailable in every build that currently exists.** `getExpoPushTokenAsync` needs an EAS `projectId`, and no EAS project has been created (#938, open and `[human]`), so `isPushAvailable()` is false on device and in Go alike. That is reported rather than papered over: `pushUnavailableReason()` returns a *different sentence per cause* — an Expo Go session cannot receive push at all, a missing project id is a deployment setting the member cannot change — and a placeholder project id is never invented ([`../design-system/components.md`](../design-system/components.md) §5, the ruling the dues Pay CTA already follows).
- **Local notifications need the module but not the project id.** They never leave the device, so the study-pause notice (#1065, [`../../behavior/study-sessions.md`](../../behavior/study-sessions.md) § Anti-Distraction) is the one push-shaped thing that works in a real build today. It is posted only after `/pause` returns, cleared on resume and on session end, and every call is best-effort — a notification that cannot be posted must never fail the pause that triggered it.
- **Taps resolve through one table.** `lib/notifications/targets.ts` maps `data.target.screen` to a route, and s14's in-app rows resolve their `href` through the same module, so an in-app tap and a push tap cannot name different screens. The vocabulary is the server's (`chat`, `events`, `tasks`, `billing`, `points`, `service`, `members`); anything unrecognized — or missing its required param — falls back to `/notifications`, which always renders. A cold-start target is **held pending** until the member is authenticated with a chapter, and dropped if they sign out first.
- **`app.json` config, and what is deliberately absent.** The `expo-notifications` plugin sets `color` (`#EFB63B`, house gold) and `defaultChannel` (`"default"`, the one Android channel this app defines) and **no `icon`**: no notification icon asset exists, and pointing the plugin at a wrong asset would be inventing configuration. `UIBackgroundModes` is deliberately not set — that flag is for silent/background pushes, which this app does not send.
- **Implementation map.** `lib/notifications/push.ts` (isolation module and availability), `push-module.ts` / `push-module.native.ts` (the split), `push-types.ts` (structural type), `targets.ts` (payload → route), `push-registration.ts` (the registered row, stored because deregistration is `DELETE /v1/push-tokens/{id}` by **row id** — there is no delete-by-token and no list route, so the id returned at registration is the only handle on the row), `primer.ts` + `components/notifications/push-primer-card.tsx` (the s03 card, hosted by `(auth)/welcome.tsx`), `study-pause.ts` (#1065), and `use-push-runtime.ts`, mounted once by `components/app-runtime.tsx` above the auth gate because tab screens mount lazily and a runtime on a screen would miss the cold-start read.

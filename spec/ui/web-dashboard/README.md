Two rules for reading the board, each learned by breaking it once:

- **Transcribe it, never lift it.** Its CSS was written for one demo tenant in a design tool. Copied verbatim, its scrollbar rule renders none of what it specifies in Chromium 121 and later ([`tokens.md`](tokens.md) § L-01), its 404 crest at `opacity:.9` composites to a gold that is not the mark's, and its 24px radius is off [`foundations.md`](../design-system/foundations.md)'s §8 radius map, and its 40px buttons, on the §9 scale to a mouse since 2026-11-05, were under the touch floor before the scale split by pointer. Take its intent at this repo's tokens.
- **Where the board draws a product this codebase does not have, the product wins.** It draws a two-tier plan with a price, seats and a card on file, and a Join code tab and a Subscription tab. None of those exists, so none is drawn ([Billing](#billing), [Settings](#settings)). Its demo tenant is also the house tenant, so a gold on the board may be the chapter accent, the fixed Ask family or the mark, and the board cannot say which: [`tokens.md`](tokens.md) § L-01 names that trap.

### No em dashes in product copy

This lock is about **product copy**: UI strings, empty states, error text, labels, tab titles, and anything else a member reads in the app. It is a de-slop rule, not a typographical purge. [`../landing/README.md`](../landing/README.md) extends it to the landing's marketing copy.

It deliberately does **not** reach two places:

- **Approved microcopy in [`../design-system/writing.md`](../design-system/writing.md) §7.** Several approved strings carry an em dash, including the shipped connection-state copy, and they ship on more than one surface. Rewriting one is a writing.md change with its own review, not a side effect of another change; a change that touches one rewrites it and updates §7 in the same diff.
- **Repository prose.** Specs, ADRs, code comments and commit messages keep the house style.

One known gap: `@repo/chat-core`'s dispatch notices carry em dashes and render on `/chat`, as a failed slash command's `message._error`. That package is shared with `apps/mobile`, which this lock does not reach, so rewriting them is a two-surface copy decision ([#2184](https://github.com/pdcarlson/Frapp/issues/2184)).

No CI check enforces this lock; it is a review rule. A line grep for `—` over `apps/web` is mostly comment prose, so sweep with a JS/TSX-aware lexer that reads only string literals and JSX text.

## Navigation map

Source of truth: [`apps/web/components/layout/nav-config.ts`](../../../apps/web/components/layout/nav-config.ts). Each item may declare `requirePermission` or `requireAnyOf`, and an item with neither shows to every member; the shell hides items the caller cannot access. The caller's effective permission set is loaded per chapter via `GET /v1/users/me/permissions` and cached with TanStack Query, keyed by chapter id (resolution rules: [`spec/behavior/rbac.md`](../../behavior/rbac.md)). Controls inside a screen gate through `<Can>` or the `can()` / `canAny()` / `canAll()` helpers, which live in `@repo/validation` ([`packages/validation/src/permissions.ts`](../../../packages/validation/src/permissions.ts)) rather than in `apps/web`, because `apps/mobile` needs the same gate and the wildcard `*` rule has to match the server's `PermissionsGuard`: a per-app copy is how that drifts.

A Chat anchor, two member sections (Chapter, Resources), and one unlabeled group holding Directory and Chapter settings (Billing left it for Chapter settings' Plan and billing row in [#3827](https://github.com/pdcarlson/Frapp/issues/3827)). Activity leads the Chapter section: it is the inbox for the rows under it ([§ Activity](#activity)). There is no Polls row: polls live in the channel where they were made, and the chapter-wide `/polls` list, which could only show the older REST poll shape no client creates any more, was retired ([#3871](https://github.com/pdcarlson/Frapp/issues/3871), Shawn, 2026-11-09). Officer setup and officer tools sit behind the Chapter settings row; there is no Admin group ([#2946](https://github.com/pdcarlson/Frapp/issues/2946)). The row was named Settings until 2026-11-10: it is the chapter's, and a member's own settings are a separate page on the account menu ([§ Two doors](#two-doors-chapter-settings-and-your-settings), [#3856](https://github.com/pdcarlson/Frapp/issues/3856)).

Five structural facts the table alone does not carry:

- **Chat is an anchor, not a section.** It renders first with no heading, because it is where `/`, `/dashboard`, and the route-group index all land — it is the app's home rather than a member of any group.
- **The nav fits a 1024×768 window for every seeded role.** Each row costs 36px (34px plus the 2px gap) and a section heading about 37px, against a 666px nav region at a 768px window. Before #2946 a President's 17 rows needed an 828px window and scrolled by 60px at 768. Folding the six-row Admin group into the Settings row took them to 12, which fit from a 613px window. [`apps/web/tests/visual/nav-fit.spec.ts`](../../../apps/web/tests/visual/nav-fit.spec.ts) fails the required `web-responsive-floor` job when the list no longer fits. The harness runs sessionless with an owner's permissions stubbed and the chapter read held open, so it measures every row at once. A new destination finds a home inside an existing row (a tab, or Settings) rather than growing the list. Paul chose this shape and its follow-ups on 2026-09-30; the options and evidence are recorded on #2946. *Changed in #3897 by shawnatomklein-eng, 2026-11-10:* the Activity row is a new destination that grows the list to 13 rows (36px more, still inside the 768px window; `nav-fit.spec.ts` measures it). Paul green-lit the page on #3897 and Shawn chose its own nav row over growing it out of chat; the rule stands for other destinations.
- **A section heading hides with its items.** Section visibility is derived, never declared: `isNavItemVisible` (`apps/web/components/layout/protected-nav-item.tsx`) is exported so `app-nav.tsx` can ask the same question the items do, and a section with zero surviving items renders nothing at all. No section is officer-only any more: `protected-nav-item.spec.tsx` fails if every row of a section is hidden from an ordinary member, because that is the Admin group coming back.
- **Chapter settings is gated on "has anything here".** An ungated entry point sent members without `chapter-config:view` to a screen that could not load, which is the fail-fast rule in [`../design-system/README.md`](../design-system/README.md) §5 inverted. The row shows only when Settings holds a tab or a tool whose module is on for the viewer (`hasSettingsDestination`, `apps/web/components/settings/settings-access.ts`, applied through `NavItem.showWhen`). A treasurer whose only tool is Reports loses the row when the chapter switches Reports off, as the Reports row used to hide. The chapter switcher's "Chapter settings" link asks the same question, since it is another door into Settings, and so does the top bar's "Settings ›" crumb on the officer tools, which shows only when this row does (`page-title.ts`).
- **Profile left the nav** for the account menu (below). It is about the viewer, not the chapter, so it did not belong among chapter surfaces. It held two chapter-scoped cards until 2026-11-10: Notifications (#564), because `notification_preferences` is keyed `(user_id, chapter_id, category)`, and Blocked members (#2313), because a chat block is per-chapter too. Both are sections of the personal Settings page now, in its "In _chapter name_" group, and each still states its own no-chapter rung ([§ Two doors](#two-doors-chapter-settings-and-your-settings)).

**Directory is one screen with two tabs.** `/members` hosts `?tab=members|alumni` (`apps/web/components/members/directory-page.tsx`), and `/alumni` redirects into `?tab=alumni`. Actives and alumni are one directory; asking a member to know which list a person is on before they can look them up was the defect. The redirect keeps existing links and bookmarks alive, the same shape `/roles` uses to reach Settings → Roles (role IA canon: [`spec/behavior/settings/customization.md`](../../behavior/settings/customization.md)). `nav-config.ts` remains the source of truth for what renders. Every row links to a built route; the nav draws no roadmap entries, since a disabled row with nothing behind it is a dead-end control (the `Soon`-chip branch was deleted unused, #3089).

**The actives tab shows presence.** Each row carries a presence dot on the avatar (Online, Idle, Do Not Disturb, or Offline; the shapes are [`components.md`](../design-system/components.md) § Chat member list), and the member's custom status line under their name, from the chapter-scoped Realtime Presence topic specified in [`../../behavior/chat/README.md`](../../behavior/chat/README.md#messages) § Messages. Three rules it follows, each of which is the interesting case rather than the happy path:

- **No dot is not Offline.** Before the first presence `sync` lands, and whenever the network provider reports offline, no dot renders at all. Offline is a claim about *that member*; rendering it from our own unfinished join or our own dead socket would state something false about every person on the screen.
- **Colour is not the only carrier — for the Online/Idle pair.** Online is a filled dot and Idle is a ring, because `--success` and `--warning` are the green/amber pair colour-vision deficiency collapses; the ring's interior is opaque so an avatar photo cannot show through and make Idle read as filled. Online and Offline are separated by colour and opacity alone, which is acceptable only because the status is also *named*. The row is a button, and an `img`-role descendant would be absorbed into its accessible name and silently rename it as presence changed, so the dot is `aria-hidden` (`AvatarPresenceDot` has no labelled variant) and the row's own `aria-label` carries the status last, in a fixed position. Whatever renders the dot owns announcing the status.
- **No stale roster can be rendered as current**, and it takes two mechanisms because there are two ways to go stale. A teardown *we* initiate is covered by an attach **generation** bumped in render whenever the inputs that mint a channel change — a counter rather than a stamp of the inputs themselves, because the inputs come back: a wifi flap takes the subscription down and up with the chapter unchanged, so an input-derived stamp would match again on the way back and re-adopt the pre-outage roster. A channel that simply *stops* is the other way, and the generation cannot see it: a socket drop that never flips `navigator.onLine` leaves every input unchanged, so the transport has to say so — the subscription reports its own disconnection and the roster stops counting as evidence until it re-joins and re-syncs. From the inside, a quiet channel and a dead one look identical.

The **publisher is the dashboard shell, not this screen** ([`apps/web/lib/providers/chapter-presence-provider.tsx`](../../../apps/web/lib/providers/chapter-presence-provider.tsx)). A member is present because the app is open, not because they are looking at the Directory — scoping the tracking to the reading screen would make the dot mean "has the Directory open" and render everyone in Chat as Offline. It also keeps the topic to one channel: `attachRealtimeChannel` frees an occupied topic before minting, so a second subscriber would tear the first one down.

## Account menu

`apps/web/components/layout/account-menu.tsx` is mounted twice: on the top-bar avatar (`variant="topbar"`, at every width) and as a full-width row at the bottom of the mobile drawer (`variant="sheet"`, `dashboard-shell.tsx`). It carries the viewer's identity, then Status and the custom status line (2026-11-09, #3845: first, because it is the row a member reaches for before practice, as on Discord and Slack), then Profile, Settings (`/preferences`, the member's own settings page; it replaced the "Notification settings" link into `/profile` on 2026-11-10, [#3856](https://github.com/pdcarlson/Frapp/issues/3856)), What's new (`/whats-new`, the changelog members read, from `RELEASE_NOTES` in `@repo/validation`, the same list as mobile Settings → What's new; 2026-11-07; [§ What's new](#whats-new) has its unread dot), and Sign out. It replaced three scattered affordances in the same change — the Profile nav row, the header's bare `Sign out` button, and the standalone header theme toggle — rather than shipping beside them. The theme control it absorbed was itself deleted with `next-themes` in the #920 shell slice: the surface is dark-only, with no user-facing theme switch. That was half-true until the Profile & pre-auth slice — `/profile` still shipped a light/dark/system `Select` writing `user_settings.theme`, a field nothing on any surface has read since `next-themes` left. The control is gone; the orphaned API field is tracked separately.

- **Status** is a submenu row showing the member's current status (its dot, its name, and "Until 3:45 PM" while it has an end). It opens Online, Idle, Do Not Disturb and Invisible, each with its dot. Do Not Disturb opens its own submenu: Until I turn it off, For 1 hour, For 8 hours, and Until tomorrow (with the time it ends, 8:00 AM). Until I turn it off is the default and comes first, because a submenu row can only open its submenu, never select: opening it puts focus on the first row, so Enter takes the default. Do Not Disturb says "Only urgent notifications ring" and Invisible "You'll appear offline", each as a caption under its name. The current status carries a check. Where the window has no room to the right, Radix opens a submenu to the left, over the menu it came from.
- **The custom status row** reads "Set a custom status", or the line itself once there is one, and opens a dialog: one field (placeholder "At practice till 6", a code-point counter to 80, one line), "Clear after" (30 minutes, 1 hour, 4 hours, Today, Don't clear; Today the default), and Save, Cancel and, with a line set, Clear status. A field inside the menu was the alternative; the dialog is what Discord and Slack do, because a text field fights a menu's typeahead and arrow keys.
- **Both rows are disabled while the dashboard is offline**, as the Profile notification switches are ([`notifications.md`](../../behavior/notifications.md) § Preference sync), and until the member's settings have loaded. A pick saves optimistically through the shared settings mutation, so the dot moves on the click; a refused save rolls back and toasts.
- **Your own dot sits on the avatar** that opens the menu, in both variants, and the trigger's accessible name ends with the status ("Account menu for Paul Carlson, Do Not Disturb").

## What's new

What's new opens by itself once after an update, as on the phone (2026-11-09, [#3943](https://github.com/pdcarlson/Frapp/issues/3943)). The rule is the phone's, one function both surfaces call (`decideWhatsNew` in `packages/validation/src/release-notes.ts`), and [`mobile/screens.md` s16](../mobile/screens.md) describes it: which entries show, what counts as newer, and why a new member is shown nothing. This section holds only what is the web's own.

- **A dialog, not a sheet**, mounted in the dashboard shell beside the first-run tour ([`whats-new-host.tsx`](../../../apps/web/components/whats-new/whats-new-host.tsx)). It holds the entries this browser hasn't shown, drawn as the What's new page draws them, and scrolls inside itself when they run long. Esc, the X and a click outside close it. It has no Got it button, which would be a second close ([`components.md` § Chrome weight](../design-system/components.md#chrome-weight)); its one action is See all updates, to `/whats-new`.
- **"Seen" is kept per browser** (`localStorage`, [`lib/whats-new.ts`](../../../apps/web/lib/whats-new.ts)), as the phone keeps it per phone, **and on the account** (#4043). The first device a member opens after an update shows the notes in full; a browser whose account has already seen the entry it would open doesn't open it, and marks the account menu's row instead until What's new is opened there. [`mobile/screens.md` s16](../mobile/screens.md) states the rule for both. Before #4043 nothing on the account recorded it, so an entry read on the phone showed once more on the web, and once more in each new browser.
  - Changed in #4043 by shawnatomklein-eng, 2026-11-11: once per account, with a quiet mark on the other devices, where #3943 kept it once per browser.
- **A new member is whoever's account is no older than the newest entry**, or whose first-run tour is due. A browser holds nothing that tells an old install from a fresh one, which is what the phone goes by, so the account's age stands in. For them the entry is recorded without being shown. The stand-in has a known gap: someone whose account is older than the newest entry but who reaches the dashboard for the first time without the tour (a founder who signed up days before finishing the chapter wizard, or a member who onboarded on the phone) is shown the newest entry once.
- **It never covers a flow in progress.** Nothing is decided until the member has a chapter, so the chapter wizard is never interrupted; join links and sign-in are outside the shell. When it is time to open, it stands down if a dialog or menu is already up (the Terms prompt, an invite, anything the member opened), on Chapter settings (Plan and billing there is a checkout landing, and the shell reads only the pathname, so the whole route stands down, as the tour does; `CHECKOUT_LANDING_PATHNAMES` in `billing-paths.ts`) and on `/whats-new` itself. A stood-down entry stays unread and the next navigation tries again.
- **The account menu's What's new row carries a dot while an entry is unread**: the neutral `--foreground` dot every unread mark uses. It clears when the dialog opens or the member reads the What's new page, whichever comes first. When another device showed the entry first (#4043) the dot is all there is, and it stays across reloads until the member opens the What's new page.

## Top bar

A 48px bar ([`top-bar.tsx`](../../../apps/web/components/layout/top-bar.tsx)): the mobile nav trigger (`lg:hidden`) and the page title, a centered find field, the connection pill while there is a connection problem to report ([`connection-state.md` § One indicator](../resilience/connection-state.md#one-indicator); a fixed 28px dot slot below `xl`, so it never resizes the find field), notifications, the ✦ Ask entry, and the account avatar.

- **The page title is here** (2026-11-05, reversing #2141's "titles not in top bar" at the owner's request, and back where board `1f` pin 1 drew it, "Page title in the top bar"). `/chat` gets "Chat" there too, which the chat board `1b` leaves out: one rule for every route rather than a chat exception, with the channel name the thread's own `h2`. It is the route's only `<h1>`, at `label`/700 in the left cell, and it is derived from the route ([`page-title.ts`](../../../apps/web/components/layout/page-title.ts)) rather than passed up by the page, so the loading, offline, error and denied paths all carry it. The words are the nav row's label, so the row a member clicked and the heading they land on match, and each route's `metadata.title` (the browser tab) uses the same words; `page-title.spec.ts` checks the two against each other. Settings' tab read "Chapter settings" until then and now reads "Settings". A page reached from inside Settings (Chat admin, Discord import, Study zones, Reports) shows its parent as a link and a chevron, "Settings › Study zones", taken from the nav row that claims the route in `activeFor` and shown only when that row is. A page under a nav row that reads as its own step does the same under that row, "Backwork › Bulk upload" (`SUB_PAGE_TITLES`), and below `sm`, where the crumb is hidden, carries its own back link to the row; a top-level route shows its title alone, with no chapter-name prefix, because the chapter switcher sits beside it in the nav. Below `sm` the title is visually hidden and stays the `<h1>` for a screen reader: a 390px bar has room for the drawer trigger, the find field and the right cluster only, and sharing it cut both the title and the field to a stub. From `sm` up it truncates rather than wrap the bar. A route `page-title.ts` does not know gets no title rather than an invented one. **From the side-by-side width (1056px) up, a tool page's title moves into the page's own header** (2026-11-11, Paul asked for a way to close the panels on the right): beside chat, the top bar's copy sat over chat rather than over the page it named. The top bar's left cell is then empty on a tool route, the page's header carries the title (with its parent link) and the `<h1>`, and `/chat` keeps its title in the top bar. CSS shows one copy or the other, so the first paint is right before the width is known ([§ Chat](#chat)). Mobile keeps its in-screen titles ([`../mobile/patterns.md`](../mobile/patterns.md) § Screen headers).

- **Find** ([`find-bar.tsx`](../../../apps/web/components/layout/find-bar.tsx), [`find-dialog.tsx`](../../../apps/web/components/layout/find-dialog.tsx)) is a field-shaped button in the bar that opens a centered dialog, as does Cmd/Ctrl+F. The dialog searches channels, members, messages, events and backwork, in that order, with filter chips to narrow to one group, and every dated row carries its date: a message its sent day, an event its start, a backwork file its course, term and the day it was added ([`find-results.ts`](../../../apps/web/components/layout/find-results.ts)). Events and Backwork drop out when the chapter switches their module off (and stay out while that setting is still loading), and Backwork also drops out for a member without `backwork:upload` or `backwork:admin`, whom `/v1/search` sends no backwork rows either ([`search.md`](../../behavior/search.md)). Typing on the focused field opens the dialog with that text, as it would in the field it looks like. It replaced the ⌘K `cmdk` palette, which is deleted, and the chat channel list's own search field, which went with it. It carries **no navigation list**, so nav gating stays in one place (`nav-config.ts` and `isNavItemVisible`); a hand-maintained list of destinations here would be the defect the palette's derived list once fixed. One narrowing it carries: its Channels group matches the channel payload's `name`, which for a DM is not the participant's name, so typing a person finds the member but not the DM ([#2220](https://github.com/pdcarlson/Frapp/issues/2220)). Member, event and backwork rows open their route, not the item, because none of those routes takes a deep link yet. `cmdk` stays a dependency, because the slash palette and the onboarding wizard still use `components/ui/command.tsx`. **It departs from the board on three points** (Paul, 2026-11-05). It shows no `⌘F` / `esc` keycap, because the field is always on screen and the shortcut is a convenience rather than the way in. The field fills with `--surface-1`, the bar's own surface, rather than the board's `--card`, so it reads as part of the bar instead of a raised card on it. And the results open in a centered dialog rather than under the field (`1b` drew a visible field with no palette): the dropdown had no room for dates, full message previews or the two extra groups, and leaving Backwork out meant a search for a file that existed answered "No matches.". The field stays as the visible way in, so the board's reason for dropping the palette, a search you had to know a shortcut to reach, still holds. **Find is not Ask:** Find lists places to go from everything the member can read, chat included, in neutral chrome; Ask answers a question from official sources only ([`../../behavior/ai.md`](../../behavior/ai.md)) in house gold. When Ask can answer on web it opens as its own panel, not inside this dialog.
- **Ask** (`ask-pill.tsx`) is a shell. It opens a small popover anchored to the pill, stating that Ask cannot answer yet and pointing at the find field and Documents (a popover rather than a dialog since 2026-11-05, [Shell chrome](#shell-chrome)) — a control that silently did nothing would be the dead end [`../design-system/README.md`](../design-system/README.md) §5 rule 2 bans. No retrieval, no corpus, no model call. It paints in Signet's fixed gold family (the `gold-ask-*` tokens, 34px height / 10px radius in `ask-pill.tsx`; see [`../design-system/components.md`](../design-system/components.md) §7) — house gold, never the chapter accent.

## Page grammar

Every tool page sits flush on the shell (chat is a panel, not a page: see [The content row](#the-content-row)). The board draws few page bodies (`4d` for settings and billing, `4e` for roles, `4c` for the settings drawer, `1j` for the upload sheet, `1k` for 404 and error), so for the rest this grammar is **derived**: from `1f` pin 2 ("one toolbar row, no wrapper card, no description paragraph"), `1t`'s deletion list, and the table rule `4d` and `4e` share. A route that departs from it says why under [Surface decisions](#surface-decisions).

- **No wrapper card and no narration paragraph.** The body sits on `--background`, and the top bar supplies the title on every path, offline included, so a route draws no heading row of its own. A paragraph explaining the page to someone already on it is deleted, not restyled. A line that reports state stays, moved onto the page surface: the Reports preview's row count and partial-export note are state, not a card describing itself. A `<Card>` paints `--card`, one rung up the ladder. Where the board frames a block it draws a hairline frame, never a `Card`: billing's plan panel is `--surface-1` at radius 16, and its plan matrix a radius-14 frame on the page surface.
- **One toolbar row** carries the route's filters, search and primary action, pushed to the trailing edge ([`page-actions.tsx`](../../../apps/web/components/layout/page-actions.tsx)); a route with none draws no row and its body starts at the top of the pane. The controls sit at the toolbar height: 36 to a mouse, 44 to a finger (Button's `toolbar` size and the toolbar recipes in `table-controls.ts`, [`components.md`](../design-system/components.md) §3). A list row's secondary actions (Edit, Delete, an icon) take Button's neutral `ghost` variant.
- **Lists are flush.** A list is a `<ul>` on `denseListClassName` ([`components/shared/table-controls.ts`](../../../apps/web/components/shared/table-controls.ts)): top-border dividers, no zebra, no per-row fill, no `<Table>`. Rows come in two shapes, and the difference is deliberate:

  | | `/documents`, `/backwork`, `/billing` invoices, `/discord-import`, Chat Admin's categories and report queue | `/members` (actives and alumni), Chat Admin's channels |
  | --- | --- | --- |
  | Row is itself a control | No: text plus trailing controls | **Yes**: the row opens the member |
  | Height | `min-h-11` (44; on the Small step's 36 / 44 once [#3511](https://github.com/pdcarlson/Frapp/issues/3511) lands). `/backwork` is the exception: a seven-column grid at `@4xl:min-h-12` (48), stacking to two lines below a 896px page (`@4xl`) | `min-h-9`, and `pointer-coarse:min-h-11` (36, 44 on touch: the Small step) |

  `pointer-coarse` is [`components.md`](../design-system/components.md) §2's "compact 34px controls are web/pointer-only" carve-out in CSS: a mouse gets the board's density (`4a` draws a 34px member row), a finger the full 44. Trailing 32px row controls take `compactControlClassName` on the same rule. Rows **stack** on a narrow page (`flex-col`, becoming a row at a breakpoint: `sm` or `md` on pages not yet converted, the page's or list's own `@xl` or `@md` on those that are, § Responsive contract) rather than hide fields, because `display:none` removes text from the accessibility tree too, and at the 375px floor a hidden meta line exists nowhere in the product.
- **The checkbox column is gone; selection is not.** The checkbox is the row's leading element, and select-all sits in the list header whenever there are rows, never inside the selection bar (Events puts both behind Select, in a trailing column: below.) In the bar it would be a control conditioned on its own output: unreachable until a row is ticked, and unmounted by its own use, which drops keyboard focus to `<body>`.
- **States are the nested family, with `sole`; loading is the page's skeleton.** Loading draws the route's own skeleton ([`components.md`](../design-system/components.md) §10), not a state component. The whole-screen `ErrorState`, `LoadingState` and `OfflineState` paint `--card` (empty is one line since 2026-11-07, §10), so on a flush route they redraw the card the route deleted. `elevation-contrast.spec.ts` measures why the nested fill is right, but it reads only tokens and cannot see a route. The DOM guard is `cardFilledContainers` ([`tests/card-surfaces.ts`](../../../apps/web/tests/card-surfaces.ts)). `chat-admin-page.spec.tsx`, `chat-reports-card.spec.tsx` and `discord-import-page.spec.tsx` run it on the loaded list (the import page: each state of its one import) and on each loading, empty, error and offline state their surface draws (Chat Admin's pins, the report queue's no-chapter state and the import channel panel included), and `discord-import-wizard.spec.tsx` on the connect step's loading, error and offline states, so a `--card` container put back in one of those fails CI. `profile-panel.spec.tsx` runs it on `/profile` and its loading, error and offline states (the screen was seven stacked cards until 2026-11-05; each block is a section under its label now, in one form-width column). The chapter-ops routes flushed on 2026-11-05 run it too: `tasks-board.spec.tsx` on the loaded and empty board, `events-page-list.spec.tsx` and `events-calendar.spec.tsx` on the list, the true-empty state and the calendar, `points/page.spec.tsx` on the loaded page and its loading, error and offline paths (and `points-audit-card.spec.tsx` on the audit list and its denied state), `service-page.spec.tsx` and `study-page.spec.tsx` on the loaded page only, and `geofences-admin-page.spec.tsx` on the zone list. `members-directory.spec.tsx` runs it on the roster and its error state only, so the Directory's loading, empty and offline states are unguarded, as are the wizard's other steps and any state added without a test under the guard; `/documents`, `/backwork` and `/billing` have no guard at all. The exception is a no-chapter branch that replaces the whole page rather than a list (alumni, Backwork).
- **Empties split three ways**: empty, filtered and searched, per `3b` ("No results = neutral tile, names the query") and its six-word status budget. The strings live in [`../design-system/writing.md`](../design-system/writing.md) §7, which moves in the same change as any new state. **Amended 2026-11-06:** Points and Events draw these as one line where the rows would be, not a tile, and their search line doesn't quote the query, since it sits under the field that holds it and carries a Clear search link instead. Events splits further (the lines are listed in [`writing.md` § Events (dashboard)](../design-system/writing.md#events-dashboard)): the time window (`No upcoming events.`) is its own, because the default window hides past events without anyone touching a filter.
- **An absent value is absent, not a glyph.** In a `·`-joined meta line an absent fact drops out of the line. In a label-over-value tile the value reads `Not set` or `Not recorded`, because a label over nothing names nothing. A lone `—` is a character a screen reader announces standing in for nothing.
- **The upload sheet is `1j`** ([`components/shared/upload-sheet.tsx`](../../../apps/web/components/shared/upload-sheet.tsx)): radius 20, an 18/700 title, fields and footer buttons at the Small step (36 to a mouse, 44 to a finger; the board drew 44, [`../design-system/foundations.md`](../design-system/foundations.md) §9), inline errors on touched fields, and no instructional paragraph. Upload stays enabled and a missing file is an inline error; only a subscription refusal disables it, because that is a verdict about the chapter rather than the form. The well collapses to a file row. Since 2026-11-06 the well is a drop target, and `/documents` uses it inside a panel rather than this dialog ([`components.md`](../design-system/components.md) § Surface size, "Chapter document upload is a panel"), so the dialog chrome is `/backwork`'s alone. One thing the board draws is **not built**: an error slot on a metadata field, since no metadata field can be required yet, so the change that adds the first required one adds the recipe with it. A dialog with a genuine description (renaming a document folder re-files every document in it; a draft invoice is invisible to the member until it is sent) keeps it.
- **Confirmations are dialogs.** Every destructive confirmation goes through `useConfirmDialog` ([`components/shared/confirm-dialog.tsx`](../../../apps/web/components/shared/confirm-dialog.tsx)); no live `window.confirm` or `window.prompt` is left in `apps/web`. A dialog rendered inside a query's success branch is safe across a refetch, because the host settles a pending `confirm()` to `null` when its caller stops rendering it; check that before restructuring a caller around it.
- **The per-page settings drawer is `4c`**, its gear at the trailing edge of the route's `PageActions` row. `4c` pin 1 puts the gear "beside the page title"; since the title moved to the top bar (2026-11-05) it sits with the route's other actions instead, still shown only to roles that hold the page's manage permission. It is built once as [`components/layout/page-settings-drawer.tsx`](../../../apps/web/components/layout/page-settings-drawer.tsx) because `4c` pin 1 says "same gear, same drawer, on every page". It is a right-side `Sheet` at 400px, the primitive Notifications already uses, rather than the board's in-layout rail: taking the rail literally would add a third column to the shell's content row beside chat and the tool page. A second adopter uses this shell and does not draw its own panel. Its toggles are the shared `Switch`, which since 2026-11-05 is `4c`'s 36×22 to a mouse and 50×30 to a finger ([`components.md`](../design-system/components.md) §4): the board's size reaches a mouse, and a finger keeps the larger track. Neither track is 44px tall, so the drawer row around it still carries the touch target ([#3057](https://github.com/pdcarlson/Frapp/issues/3057)).
- **Crest art appears in one place**: the 404 page and the root error page, through one recipe ([`components/shared/crest-page.tsx`](../../../apps/web/components/shared/crest-page.tsx), board `1k`). `crest-page.spec.tsx` asserts that inventory, so no empty state grows crest art. The dashboard's own error boundary (`app/(dashboard)/error.tsx`, [#2175](https://github.com/pdcarlson/Frapp/issues/2175)) draws [`components.md`](../design-system/components.md) §10's card for a failed region instead, since the shell around it still works.

## Surface decisions

Per-route decisions that still bind. Each is either the product declining to be what the board drew, or a call the board did not make. A later change may revisit one, but it reverses the reason stated here rather than rediscovering the question.

### Activity

`/activity` gathers what is waiting on the member and what they made, so they don't have to look through channels and module pages for it ([#3897](https://github.com/pdcarlson/Frapp/issues/3897): Shawn's idea, 2026-11-09; green-lit by Paul, 2026-11-10; Shawn picked its own page over growing it out of chat, and the name). It is an inbox beside chat, the way Slack's Activity and Later, Discord's Inbox and GitHub's notifications sit beside their main surface. It is not a home: `/` and `/dashboard` still land on `/chat`. What the read returns, and who sees which row, is [`../../behavior/activity.md`](../../behavior/activity.md).

- **The page opens with a summary** ([#4173](https://github.com/pdcarlson/Frapp/issues/4173): Shawn found the page "a little bland and unimportant", 2026-11-11). One line says how much is waiting ("8 things need you", or "You're all caught up" at zero), with the next event under it, then a count tile per kind of ask, as Apple Reminders opens on its count tiles. A tile counts up to the read's cap of 25 and then says `25+`; a tile whose section could not be read shows a dash, and the headline then never says caught up ("Some of what needs you couldn't load", or "At least 8 things need you"). The tiles: Your tasks and Polls to vote on for everyone; To confirm for a `tasks:manage` holder and Hours to approve for a `service:approve` holder, since nobody else is asked; Check in now first, only while an event is open for check-in. A module the chapter has off shows no tile. A tile sets its chip, and pressing the lit one clears it; To confirm narrows to the confirmations alone, under a lit Tasks chip; a tile at zero dims rather than hides, so the row doesn't jump.
- **Four groups, in this order:** Needs you, Coming up, Links, Made by you. Each is a section label with its count over a dense list; a group with nothing says so in one line. An event the member can check in to right now sits under Needs you and not again under Coming up. **Needs you splits into Now and Later** (#4173): Now is anything waiting on the member's confirm or approval, an event open for check-in, a task overdue or due today or tomorrow, and a poll closing within a day; the rest is Later. When everything is one or the other there is no sub-heading. **Made by you splits by kind** (Polls you posted, Events you made, Tasks you assigned), so 17 assigned tasks no longer bury the rest; Files you uploaded was a fourth kind until [#4291](https://github.com/pdcarlson/Frapp/issues/4291) (Shawn, 2026-11-11), since a member's uploads are already in Documents and Backwork. **Polls you posted lists open polls only** ([#4258](https://github.com/pdcarlson/Frapp/issues/4258), Shawn, 2026-11-11): a poll closed by hand or past its closing time leaves the list, the moment its time runs out if the page is open, for an **Archived polls (N)** text button at the foot of Made by you, which opens the closed ones newest closed first, each opening its card with the final result. Needs you and the Polls to vote on tile likewise drop a poll whose time ran out since the read. A Needs you part draws 5 rows and a Made by you part 3, with **Show all N** for the rest; under a chip nothing is held back.
- **Chips narrow every group to one kind:** All, Tasks, Polls, Events, Hours, Links (Files went with [#4291](https://github.com/pdcarlson/Frapp/issues/4291)). Under a chip, Coming up, Links and Made by you are left out when they hold nothing of that kind (Made by you stays while it has archived polls under the Polls chip); Needs you always stays.
- **A row is one hit target:** a lead, a title, one line of detail (who and when), and a badge naming what it asks or where it stands. The lead is the kind's glyph from the shared nav set in a neutral 40px tile (a task the Tasks shape, hours the Service shape), as Teams' Activity marks each row, or for an event a calendar-style block with its month and day (#4173). The block is decoration: the detail line still says the day in words ("Tomorrow · 7:00 PM"), which is what a screen reader reads, and the year outside the current one. The glyphs stay neutral: on this page colour is for asks and status, never for a kind. An ask (`Vote`, `Confirm`, `Approve`, `Check in`) draws as the action it opens, in the tinted button's recipe, so it reads apart from a status (#4173; until then it was the `warning` badge, which looked like `To do` beside it). An overdue task is `destructive`; any other state is an `outline` or `success` badge. A task's state uses the shared task words every task surface uses.
- **An unread row carries a dot** ([#4402](https://github.com/pdcarlson/Frapp/issues/4402), 2026-11-12; what counts as unread is [`activity.md` § Unread](../../behavior/activity.md#unread)): the neutral `--foreground` dot every unread mark uses, in a slot of its own before the lead, as the notification drawer's rows and Linear's and GitHub's inboxes draw theirs. The slot stays when the row is read, so rows don't shift as dots clear, and a screen reader hears "Unread:" before the title. Opening the row (its panel, or a link's own page) clears it at once; scrolling past does not. Made by you never has one.
- **A row opens the record in a panel, drawn with chat's own card** (`components/chat/renderers/`), so the member votes, starts or finishes a task, confirms it, or checks in with the controls chat already taught them. The cards are not forked: the page hands each one a message built from the row (`@repo/chat-core/activity-cards`), and the card reads the record's live state as it does in chat. Things sit around a card where the card doesn't carry them: a poll has **Open in chat**, a link to its message; an event has **Open in Events**, a link (`/events?event=<id>`) that opens its detail sheet on the Events page, where a member with `events:update` edits it; a pending service entry has **Approve** and **Reject**, the Service hours page's own review flow (chat's hours card is a read-only record).
- **The panel stays open after an action.** A vote shows its tallies; the row leaves Needs you underneath. Approving or rejecting hours closes it, since nothing is left to show. A poll's votes are re-read every 15 seconds while its card is open, because the page holds no live channel subscription; a vote or a close made here is also written into that channel's chat cache when it is loaded, so the thread does not show a stale tally.
- **The list is re-read every time the page opens or the window regains focus**, and after each action. The records it gathers are changed from other surfaces (a vote in chat, a task finished on the board), so it never trusts a cached copy. A re-read that fails keeps the list already on screen.
- **A file row is a link** to Documents or Backwork. A file has no card.
- **Links: sign-up links posted in chat** (forms, sheets, booking pages; which ones and who sees them: [`activity.md` § Links](../../behavior/activity.md#links)). A row is the link itself: the page's name when the API read one, else its kind ("Google Form", "Calendly"), then, under it, the kind when the name is the title (#4187), who posted it, where and when; it opens the link in a new tab and draws no badge. **Done** (a check) sits on the row, as GitHub's notifications and Slack's Later put theirs, since marking one done is what a member does after filling it in. The row's `⋯` menu (or a right-click off the link) holds **Hide: not chapter business**, **Open in chat** (the message it was posted in; a thread reply goes to its thread's first message, since the web has no link that opens a thread), and, for a `channels:manage` holder, **Remove for everyone**. Each of Done, Hide and Remove takes the row away at once and toasts with **Undo**. Links are their own group, not Needs you, and not in the nav count.
- **Leave out of Activity** is a switch in the channel editor (Settings → Chat admin, `/chat-admin`, `channels:manage`), for a channel like #advertising whose links aren't chapter business. Direct messages are not listed there, so they never show it. The phone has no channel editor, so the switch is web-only.
- **A section that could not be read is said** ("Couldn't load polls"), never drawn as empty.

### Chat

- **Chat opens beside the chapter tools** ([#3779](https://github.com/pdcarlson/Frapp/issues/3779); proposed by Winston, approved by Paul 2026-11-10). Chat is a panel of the shell, not a page: the nav column always stays, its **Chat** row opens and closes the chat panel (channels, thread, members) right of the nav, and a tool row (Events, Tasks, …) opens that tool's page right of chat. Clicking the open tool's row closes it, and clicking another tool switches to it, so chat and at most one tool are open. With neither open the shell shows the **home view**: the chapter's mark, name and school on a glow of its accent ([`chapter-home.tsx`](../../../apps/web/components/layout/chapter-home.tsx)). Between chat and the tool page a **divider** sets the split: it starts 50/50 between the thread and the page, drags, moves with the arrow keys (Home and End to the limits, Enter or a double-click to reset), is remembered in a cookie read on the server, and never lets the thread or the page drop below **375px**, the width the thread is tested at ([`split-divider.tsx`](../../../apps/web/components/layout/split-divider.tsx)). While chat and a tool are both open the **member column closes on its own** and the people button opens the list as a Panel; the member's own show-or-hide choice is kept for chat alone. **Every tool page can be closed from itself** (Paul, 2026-11-11): before, only a tool with a nav row of its own could be closed, by clicking the row again, and the Settings tools, Profile and the personal Settings page had none, so a member who opened Chat admin beside chat could not get rid of it. From 1056px up the tool page has a 48px header lined up with chat's channel header, its title on the left and a close button on the right ([`tool-page-header.tsx`](../../../apps/web/components/layout/tool-page-header.tsx)); Escape inside the page closes it too, except from a text field or when a dialog or menu inside used the key; and dragging the divider to an edge closes that side, the page at the right edge and chat at the left, the way VS Code's and Figma's panels snap shut. The side stops at its 375px floor and fades once the pointer is past half of it, so the member sees what letting go will do; dragging back cancels, and a close keeps the split from before the drag. Closing the page goes to `/chat` as a nav row's close does. **Chat closes from its own header too** ([#4223](https://github.com/pdcarlson/Frapp/issues/4223), asked by Shawn 2026-11-11): from 1056px up, with chat beside a page, an X at the right end of chat's channel header, after the people and ⋯ buttons, closes chat and leaves the page filling the row. It is the tool page header's close button (`PanelCloseButton`), 16px from its panel's edge as the page's is, so the two panels close the same way, as Slack's channel and right-hand panel and Discord's thread and member panels each carry their own X. An open thread covers the channel header, so the thread's header carries the same X. Focus moves to the page, since the X goes with the panel. With chat alone, or below 1056px, there is nothing to close chat into and the X is not drawn; the Chat row still opens and closes chat, and reopening it returns to the same channel. Escape inside chat does not close it, because Escape there already closes a thread or cancels a reply. This changes the rule on [#4023](https://github.com/pdcarlson/Frapp/issues/4023) that the nav rows stay the only open and close controls (Winston, 2026-11-10), which the page's own close (above) had already relaxed for tool pages. The members column and the side sheets (event, member, upload panels) already closed: the people button toggles the column, and every sheet has its close button and Escape. Panels open with Signet's `context` duration and `entrance` ease and close with `standard` and `exit`, gliding 16px from the nav side; a page load or a link paints them in place, and reduced motion makes it instant. State: the open tool is the URL, so links and Back work as before; `/chat` means "no tool" (chat alone, or the home view when chat is closed); chat open or closed is a cookie. Any arrival at a `/chat` URL (a link, a notification, a Find result) opens chat, except the shell's own move there when a tool row closes the tool. Widths and the single-page fallback: [§ Responsive contract](#responsive-contract); the state model: [`shell-layout.ts`](../../../apps/web/components/layout/shell-layout.ts). Tool pages lay out by their own width beside chat, not the window's ([§ Responsive contract](#responsive-contract), #4022, #4033). Not yet: the same for Settings and Profile, which the Settings rebuild ([#3856](https://github.com/pdcarlson/Frapp/issues/3856), open as #4106) is replacing ([#4033](https://github.com/pdcarlson/Frapp/issues/4033)), members rearranging the panels, and an officer-uploaded chapter photo for the home view (sub-issues of #3779).
  - *Replaced 2026-11-10, recorded by Paul 2026-11-05/06:* **the channel list was the left column.** From `lg` up on `/chat` the shell's left column showed the channels in place of the module nav, a back arrow slid the nav in, and the same column served every route so nothing jumped going in and out of Chat. The reason was width: the nav's 220px and the channels' 240px side by side cost 460px before a single message. Changed in #3779 by `whewitt-frapp`, 2026-11-10, with Paul's approval: with chat open the nav and the channels sit side by side again (480px), because keeping a tool page in view while talking about it was worth that width. The one-column rule still holds for the nav itself, which no longer changes between routes at all.
- **Getting back from a channel** (2026-11-09, [#3824](https://github.com/pdcarlson/Frapp/issues/3824)). Below `lg` the list and the thread are one screen each. The thread header's back arrow is a 40px target, `Esc` returns to the list wherever nothing else takes it (a field, the composer or an open overlay keeps it), and picking a channel from the list pushes a same-URL history entry, so the browser's Back returns to the list rather than leaving Chat. A thread that opened without a pick (the landing channel, a link) has no entry of its own; going back from it just shows the list. While the list is showing, the channel left behind is not counted as being read: a message landing in it is not stamped read, so it lights the nav's Chat row under the usual rules (an @-mention or a DM, or any message in a channel not muted) and stays unread for the next visit. Its own row keeps the selected-row look until another channel is picked. From `lg` up the list is beside the thread in the chat panel and nothing is pushed, and `Esc` does nothing there (until #3779 it brought the channels back over the module face). ### Chat Admin and Discord Import

Flushed last ([#2500](https://github.com/pdcarlson/Frapp/issues/2500)); the board draws neither, so the grammar above is derived for both.

### Billing

`4d` and `4b` draw this page, so its grammar is taken rather than derived. What needs stating is where the board describes a product this codebase does not have.

- **Omit, never placeholder.** `4d` draws a price, a seat count, a renewal date, a card's brand and last four, and a next charge. None has a source (no endpoint returns them, and `IBillingProvider` reads no subscription back from Stripe), so none renders: a row reading "Next charge" with no value claims there is one. Wiring them is a behavior issue. The plan panel's heading is derived from `subscription_status`, never written: `active` and `past_due` hold the subscription ("Pro"), `incomplete` and `canceled` hold none ("No subscription"), and an unresolved status names the section and asserts no plan.
- **Sell nothing that cannot be bought.** There is one tier, so there is no "Upgrade to Pro". The panel's primary action is the recovery for the status the chapter is in ([#929](https://github.com/pdcarlson/Frapp/issues/929)): `past_due` opens the Customer Portal, `incomplete` and `canceled` start checkout, and `active` offers the Portal as a secondary.

The filter is the `module` keys in `nav-config.ts`, plus `dues` (its surface is this page's invoice list; no row while it is [beta-off](../../product/modules.md#beta-off-modules)) and never `billing` (`BillingController` is subscription-exempt). `plan-matrix.spec.tsx` pins it against the catalog and the nav. Each verdict cell names its own column in visually hidden text, and the "not included" dash is `--muted-foreground`, because it is informational content, not a disabled control.
- **One invoice list.** `GET /v1/invoices` returns the whole chapter to a `billing:view` holder and only the caller's own rows to everyone else, so the two lists the route once stacked were always the same data. The officer controls are gated on `billing:manage`, and so is the `useMembers` read that serves them (`enabled` on the same check), which would otherwise be a guaranteed 403 for every member.
- **The PRO chip states an entitlement, so it takes the accent** ([`pro-chip.tsx`](../../../apps/web/components/billing/pro-chip.tsx), `4b`'s geometry). Never `--gold-ask-*`: the board's chip reads as fixed gold only because its tenant is the house tenant, and taking the Ask family would freeze it gold on every chapter. It goes only on a control gated by entitlement. A write blocked because the chapter is `past_due` or `canceled` is disabled without a chip, and `SubscriptionNotice` says why, because "not in your plan" is the wrong one of `4b`'s two kinds of locked.
- **A lapsed chapter gets one line, at the top of this page and nowhere else** (`4d` note 4), keyed on `subscriptionStatusKind(status) === "destructive"`, so `canceled` as well as `past_due`. `incomplete` gets none, and an unresolved status gets nothing.
- **"Ask an officer" is the `deniedFallback` only.** `fallback` stays `null`, so an officer is not told to ask an officer while their own permissions load, and `offlineFallback` stays the gate's control-slot state. An `active` chapter passes no copy at all.
- **Stripe is blocking and nothing is optimistic.** Both actions await the mutation, disable their own button and hand off with `window.location.assign`. Neither moves the status chip, which reports the chapter record and nothing else; the bounded poll after checkout ([Surviving data contracts](#surviving-data-contracts)) exists to keep it that way.

## Gating & routing semantics

- **Module gating is hide, not grey.** Each nav item carries a `module` field, and `<ProtectedNavItem>` **hides** an item whose module is disabled, never greys it. The shell reads module state with `useChapterModuleGate()` (`apps/web/lib/hooks/use-chapter-module-gate.ts`), from `enabled_modules` on `GET /v1/chapters/current`. That is the member view. It deliberately doesn't read `useOrgConfig()`: that endpoint needs `chapter-config:view`, so for every seeded role below President it errored and the gate failed open for good ([#1982](https://github.com/pdcarlson/Frapp/issues/1982)). While the read is in flight nothing is gated, so no row flashes out; once it has failed, module rows hide. A module toggle reaches it at once: `usePatchOrgConfig` writes the new `enabled_modules` into the cached current-chapter payload as well as the config cache, and re-reads both once the write settles. Permission gating and module gating coexist: an item shows only when the caller holds the permission *and* the module is enabled. Disabling a module from Settings → Modules immediately removes its sidebar item, and strips its slash commands from the chat palette; turning Polls off also withdraws the Vote on chat poll cards, which read the same hook's `useChapterModuleGateState()` and hold the Vote, saying why, until the read answers ([#3012](https://github.com/pdcarlson/Frapp/issues/3012)). Data is preserved and re-enabling restores everything ([`spec/behavior/settings/README.md`](../../behavior/settings/README.md)).
- **Default route.** Chat is the post-sign-in landing surface (`/chat` is the shell with no tool page open, [§ Chat](#chat)): `/` redirects to `/chat` once a Supabase session is present (and to `/sign-in` without one, since 2026-11-05), `/dashboard` is a legacy alias that also redirects to `/chat`, and `app/(dashboard)/page.tsx` (the route-group index) redirects there as well so bookmarks and internal tooling always find a segment root. The standalone `/home` overview was removed in the chat-first rework; chapter health at a glance is meant to become the pulse card, an inline chat artifact that is designed but not built yet ([`spec/behavior/chat/catch-up.md`](../../behavior/chat/catch-up.md)). Users with zero permissions land on `/no-access`, which explains how to request a role without dumping them back to sign-in. The shell sends them there once `GET /v1/users/me/permissions` has answered with an empty set ([`no-access-redirect.tsx`](../../../apps/web/components/layout/no-access-redirect.tsx)), never while that read is loading or after it failed with nothing cached, and only when the active chapter is their only one: `/no-access` has no chapter switcher, so a member of another chapter stays in the shell, where they can switch. An account with no chapter at all gets the chapter wizard instead. *Corrected 2026-11-06 ([#3236](https://github.com/pdcarlson/Frapp/issues/3236)):* until then nothing routed anyone to `/no-access`, so a role-less member landed on `/chat`, where every read 403s because the chat endpoints require `members:view`.
- **Unauthenticated deep links keep their destination.** [`apps/web/proxy.ts`](../../../apps/web/proxy.ts) guards every protected prefix: with no Supabase session it redirects to `/sign-in?redirectTo=<pathname + search>`, and once a session exists the same proxy returns the caller there instead of the `/chat` default. The value must start with `/` or it falls back to `/chat` — the open-redirect guard, applied in the proxy and again in `resolveRedirectPath` ([`apps/web/lib/auth/redirect.ts`](../../../apps/web/lib/auth/redirect.ts)) — and it survives the sign-in ↔ sign-up hop. Email links — the magic link and the sign-up confirmation — **and Google / Apple OAuth** carry it as the `next` of `/auth/callback` ([`apps/web/app/auth/callback/route.ts`](../../../apps/web/app/auth/callback/route.ts)), the one route outside the proxy's matcher. The hosted Magic Link template should href `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=magiclink` so the click stays on `app.{staging.}frapp.live` (or `frapp:///?` on mobile) instead of `*.supabase.co/auth/v1/verify` — Gmail treats a `frapp.live` From plus that Auth hostname as the default Supabase phishing shape. Web's `emailRedirectTo` already has `?next=`; mobile's ends with `?` so the `&` is valid. The callback calls `verifyOtp` with that hash; that path does not need the PKCE cookie, so the link works in a different browser than the one that requested it. An un-rewritten GoTrue `ConfirmationURL` still arrives as `?code=…` after the hosted verify hop; `@supabase/ssr` exchanges that code server-side against the cookie-held verifier. OAuth uses that same `?code=…` exchange. Either way the callback re-applies the open-redirect guard to `next` and redirects there signed in. One exception, since [#3786](https://github.com/pdcarlson/Frapp/issues/3786): when the **sign-in** screen started a Google or Apple round trip (it adds `intent=sign-in`; the sign-up screen doesn't) and the exchange returns an account that provider created just now (`created_at` within five minutes of `last_sign_in_at`, which GoTrue writes at the code exchange), the member asked to sign in and got a new, empty account, usually because they joined with a different provider on the phone. The callback sends them to `/new-account?next=…` first, which names the account and offers **Sign out** (one step, back to `/sign-in` with the destination kept) or continuing to `next`; Continue leads when `next` is an invite, since invite links send newcomers to `/sign-in` too. Copy: [`writing.md` § New account](../design-system/writing.md#new-account-pre-auth). A magic link is not covered: it creates the account when it is requested, not when it is opened. Nothing is linked or merged; attaching a second provider from settings is [#2223](https://github.com/pdcarlson/Frapp/issues/2223). A failed link (expired, reused, bad hash) or a colliding OAuth identity lands on `/sign-in` with `redirectTo` intact and `authError` naming the reason, which the page shows once as a toast. A PKCE `code` that can't be exchanged (opened in another browser, or after a later email request in this one replaced the verifier) fails with `exchange_failed`, with one exception since 2026-11-09 ([#3831](https://github.com/pdcarlson/Frapp/issues/3831)): every email link web asks for (sign-up, Resend, the sign-in magic link) carries `intent=confirm`. GoTrue hands out a code only after verifying the link, which confirms the address, so such a code lands with `authError=email_confirmed` and the page says to sign in. The hosted Confirm signup template still links `ConfirmationURL`, so this is the path a sign-up confirmation takes until it moves to `token_hash` ([#1925](https://github.com/pdcarlson/Frapp/issues/1925)).
- **Web study pause is server-owned.** The `/study` timer calls `POST /v1/study-sessions/pause` when the tab is hidden (Page Visibility API) or manually paused, so the server stops crediting time and starts the grace clock; returning calls `/resume` with fresh coordinates, and overrunning the zone's `pause_grace_minutes` ends the session `PAUSED_EXPIRED`. Full rules: [`spec/behavior/study-sessions.md`](../../behavior/study-sessions.md). `/geofences` configures each zone's polygon, points rate, minimum session length, and pause grace.

The side-by-side tier at 1056px ([#3779](https://github.com/pdcarlson/Frapp/issues/3779)) changes what fills the content column, not the navigation. Its breakpoints are derived from the pane floors in [`shell-layout.ts`](../../../apps/web/components/layout/shell-layout.ts), which asserts them, and the shell spells them out in its Tailwind classes (1056, and the forced-rail band `min-[1056px]:max-[1240px]:`, which `shell-layout.ts` checks against the widths). The server cannot know the window width, so it draws chat beside a tool by CSS and the client drops it on a narrow window. The forced rail is drawn the same way ([#4024](https://github.com/pdcarlson/Frapp/issues/4024)): until hydration the shell renders both nav columns and the band's CSS shows the rail from 1056 to 1239px, so it is right on the first frame; the first client render keeps only that column, as the same node.
- **No shell cap.** The nav sits flush against the viewport edge and content takes the remaining width; the former `max-w-[1400px]` wrapper is gone (`dashboard-shell.tsx`). The tool page pads `px-4` below 640px and `px-6` from 640px up ([§ The content row](#the-content-row)).

The drawer's rows are 44px, the touch minimum, so the no-scroll rule doesn't bind it: on a phone with less than about 750px of visible height a President's drawer scrolls. That is explicitly out of scope (Paul, #2946), and the answer is not a trimmed second list. Navigation MUST NOT be duplicated into a separate mobile list; the trigger keeps its "Open navigation menu" accessible name and the drawer keeps its labelled title and description. The account menu is mounted separately in the drawer (`variant="sheet"`), but it is the same `AccountMenu` component, so a change to its contents reaches both; only the trigger and placement differ.

The shrink only takes effect if the **content column** is also `min-w-0` — see the floor rule below.
- **A tool page lays out by its own width** ([#4022](https://github.com/pdcarlson/Frapp/issues/4022)). Beside chat a page is 375px or more wide (about 480px at the default split in a 1440px window) in a window wide enough for every viewport breakpoint, so a converted page's layout breakpoints are container queries, not `sm`/`md`/`lg`/`xl`: `@container` on the page root (Documents' list is its own container too, so its rows count the list's width beside the folder rail), then Tailwind's `@md` 448px, `@xl` 576px, `@2xl` 672px, `@3xl` 768px and `@4xl` 896px variants. Every tool page is converted ([#4033](https://github.com/pdcarlson/Frapp/issues/4033) did Reports, Roles, Members and Alumni, Billing, Chat admin, Discord import, Geofences, Service and Study) except Profile, which still follows the window. [`beside-chat-floor.spec.ts`](../../../apps/web/tests/visual/beside-chat-floor.spec.ts) opens every tool page but Chapter settings (Chat admin and the Alumni tab included) at its 375px floor beside chat in a 1440px window; in CI it runs sessionless, so populated pages are measured only by its signed-in local mode. Viewport breakpoints stay for what follows the window: the top bar, the nav, dialogs and sheets. A shape CSS can't draw is measured instead ([`use-is-narrow.ts`](../../../apps/web/lib/use-is-narrow.ts)): below 600px the Events calendar is a month of days with a dot per event, and the picked day's events listed under it by name ([`writing.md` § Events (dashboard)](../design-system/writing.md#events-dashboard)).
- **375px is the floor.** Every dashboard route MUST render without horizontal scroll down to 375px. Every route in `DASHBOARD_ROUTES` ([`apps/web/tests/visual/routes.ts`](../../../apps/web/tests/visual/routes.ts) — the count lives there, not here) holds it, and [`apps/web/tests/visual/responsive-floor.spec.ts`](../../../apps/web/tests/visual/responsive-floor.spec.ts) measures it — a plain `scrollWidth <= 375` assertion per route, no baseline. The **pre-auth** routes are measured too, by a second spec ([`pre-auth-floor.spec.ts`](../../../apps/web/tests/visual/pre-auth-floor.spec.ts)) in the same required job, because they need the opposite redirect assertion: the dashboard suite asserts a route did *not* land on `/sign-in`, which for `/sign-in` itself is backwards. Both specs take their routes from `routes.ts`, and the pre-auth spec adds one guard; `/join` is the gap, since its own session check redirects a sessionless harness away. Before #1142 nothing measured it at all, because the visual snapshot suite of the day pinned every shot to 1440×960 and could not see this class of defect. **It is meant to block.** #1152 split it out of the advisory `web-visual-regression` into its own `web-responsive-floor` job and listed that job in [`scripts/ci/lib/required-checks.mjs`](../../../scripts/ci/lib/required-checks.mjs); that snapshot job was advisory because baselines drift with Chromium, and the floor gate had inherited the exemption purely by sharing a directory with it despite storing no baseline and comparing no pixels. The snapshot job has since been deleted, so `test:floor` now runs the whole directory rather than a tagged slice of it. Whether the job is *live* on a branch depends on when an admin last ran `npm run configure:branch-protection` — read live state per [`github-branch-protection-runbook.md`](../../../docs/ops/github-branch-protection-runbook.md#required-status-checks), not from this page. Either way, read a green board carefully: it does not on its own prove the floor held — see the coverage limits below.
- **Sign-in and sign-up fit a laptop window.** `/sign-in` and `/sign-up` MUST render without vertical scroll in a 1280×650 window, a 1366×768 or 1280×720 laptop after the browser's own chrome (Paul, 2026-11-05, after the split frame scrolled on his laptop). [`apps/web/tests/visual/pre-auth-fit.spec.ts`](../../../apps/web/tests/visual/pre-auth-fit.spec.ts) measures it in the same job as the floor. A field, hint or consent line added to either form spends from this budget.
- **What that gate does and does not cover.** It runs a sessionless harness — no active chapter — so on most dashboard routes `<main>` is a 160–256px empty-state card and the route's real content never mounts. The pre-auth routes are the inversion of that limit and the reason they are worth measuring: signed out is not a degraded mode for a sign-in screen, it is the only mode, so there the harness renders exactly what a visitor sees. It therefore pins the **shell** on every route — which is what actually broke — and the page content only where the route renders it without a chapter (`/points` does). A populated table that overflows at 375px while its empty state does not would still pass. Signed-in coverage is not solved; do not read a green run as "this screen is responsive".
- **The content column MUST stay `min-w-0`.** It is a flex item, so its automatic minimum size is its min-content width: without the override it will not shrink below the widest unbreakable thing on the route, the header never gets a reason to collapse, and the page scrolls sideways. This is not a micro-optimisation — a missing `min-w-0` here was six of the seven routes reported in #1142 (`/documents` 426px, `/reports` 408, `/settings` 408, `/study` 392, `/service` 390, `/geofences` 383). It presents as per-route content overflow, and was filed that way, because page content is what supplies the min-content number; the shell measured clean on its own. Read a floor failure as a shell question first.
- **In-page columns collapse on their own breakpoint.** Chat is flush columns (channels, then the thread, then from 1280px the member list) ([`apps/web/components/chat/chat-shell.tsx`](../../../apps/web/components/chat/chat-shell.tsx)); its panes are **not cards** — the thread sits on `--background`, so the `--card` cards posted into it read as the step above it and a hovered message row lifts to `--surface-1` (the message bubbles this once framed are gone since the compact layout, #2873), and the channels column, and the member list column from 1280px, take `--surface-1`, the ladder step the sidebar already uses (rationale: [`../design-system/components.md`](../design-system/components.md) §2); Settings is a wrapped horizontal tab row below 1024px and a 200px vertical rail at `lg` ([`apps/web/components/settings/settings-rail.tsx`](../../../apps/web/components/settings/settings-rail.tsx)). grep -rniE '\bbone\b|\bbronze\b|Geist' apps/web/components apps/web/app --include=*.tsx --include=*.ts --include=*.css
# 5. Every components/ui file has an importer outside itself
for f in apps/web/components/ui/*.tsx; do
  n=$(basename "$f" .tsx); case "$n" in *.spec) continue;; esac

## Surviving data contracts

Per-screen truths that outlive the retired screen docs. Where a fact is canonical in `spec/behavior/`, the pointer is the fact — do not restate it here.

- **Global query defaults.** One browser-wide `QueryClient` ([`apps/web/lib/providers/query-provider.tsx`](../../../apps/web/lib/providers/query-provider.tsx)), whose caches report final failures to Sentry ([`observability.md` § Error Tracking](../../behavior/observability.md#error-tracking)), defaults queries to `staleTime: 30_000`, `gcTime: 10 * 60_000`, `retry: retryQuery` (three more attempts, except after a definitive 4xx, the throttler's 429 included; [`api-retry.md` § Reads](../resilience/api-retry.md#reads)), `retryDelay: min(1000 * 2 ** attempt, 30_000)`, `refetchOnWindowFocus: true`, `refetchOnReconnect: "always"`, and mutations to `retryMutation` (two more attempts, only for a failure that may be transient: a 5xx, no status, or an intermediary's 408/499/460; [`api-retry.md` § Writes](../resilience/api-retry.md#writes)) with the same backoff capped at 10s plus **`networkMode: "always"`, which is load-bearing**. TanStack's default `"online"` *pauses* an offline mutation rather than rejecting it, so `await mutateAsync(...)` never settles: the success toast never fires, the `catch` holding the error toast is unreachable, the dialog never closes, and `isPending` latches `true`. `"offlineFirst"` does not fix it either — it clears `canStart` but not `canContinue`, so the first failure still pauses. `"always"` clears both, so the retries run to exhaustion and the promise rejects. Queueless writes are meant to fail offline, not queue ([`../resilience/connection-state.md`](../resilience/connection-state.md)); the pause was an accidental queue with no UI (#1707). One residual, unchanged by that fix and shared with every retried mutation: `canContinue` also requires `isFocused()`, so a tab hidden during a backoff pauses until it is refocused, then settles. Both retry policies are status-driven (the query policy since #3141; it sets no `networkMode`). The other systematic status-driven behavior is the unauthenticated redirect under [Gating & routing semantics](#gating--routing-semantics). The chat message cache opts out with `staleTime: Infinity` because realtime, not polling, keeps it fresh. That is also why chat resolves author and DM names from the cached chapter roster (`GET /v1/members/roster`) by `sender_id` instead of joining them onto the message; `spec/behavior/chat/README.md` owns that rule and the reasoning behind it.
- **Mutation optimism is opt-in, not the default.** The domain hooks in [`packages/hooks/src/`](../../../packages/hooks/src) are pessimistic — `mutationFn`, then `invalidateQueries` on success; the only `onMutate`/rollback paths that ship are the chat send ([`packages/chat-core/src/cache.ts`](../../../packages/chat-core/src/cache.ts)) and the chapter-config PATCH ([`packages/hooks/src/use-org-config.ts`](../../../packages/hooks/src/use-org-config.ts)), the one opted-in exception inside the package itself. Two writes must stay pessimistic whatever the default becomes: invoice status transitions (`useTransitionInvoiceStatus`) and service approve/reject (`useReviewServiceEntry`) are irreversible, so the UI waits for server confirmation rather than rendering a state it cannot roll back.
- **Billing pay affordance (client gate).** The Pay action renders only when the invoice is `OPEN`, its `user_id` is the signed-in member's, and `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is configured (absent → the affordance does not render, so local dev, CI, and the build prerender are unaffected). The Stripe Elements dialog confirms against the `client_secret` from `POST /v1/invoices/:id/payment-intent` with `redirect: "if_required"` (3-D Secure stays in-page), then re-reads the invoice until the server reports PAID. List scoping, failure-code mapping, and the webhook-is-truth-for-PAID rule: [`spec/behavior/billing.md`](../../behavior/billing.md) §Member payment flow.
- **Billing plan panel (checkout entry point).** Plan and billing (`/settings?tab=billing`; the `/billing` route until #3827) renders the plan panel ([`plan-panel.tsx`](../../../apps/web/components/billing/plan-panel.tsx), board `4d`; it replaced the subscription checkout card in [#2172](https://github.com/pdcarlson/Frapp/pull/2172)) first, under only the page header and the lapse line, because when a chapter is locked its action is the only control on the screen that can succeed. It reads `subscription_status` from the chapter payload — the same query the subscription gate uses, never a second source — and renders no action while that is unresolved, so a slow or failed fetch never asserts a lock. Checkout is offered at `incomplete` and at `canceled`; only `past_due` routes to the Customer Portal, because only it still holds a live subscription a second checkout would duplicate ([`spec/behavior/billing.md`](../../behavior/billing.md) §Duplicate checkout). Stripe returns to `/settings?tab=billing&checkout=success|cancelled` (`/billing?checkout=…` before #3827; `/billing` forwards the param); because the webhook — not the redirect — activates the chapter, `success` polls for the flip on a bounded schedule (10 × 3s) and invalidates both the `["chapters"]` and `["billing"]` caches so the page cannot half-update. The panel reads `?checkout=` via `useSearchParams`, so it must stay under a `<Suspense>` boundary. A stale `?checkout=success` never suppresses the recovery control for a chapter that has since lapsed.
- **Slash palette fails closed.** The `cmdk` palette reads its catalog from `@repo/chat-core/integrations` filtered by the module gate from `useChapterModuleGateState()`, which reads the same member view as the nav, not `useOrgConfig()` ([#2957](https://github.com/pdcarlson/Frapp/issues/2957)). While that read is running it renders an explicit "Loading commands…" panel; while it can't run offline (paused, or retrying and failing while the dashboard is OFFLINE), an offline panel with Retry; on error, or with no active chapter, a "Modules unavailable" panel with Retry — never the unfiltered catalog. A paused or disabled read used to show "Loading commands…" indefinitely ([#3160](https://github.com/pdcarlson/Frapp/issues/3160)). Empty match → "No matching command." A module-backed command typed out in full and sent with Enter goes through the same gate (`slashModuleRefusal` in `composer.tsx`): it is refused with a toast while its module is off, still loading, unreachable offline, or failed to load, and the member's text stays in the composer ([#2993](https://github.com/pdcarlson/Frapp/issues/2993)).
- **Chat reconnect order (web client).** The client gates REST backfill (`GET /v1/channels/{id}/messages?since=<lastSeen>`) on the realtime subscription reaching `SUBSCRIBED` — subscribe first, then backfill — relying on the single idempotent per-channel merge keyed by `client_message_id` to dedupe overlap (`packages/chat-core`, wired through the web glue in `apps/web/lib/chat/`); that merge lands in one normalized cache per channel under query key `["chat", channelId, "messages"]`, shaped `{ byId, order, actionIndex }`. Message-delivery guarantees: [`spec/behavior/chat/README.md`](../../behavior/chat/README.md) and [`../resilience/`](../resilience/README.md).
- **The chat composer is never disabled offline.** It takes `isOffline`, which only refuses the queueless slash commands; the top bar's connection pill carries the offline label and the queue's promise while a chat is open ([`connection-state.md` § One indicator](../resilience/connection-state.md#one-indicator); the composer drew its own line until 2026-11-06); `sendMessage` writes to the Dexie outbox before it touches the network, so gating it would defeat the queue. This is [`../resilience/connection-state.md`](../resilience/connection-state.md)'s rule, which web broke until the #920 chat slice — `submit()` returned early on the same flag, so Enter discarded the draft silently.
- **Chat unread and mention counts come from `GET /v1/channels/unread`**, read through `useChannelUnreadCounts()` in `@repo/hooks` and never re-derived client-side ([`spec/behavior/chat/README.md`](../../behavior/chat/README.md) § Read Receipts). The channel payload carries no counts; a `unread_count?` field on the web channel type claimed otherwise for a long time and nothing ever populated it, so the badge could not render. Plain unread is a bold name with no number, mention/DM the fixed red badge (2026-11-07, [foundations.md](../design-system/foundations.md) §5) — never the chapter accent.
- **Chat drafts & outbox (Dexie).** `drafts(userId, channelId, body, updatedAt)` restore on reload; `outbox(userId, chapterId, clientId, channelId, body, attempts, queuedAt, status)` flushes in order on reconnect — a 4xx moves the entry to `failed` (surfaced inline with Retry / Discard), network errors and 5xx stay queued. Every row is keyed on the member who wrote it (`userId` is the Supabase auth uid), so a shared browser cannot show one member's draft to another or flush one member's queue under another's token (#2226). These are **outbound**, and the inbound first-chunk read cache is a separate IndexedDB database governed by the opposite rule; both rows, why they differ on an identity change, and why only the outbox is chapter-scoped, are in [`../resilience/caching.md`](../resilience/caching.md#cache-layers).
- **Realtime primitive.** Live surfaces (event attendance rosters, the events list, the notification drawer) subscribe to a **private broadcast change-ping** via the shared `useRealtimeTable` hook ([`apps/web/lib/realtime/use-realtime-table.ts`](../../../apps/web/lib/realtime/use-realtime-table.ts)), and one shared browser Supabase client multiplexes every subscription over a single websocket ([`apps/web/lib/realtime/supabase-realtime.ts`](../../../apps/web/lib/realtime/supabase-realtime.ts)). The hook takes `{table, scopeId}` and builds its topic from the contract in [`change-topics.ts`](../../../packages/chat-core/src/change-topics.ts); the ping carries no row data and the hook's whole body is `invalidateQueries`. **Not `postgres_changes`** — those tables are API-enforced and publishing them would move the enforcing layer into RLS (#867).
- **Notification drawer.** Endpoint + realtime contract and the web-push scope decision: [`spec/behavior/notifications.md`](../../behavior/notifications.md).
- **Event attendance by role.** The rule and its wire semantics (the three role lists and `others_invited`): [`spec/behavior/events.md`](../../behavior/events.md) §Event Creation. The editor is `components/events/attendance-editor.tsx`.
- **Onboarding wizard.** Trigger, re-trigger signal, and server-side config materialization via `POST /v1/chapters/onboard`: [`spec/behavior/onboarding.md`](../../behavior/onboarding.md). Wizard UI contract: full-screen overlay at [`apps/web/components/onboarding/chapter-wizard.tsx`](../../../apps/web/components/onboarding/chapter-wizard.tsx), mounted by `ChapterWizardGate` in [`chapter-wizard-gate.tsx`](../../../apps/web/components/onboarding/chapter-wizard-gate.tsx) — a separate file since [#2145](https://github.com/pdcarlson/Frapp/issues/2145) put the wizard behind `next/dynamic`, so the shell no longer pays for it on every route. It is **not** covered by the [375px floor](#responsive-contract) gate — it is an overlay the gate mounts conditionally on a zero-membership account, never a route, so neither floor suite can reach it, and this page asserted a floor nothing was measuring until the Profile & pre-auth slice said so — directory combobox debounced 250ms against `GET /v1/chapter-directory/search` with explicit idle/loading/no-results/error states, and a manual-entry path that is always available.
- **Custom fields CRUD.** Endpoint permissions and status-code semantics (409 duplicate key, `key`/`type` immutability): [`spec/behavior/settings/customization.md`](../../behavior/settings/customization.md).
- **Points audit.** `GET /v1/points/transactions` (`points:view_all`, `limit` clamped 1–200, default 50) and anomaly flagging: [`spec/behavior/points.md`](../../behavior/points.md).
- **Config, theme, archetype.** Config reads/writes go through `GET`/`PATCH /chapters/:id/config` and every write produces an audit row mirrored to `#chapter-audit`; the Settings accent save goes through `PATCH /v1/chapters/current`, which recomputes and stores the palette in the same write, and the refetched chapter repaints it without a reload (`POST /chapters/:id/theme-palette` recomputes on its own, but no client calls it). The engine persists **hex**, so any token it writes MUST be stored as a complete colour value and read as a bare `var()`, never wrapped in `hsl()` — the wrapper turns an injected `#C49A3A` into the invalid `hsl(#C49A3A)` and the chapter's branding silently does not paint (#1143). Every colour token in both stylesheets — [`packages/theme/src/signet.css`](../../../packages/theme/src/signet.css), which this surface and `apps/landing` both ship since #2366, and the legacy `packages/theme/src/globals.css`, deleted in that same cutover — is stored that way — one format, no per-token pairing rule — owned by [`../design-system/accent-engine.md`](../design-system/accent-engine.md) §6 and not restated here; [`packages/theme/src/tailwind.config.spec.ts`](../../../packages/theme/src/tailwind.config.spec.ts) and [`packages/theme/src/signet.css.spec.ts`](../../../packages/theme/src/signet.css.spec.ts) enforce both halves of it per stylesheet, including a repo-wide ban on hand-written `hsl(var(--token))` (#1151): [`spec/behavior/chapter-config.md`](../../behavior/chapter-config.md). Archetype switching resets modules and vocabulary, changes no roles, and preserves identity, branding, and custom fields: [`spec/behavior/settings/README.md`](../../behavior/settings/README.md).

**Later, and not part of that slice: a third query, and the first chapter-scoped control on `/profile` (#564).** The Notifications card reads `GET /v1/notifications/preferences` and shipped with its own state ladder from the start, so the rule above held rather than being re-learned. It carries a no-chapter rung the other cards of that slice do not, and its reason is not the one a reader would guess. It is **not** that a disabled query spins — v5 derives `isLoading = isPending && isFetching`, so a query held by `enabled: !!chapterId` never reaches the loading rung at all. The rung exists because without it the card falls through to `null` and renders six live-looking switches whose clicks the handler silently drops, which is a dead control rather than a missing one.

**That rung's copy instructs, and does not assert.** `activeChapterId` initialises to `null`, so before the persisted store rehydrates — and in the server-rendered HTML — a member *with* a chapter is indistinguishable from one without. "Select a chapter" is true in both states; "you have no active chapter" would be a confident falsehood in one of them. Gating the rung on the store's `hasHydrated` instead was tried and **reverted**: that flag has three ways to stick at `false` for the life of a session, verified empirically against `zustand@5.0.15`. When `localStorage` access throws, `createJSONStorage` returns `undefined` and `persistImpl` early-returns on `!storage` without ever calling `hydrate()` — and in that branch `api.persist` is never assigned either, so `useChapterStore.persist.hasHydrated()` is not a safe substitute; it throws. Corrupt JSON under the storage key, and a `setItem` that throws on quota, both land in the hydration chain's `.catch`, which calls the callback as `postRehydrationCallback(undefined, e)` — and `chapter-store.ts`'s `state?.setHasHydrated(true)` optional-chains into a no-op. In all three the card would hang on a permanent skeleton, shown to exactly the members for whom the no-chapter state is genuinely correct. A sentence that is wrong for an instant is worth fixing; a card that never resolves is not the fix. `hasHydrated` consequently still has no consumer.

This was also the first control on the screen with a tenant, `notification_preferences` being keyed `(user_id, chapter_id, category)`; see the qualification in the "Profile left the nav" bullet above.

**Two more queries, and a second tenant: Blocked members (#2313).** [`blocked-members-card.tsx`](../../../apps/web/components/profile/blocked-members-card.tsx) reads `GET /v1/chat/blocks` through `useBlockedUserIds`, whose status is tri-state, so the card says "empty" only after a read confirmed it. A failed or offline read either shows the error state or keeps a cached list under a "couldn't refresh" line. Blocks are chapter-scoped ([`../../behavior/chat/README.md`](../../behavior/chat/README.md) § Block), so it carries a no-chapter rung like the Notifications card, for a different reason: with no chapter the query is disabled and never settles, and `useBlockedUserIds` reports a query that neither succeeded nor failed as `loading`, so the card would show a skeleton forever. Its second read is the roster (`useMemberDisplayNames`), for names only, and it has no states of its own on purpose: a member the roster cannot name, because the read failed or because they left the chapter (a block outlives membership), is listed under a fallback label and can still be unblocked. It is web's durable way to undo a block, alongside the tombstone's Unblock in `/chat`.

The **legacy engine cutover** (slice 9) closed the series. It touched no screen — every family was already Signet — and deleted the `derivePalette` accent engine, which had gone on being computed and persisted on every chapter save although nothing had read its output since the shell slice. Its only production caller was `buildChapterPalette` in the API, which now writes one map instead of merging two. Three things about it are worth keeping.

**A stored artifact outlives the code that wrote it.** `chapters.theme_palette` is unconstrained jsonb, and at the cutover nothing pruned it, so every row saved before then holds the eight dead legacy keys until the #1165 stale-palette sweep recomputes it, in each environment once that environment runs #1165 ([`../design-system/accent-engine.md`](../design-system/accent-engine.md) §4). Deleting the writer was safe *because* both clients read by allow-list — [`use-chapter-theme.ts`](../../../apps/web/lib/hooks/use-chapter-theme.ts) takes a fixed `--signet-*` list, mobile a fixed handful of keys ([`accent-engine.md`](../design-system/accent-engine.md) §6, Delivery (native)) — and those allow-lists are therefore load-bearing rather than historical. The guard asserting no legacy token reaches `:root` outlived its subject for the same reason.

**A documented blocker can be wrong about its own subject.** [`../design-system/accent-engine.md`](../design-system/accent-engine.md) §6 gated this deletion on "mobile's pre-Signet-map fallback retiring". That fallback is `resolveChapterAccentColor`, a different function in a different package that re-validates `accent_color` and never read the deleted engine's map — `apps/mobile` does not even declare `@repo/chapter-theme`. The two were coupled in prose only, and the same §6 said elsewhere that the legacy units die "at the end of the #920 series". Read the code the blocker names before treating it as a gate.

**A chapter now supplies one colour, not two.** `branding.colors.dark` fed only the deleted map, so it went with it — DTO, Zod schema, regenerated contract, and the "Primary (dark) color" picker in both onboarding wizards. The neutral ladder was already fixed rather than branded ([`../design-system/accent-engine.md`](../design-system/accent-engine.md) §5), so there was nothing left for a second colour to paint; #541, which tracked building a picker for it, is obsolete.

Every permission's scope is `chapter` today.

Chapters can define **custom permission strings** beyond this catalog. Custom permissions are used for:

- Channel gating (a channel can require any permission string, including custom ones).
- UI visibility hints (show/hide a tab or action based on permissions).
- Future extensibility (new API features can adopt existing custom strings without schema changes).

The system does NOT reject unknown permission strings. It stores and evaluates them for gating purposes the same way it handles system permissions.

## Permission Check Algorithm

1. Fetch the user's `role_ids` for the active chapter from `members`.
2. Fetch the `permissions` arrays for those roles from `roles`, **filtered to the active chapter**. An id carried on the membership that belongs to another chapter (stale, or written before an earlier validation gap was closed) matches no row and contributes no permissions. A request with no resolved active chapter is denied outright rather than resolved chapter-wide.
3. Flatten to a unique set of permissions. `roles` is the only source: the second role system, `chapter_custom_roles`, was folded into it ([below](#custom-roles-folded-into-roles)).
4. If the set contains `*`, access is granted.
5. Otherwise, check that **all** required permissions for the endpoint are present in the set.

Permissions are never cached across requests. Each request resolves the user's permission set, so a role change takes effect on the next request. The one exception is a burst of reads: `GET` and `HEAD` requests that arrive together may join a membership or role read that another such request started at most 250 ms earlier (`IN_FLIGHT_JOIN_WINDOW_MS`). So a role change committed inside that window can be missed by the reads that joined, and every request arriving after it sees the change. A request that may write never joins one, so a role change stops it at once. Paul decided this on 2026-11-13 (#3752, reversing his 2026-11-08 call), after a single app open of about 70 requests filled PostgREST's 10-connection pool and stalled production for up to 15 seconds.

The same resolution backs `GET /v1/users/me/permissions` (the effective-permission set clients use to render permission-aware UI), so the chapter filter applies there too.

### Lifecycle rules are separate from permissions

A permission answers "may this member do X?"; a **lifecycle rule** answers "is this member still an active participant?". The two are enforced independently, and passing the permission check above does not imply a lifecycle rule allows the action.

The only lifecycle rule today is the **Alumni** role (see [`alumni.md`](alumni.md)), which blocks study-hour accrual, event check-in, and posting outside `#alumni` / DMs. It is deliberately not modelled as a permission: the seeded Alumni permission set is `members:view` (exactly what active members hold) plus `alumni:post`, which was a _channel_ marker rather than a capability and since #3722 is replaced by naming the Alumni role on a channel's posting list — so widening or narrowing the caller's permissions could not express the rule — and the study controller's `members:view` requirement is satisfied by alumni, which is why the rule is enforced in the domain services rather than in `PermissionsGuard`. Holding the role is what restricts, so a member who still needs to act operationally should not carry it.

## Role Lifecycle

- On chapter creation, the **starting tiers** and the **default system roles** are seeded: President (`*`), Treasurer, Vice President, Secretary, Everyone (once called Member, [#4191](#the-everyone-role)), New Member, Alumni, each in its starting tier ([Tiers and overrides](#tiers-and-overrides)).
- **Seeded permissions** (`STARTING_ROLE_TIERS` and `DEFAULT_SYSTEM_ROLES` in `apps/api/src/domain/constants/permissions.ts` own the lists; this is what they give a chapter created today: each role can do what it could before tiers existed, and the two top tiers add the officer defaults below):
  - The **member defaults** (Paul, 2026-11-07, #3709: start from social trust and let chapters tighten it) are `members:view`, `events:create`, `backwork:upload`, `service:log`, `polls:create`, and the six member recruitment keys (`rush:view`, `rush:add`, `rush:notes`, `rush:vote`, `rush:view_results`, `rush:bid`; [`rush.md`](rush.md#permissions)). Each of the top three tiers gives them, so an officer invited straight into their own role (who then holds no Everyone role) can do what the members they lead can. `events:create` puts an event on the calendar; making anyone required and attaching points take `events:update` ([`events.md`](events.md#event-creation)).
  - **Exec board** (tier 1) gives its roles the member defaults, `events:update` and `events:delete` (edit and delete any event, which is what makes one required or worth points, #3709), `polls:view_all` (baseline chapter API access plus `GET /v1/polls`, the chapter-wide poll list, whose web page was retired in #3871; the permission's fate is #3887), `meetings:record` (starting minutes, #4312), the officer defaults below, and `roles:manage`, `chapter-config:view` and `chapter-config:manage`. In it: **President** (also `*`, as an override), **Vice President** and **Secretary** (nothing beyond the tier), and **Treasurer** (also `billing:view`, `billing:manage`, `points:adjust`, `points:view_all`, `reports:export`, `events:create`, `events:update`, as overrides, kept from before tiers so a chapter that takes an event key off the tier doesn't take it from the Treasurer).
  - **Officers and chairs** (tier 2) gives the member defaults and the officer defaults. No role is seeded into it; it is where a chapter puts its chairs.
  - The **officer defaults** (Paul, 2026-11-10, #4068 decision 9) are `service:approve`, `announcements:post`, `tasks:manage`, `channels:create` and `channels:manage`, and since #4076 `groups:manage` (which migration `20261113040007` also gave every existing tier and role holding `roles:manage` or `channels:manage`). They reach chapters created from #4071's second PR on; no existing chapter gained them, and granting them there is each chapter's own choice (#3858 is Paul's own chapter). `roles:manage` on the whole top tier is safe because of the [rank rules](#rank): the Vice President cannot edit the President's role, a fellow officer's, or the Exec board itself.
  - **Members** (tier 3) gives the member defaults. In it: **Everyone** ([The Everyone role](#the-everyone-role)).
  - **New members** (tier 4) gives `members:view`, `backwork:upload`. In it: **New Member**.
  - **Every starting tier** also gives `ai:use` (#4308, 2026-11-12), so every active member can use the AI features the president turns on, once they turn Frapp AI on. Chapters created before that hold it only through the President's `*`, until they grant it.
  - **Alumni** sits outside the tiers and holds `members:view`, `alumni:post` as overrides.
- System roles can be **renamed** and have their **permissions modified**, but cannot be deleted. The Everyone role is the exception to renaming: its name and tier are fixed ([The Everyone role](#the-everyone-role)).
  - **Renaming is safe: system roles carry a stable `system_key`.** Each seeded role is created with a rename-proof identifier (`PRESIDENT`, `TREASURER`, `VICE_PRESIDENT`, `SECRETARY`, `MEMBER`, `NEW_MEMBER`, `ALUMNI`) stored in `roles.system_key`, unique per chapter. Every lookup that asks "is this _the_ Alumni/President/Member role?" — the Alumni lifecycle restrictions (see [`alumni.md`](alumni.md)), the President notification target, the invite fallback role — resolves on that key, never on `name`. Renaming a system role is therefore a pure relabel: it changes no authorization or lifecycle outcome, and a custom role that takes the freed name inherits nothing.
  - `system_key` is **not writable through the API**. Role create forces it to `null` (custom roles never carry one) and role update strips it, so `roles:manage` can neither mint a role impersonating a seeded one nor detach a key from one.
  - **One legacy gap.** The backfill that introduced `system_key` matched existing rows by their current name, so a chapter that had _already_ renamed a system role before that migration has no key on it and keeps the historical fail-open behavior (the restriction simply does not apply). The original identity is not recoverable after the fact. The guarantee is forward-looking: renames from that point on cannot break enforcement.
- Chapter admins with `roles:manage` can create unlimited **custom roles**. A Discord import can create them too, and add a `channels:read:<name>` read permission to a role: saving its role mapping and starting it both need `roles:manage` whenever they would do so, and it never assigns anyone ([`chat/README.md` § Imported archive messages](chat/README.md#imported-archive-messages)).
- Role **create, update, and delete** are scoped to the caller's active chapter (per the multi-tenancy invariant): update/delete load the target role and verify its `chapter_id` matches the active chapter, returning `403 Forbidden` when a role ID from another chapter is supplied.
- **Deleting a role takes it off everyone holding it** (#4547, migration `20261113164050`). The `delete_role` RPC, in one transaction, removes the role's id from every holder's `role_ids` and gives the Everyone role to any holder it leaves with no role granting member access (`members:view` or `*`) and no New Member or Alumni role, the rule [`rolesAfterSave`](#the-everyone-role) applies to a save. Before this the id stayed behind, and a member whose only role it was got `403` on every route. The `role_deleted` audit row lists both ([`settings/README.md` § Audit Rules](settings/README.md#audit-rules)). Ids are compared lower-cased, as the guard compares them.
- Role **create, update, and delete** follow the [rank rules](#rank): a caller edits only roles ranked below their own, and grants only permissions they hold.
- Role **create, update, and delete** each write a `chapter_audit_log` row (`role_created`, `role_updated`, `role_deleted`) mirrored to `#chapter-audit`, including those a Discord import makes as the member who started it. A permission switch on a role is a role update, so every grant and revoke is on the record. The diff shapes and the no-op rule are in [`settings/README.md` § Audit Rules](settings/README.md#audit-rules).
- Roles have a **display_order** (integer, for UI sorting) and an optional **color**, for chat name colors like Discord (#3485).
  - The color is one of ten fixed palette values (`ROLE_COLOR_PALETTE` in `packages/validation/src/role-colors.ts`), each readable as text on every charcoal surface. Role create and update refuse any other value (`400`), and `null` clears it. Red and gold are left out: red means a mention or an error, and gold is the Ask surface's.
  - A member's name in chat takes the color of their highest-ranked colored role: the lowest `display_order` among their roles that has one. A member with no colored role reads in the plain foreground, and the viewer's own name keeps the chapter accent. `GET /v1/members/roster` carries it per member as `role_color`, so no client needs `role_ids` to paint a name. Clients paint only palette values, so an older stored hex paints nothing.
  - Seeded roles get palette defaults from `DEFAULT_SYSTEM_ROLES` (`apps/api/src/domain/constants/permissions.ts`), which owns the per-role values. The rule is that the officer and Alumni roles are colored and Everyone and New Member are not, so officers stand out.
- Roles have a **mentionable** switch (2026-11-06, owner direction: "anyone can ping any role by default. officers can change defaults"): on by default for every row of `roles`, seeded, created on the Roles page or imported, except the Everyone role, which starts off ([The Everyone role](#the-everyone-role)). Mention resolution and the picker read `roles` and `members.role_ids` (#3638), and since #4076 the chapter's tiers and groups with who is in each. A `roles:manage` holder turns it off on the web Roles page; while it is off, only a member holding `channels:manage` or `roles:manage` (or the wildcard) can `@` the role in chat. The mention rules are in [`chat/README.md`](chat/README.md#role-mentions) § Role mentions.
- A user with no assigned roles has zero permissions (fail-safe closed).

## The Everyone role

Paul, 2026-11-11 ([#4191](https://github.com/pdcarlson/Frapp/issues/4191)): "@members should just be @everyone in my opinion, and there should not be a member role." The seeded Member role became **Everyone**, the way every Discord server has an `@everyone` role nobody assigns.

- **It is the old Member role, kept whole.** Same row, same id, same `system_key` (`MEMBER`), same tier (Members), permissions, overrides and holders. Nothing anyone can do changed, and every stored reference to it means what it meant: `members.role_ids`, `chapters.default_invite_role_id`, invites, channel see and post lists, events' attendance by role, and mobile builds already in the stores. Migration `20261112251000` renamed it in existing chapters; new chapters are seeded with it (`DEFAULT_SYSTEM_ROLES`). It reaches production only when Paul deploys it.
- **It stays in its tier on purpose.** Its tier is where plain members rank, and it is where [presidency's claim walk](#presidency-transfer) stops: outside the tiers it would rank below every tier and let New members claim the wildcard. So it can't leave its tier, only enter one when a chapter had moved it out, and its name is fixed, since `@everyone` reads it (`400`, `role.everyone_fixed`); renaming a row still called Member to Everyone is allowed, for one the previous API seeded after the migration ran. New Member and Alumni stay at or below it (#4548): a tier reorder may not lift a tier holding either above its tier (`400`, `role_tier.below_everyone`), a role edit may not move either into a tier above it (`400`, `role.below_everyone`), and the claim walk skips both wherever they sit. Its permissions, color and `@everyone` switch stay editable on its role page.
- **Nobody assigns it.** No role list, chip, filter or picker offers it to give to a member: not the Members filters, role chips or bulk Assign role, the member role editors, the channel see and post lists' Add menu, or the attendance picker; the invite role pickers offer it as "No role". A list that already names it still shows it so it can be removed. The Roles overview still lists it (captioned "Pinged as @everyone", with no row menu) so its permissions can be edited, and a Discord import may still map the role that holds a whole server's actives ("Brothers") onto it, so those channels open to the chapter's members as they did. `PATCH /v1/members/:id/roles` settles it whatever the request sends (`rolesAfterSave` in `@repo/validation`, which web's and mobile's editors also apply before asking about access):
  - **never beside New Member or Alumni**, which rank below it, whatever those roles carry: graduating a member used to mean unticking Member and ticking Alumni;
  - **given** when the save takes away the member's last New Member or Alumni role (a pledge made a member, a chair, or both), and when it leaves them no role granting member access (`members:view` or `*`), the way a redeem adds it and the way Discord leaves a member with no roles in `@everyone`;
  - **kept as held** otherwise, so a member made a chair keeps it and an officer invited straight into their role isn't handed it. A mobile build already in the store still draws it as a chip, and a tap on it saves nothing different.
    Because the rule moves it, not the caller, it is left out of the [rank rule](#rank) on giving and taking roles.
- **Pinging it is `@everyone`.** It reaches every member of the chapter, holders or not ([`chat/README.md` § Role mentions](chat/README.md#role-mentions)). Its `mentionable` switch starts off, so only officers (`channels:manage`, `roles:manage` or `*`) may use it until a chapter turns it on. The same switch governs `@here` (2026-11-12), the members online now, as one Discord permission covers both; its role page says "Anyone can use @everyone and @here".
- **No other role may read as `@everyone` or `@here`.** Role create and rename refuse a name that folds to either ("Everyone", "every-one", "Here"; `409`, `role.everyone_name`), and so does a Discord import's new role (`400`). The migration renamed any role then named like `@everyone` `<name> (role)`; a role named "Here" before 2026-11-12 keeps its name but is no longer mentionable by it.
- **Invites name it by omission.** An invite that grants only Everyone shows no role on its card (the preview's `role` is `null`); the default invite role picker's "No role" is Everyone too. An invite created naming "Member", as builds from before the rename do, is stored naming Everyone unless a role in the chapter is still called Member, so a role created later under that freed name can't take the invite over.
- A chapter whose Member role lost its `system_key` (the legacy gap above) has no Everyone role, and none of this applies to it.

## Tiers and overrides

Roles are grouped into **tiers** (#4071, Paul 2026-11-10). A tier does two jobs: it is the starting bundle of permissions for every role in it, and it is rank.

- **Tiers are the chapter's own.** How many there are, what each is called and their order are rows in `role_tiers` that the chapter edits ("not all chapters will have the same tier structure and thus there should be heavy customization at the very least in naming conventions"). The four a chapter starts with are seed data. Nothing in the product may read meaning into a tier's name or number beyond "a lower `position` ranks higher", and what a chapter calls a tier at all is its `tier` vocabulary term ("Tier" until the chapter sets its own, `vocab("tier", …)` in `@repo/org-archetypes`).
- **A role sits in one tier or outside them.** `roles.tier_id` is null for a role outside the tiers, as Alumni is. A role outside the tiers gets nothing from any tier and ranks below every tier.
- **An override switches one permission on or off for one role, and beats the tier.** `roles.permission_overrides` maps a permission key to `true` or `false`. A role's effective permissions are its tier's permissions, plus its overrides that are `true`, minus its overrides that are `false`. An override stays until it is cleared, whatever the tier later does.
- **A person still holds the union of their roles.** Overrides act on one role. An "off" override on one role does not remove a permission another of the member's roles grants: there is no deny across roles and no per-person override.
- **The effective list is written back.** `roles.permissions` always holds the role's effective list, so the [Permission Check Algorithm](#permission-check-algorithm) reads exactly the column it always read and `PermissionsGuard` knows nothing about tiers. The database keeps it true inside the writer's own transaction (migration `20261111140000`): a change to a role's tier or overrides rewrites that role's list, and a change to a tier's permissions rewrites the list of every role in it.
- **A write of `permissions` alone still works.** `PATCH /v1/roles/:id` with a `permissions` list, a role's permission switches on the Roles page, a module page's "Who can" and a Discord import all write the list and nothing else. The role then holds exactly that list, and the difference from its tier is recorded as overrides, changing as few as possible.
- **A tier never carries `*`.** The wildcard moves only through [Presidency Transfer](#presidency-transfer); a tier holding it would hand it to every role moved in. The President role holds `*` as an override.
- **A tier that still has roles cannot be deleted**, and a role can only sit in a tier of its own chapter. Both are database constraints.

### Chapters that existed before tiers

Migration `20261111140000` gave every existing chapter the four starting tier names and placed its roles without changing what any role can do: no role's `permissions` was written, and `scripts/pglite/tiers/role-tiers.mjs` proves the lists are byte-for-byte the same before and after.

- A role holding `*`, and the seeded President, Vice President, Treasurer and Secretary, went to the first tier; the seeded Member to the third; the seeded New Member to the fourth.
- The seeded Alumni, and any role with no permissions at all (most roles a Discord import made), stayed outside the tiers.
- Any other role went to the second tier when it held a permission the chapter's Member role lacked, and to the third otherwise. Ranking such a role too high takes nothing from anyone; ranking an officer's role too low would have stopped them editing roles they edit today.
- Each tier started with the permissions that every seeded role placed in it already held, leaving out any role holding `*`. A tier with no seeded role in it (the second tier always, since no role is seeded there) started with what every role placed in it held, so a chapter whose only officer role held `events:create` has a second tier that gives `events:create`; a tier with no roles started empty. Each role recorded its difference from its tier as overrides. So an existing chapter's President role carries "off" overrides for the tier's few permissions beside its `*`, which change nothing the wildcard grants.

### Member defaults for chapters that already existed

Migration `20261112152000` (#3709) carried the member defaults' two new keys to chapters created before them. In each chapter, keyed on the seeded Member role: the tier holding it and every tier ranked above it gain `events:create`, so officers who hold no Member role get it too; the tiers above it also gain `backwork:upload` when the Member role holds it, and a chapter that took backwork away from its members isn't handed it back. Tiers ranked below (New members) and roles outside the tiers are left alone. Every role in those tiers then holds the keys through its tier, except a role with an "off" override for one, which keeps it off. A chapter whose Member role sits outside the tiers gets `events:create` as an "on" override on that role instead, unless it already has an override for it. Existing chapters' Exec boards are not given `events:update`; a chapter grants it itself. It reaches production only when Paul deploys it, and like the earlier permission backfills it writes no audit row.

### Editing tiers and overrides

Every write below takes `roles:manage` and the [rank rules](#rank); reading takes `members:view`, as reading roles does.

- **`GET /v1/role-tiers`** lists the chapter's tiers, highest first.
- **`POST /v1/role-tiers`** adds a tier at the bottom, below every other, with a name and a permission list.
- **`PATCH /v1/role-tiers/:id`** renames a tier or replaces its list. A new list rewrites every role in the tier in the same transaction, each with its own overrides applied.
- **`PUT /v1/role-tiers/order`** takes every tier of the chapter, highest first. The database (`reorder_role_tiers`, migration `20261112001000`) re-checks, with the tiers locked, that the list is exactly the chapter's tiers and that the tiers the caller may not move are still where the caller saw them, and answers `409` otherwise, so two officers reordering at once can't lift a tier past either of them. Under the same lock it refuses (`400`, `role_tier.below_everyone`, #4548) an order that lifts a tier holding the New Member or Alumni role from at or below the Everyone role's tier to above it. A tier already above it may stay or come down, so a chapter in that state can still reorder.
- **`DELETE /v1/role-tiers/:id`** deletes an empty tier; `409` while a role sits in it.
- **`PATCH /v1/roles/:id`** takes `tier_id` (a tier of the chapter, or `null` for outside the tiers) and `permission_overrides`, merged into what the role has: `true` switches a permission on for the role, `false` switches it off, `null` clears the override so the tier decides. One request sends either these or a whole `permissions` list, not both (`400`). The wildcard is never an override a request can set, clear or flip.
- **`POST /v1/roles`** takes an optional `tier_id`. A role created with a list holds exactly that list; one created with an empty list takes its tier's.
- Each tier change writes a `chapter_audit_log` row (`role_tier_created`, `role_tier_updated`, `role_tier_deleted`, `role_tiers_reordered`) mirrored to `#chapter-audit`; a role's move and its override changes are in its `role_updated` row (`tier_id` and `permission_overrides`, each from and to).

### Tiers can be pinged

Paul and Shawn, 2026-11-11 (#4076): a tier's name is a mention. `@<tier name>` reaches everyone holding any role in the tier, and each tier carries a `mentionable` switch, on by default, with a role's rule ([`chat/README.md` § Role mentions](chat/README.md#role-mentions)). A tier holding the Everyone role also follows the Everyone role's switch, so `@Members` is officers-only wherever `@everyone` is. It is set on the tier's page under Roles by anyone who can edit that tier.

### Groups are not roles

A group ([`members.md` § Groups](members.md#groups)) is a named set of members with no permissions, kept apart from roles in its own table so that nothing granting access can be attached to one. `groups:manage` manages them. A group can stand on a channel's who-can-see and who-can-post lists (`group:<id>`), which is the one thing it opens; so once a list names one, changing its members or deleting it also needs `channels:manage`. A class year's group can't stand on a list, since members set their own graduation year.

## Rank

A tier is rank as well as a bundle (#4071, Paul 2026-11-10). A role's rank is its tier's `position`; a role outside the tiers ranks below every tier; a role carrying `*` ranks above everything wherever it sits. A member's rank is the highest of their roles'. The rules read the chapter's own rows, so renaming, adding or reordering tiers moves rank with them, and a chapter with seven tiers or two works the same. `apps/api/src/domain/utils/role-rank.ts` owns the helper (`ranksAtOrAbove` answers "is A's highest tier at or above B's", for #3985-style reach rules).

For any caller who does not hold `*` (the President is exempt; presidency still moves only through [Presidency Transfer](#presidency-transfer)):

- **Nobody edits a role or tier ranked at or above their own.** That covers renaming, recoloring, permissions, overrides, moving, deleting and reordering. A chair cannot edit their own role, another chair's, or the chairs' tier, and the Vice President cannot edit the President's role or the Treasurer's.
- **Nothing goes in at or above the caller.** A role can only be created in or moved into a tier ranked below the caller; a new tier goes in at the bottom; a reorder must leave every tier from the top down to the caller's own where it is.
- **Nobody grants a permission they do not hold.** Whatever a role or tier holds after a write that it did not hold before must be in the caller's own set, and so must any override the write switches on. Taking permissions away is not limited this way.
- **Giving and taking roles** (`PATCH /v1/members/:id/roles`): every role added or taken away must rank below the caller, and the member must rank below the caller too unless it is the caller themselves, so a chair cannot strip an officer's roles. Every role added must also carry only permissions the caller holds, whoever it goes to: a role below the caller can still carry more than they have (a role outside the tiers, an override), and a second account would otherwise collect it. What the chapter's Everyone role carries is exempt, since every member gets it.
- **Removing a member** (`DELETE /v1/members/:id`): the member must rank below the caller, so a chair holding `members:remove` cannot remove an officer or another chair. Nobody removes themselves, the President included: there is no leave-chapter flow, and the President removing their own membership would orphan the chapter. A single-member profile read carries `viewer_can_remove`, the same answer for that viewer and member, which is what the clients draw Remove from chapter from (2026-11-11, Paul: removal was offered on everyone's profile, his own included).
- **Correcting a member's name or graduation year** (`PATCH /v1/members/:id/profile`, `roles:manage`, #4367): the member must rank below the caller, and nobody corrects themselves through it. The profile read carries `viewer_can_edit_profile` for the same answer ([`members.md` § Profiles](members.md#profiles)).
- **Invites** grant a role ranked at or below the inviter: a member brings in a peer or someone junior, never a superior. A role the sender names is refused (403) when it doesn't pass; a chapter default invite role that doesn't pass gives way to the Everyone role (#4546), so a sender who names no role, as the phone never does, still sends a working invite. The inviter must hold the role's permissions too (Everyone's exempt, as above), so a Vice President cannot invite a second account as Treasurer. A name no role carries is checked as the Everyone role the redeem falls back to. No invite grants a role carrying `*`, the President's included, and a redeem of an older invite naming one grants the Everyone role instead. The same rule decides which invites a sender can reach (Paul, 2026-11-13, #4546): `GET /v1/invites` lists only those whose redeem grants a role the caller could invite someone into now, and `DELETE /v1/invites/:id` answers 404 for the rest, so a chair can't copy or revoke the President's Treasurer invite. Those invites still work, and a `*` holder reaches all of them. `GET /v1/invites/roles` names the roles the caller may invite into. What the Invite members panel shows, and which older invites a resend retires, is in [`members.md` § Invite Flow](members.md#invite-flow).
- A caller whose roles are all outside the tiers reaches nothing.

So in a chapter with a President, four exec officers and a dozen chairs, a chair given `roles:manage` can set up the roles below the chairs and hand them out, and cannot make themselves, or anyone, a chair or an officer. The refusals are `403` and say which permissions the caller lacked.

One writer is not rank-checked yet: a Discord import, behind `roles:manage`, creates its new roles outside the tiers and adds `channels:read:<channel>` for the channels it imports to the roles its mapping names, which can include roles ranked at or above the member who starts it ([#4321](https://github.com/pdcarlson/Frapp/issues/4321)).

## Default Invite Role

A chapter can nominate the role that new invites use when the sender does not name one. It is set in Settings → Roles by a caller holding `chapter-config:manage`, read and written through `GET`/`PATCH /v1/chapters/:id/config` as `default_invite_role_id`, and audit-logged like every other config change.

- **Resolution order** is explicit role → `chapters.default_invite_role_id` → the seeded Everyone role, which is resolved by `system_key` rather than by name (see Role Lifecycle above). A chapter that sets no default therefore behaves exactly as it did before this field existed. A blank or whitespace-only role name counts as "not named" rather than being stored as-is.
- **The id is stored, not the name.** `invites.role` is a display-name string matched by name at redeem time; a name persisted here would silently dangle on rename or delete, quietly demoting every later invite to the Everyone fallback. The id is resolved to a name at invite time instead.
- **Deleting the role clears the default** — the column is `on delete set null`, so the chapter reports "no default configured" rather than pointing at a role that no longer exists.
- **Cross-chapter ids are rejected with 400.** The database foreign key only proves the role exists; that it belongs to _this_ chapter is enforced in `ChapterConfigService`, which is the layer that knows the caller's chapter. This matters because RLS is enabled with no permissive policies and the API holds the service-role key, so tenant isolation here is application-layer. The exception carries the code `chapter.config.invalid_default_invite_role`, which reaches clients in the error body since #1020 ([`architecture/README.md` § Error responses](../architecture/README.md#error-responses)).

## Presidency Transfer

The President role is a system role that always carries the `*` wildcard permission.

- **Transfer:** The current President assigns the President role to another member and removes it from themselves. This is a **single atomic operation** — the system never allows a chapter to have zero Presidents or two Presidents simultaneously.
  - Enforced at the database layer by the `transfer_presidency` RPC (migration `20260604120000`): the removal from the current President and the addition to the target run in one transaction, so a failed target update rolls back the removal — a partial failure can never drop or duplicate the President. A concurrent/stale transfer whose source no longer holds the wildcard role is rejected (`403`) rather than applied, and a transfer that targets the current President themselves (`target == current`) is rejected (`400`). `RbacService.transferPresidency` also compares **both** members' `chapter_id` to the active chapter after `findById` (target and current); the RPC remains the authority. The `currentMemberId` on this path comes from `@CurrentMember()`, so it is already chapter-bound — the extra comparison is defence-in-depth if a future caller passes an id from elsewhere.
  - **The outgoing President keeps member access** (#3670, migration `20261108200000`). When the roles left after President is removed grant no member access (no live role in the chapter carrying `members:view` or `*`), the same RPC transaction appends the chapter's Everyone role (by `system_key`, once Member), after their other roles. A founder holds President alone, so without this a transfer left them with no roles and refused on every screen. A member already holding it gets no second copy, and a chapter with no resolvable Everyone role transfers as before. Before #4075 a held custom role carrying `members:view` counted as access too; `20261111210000` dropped that clause once every custom role had become a role.
- **Edge case:** If the President leaves the chapter (account deletion or manual removal by Frapp support), the system flags the chapter and prompts the next member with the highest-ranked admin role to claim the presidency. If no suitable member exists, Frapp support intervenes.
  - **The flag.** `chapters.needs_president` (`not null default false`) is set by `RbacService.flagIfPresidentRemoved`, called from the two orphaning paths: `MemberService.remove` (removing the President — the "manual removal by Frapp support" case; since 2026-11-11 the [rank rules](#rank) leave only another `*` holder able to do it through the API, and nobody can remove themselves) and `AccountDeletionService.deleteAccount` (the President anonymizing their own account), once per chapter membership that carried the wildcard-carrying President role. It is a no-op when the removed member did not hold that role, or the chapter has none.
  - **Eligibility.** "The next member with the highest-ranked admin role" resolves against the chapter's _live_ `roles` and `role_tiers` by [rank](#rank): roles in a tier, highest tier first and ascending `display_order` within a tier, skipping the vacant President role, and stopping at the first role with at least one live member holding it — not a hardcoded `SystemRoleKeys` list, since a chapter may add, rename or reorder roles and tiers freely. A role outside the tiers is never a candidate. Before #4071 this walked `display_order` alone, which a `roles:manage` holder can set: an empty role outside the tiers listed first would have made its holder the only claimant. All members holding that one role are eligible; no other role's holders are. `RbacService.resolveEligibleClaimants` implements this and is shared by the read and write paths below.
    - **Floored at the chapter's own Everyone role.** The walk stops considering candidates once it reaches the tier of the chapter's seeded Everyone role (once Member; resolved by `system_key`), which can't leave its tier ([The Everyone role](#the-everyone-role)) — roles ranked at or below that are the ordinary-member baseline, not an admin tier. The New Member and Alumni roles (by `system_key`) are never candidates, whatever tier they sit in (#4548). Without this floor, a chapter whose officer seats (Treasurer/VP/Secretary) are all vacant would fall through all the way to Everyone, letting any ordinary member — there may be dozens — claim the wildcard. When no role between President and Everyone has a live member, or the chapter's Everyone role cannot be resolved at all (the legacy `system_key` backfill gap, see the Role Lifecycle section above), nobody is eligible — the "Frapp support intervenes" case. This decision grants `*`, so the unresolvable-boundary case fails closed rather than removing the floor.
  - **`GET /v1/roles/presidency-claim-status`** — `{needs_president, eligible, next_role_name}` for the caller. Gated only on the controller's baseline `members:view` (i.e. every member), deliberately not `roles:manage`: the eligible claimant is by definition not the outgoing President, and a chapter's eligible officer need not hold `roles:manage` (chapters created before #4071 gave it only to the President), so the very member who needs to see this would otherwise be locked out of the page that shows it. The web Roles page renders its claim banner outside the `roles:manage` gate for the same reason, and distinguishes a failed status fetch from a genuine "no eligible officer" result — the two must not read the same to an actually-eligible officer.
  - **`POST /v1/roles/claim-presidency`** — `RbacService.claimPresidency` re-validates `needs_president` and eligibility server-side (the status endpoint is advisory for the UI, not the enforcement point), then grants the role via the `claim_presidency` RPC (migration `20260901183000`): a compare-and-set on `needs_president` (true → false) in the same transaction as the role grant, so two eligible members racing to claim resolve to exactly one winner — the loser gets `409 Conflict`. An ineligible caller gets `403`; a chapter that doesn't currently need a President gets `400`. The RPC additionally re-verifies, atomically with the grant, that the claiming member still holds the role that made them eligible — the application-layer eligibility check and the RPC call are not the same transaction, so a concurrent `PATCH /v1/members/:id/roles` could otherwise strip that role from the claimant in between and still see the grant succeed.
  - `president_orphaned` (on flagging) and `presidency_claimed` (on a successful claim) are written to `chapter_audit_log` and mirror into `#chapter-audit`, and so is `presidency_transferred` on a successful transfer (the outgoing President as actor, `president_member_id` from their member id to the target's).
- **Safeguard:** Only the current President can initiate a presidency transfer. No other role (even with `roles:manage`) can assign or remove the President role.
  - `PATCH /v1/members/:id/roles` (the generic role-update endpoint) rejects any payload that adds or removes a role carrying `*` with **`403 Forbidden`**: the system President role, or a legacy non-system role still carrying a pre-validation `*`, since the check keys on the permission ([Custom roles folded into roles](#custom-roles-folded-into-roles)). The dedicated `POST /v1/roles/transfer-presidency` flow is the only path that can move the wildcard role. Web and the phone mark such a role locked and offer no control that would move it (`isLockedRole` in `@repo/hooks/chapter-roles`, #4164).
  - `PATCH /v1/members/:id/roles` also validates every incoming `role_id` against the active chapter's roles and returns **`400 Bad Request`** for unknown or cross-chapter / fabricated role IDs, preventing such IDs from being persisted on a member. One exemption: an id the member **already holds** is accepted even when it no longer resolves (a row that still carries an id resolving to no role; a role delete strips its own id, #4547), so a client echoing the member's current row back never has its save rejected; such ids resolve to no row and grant nothing.
  - `PATCH /v1/members/:id/roles` writes only if the member's `role_ids` still hold what the save read and every newly given role still exists, through the `set_member_role_ids` RPC (#4830, migration `20261113175520`), and answers **`409 Conflict`** otherwise; a member removed mid-save is a `404`. On a 409, `useUpdateMemberRoles` re-reads the member and the chapter's roles; web shows the server's "Reload and try again" message, and the phone's roles sheet puts the change back and says someone changed the roles at the same time. Without this, a save that read before a role delete and wrote after put the deleted id back and dropped the Everyone the delete gave. The RPC locks the roles it names before the member row, the order `delete_role` takes them, so that by design a delete either waits and then strips the id from what the save wrote, or has committed and the save is refused. CI checks each end state and that the locks are taken in that order (PGlite tier `set-member-role-ids.mjs`), not the overlap itself, which was run by hand with two connections ([#4862](https://github.com/pdcarlson/Frapp/issues/4862)).
  - The endpoint does **not** refuse a save that leaves the member with no role carrying member access (`members:view` or `*` on a live role): an officer may mean to. The role editors ask first instead (#3670), with one shared rule (`memberAccessRoleIds` / `removesMemberAccess` in `@repo/validation`): web's member sheet before a save that removes the last such role, and mobile's Directory roles sheet before the tap that does. A member who already lacked access is not asked about again. Web's sheet doesn't save until the roles list has loaded, so the question can't be skipped on placeholder rows.

## Custom roles folded into roles

Frapp has one role system: the `roles` table. Every role a chapter creates on the Roles page or brings in from a Discord import is a row there, beside the seeded ones, and is edited, tiered, colored and assigned the same way.

Until #4075 (2026-11-11) there was a second: `chapter_custom_roles` (label, rank, capabilities, `core`), assigned through `members.custom_role_ids`, edited in a Custom roles section of Settings → Roles, and bridged into enforcement by a second read in `PermissionsGuard`. Paul decided on 2026-11-10 to fold it into `roles` rather than build tiers for both, and to remove the Settings surface that edited it. Migration `20261111210000_fold_custom_roles.sql`:

- **Turned each custom role into a role** in the same chapter, holding its capabilities without `*` (the guard never honored a custom role's wildcard). It is always a new role, even when the chapter already had one of that name holding the same list, because events, mentions and the Members list key on role ids and reusing one would change what the custom role's holders see. It is named after the label, or "Label (custom)", then "Label (custom 2)", when the name was taken, cut to fit the 100-character cap. `chapter_custom_roles.folded_role_id` records which role each became and `folded_at` when, so a re-run skips it even after the role is deleted.
- **Placed it in a tier by what it grants, not by `rank`.** The only writer of `rank`, the web Settings page, set it to creation order, and the API default was 99, so no `rank` said anything about a tier. The rule is the one [`20261111140000`](../../supabase/migrations/20261111140000_role_tiers.sql) used for every unseeded role: no permissions puts it outside the tiers, a permission the chapter's Member role lacks puts it in the tier at position 2, and otherwise position 3; outside the tiers when the chapter has no tier at that position. The role keeps exactly its list either way.
- **Moved assignments into `role_ids`**, after the roles the member already held (so the first role, which web's Members list shows, did not change), once each. Ids naming a deleted or another chapter's custom role granted nothing and were dropped. `custom_role_ids` was emptied.
- **Kept every member's effective permissions identical**, which the PGlite tier `scripts/pglite/tiers/fold-custom-roles.mjs` checks member by member against the old guard's formula.

What is left, and goes in a later release ([#4194](https://github.com/pdcarlson/Frapp/issues/4194)): the `chapter_custom_roles` table and `members.custom_role_ids` stay for one release, for rollback and so the fold can run again before the drop. Nothing reads either for access. `GET /v1/custom-roles` stays as a deprecated route that returns `[]`, and `custom_role_ids` stays on the member profile (always empty), because store builds of the mobile app already shipped call and read them. `PATCH /v1/members/:id/roles` still accepts `custom_role_ids` because a web page loaded before the deploy sends it: `[]` is ignored, and a non-empty list, which only a page holding the member's pre-fold row can send, is refused with `409` so its stale `role_ids` can't drop the folded roles. The create, update and delete routes are gone.

The wildcard rules that protected both tables now protect `roles` alone: role create rejects `*`, role update rejects _introducing_ `*` to a role that does not already carry it, and the seeded President role may not have its `*` _stripped_ either (its other permissions stay editable), since the chapter would otherwise irrecoverably lose its wildcard holder. A legacy non-system role carrying a pre-validation `*` remains strippable, as that is its cleanup path. The generic member-role-update endpoint refuses to add or remove **any** wildcard-carrying role, keyed on the permission and compared as sets, so neither a duplicated id nor a legacy `*` role can smuggle wildcard access onto a member. The presidency-transfer flow is the only path that moves the wildcard between members.

## Custom-field visibility tiers

Custom member fields declare a `visibility` of `self` / `chapter` / `exec` / `president` (see [`members.md`](members.md#custom-fields)). When a member profile is read, the server resolves the viewer's **allowed visibility set** from their effective permissions plus whether they are the member, and only fields in that set are queried:

- `chapter` → any viewer who can see the directory (holds `members:view`).
- `self` → only the member themselves (the owner). The president does **not** override `self`, so privately-scoped fields stay private.
- `exec` → viewers with member/role management authority. Since the default role pack has no dedicated "exec" permission, exec tier is keyed off holding `roles:manage` **or** `members:remove` (or the wildcard). A chapter that grants those manage permissions to additional officer roles widens the exec tier accordingly.
- `president` → only the wildcard (`*`) holder.

`sensitive` fields follow the same gate: a field outside the allowed set is never selected, so its value never enters the response (enforcement is server-side, never client-only).

## Edge Cases

- If a role is deleted while members still hold it, those members lose the permissions from that role on their next request (no stale cached permissions).
- If a chapter has only one member (the President), that member cannot remove themselves or cancel the presidency.
- Role names must be unique within a chapter. Attempting to create a duplicate returns 409 Conflict.
- Role names are capped at **100 characters** (409's sibling failure: a longer name returns 400). Role names are chapter-authored strings that render in member lists and the role picker.
- A role name must contain something besides whitespace: create and rename refuse an empty or whitespace-only name with 400, and the database holds the same rule (`roles_name_not_blank`, #4749). The API refuses a blank tier name the same way.

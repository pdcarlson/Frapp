# Members

The `members` module is always-on (free tier). Every chapter has a searchable member directory built around it.

## Directory

- The directory is searchable across **name, email, and custom-field values**. Custom-field search is **visibility-scoped** — a viewer can only match on field values they are permitted to see.
- Filters: role, group (since 2026-11-19, [#5684](https://github.com/frapplive/Frapp/issues/5684): a group with members keeps the members in it), graduation year, and status, on web's toolbar and in the sheet behind the Actives tab's Filters chip on mobile ([#3971](https://github.com/pdcarlson/Frapp/issues/3971)). Both apply the same rules to the actives: a role filter keeps members holding that role, Status's Active is a member who finished onboarding and Pending one who hasn't, a year, role or group that no longer exists (or a group that has emptied) reads as unpicked, and a long role list is searched by typing (every word typed starts a word of the role's name, case and accents ignored, so "rec" finds "Rush/Recruitment Chair"). On mobile the filters narrow the Actives tab only: search spans both lists unfiltered, and the Alumni tab keeps its own year, city and company filters. The graduation-year filter is labelled "Graduation year", never the chapter's class/line/cohort term: one pledge class can span several graduation years, and that term is kept for real pledge classes ([#3939](https://github.com/pdcarlson/Frapp/issues/3939)).
  - Changed for [#3941](https://github.com/pdcarlson/Frapp/issues/3941) by shawnatomklein-eng, 2026-11-09 (was: "class/line/cohort (rendered via the chapter vocabulary term)").
- A chapter that keeps pledge classes also gets a **pledge class filter** on web, beside graduation year and separate from it, labelled with the chapter's own word and listing its classes in the chapter's order ([#3939](https://github.com/pdcarlson/Frapp/issues/3939)). Mobile's Actives filters carry it too, on the same terms.
- **Phone app filter** (2026-11-19, Paul): officers who can invite members or manage roles (`PHONE_REACH_AUDIENCE` in `@repo/validation`, the same people told when someone joins) get a "Phone app" filter beside Status, on web's toolbar and in mobile's Actives filters, with Any, Notifications on, Not reachable (notifications off plus web only) and Web only. Each member's state comes from their current phones: the one opened most recently, and any other opened within 30 days of it (an older row is usually a phone left behind). **Notifications on** when a current phone allows them, **Notifications off** when none does and the phone opened last says off, **Phone app** when none does and the phone opened last is on a build that hasn't said yet, **Web only** with no phone signed in. While the filter is set, each row names its member's state, a phone unopened for 30 days adds "Last opened" with the date, and a line above the list counts how many actives can't get notifications. The member's profile on web and the phone carries a "Phone app" row ("iPhone, notifications off", "Last opened November 18"). `GET /v1/members/phone-reach` serves every member's state only to those officers and anyone else only their own, so a member sees their own row and nobody else's; only the platform, on/off and the last-opened date leave the server.
- **Sorts (web):** name, role and points, each in both directions, and **fraternal order** (below), labelled with the chapter's word for a member's order number and offered only to a chapter that has a pledge class or has given a member a number. There is no sort by when a member joined: "Newest first" and "Oldest first" ordered by when the membership was created in Frapp, not when someone joined the chapter, and were removed for #3939 (asked by shawnatomklein-eng; Paul left remove-or-relabel to the builder on the issue, 2026-11-10). This bullet replaces "Search also supports name, role, and join date", which described the sorts.
- **Sort (mobile):** the Directory lists by name. For a chapter that has a pledge class or has given a member a number, the Actives tab's chip row ends with one chip, "Sort:" and the chapter's word for a member's order number ("Sort: Fraternal order"), that lists the actives in fraternal order while it is on. It is one toggle and not a sort menu because the list has those two orders only. Name search and the Alumni tab stay by name: the Alumni tab's chip row ends with its Filters chip, and web's Alumni tab has no sort either ([#4088](https://github.com/pdcarlson/Frapp/issues/4088)).
- A member's pledge class is named on their Directory row when they have one, on web and on mobile. If the class list can't be read, the Directory drops the fraternal-order sort, the class filter and the class on rows rather than sort by a list it doesn't have; everything else still works. A list already read is kept when a later refresh of it fails.
- The directory paginates at **25 rows per page**; the pager renders only when the filtered set exceeds one page. (The table and card layouts this line used to name were deleted by the greenfield Directory lane, [#2146](https://github.com/pdcarlson/Frapp/issues/2146). Since [#4175](https://github.com/pdcarlson/Frapp/issues/4175) a member picks List or Grid for the whole Directory, both tabs and a search, and Grid pages the same 25; the control and where the pick is kept: [`components.md` § Segmented control](../ui/design-system/components.md#segmented-control).)

## Pledge class and order number

Added for [#3939](https://github.com/pdcarlson/Frapp/issues/3939) (asked by shawnatomklein-eng; approved by Paul on the issue, 2026-11-10).

- A chapter keeps its own ordered list of **pledge classes** (`GET /v1/pledge-classes`). A class is a name ("Alpha", "Fall 2019") and a place in the list, oldest first. The order is the chapter's, never alphabetical, because Greek-letter names don't sort that way. A new class goes at the end.
- Each member may belong to one class, and may carry an **order number**: an integer an officer gives them. It is one number on purpose. A chapter that orders people inside a class and a chapter that numbers everyone chapter-wide (a roll or bond number) both store it there, and it needs no class, so a chapter that keeps only a chapter-wide number can use it alone. Two members may hold the same number; nothing requires them to be unique.
- **Fraternal order** is the sort these make: oldest class first, then order number within the class, lowest first, then name. A member with a class and no number follows the numbered members of that class. Members with no class come after every class, ordered by their number, and members with neither come last, by name.
- Pledge class and graduation year are different things and both stay: one pledge class can span several graduation years.
- Nothing assumes how a chapter runs (Paul, 2026-11-10, #3967). A chapter with no classes and no numbers sees no pledge class or order controls outside the place an officer sets them up.
- What a chapter calls these is its vocabulary: `vocab("class")` for the class ("Pledge class", "New member class", "Line", "Cohort") and `vocab("order")` for the number ("Fraternal order" for IFC, "Bond number" for NPC, "Line number" for NPHC, "Roll number" elsewhere), both the chapter's to change in Settings → vocabulary.
- Reading needs `members:view`, like the Directory. Writing (the class list, and any member's class and number, one at a time or many at once through `PUT /v1/pledge-classes/assignments`, which writes all of them or none) needs `roles:manage`: the officers who already set a member's roles. A member without it cannot set their own. Setting a member's class or number also keeps two rules: an officer sets them only for members ranked below them, or for themselves, the rank rule that setting a member's roles keeps ([`rbac.md` § Rank](rbac.md#rank)), so a chair can't renumber the President; and a class has a group ([§ Groups](#groups)), so once a channel's who-can-see or who-can-post list names that group, moving anyone into or out of the class needs `channels:manage` too, as changing a manual group's members does. Only the members whose class or number would change are judged. Deleting a class keeps both: every member in it must be within the officer's reach, and a class a channel list names needs `channels:manage`, because deleting it takes its group off those lists. The refusals are `403`.
- **Where an officer sets them (web, and the mobile profile).** Chapter settings has a tab for the class list, shown to `roles:manage` holders: add, rename, delete, and drag a class to its place (the grip also takes the arrow keys, and a touch screen gets Move up and Move down). Each class opens an editor, once the roster has loaded, listing its members in fraternal order, each row led by its number. Its "Add a member" search lists everyone who can be added as soon as it is clicked, members in no class first and then members of another class ("Moves from Alpha"), and narrows as you type; picking one adds them at the end and keeps the list open for the next. Members are taken out with the row's x and put in order by dragging, or by the grip's arrow keys; nothing is written until Save, which sends every change in one request. The numbers follow the list, and there is no number to type in the editor. A drag deals out, lowest first down the list, the numbers the members already hold plus the next numbers after the highest for anyone without one, so a chapter-wide roll keeps its numbers (its first number is set once on a member's profile) and a class with none is numbered 1 to n. Adding a member changes no one else's number: the newcomer takes the next number after the highest when the class has numbers, and none when it has none, so a chapter that doesn't number its members never gets numbers from an add. A member taken out of a class keeps their number. (Changed 2026-11-20 for [#5738](https://github.com/frapplive/Frapp/issues/5738), asked by shawnatomklein-eng: the search showed nothing until you typed, and each member had a typed number box.) The member profile sheet has the same two fields for one member, beside the role editor; so does mobile's, below.
- **Who sees them on a profile.** The sheet shows a member's class and number to anyone who can open it, each only when set. On web a viewer holding `roles:manage` always sees both, with Edit, once the profile read has answered: the sheet is a place an officer sets them, and the only one for a chapter that keeps a number and no classes. Mobile's member profile screen does the same for a `roles:manage` holder: both rows always, "Not set" when unset, and a tap on either opens an editor for the class and the number, saved together through the same route ([#3991](https://github.com/pdcarlson/Frapp/issues/3991), 2026-11-12; until then mobile was read-only). To anyone else, and on the member's own Profile, mobile shows each when set and nothing when not. Profile reads them from the member's own Directory profile, so a member whose roles carry no `members:view` sees neither row there.
- Deleting a class leaves its members with no class; they keep their order number. Alumni keep both.
- `GET /v1/members` returns `pledge_class_id` and `order_number` on every profile.

## Groups

Added for [#4076](https://github.com/pdcarlson/Frapp/issues/4076) (epic #4068, Paul 2026-11-10). A **group** is a named set of members, such as Third floor or Live-ins, that carries **no permissions**. It exists to be `@`-mentioned ([`chat/README.md` § Role mentions](chat/README.md#role-mentions)) and to be named on a channel's who-can-see and who-can-post lists ([§ Who can see and post](chat/README.md#who-can-see-and-post)). It is Slack's user group, not a Discord role: what a member can do stays with roles and tiers ([`rbac.md`](rbac.md)).

- **Manual groups** are the chapter's own: an officer names one, picks a palette color and who is in it, and can switch off its ping. A name is 1 to 80 characters, and can't match a role, tier or other group of the chapter, compared as a mention compares (case and punctuation ignored), or read as `@everyone` or `@here`. A chapter can have 200; a group can hold 2,000 members. Its member list is replaced whole on Save, all or none, so picking someone who left the chapter meanwhile fails the save. A member who leaves the chapter leaves its groups.
- **Automatic groups**: Frapp keeps one per pledge class (named as the class, renamed with it, deleted with it) and one per graduation year that a member has ("Class of 2027"). Who is in them follows the members' own data, read live, so they are never out of date. A class year is for `@`-mentions only and can't go on a channel's lists, because members set their own graduation year. Only their color and ping switch can change. One nobody is in is left out of the Groups page, the pickers and the mentions, and comes back when someone joins it.
  - Added 2026-11-20 ([#5786](https://github.com/frapplive/Frapp/issues/5786), Shawn: "freshman, sophomore, junior, senior… still ping without the roles"): a class year also goes by its **standing**, worked out from its graduation year against the current academic year (`classStanding` in `@repo/validation`, one rule for the API and both apps). The academic year turns over on **June 1, UTC**, after spring graduations: from June 1, 2026 to May 31, 2027 the Class of 2027 are Seniors, 2028 Juniors, 2029 Sophomores and 2030 Freshmen, and on June 1, 2027 every class moves up a standing with nobody editing anything. A fixed date rather than the chapter's semester rollover, which an officer runs by hand each term and which can't say which term ends the year. A year past senior (alumni, or a fifth-year who hasn't moved their graduation year on) or more than three out has no standing and keeps only its "Class of" name; a fifth-year who sets next year's graduation year reads as a Senior. `@Seniors` reaches exactly whom `@Class of 2027` does, with the same ping switch; the mention picker lists the standing just before the year. Like a major, the standing gives way to every other name in the chapter: while a role, tier, other group or member is named "Sophomores", `@Sophomores` is theirs alone, so a chapter that made a role per class keeps it working until an officer deletes the role, and from then on the standing answers. A major can't take a standing's name. The Groups lists on web and the phone show the group as "Sophomores · Class of 2029".
  - Added 2026-11-20 ([#5778](https://github.com/frapplive/Frapp/issues/5778), Shawn: "make majors pingable… so that you don't need to add roles for majors"): a third kind, **one per major** a member of the chapter has. Majors match ignoring case and runs of spaces ("mechE" and " MechE " are one group), never by meaning ("MechE" and "Mechanical Engineering" stay two), and the group is named as most of its members write it. The first member to save a new major makes its group (`@Industrial Systems` reaches them at once), and the last to change theirs empties it. `users.major` is shared across a person's chapters, but each chapter's group holds only that chapter's members. Like a class year it is for `@`-mentions and task audiences only, never a channel list or a task's From, because members set their own major. Pingable by default, its color and switch editable like the others, and marked "Follows major". Since members choose the name, a major gives way to every other name in the chapter: one named like a role, tier, other group or member isn't a mention target ([`chat/README.md` § Mentions](chat/README.md#mentions)), and an officer may still give a manual group a major's name. Ask never sees a member's major, so it doesn't see majors' groups either. To keep near twins from forming, the profile's Major field, on web and the phone, suggests the chapter's existing majors as you type; a new one is still taken as typed. Migration `20261120215726_major_groups.sql`.
- **The API refuses anything else on a group**: no permissions, no tier, and no member list for an automatic one (`/v1/groups`; an unknown field is a 400).
- **Who can do what.** Reading needs `members:view`, like the Directory. Every write needs `groups:manage` ([`rbac.md`](rbac.md#permission-model)), which the Exec board and Officers and chairs tiers start with, and which every existing role or tier holding `roles:manage` or `channels:manage` was given when groups shipped. There is no rank rule on it, unlike roles: a group grants no permission. Once a channel's or category's who-can-see or who-can-post list names a group, changing who is in it or deleting it also needs `channels:manage`, since it changes who reads that channel ([`chat/README.md` § Who can see and post](chat/README.md#who-can-see-and-post)).
- **Where.** Web's Chapter settings → People → Groups listed manual groups, then pledge classes and class years marked "Follows pledge class" or "Follows graduation year" (majors, "Follows major", since #5778). Each opens an editor; creating one opens it to pick members, from an "Add a member" search that lists everyone not yet in the group as soon as it is clicked and narrows as you type (#5738, the same field as the pledge class editor's). The member profile sheet listed the groups a member is in, on web and mobile, read-only.
  - Changed 2026-11-19 (Paul: "Why would we keep roles and groups in 2 DIFFERENT PLACES?"): groups are on the same page as the roles, Chapter settings → **Roles and groups** (`?tab=roles`; `?tab=groups` lands there), under the tiers and their roles, with the same editor. A `groups:manage` holder without `roles:manage` or config access reaches that page for its groups alone. A member's roles and groups are also set **from the member**: their card and their profile, on web and the phone, show two rows of chips, Roles then Groups, and a viewer who may change them gives or takes one from a single list ("+ Add role" or "+ Add to group", the second opening at the groups) of the roles under their tiers and the chapter's own groups, each tick saving at once; on web a chip also has an x to take it away (`POST` and `DELETE /v1/groups/:id/members/:userId` for a group, the gates above; `PATCH /v1/members/:id/roles` for a role, with its rank rules, a role out of reach listed but disabled with why). There is no Edit mode. A pledge class's or class year's group is never offered there and never removable, since it follows the member's own details. The Directory filters by group beside Role, on web and the phone ([§ Directory](#directory)). The phone's Chapter settings → Roles and groups lists the groups under the roles with their member counts; making and renaming them stays on web.
  - Changed 2026-11-19 (Paul picked "a small card from the row"): a Directory row or tile opens the member's card beside it, the same card a name in chat opens, rather than the profile taking the Directory's place; View profile on the card opens the full profile as before.
  - Changed 2026-11-20 ([#5749](https://github.com/frapplive/Frapp/issues/5749), [#5752](https://github.com/frapplive/Frapp/issues/5752), Shawn): on web a Directory list row opens the card below the row (above it near the window's bottom), and a grid tile beside it, so the card stays on screen. The "+ Add role" list stays open after a tick, showing the tick at once, so several roles and groups are given in one opening; quick ticks save one after another, and a click outside or Escape closes it.
  - Changed 2026-11-20 ([#5783](https://github.com/frapplive/Frapp/issues/5783), Shawn: "maybe their top three roles… if you want to see more, there's a See more button"): each row shows its first three chips, roles highest-ranked first ([`rbac.md` § Rank](rbac.md#rank), `compareRolesByRank`), then a "+N more" that opens the rest in place and "Show less" to fold them back, the same on the card, the profile and the phone (`cutChips` in `@repo/hooks`). A row of four shows all four, since "+1 more" would take the room of the chip it hides. Opened, every chip the viewer may take away shows its x; the "+ Add" list always holds every role and group.
- Every change writes a `chapter_audit_log` row mirrored to `#chapter-audit`.

## Profiles

- Each member has a profile card showing: display name, profile photo, role(s), point balance, join date, and optional bio.
- Core profile fields shown on the detail view: name, email, role, joined date.
- **The detail view reads like a contact card** (#3711, 2026-11-12): contact details (phone, a tap away from a call or a text, and email) come right after Message, and the chapter's custom fields sit behind More details, closed on each opening. Each client's order is its screen spec's: mobile s13 in [`spec/ui/mobile/screens.md`](../ui/mobile/screens.md), web in [`spec/ui/web-dashboard/README.md`](../ui/web-dashboard/README.md).
- The detail view is one sheet per client, read by `users.id`, and opens from the Directory and from chat (a sender's name or photo, an `@` chip naming one member, a channel member-list row): [`chat/README.md` § Mentions](chat/README.md#mentions). A viewer holding `roles:manage` (the gate on `PATCH /v1/members/{id}/roles`) can change a member's roles from it wherever it opened, chat included (#3726).
- Profile photos are stored in the private `profiles` bucket under `chapters/{chapter_id}/profiles/{user_id}/`, in the folder for the chapter the member uploaded from. The member's `users.avatar_url` holds that object's path.
- **A profile photo is downscaled to at most 512px on its longest edge before upload** (`AVATAR_MAX_EDGE` in `@repo/validation`, #2912), because what is stored is what every avatar downloads, at 24 to 84px for a photo (web's profile header is the largest; the chapter logo, which shares the bound, reaches 112px on web's chapter home). Web shrinks it in the browser (`apps/web/lib/downscale-image.ts`) and mobile after the square crop (`encodeAvatar` in `apps/mobile/lib/chat/attachment-upload.ts`). A photo that is re-encoded becomes JPEG, and a GIF keeps its first frame. The bound has exceptions, where the file goes up as picked: an image already within it and under 256 KB (it keeps its own type), a re-encode that would come out no smaller, and on web a file the browser can't decode or encode. What is served is the stored object, with no transform on sign: Supabase image transformations were passed over because they bill per origin image past the Pro plan's quota. Photos stored before #2912 are shrunk in place by `scripts/backfill-avatar-downscale.mjs`; until it runs they still render, at their original size. A build that predates #2912 still uploads at full size, under the 25 MB cap.
- Authenticated members may edit **their own** display name (unless their chapter locks names, below), phone, birthday, major, graduation year, bio, current city, current company and profile photo — no additional permission required. Web (`/profile`) and mobile (s15, on the You tab since #3839) both edit all of them: the photo through the three steps below, the rest through `PATCH /v1/users/me` (mobile's Edit sheet since #3387; corrected 2026-11-04, this listed only name, bio and photo, and the photo alone for mobile). The graduation year's bounds are `GRADUATION_YEAR_MIN` / `GRADUATION_YEAR_MAX` in `@repo/validation`, which the API's `UpdateUserDto` enforces; what mobile refuses before sending is s15's row in [`spec/ui/mobile/screens.md`](../ui/mobile/screens.md). The API refuses a blank name ("Enter a name.") and one longer than `DISPLAY_NAME_MAX_LENGTH` (100), trimming it first, the same rule as an officer's correction below (2026-11-17). Mobile refuses a blank name before sending; the web form doesn't yet, so a cleared name is sent and the save's toast shows the API's "Enter a name." (#3392). The bio takes up to 2,000 characters and City and Company 200 each (`USER_BIO_MAX_LENGTH`, `USER_CITY_MAX_LENGTH`, `USER_COMPANY_MAX_LENGTH` in `@repo/validation`), and an empty value clears each. Every field that edits the name, bio, city or company stops at its limit (web `/profile`, the phone's Edit sheet and welcome name step), and a refusal past one reaches the member in the API's words ("Keep your bio to 2,000 characters or fewer."), read by `copyForServerMessage`. Both forms send only the fields the member changed (web's `profileSaveBody`, mobile's `profilePatch`), so a value stored before a limit never refuses an unrelated edit. A name copied from a sign-in provider is cut to 100 characters when sign-in stores it (`AuthService.syncUser`). Major (`users.major`, added 2026-11-06) is free text up to `MAJOR_MAX_LENGTH` (100); both forms take their labels and placeholders from `PROFILE_FIELD_COPY` in `@repo/validation`, and show it on the member's own profile, the mobile member detail line and the alumni directory row. Both forms draw City and Company only from the member's graduation year on, or while either already holds a value so it can be cleared (`showsAfterGraduation` in `@repo/validation`, Paul, 2026-11-06: an undergrad has no after-graduation city or company); the API takes them from anyone.
- **Phone** (`users.phone`, added 2026-11-12, #3711) is optional free text up to `PHONE_MAX_LENGTH` (32) that `isPhoneNumber` in `@repo/validation` accepts: digits with spaces, dashes, dots, parentheses and an optional leading `+`, 7 to 15 digits. A blank value clears it. Anyone who can open the member's profile (`members:view`) sees it; a member who wants it private leaves it empty. It is erased with the rest of the profile when an account is deleted (`anonymize_user`).
- **Birthday** (`users.birthday_month`, `birthday_day`, `birthday_year`, `birthday_visibility`, added 2026-11-14, #4959, asked by Shawn) is optional: a month and day, and a year that no one but the member ever sees. Both forms edit it (web `/profile`, the phone's Edit sheet), with a switch under it once a month and day are entered, **Share my birthday with my chapter**: off is `nobody`, the default, so nothing typed is shown until the member chooses; on is `chapter`. The line under it says who sees what. (A Your chapter / Only you segmented control until 2026-11-17; changed in #5282 by pdcarlson, 2026-11-17: "I don't know what who can see it refers to", and no segmented switchers.) The rules are `isValidBirthday` in `@repo/validation`, which `PATCH /v1/users/me` and the `users_birthday_valid` check also enforce: month and day together, a day the month has, a year in 1900-2100, and 29 February only in a leap year when a year is given. A shared birthday shows as "March 4" on the member's profile (`birthday_month` / `birthday_day` on `MemberProfileDto`, null unless shared) and `GET /v1/members/birthdays` lists the chapter's shared ones; the year is never sent to anyone else. A 29 February birthday falls on 28 February in other years (`birthdayDateInYear`). Account deletion clears it: the `users_clear_birthday_on_tombstone` trigger empties it on any write to a tombstoned row, which `anonymize_user`'s scrub is. **The birthday post** (2026-11-14, #4959): on a member's birthday, if they share it with the chapter and an officer picked a channel (Settings → Chapter → Birthday posts, `chapters.birthday_channel_id` through the config PATCH, `chapter-config:manage`; off by default), Frapp posts "Happy birthday, Name! 🎂" there as itself, once, from 9 AM in the member's own time zone (the zone their pushes use: `user_settings.time_zone`, then `quiet_hours_tz`, then New York). Only a public channel that isn't archived or the audit feed can be picked, and a channel that changes since stops the posts; so does a chapter that is read-only for billing. `BirthdayPostSweepService` runs every 30 minutes on every API replica and claims the member's day for the chapter in `birthday_posts` before posting, so a birthday is posted once even when an officer switches the channel that day ([`api-process.md` § In-process scheduled jobs](../../docs/ops/deployment/api-process.md#in-process-scheduled-jobs)). Account deletion drops a member's claims with the rest of their profile.
- **Members can change their own name** (#5801, Paul 2026-11-21: a member kept renaming themselves to the president's name). A chapter setting, `chapters.members_can_change_name`, set through the config PATCH (`chapter-config:manage`) from Chapter settings on web (the Chapter tab, **Member names**, [`settings/README.md`](settings/README.md#chapter-tab-taborg)) and the phone (Chapter), off by default in every chapter (Paul's pick). While it is off, `PATCH /v1/users/me` refuses a changed `display_name` with `403` ("Your chapter's officers set names, so ask one to change yours.") from a member who has settled in the chapter and doesn't hold `roles:manage` there (Paul's pick: they already rename members below them); an officer fixes the name through the correction below. Settled means the member finished the welcome screen (`has_completed_onboarding`) or joined more than a day ago (`WELCOME_NAME_WINDOW_MS`), so a new member names themselves once and one who skips the welcome screen can't stay unlocked. **A member of two or more chapters is never locked**: the correction below refuses them, so a lock would leave a name nobody could fix. `GET /v1/users/me` and every `/v1/users/me` write answer with `display_name_locked`, and while it is true web `/profile`, the phone's Edit sheet and both welcome screens show the stored name read-only with "Your chapter's officers set names." and never send it (`NAME_LOCK_COPY` and `isDisplayNameLocked` in `@repo/validation`; `DisplayNameLockService` in the API). The member's row is read again when they finish the welcome screen, when a save is refused and when the switch changes, so the lock shows without waiting for the cache. Sign-in fills a stored name only while it is blank or the `Member` stand-in (`shouldFillDisplayName`), so it can't replace a name the member chose. **Every rename is recorded**, whether names are locked or not: a member's own is written as `member_renamed` to the audit log of each chapter they are in before it is saved, so a failed write refuses the rename, and the audit line reads "changed their name · Ethan Smith to Paul". A first name replacing the sign-in stand-in (`needsName`) isn't a rename and isn't written. An officer's correction reads its names the same way (`auditLineText` in `@repo/chat-core`).
- **Officer corrections** (#4367, 2026-11-12; a choice made for Paul, easy to flip). An officer may fix another member's **display name and graduation year**, nothing else: the typo'd name a member never corrects, or the class year a new member skipped. Phone, email, photo, bio, major, city and company stay the member's own. `PATCH /v1/members/{id}/profile` takes `display_name` and `graduation_year` (null clears it) and needs `roles:manage`, the permission that already sets a member's roles, class and order number. It is refused with `403` for your own profile (you edit that from Profile), for a member ranked at or above you by the [rank rules](rbac.md#rank) (a wildcard holder may edit anyone), and for a member who also belongs to another chapter, because the `users` row is shared across chapters and one chapter's officer must not rename someone in another. Each saved change is written to the chapter audit log as `member_profile_corrected` with the before and after values; the member is not notified. The profile reads (`GET /v1/members/{id}` and `/by-user/{userId}`) return `viewer_can_edit_profile`, and both clients offer "Edit name and graduation year" in the profile's `⋯` only where it is true. Both forms take their rules and wording from `correctionPatch` in `@repo/validation`, send only what changed, and show a refusal once Save is pressed.
- **Setting the photo is three steps** (#732): `POST /v1/users/me/avatar-url` mints a signed upload URL for a server-minted, unique key; the client PUTs the bytes; `POST /v1/users/me/avatar` confirms it. The confirm accepts only an existing object directly in the caller's own folder for the active chapter, then deletes the photo it replaced and any unconfirmed upload in that folder older than a day. A younger one is left alone, since it may be another device's upload about to be confirmed. `DELETE /v1/users/me/avatar` clears it. `PATCH /v1/users/me` does not accept `avatar_url` (#2519): a free-text value let a member point their photo at any path.
- **Every read serves the photo as a signed URL** (one hour), because the bucket is private and a bare path renders nothing. That covers `GET /v1/users/me`, the member list, detail, search, the alumni directory, `GET /v1/members/roster` (which chat reads), `GET /v1/members/birthdays` (#4959), and the actors on `GET /v1/activity-feed` (built server-side from the same roster read, `MemberService.findRosterWithJoinDates`). Only a path in the row owner's own folder is signed. Anything else serves as `null`, so the client draws initials; that includes a URL, which only the old free-text `PATCH` could have stored: sign-in syncs only the email and name, and no migration or seed sets the column.
- Viewing other members' full profiles requires the `members:view` permission.

## Custom Fields

- Custom fields (defined in the settings Fields tab) render per chapter on the member detail view, each respecting its configured visibility (`self` / `chapter` / `exec` / `president`).
- **Only fields with a value are shown** (#1749, 2026-11-15): a field the member has no value for is left off the detail view, and with none set the More details row itself is not drawn. Nothing in the product writes a value yet (the write path is #581), so a chapter's seeded fields would otherwise draw a block of empty rows on every profile.
- Field **definitions** live in `chapter_custom_fields`; a member's **values** live in `member_custom_field_values` (one row per member+field), so the visibility check is applied as a query predicate against the definition rather than a post-fetch scrub.
- **Visibility is enforced server-side.** `GET /members/:id`, and `GET /members/by-user/:userId` (the same profile looked up by `users.id`, which is what chat holds; 404 for someone outside the chapter), resolve the viewer's allowed visibility tiers and only fields in that set are queried, so a sensitive field is never returned to a viewer who lacks access. Client-side filtering alone is never trusted for `sensitive` fields. The allowed-tier rule is defined in [`rbac.md`](rbac.md#custom-field-visibility-tiers):
  - `chapter` → any viewer who can see the directory (`members:view`).
  - `self` → only the member themselves (the owner). Not overridden by the president — private fields stay private.
  - `exec` → viewers with member/role management authority (`roles:manage` or `members:remove`) or the wildcard.
  - `president` → only the wildcard (`*`) holder.
- The read-only `GET /custom-fields` endpoint lists a chapter's full field-definition set for the **settings Fields tab** (gated by `chapter-config:view`); definition write CRUD also belongs to that tab. The member directory does not call it — it renders each member's values from the tier-filtered profile read (`GET /members/:id` on web, `GET /members/by-user/:userId` on mobile), so the existence of higher-tier/sensitive fields is never exposed to baseline members.

## Invite Flow

- Invites can be shared as a **join link** (one token per link; `POST /v1/invites/batch` still mints several at once, though no client calls it since 2026-11-06), or sent to a **list of email addresses** (up to 50 at a time — `POST /v1/invites/email` mints one token per address, stores the address on the invite (`invites.email`), and emails each a join link that names the chapter and who sent it; a per-address delivery failure does not fail the whole batch, and its token is still valid to share manually). Emailed invites have a daily ceiling per chapter and per sender ([`README.md` § Daily limits](README.md#daily-limits)); join links have none. A **bulk CSV upload** path is specced but not yet built — see #580.
- **The web Invite members panel never shows a token (2026-11-06, Paul).** Its top is the composer, shared with the web setup wizard's invite step (`apps/web/components/members/invite-composer.tsx`): an email field that turns each typed or pasted address into a chip, a role picker offering only the roles the sender may invite into ([`rbac.md` § Rank](rbac.md#rank)), and Send. An address that isn't one turns red when it becomes a chip, never per keystroke, and blocks Send (the client and `BulkEmailInviteDto` use the same check, `isInviteEmail`); an address the server couldn't email stays in the field, marked, so Send tries it again. Below it, a copy-link control mints one fresh single-use link and copies only the join URL. Nothing is minted before a press. Under that, the panel lists every pending invite and the joined or expired ones from the last 14 days, leaving out any whose role the sender couldn't invite someone into themselves (#4546, [`rbac.md` § Rank](rbac.md#rank)), newest first, by address (or as a share link), with the role, when it was sent, and its status. Revoked invites are not listed. Between the composer and the list sit the **chapter links** (#3353, Paul 2026-11-19; per role #5633): one 7-day link per role, at a role the officer picks from the same list as the composer's, each to copy, replace or turn off ([`onboarding.md` § Invite Token Rules](onboarding.md#invite-token-rules)); it is not listed under Invited. A pending invite's row menu copies its link or revokes it; an emailed invite that is pending or expired can be sent again. **Mobile lists the same invites and offers the same actions** (2026-11-09, #3828): both apps read `listedInvites` and `inviteMenuActions` from `@repo/hooks`. The phone's rows leave out the role, and it shares a link where web copies it ([`navigation.md` § Inviting members](../ui/mobile/navigation.md#inviting-members)). The wording of each control is in [`writing.md`](../ui/design-system/writing.md) § Invite members.
- **One live invite per address.** When a new email invite is delivered, the address's older pending invites in the chapter that the sender could see are revoked, so sending again (from the row menu or by retrying a marked chip) never leaves two live links for one person. An address whose new email failed keeps its older invite, which may be the one that reached them.
- **Status (#3607).** `GET /v1/invites` returns typed rows with a `status`: `revoked` when `revoked_at` is set, else `joined` when `used_at` is set, else `expired` past `expires_at`, else `pending`. A revoke sets `revoked_at` and `used_at` together, so every path that refuses a used token refuses a revoked one, and a redeem that claimed the token but failed to add the member cannot reopen it.
- Invite gating follows the subscription rules in [`onboarding.md`](onboarding.md) § Invite Token Rules: minting is free-tier for an `incomplete` chapter, but blocked for `past_due` (even in grace) and `canceled`; redeeming an already-minted token is refused (403, token kept) once the chapter is under the hard lock — `canceled`, or `past_due` past grace — and admitted otherwise (#1546).
- **Default invite role.** A chapter can nominate the role new invites use when the sender does not pick one, set in Settings → Roles and persisted as `chapters.default_invite_role_id`. Naming a role on the invite still wins, so the default is a starting point rather than a restriction. Either way the role must rank below the inviter (checked again at redeem against the inviter's roles then), and never carries `*`; a default the sender couldn't invite into gives way to the Everyone role ([`rbac.md` § Rank](rbac.md#rank)). Resolution order is explicit role → chapter default → the seeded Everyone role (once Member, [`rbac.md` § The Everyone role](rbac.md#the-everyone-role)); a chapter that has set no default behaves exactly as it did before the field existed. See [`rbac.md`](rbac.md) § Default Invite Role for the validation and deletion rules.
- **On send:** write a member-visible row to `chapter_audit_log`, which posts an audit message to `#chapter-audit`.

# Members

The `members` module is always-on (free tier). Every chapter has a searchable member directory built around it.

## Directory

- The directory is searchable across **name, email, and custom-field values**. Custom-field search is **visibility-scoped** — a viewer can only match on field values they are permitted to see.
- Filters: role, graduation year, and status, on web's toolbar and in the sheet behind the Actives tab's Filters chip on mobile ([#3971](https://github.com/pdcarlson/Frapp/issues/3971)). Both apply the same rules to the actives: a role filter keeps members holding that role, Status's Active is a member who finished onboarding and Pending one who hasn't, a year or role that no longer exists reads as unpicked, and a long role list is searched by typing (every word typed starts a word of the role's name, case and accents ignored, so "rec" finds "Rush/Recruitment Chair"). On mobile the filters narrow the Actives tab only: search spans both lists unfiltered, and the Alumni tab keeps its own year, city and company filters. The graduation-year filter is labelled "Graduation year", never the chapter's class/line/cohort term: one pledge class can span several graduation years, and that term is kept for real pledge classes ([#3939](https://github.com/pdcarlson/Frapp/issues/3939)).
  - Changed for [#3941](https://github.com/pdcarlson/Frapp/issues/3941) by shawnatomklein-eng, 2026-11-09 (was: "class/line/cohort (rendered via the chapter vocabulary term)").
- A chapter that keeps pledge classes also gets a **pledge class filter** on web, beside graduation year and separate from it, labelled with the chapter's own word and listing its classes in the chapter's order ([#3939](https://github.com/pdcarlson/Frapp/issues/3939)). Mobile's Actives filters carry it too, on the same terms.
- **Sorts (web):** name, role and points, each in both directions, and **fraternal order** (below), labelled with the chapter's word for a member's order number and offered only to a chapter that has a pledge class or has given a member a number. There is no sort by when a member joined: "Newest first" and "Oldest first" ordered by when the membership was created in Frapp, not when someone joined the chapter, and were removed for #3939 (asked by shawnatomklein-eng; Paul left remove-or-relabel to the builder on the issue, 2026-11-10). This bullet replaces "Search also supports name, role, and join date", which described the sorts.
- **Sort (mobile):** the Directory lists by name. For a chapter that has a pledge class or has given a member a number, the Actives tab's chip row ends with one chip, "Sort:" and the chapter's word for a member's order number ("Sort: Fraternal order"), that lists the actives in fraternal order while it is on. It is one toggle and not a sort menu because the list has those two orders only. Name search and the Alumni tab stay by name: the Alumni tab's chip row ends with its Filters chip, and web's Alumni tab has no sort either ([#4088](https://github.com/pdcarlson/Frapp/issues/4088)).
- A member's pledge class is named on their Directory row when they have one, on web and on mobile. If the class list can't be read, the Directory drops the fraternal-order sort, the class filter and the class on rows rather than sort by a list it doesn't have; everything else still works. A list already read is kept when a later refresh of it fails.
- The directory paginates at **25 rows per page**; the pager renders only when the filtered set exceeds one page. (The table and card layouts this line used to name were deleted by the greenfield Directory lane, [#2146](https://github.com/pdcarlson/Frapp/issues/2146). Since [#4175](https://github.com/pdcarlson/Frapp/issues/4175) a member picks List or Grid for the whole Directory, both tabs and a search, and Grid pages the same 25; the control and where the pick is kept: [`components.md` § Segmented control](../ui/design-system/components.md#segmented-control).)

## Pledge class and order number

Added for [#3939](https://github.com/pdcarlson/Frapp/issues/3939) (asked by shawnatomklein-eng; approved by Paul on the issue, 2026-11-10).

- A chapter keeps its own ordered list of **pledge classes** (`GET /v1/pledge-classes`). A class is a name ("Alpha", "Fall 2019") and a place in the list, oldest first. The order is the chapter's, never alphabetical, because Greek-letter names don't sort that way. A new class goes at the end.
- Each member may belong to one class, and may carry an **order number**: an integer an officer gives them. It is one number on purpose. A chapter that orders people inside a class and a chapter that numbers everyone chapter-wide (a roll or bond number) both store it there, and it needs no class, so a chapter that keeps only a chapter-wide number can use it alone. Two members may hold the same number; nothing requires them to be unique.
- **Fraternal order** is the sort these make: oldest class first, then order number within the class, lowest first, then name. A member with a class and no number follows the numbered members of that class. Members with no class come after every class, ordered by their number, and members with neither come last, by name.
- Pledge class and graduation year are different things and both stay: one pledge class can span several graduation years.
- Nothing assumes how a chapter runs (Paul, 2026-11-10, #3967). A chapter with no classes and no numbers sees no pledge class or order controls outside the place an officer sets them up.
- What a chapter calls these is its vocabulary: `vocab("class")` for the class ("Pledge class", "New member class", "Line", "Cohort") and `vocab("order")` for the number ("Fraternal order" for IFC, "Bond number" for NPC, "Line number" for NPHC, "Roll number" elsewhere), both the chapter's to change in Settings → vocabulary.
- Reading needs `members:view`, like the Directory. Writing (the class list, and any member's class and number, one at a time or many at once through `PUT /v1/pledge-classes/assignments`, which writes all of them or none) needs `roles:manage`: the officers who already set a member's roles. A member cannot set their own.
- **Where an officer sets them (web, and the mobile profile).** Chapter settings has a tab for the class list, shown to `roles:manage` holders: add, rename, delete, and drag a class to its place (the grip also takes the arrow keys, and a touch screen gets Move up and Move down). Each class opens an editor, once the roster has loaded, listing its members in fraternal order, where members are added by name, taken out, dragged into order, or given a typed number; nothing is written until Save, which sends every change in one request. Dragging renumbers the class: when every member in it has a number the same numbers are dealt out again in the new order, so a chapter-wide roll keeps its numbers, and otherwise the members are numbered 1 to n. A member taken out of a class keeps their number. The member profile sheet has the same two fields for one member, beside the role editor; so does mobile's, below.
- **Who sees them on a profile.** The sheet shows a member's class and number to anyone who can open it, each only when set. On web a viewer holding `roles:manage` always sees both, with Edit, once the profile read has answered: the sheet is a place an officer sets them, and the only one for a chapter that keeps a number and no classes. Mobile's member sheet does the same for a `roles:manage` holder: both rows always, "Not set" when unset, and a tap on either opens an editor for the class and the number, saved together through the same route ([#3991](https://github.com/pdcarlson/Frapp/issues/3991), 2026-11-12; until then mobile was read-only). To anyone else, and on the member's own Profile, mobile shows each when set and nothing when not. Profile reads them from the member's own Directory profile, so a member whose roles carry no `members:view` sees neither row there.
- Deleting a class leaves its members with no class; they keep their order number. Alumni keep both.
- `GET /v1/members` returns `pledge_class_id` and `order_number` on every profile.

## Groups

Added for [#4076](https://github.com/pdcarlson/Frapp/issues/4076) (epic #4068, Paul 2026-11-10). A **group** is a named set of members, such as Third floor or Live-ins, that carries **no permissions**. It exists to be `@`-mentioned ([`chat/README.md` § Role mentions](chat/README.md#role-mentions)) and to be named on a channel's who-can-see and who-can-post lists ([§ Who can see and post](chat/README.md#who-can-see-and-post)). It is Slack's user group, not a Discord role: what a member can do stays with roles and tiers ([`rbac.md`](rbac.md)).

- **Manual groups** are the chapter's own: an officer names one, picks a palette color and who is in it, and can switch off its ping. A name is 1 to 80 characters, and can't match a role, tier or other group of the chapter, compared as a mention compares (case and punctuation ignored), or read as `@everyone` or `@here`. A chapter can have 200; a group can hold 2,000 members. Its member list is replaced whole on Save, all or none, so picking someone who left the chapter meanwhile fails the save. A member who leaves the chapter leaves its groups.
- **Automatic groups**: Frapp keeps one per pledge class (named as the class, renamed with it, deleted with it) and one per graduation year that a member has ("Class of 2027"). Who is in them follows the members' own data, read live, so they are never out of date. A class year is for `@`-mentions only and can't go on a channel's lists, because members set their own graduation year. Only their color and ping switch can change. One nobody is in is left out of the Groups page, the pickers and the mentions, and comes back when someone joins it.
- **The API refuses anything else on a group**: no permissions, no tier, and no member list for an automatic one (`/v1/groups`; an unknown field is a 400).
- **Who can do what.** Reading needs `members:view`, like the Directory. Every write needs `groups:manage` ([`rbac.md`](rbac.md#permission-model)), which the Exec board and Officers and chairs tiers start with, and which every existing role or tier holding `roles:manage` or `channels:manage` was given when groups shipped. There is no rank rule on it, unlike roles: a group grants no permission. Once a channel's or category's who-can-see or who-can-post list names a group, changing who is in it or deleting it also needs `channels:manage`, since it changes who reads that channel ([`chat/README.md` § Who can see and post](chat/README.md#who-can-see-and-post)).
- **Where.** Web's Chapter settings → People → Groups lists manual groups, then pledge classes and class years marked "Follows pledge class" or "Follows graduation year". Each opens an editor; creating one opens it to pick members. The member profile sheet lists the groups a member is in, on web and mobile, read-only.
- Every change writes a `chapter_audit_log` row mirrored to `#chapter-audit`.

## Profiles

- Each member has a profile card showing: display name, profile photo, role(s), point balance, join date, and optional bio.
- Core profile fields shown on the detail view: name, email, role, joined date.
- **The detail view reads like a contact card** (#3711, 2026-11-12): contact details (phone, a tap away from a call or a text, and email) come right after Message, and the chapter's custom fields sit behind More details, closed on each opening. Each client's order is its screen spec's: mobile s13 in [`spec/ui/mobile/screens.md`](../ui/mobile/screens.md), web in [`spec/ui/web-dashboard/README.md`](../ui/web-dashboard/README.md).
- The detail view is one sheet per client, read by `users.id`, and opens from the Directory and from chat (a sender's name or photo, an `@` chip naming one member, a channel member-list row): [`chat/README.md` § Mentions](chat/README.md#mentions). A viewer holding `roles:manage` (the gate on `PATCH /v1/members/{id}/roles`) can change a member's roles from it wherever it opened, chat included (#3726).
- Profile photos are stored in the private `profiles` bucket under `chapters/{chapter_id}/profiles/{user_id}/`, in the folder for the chapter the member uploaded from. The member's `users.avatar_url` holds that object's path.
- **A profile photo is downscaled to at most 512px on its longest edge before upload** (`AVATAR_MAX_EDGE` in `@repo/validation`, #2912), because what is stored is what every avatar downloads, at 24 to 84px for a photo (web's profile header is the largest; the chapter logo, which shares the bound, reaches 112px on web's chapter home). Web shrinks it in the browser (`apps/web/lib/downscale-image.ts`) and mobile after the square crop (`encodeAvatar` in `apps/mobile/lib/chat/attachment-upload.ts`). A photo that is re-encoded becomes JPEG, and a GIF keeps its first frame. The bound has exceptions, where the file goes up as picked: an image already within it and under 256 KB (it keeps its own type), a re-encode that would come out no smaller, and on web a file the browser can't decode or encode. What is served is the stored object, with no transform on sign: Supabase image transformations were passed over because they bill per origin image past the Pro plan's quota. Photos stored before #2912 are shrunk in place by `scripts/backfill-avatar-downscale.mjs`; until it runs they still render, at their original size. A build that predates #2912 still uploads at full size, under the 25 MB cap.
- Authenticated members may edit **their own** display name, phone, birthday, major, graduation year, bio, current city, current company and profile photo — no additional permission required. Web (`/profile`) and mobile (s15, on the You tab since #3839) both edit all of them: the photo through the three steps below, the rest through `PATCH /v1/users/me` (mobile's Edit sheet since #3387; corrected 2026-11-04, this listed only name, bio and photo, and the photo alone for mobile). The graduation year's bounds are `GRADUATION_YEAR_MIN` / `GRADUATION_YEAR_MAX` in `@repo/validation`, which the API's `UpdateUserDto` enforces; what mobile refuses before sending is s15's row in [`spec/ui/mobile/screens.md`](../ui/mobile/screens.md). The web form does not yet refuse a blank name, and sends it, so the column stores `''` (#3392). Major (`users.major`, added 2026-11-06) is free text up to `MAJOR_MAX_LENGTH` (100); both forms take their labels and placeholders from `PROFILE_FIELD_COPY` in `@repo/validation`, and show it on the member's own profile, the mobile member detail line and the alumni directory row. Both forms draw City and Company only from the member's graduation year on, or while either already holds a value so it can be cleared (`showsAfterGraduation` in `@repo/validation`, Paul, 2026-11-06: an undergrad has no after-graduation city or company); the API takes them from anyone.
- **Phone** (`users.phone`, added 2026-11-12, #3711) is optional free text up to `PHONE_MAX_LENGTH` (32) that `isPhoneNumber` in `@repo/validation` accepts: digits with spaces, dashes, dots, parentheses and an optional leading `+`, 7 to 15 digits. A blank value clears it. Anyone who can open the member's profile (`members:view`) sees it; a member who wants it private leaves it empty. It is erased with the rest of the profile when an account is deleted (`anonymize_user`).
- **Birthday** (`users.birthday_month`, `birthday_day`, `birthday_year`, `birthday_visibility`, added 2026-11-14, #4959, asked by Shawn) is optional: a month and day, and a year that no one but the member ever sees. Both forms edit it (web `/profile`, the phone's Edit sheet), with who can see it beside it: **Only you** (`nobody`, the default, so nothing typed is shown until the member chooses) or **Your chapter** (`chapter`). The rules are `isValidBirthday` in `@repo/validation`, which `PATCH /v1/users/me` and the `users_birthday_valid` check also enforce: month and day together, a day the month has, a year in 1900-2100, and 29 February only in a leap year when a year is given. A shared birthday shows as "March 4" on the member's profile (`birthday_month` / `birthday_day` on `MemberProfileDto`, null unless shared) and `GET /v1/members/birthdays` lists the chapter's shared ones; the year is never sent to anyone else. A 29 February birthday falls on 28 February in other years (`birthdayDateInYear`). Account deletion clears it: the `users_clear_birthday_on_tombstone` trigger empties it on any write to a tombstoned row, which `anonymize_user`'s scrub is. **The birthday post** (2026-11-14, #4959): on a member's birthday, if they share it with the chapter and an officer picked a channel (Settings → Organization → Birthday posts, `chapters.birthday_channel_id` through the config PATCH, `chapter-config:manage`; off by default), Frapp posts "Happy birthday, Name! 🎂" there as itself, once, from 9 AM in the member's own time zone (`user_settings.time_zone`, New York when none is known). Only a public channel that isn't archived can be picked, and a channel made private or archived later stops the posts. `BirthdayPostSweepService` runs every 30 minutes on every API replica; each post's `client_message_id` is the member and their local date, so the message table's dedupe key lets one replica's write land.
- **Officer corrections** (#4367, 2026-11-12; a choice made for Paul, easy to flip). An officer may fix another member's **display name and graduation year**, nothing else: the typo'd name a member never corrects, or the class year a new member skipped. Phone, email, photo, bio, major, city and company stay the member's own. `PATCH /v1/members/{id}/profile` takes `display_name` and `graduation_year` (null clears it) and needs `roles:manage`, the permission that already sets a member's roles, class and order number. It is refused with `403` for your own profile (you edit that from Profile), for a member ranked at or above you by the [rank rules](rbac.md#rank) (a wildcard holder may edit anyone), and for a member who also belongs to another chapter, because the `users` row is shared across chapters and one chapter's officer must not rename someone in another. Each saved change is written to the chapter audit log as `member_profile_corrected` with the before and after values; the member is not notified. The profile reads (`GET /v1/members/{id}` and `/by-user/{userId}`) return `viewer_can_edit_profile`, and both clients offer "Edit name and graduation year" in the profile's `⋯` only where it is true. Both forms take their rules and wording from `correctionPatch` in `@repo/validation`, send only what changed, and show a refusal once Save is pressed.
- **Setting the photo is three steps** (#732): `POST /v1/users/me/avatar-url` mints a signed upload URL for a server-minted, unique key; the client PUTs the bytes; `POST /v1/users/me/avatar` confirms it. The confirm accepts only an existing object directly in the caller's own folder for the active chapter, then deletes the photo it replaced and any unconfirmed upload in that folder older than a day. A younger one is left alone, since it may be another device's upload about to be confirmed. `DELETE /v1/users/me/avatar` clears it. `PATCH /v1/users/me` does not accept `avatar_url` (#2519): a free-text value let a member point their photo at any path.
- **Every read serves the photo as a signed URL** (one hour), because the bucket is private and a bare path renders nothing. That covers `GET /v1/users/me`, the member list, detail, search, the alumni directory, `GET /v1/members/roster` (which chat reads), `GET /v1/members/birthdays` (#4959), and the actors on `GET /v1/activity-feed` (built server-side from the same roster read, `MemberService.findRosterWithJoinDates`). Only a path in the row owner's own folder is signed. Anything else serves as `null`, so the client draws initials; that includes a URL, which only the old free-text `PATCH` could have stored: sign-in syncs only the email and name, and no migration or seed sets the column.
- Viewing other members' full profiles requires the `members:view` permission.

## Custom Fields

- Custom fields (defined in the settings Fields tab) render per chapter on the member detail view, each respecting its configured visibility (`self` / `chapter` / `exec` / `president`).
- Field **definitions** live in `chapter_custom_fields`; a member's **values** live in `member_custom_field_values` (one row per member+field), so the visibility check is applied as a query predicate against the definition rather than a post-fetch scrub.
- **Visibility is enforced server-side.** `GET /members/:id`, and `GET /members/by-user/:userId` (the same profile looked up by `users.id`, which is what chat holds; 404 for someone outside the chapter), resolve the viewer's allowed visibility tiers and only fields in that set are queried, so a sensitive field is never returned to a viewer who lacks access. Client-side filtering alone is never trusted for `sensitive` fields. The allowed-tier rule is defined in [`rbac.md`](rbac.md#custom-field-visibility-tiers):
  - `chapter` → any viewer who can see the directory (`members:view`).
  - `self` → only the member themselves (the owner). Not overridden by the president — private fields stay private.
  - `exec` → viewers with member/role management authority (`roles:manage` or `members:remove`) or the wildcard.
  - `president` → only the wildcard (`*`) holder.
- The read-only `GET /custom-fields` endpoint lists a chapter's full field-definition set for the **settings Fields tab** (gated by `chapter-config:view`); definition write CRUD also belongs to that tab. The member directory does not call it — it renders each member's values from the tier-filtered profile read (`GET /members/:id` on web, `GET /members/by-user/:userId` on mobile), so the existence of higher-tier/sensitive fields is never exposed to baseline members.

## Invite Flow

- Invites can be shared as a **join link** (one token per link; `POST /v1/invites/batch` still mints several at once, though no client calls it since 2026-11-06), or sent to a **list of email addresses** (up to 50 at a time — `POST /v1/invites/email` mints one token per address, stores the address on the invite (`invites.email`), and emails each a join link that names the chapter and who sent it; a per-address delivery failure does not fail the whole batch, and its token is still valid to share manually). A **bulk CSV upload** path is specced but not yet built — see #580.
- **The web Invite members panel never shows a token (2026-11-06, Paul).** Its top is the composer, shared with the web setup wizard's invite step (`apps/web/components/members/invite-composer.tsx`): an email field that turns each typed or pasted address into a chip, a role picker offering only the roles the sender may invite into ([`rbac.md` § Rank](rbac.md#rank)), and Send. An address that isn't one turns red when it becomes a chip, never per keystroke, and blocks Send (the client and `BulkEmailInviteDto` use the same check, `isInviteEmail`); an address the server couldn't email stays in the field, marked, so Send tries it again. Below it, a copy-link control mints one fresh single-use link and copies only the join URL. Nothing is minted before a press. Under that, the panel lists every pending invite and the joined or expired ones from the last 14 days, leaving out any whose role the sender couldn't invite someone into themselves (#4546, [`rbac.md` § Rank](rbac.md#rank)), newest first, by address (or as a share link), with the role, when it was sent, and its status. Revoked invites are not listed. A pending invite's row menu copies its link or revokes it; an emailed invite that is pending or expired can be sent again. **Mobile lists the same invites and offers the same actions** (2026-11-09, #3828): both apps read `listedInvites` and `inviteMenuActions` from `@repo/hooks`. The phone's rows leave out the role, and it shares a link where web copies it ([`navigation.md` § Inviting members](../ui/mobile/navigation.md#inviting-members)). The wording of each control is in [`writing.md`](../ui/design-system/writing.md) § Invite members.
- **One live invite per address.** When a new email invite is delivered, the address's older pending invites in the chapter that the sender could see are revoked, so sending again (from the row menu or by retrying a marked chip) never leaves two live links for one person. An address whose new email failed keeps its older invite, which may be the one that reached them.
- **Status (#3607).** `GET /v1/invites` returns typed rows with a `status`: `revoked` when `revoked_at` is set, else `joined` when `used_at` is set, else `expired` past `expires_at`, else `pending`. A revoke sets `revoked_at` and `used_at` together, so every path that refuses a used token refuses a revoked one, and a redeem that claimed the token but failed to add the member cannot reopen it.
- Invite gating follows the subscription rules in [`onboarding.md`](onboarding.md) § Invite Token Rules: minting is free-tier for an `incomplete` chapter, but blocked for `past_due` (even in grace) and `canceled`; redeeming an already-minted token is refused (403, token kept) once the chapter is under the hard lock — `canceled`, or `past_due` past grace — and admitted otherwise (#1546).
- **Default invite role.** A chapter can nominate the role new invites use when the sender does not pick one, set in Settings → Roles and persisted as `chapters.default_invite_role_id`. Naming a role on the invite still wins, so the default is a starting point rather than a restriction. Either way the role must rank at or below the inviter, and never carries `*`; a default the sender couldn't invite into gives way to the Everyone role ([`rbac.md` § Rank](rbac.md#rank)). Resolution order is explicit role → chapter default → the seeded Everyone role (once Member, [`rbac.md` § The Everyone role](rbac.md#the-everyone-role)); a chapter that has set no default behaves exactly as it did before the field existed. See [`rbac.md`](rbac.md) § Default Invite Role for the validation and deletion rules.
- **On send:** write a member-visible row to `chapter_audit_log`, which posts an audit message to `#chapter-audit`.

# Polls and Voting

- **Channel-access enforcement.** A poll is a chat message (`type: POLL`) and is governed by the same channel-access invariant as the rest of chat (`chat/README.md`, "Channel-access enforcement"). Every poll operation authorizes through the shared `ChannelAccessService` (`canAccessChannel` predicate) before doing anything else, in addition to its `@RequirePermissions` gate:
  - `createPoll` authorizes as a **`post`** to the poll's channel (it authors a message); `vote`, `removeVote`, and `close` authorize as a **`vote`**; `getPoll` authorizes as a **`read`**. `vote` clears the same read-only / `announcements:post` gate as `post`, but is exempt from the Alumni lifecycle rule — alumni are restricted from posting, not from participating in a poll they can already read, so they may vote and retract votes but not create polls. `close` is gated as a `vote` for the same reason, deliberately: an open-ended poll (no `expires_at`) with an Alumni creator must stay closeable by that creator, not get stuck open forever the moment they lose post rights. The creator-only check is separate and always enforced regardless — `close` authorizing as a `vote` widens *whose channel state* clears the gate, never *who* may call it. See [`alumni.md`](alumni.md).
  - An operation on a poll in a channel the caller cannot access returns **403** (or **404** when the poll/channel id does not resolve within the caller's chapter). The `polls:create` / `members:view` permission is necessary but not sufficient — channel visibility (`PRIVATE` / `ROLE_GATED` / `DM`) is enforced independently, so a member cannot read or vote in a restricted channel they are not in.
  - `GET /v1/polls` is **not a side-channel:** beyond the `polls:view_all` gate, it excludes polls in channels the caller cannot read (filtered via `ChannelAccessService.filterAccessibleChannelIds`). Filtering is applied after the result `limit`, so a page may contain fewer than `limit` rows; the list is never widened to backfill hidden polls.
- **Both poll reads apply the caller's chat block list** (#2495). A poll is authored by the member who created it, so `GET /v1/polls` and `GET /v1/polls/{messageId}` mask a poll from a member the caller has blocked **in place**: the row keeps its ids, timing, expiry, every `voteCount` and the caller's own `userVotes`, and loses its question and option text (`content` becomes the block sentinel, `metadata` keeps only `choice_mode`, `expires_at` and `closed_at`, and each result's `optionText` is `null`). It is not left out of the list, because the tallies are chapter state a block counts rather than hides, and dropping the row would change the page's counts. Every row carries `sender_blocked`, which is what a client keys on; an imported poll (`sender_id: null`) is never masked; and a block list that cannot be read fails the request rather than serving the poll in the clear. The rules are [`chat/README.md` § What a block does and does not hide](chat/README.md#what-a-block-does-and-does-not-hide).
- Users with `polls:create` permission can create polls in any channel they have access to.
- `GET /v1/polls` (chapter-wide list with aggregate tallies) requires `members:view` (controller baseline) **and** `polls:view_all` on the list route.
- `PermissionsGuard` merges class- and handler-level `@RequirePermissions` so both apply together.
- **Default role mapping:** `polls:view_all` is **not** on the default Member role, and every seeded role that holds it also holds `members:view`, so the guard chain succeeds. Which seeded roles those are: [`rbac.md` § Role Lifecycle](rbac.md#role-lifecycle).
- **Backfill migrations:** chapters that predate these seeds got the grants by data migration, not by re-seeding. Which migrations, and what each inserted: [`docs/guides/database.md` § Conventions](../../docs/guides/database.md#3-conventions) (RBAC seed vs existing data).
- Chapters may grant `polls:view_all` through custom roles if needed.
- **No client reads the REST list.** The web dashboard's `/polls` page was its only caller and was retired in [#3871](https://github.com/pdcarlson/Frapp/issues/3871) (Shawn, 2026-11-09): it could list only `type: 'POLL'` rows, which no client creates, so a poll made in chat never appeared there ([#3885](https://github.com/pdcarlson/Frapp/issues/3885)). The `/v1/polls` routes below stay until [#3887](https://github.com/pdcarlson/Frapp/issues/3887) removes them.
- Query parameters for `GET /v1/polls`: optional `channel_id`; optional `active` as a boolean string (`true`, `false`, `1`, or `0`); optional `limit` (default 50, clamped 1–200).
- A poll has a question, 2-10 options, and an optional expiration time.
- Members in the channel can vote. One vote per member per poll (single-choice by default; multi-choice is a poll option).
- When a member submits a new vote, the system treats it as a full replacement of that member's prior selection set for the poll.
- For multi-choice polls, the replacement flow atomically replaces all existing votes for that `(message_id, user_id)` pair with the newly selected options — no intermediate state where the member has zero votes is observable to other clients.
- Results are visible in real-time as votes come in.
- Once expired (or manually closed by the creator), the poll is locked — no more votes. **Manual close:** `POST /v1/polls/:messageId/close` (`polls:create` gate, matching `createPoll`) stamps `metadata.closed_at`/`closed_by`; only the poll's own sender may call it, and only while the poll is still open (closing an already-expired or already-closed poll 400s). `vote`, `removeVote`, `getPoll`'s `isExpired`, and `GET /v1/polls`'s `active` filter all treat a poll as closed the moment either `expires_at` passes **or** `closed_at` is set — a poll closed early with a still-future `expires_at` is excluded from `active=true` and included in `active=false` exactly like a deadline-expired one.
- Polls are stored as a special message type (`type: POLL`) in `chat_messages` with poll data in `metadata`, plus a `poll_votes` table for individual votes.
- **Closing a chat-card poll early (#3794).** The same `POST /v1/polls/:messageId/close` closes a chat card (`kind: 'poll'`), under the same rules: the `polls:create` gate and the Polls module, channel access as a `vote`, the poll's own sender only (403 otherwise), and 400 for a deleted card, one already closed, or one past its `closes_at`. A card keeps its poll in `payload`, so the close is stamped there, as `payload.closed_at` / `payload.closed_by`, rather than in `metadata`. **The API is the only writer of that pair:** a client can't update a message's payload, and `ChatService.sendMessage` drops both keys from a poll card a client posts, so a card can't arrive already closed or "closed by" someone else. From the moment it is set, the card vote path (`ChatReactionService`, through `cardPollClosedEarly` and `validateCardPollVote`'s `closedEarly` input in `poll-vote-rules.ts`) refuses a vote with the same 400 a past deadline gets, and both cards draw the card closed (`isPollCardClosed` in `@repo/chat-core/polls`): the row update reaches every open client as a Realtime UPDATE, and the closer's client merges the row the route returns without waiting for it. The creator's open, confirmed card offers **Close poll** under its tally on both clients, behind a confirmation, while the creator holds `polls:create` and Polls is known to be on; nobody else sees it (`canClosePoll`). The permission is part of the rule because posting a card doesn't require it ([#3007](https://github.com/pdcarlson/Frapp/issues/3007)), so a creator without it, such as a New Member, can post a poll they can't close early. Mobile builds shipped before this change (0.10.2, 0.10.3) read only `closes_at`, so until a member updates, their card draws an early-closed poll as open and a tap gets the server's refusal in the thread's action-error banner; the server stays correct either way. The early close is read by presence on every path, the REST shape's `metadata.closed_at` included, never by comparing its stamp to the checking process's clock. The other poll routes still take only the REST shape.
- **A chat-card poll with no deadline (#3896).** Both New poll forms offer **Doesn't close** after 1 hour, 1 day, 3 days and 1 week in "Voting closes in" (`POLL_CLOSE_CHOICES` in `@repo/chat-core/poll-draft`); a day stays the default. The forms offer it only to a member who holds `polls:create` (`pollCloseChoicesFor`), and not while that read is unknown: posting a card doesn't need the permission ([#3007](https://github.com/pdcarlson/Frapp/issues/3007)) but closing one does, so anyone else would post a poll that only deleting could end. This is the forms' rule, not the server's: the send route takes a card with no deadline from anyone, as it always took one whose `closes_at` was missing. It posts the card with `payload.closes_at: null`, which every reader treats as never closing by itself: the card vote path (`isPollClosed`), the close route, and both cards (`isPollCardClosed`), as they already did for a card whose deadline was missing or unreadable. Such a card ends only when its creator closes it early (above), so a creator who loses `polls:create` after posting (a role change, or moving to Alumni) leaves it open until the message is deleted ([#4046](https://github.com/pdcarlson/Frapp/issues/4046)). An open card with no deadline reads **Poll · No end date** in its eyebrow on both clients (`pollCardEyebrow`); a timed, open card reads plain **Poll**, and any closed one **Poll · Closed**. `/poll`'s `closes=<minutes>` always sets a deadline: the one-liner has no open-ended form, and a typed number opens the form on the nearest timed choice. Mobile builds shipped before this change read a `null` deadline as never closing too, and show the card as plain **Poll**.
- **A chat-card poll with more than one choice (#3793).** Both New poll forms have **Allow more than one choice**, off by default (a switch on web's dialog, a toggle under More options on the phone). On, the card is posted with `payload.choice_mode: "multi"`; a single-choice card carries no `choice_mode`, as every card before this did, so those read and vote unchanged. **Storage: one vote row per member, as before.** A member's vote on a multi-choice card is still the single `chat_message_actions` row ADR-07 upserts (`action_type: 'vote'`), and its `payload.option_id` is a list of option ids rather than one id; an empty list clears the vote. This was chosen over one row per option because it needs no migration and no API change: the dedupe index (`idx_chat_message_actions_dedupe`) and the upsert stand, and the card vote rules already read `option_id` as "one id or several" and already hold only a single-choice card to exactly one (`cardVoteSelection`, `validateCardPollVote`, #871), refusing a list on a single-choice card and an unknown id in any list. The cost is that a tap sends the member's whole list, and the later list wins. A vote isn't optimistic (the card redraws from the API's answer), so each card builds a tap on the member's last tap for ten seconds rather than on what it shows (`currentPollPicks`), which keeps two quick taps; two devices of one member voting at the same moment still keep the later list. A changed vote, and every pick after a member's first, is an UPDATE of that row, which the chat clients take from Realtime alongside INSERT and DELETE (`dispatchActionUpdate` in `@repo/chat-core/realtime-manager`); until this change they subscribed to INSERT and DELETE only, so other members saw a changed single-choice vote only after a reload. A cleared vote leaves the row with an empty list, so a reader that asks "has this member voted" counts picks, not rows: the cards' tally skips it, and Activity's `has_voted` reads it as not voted (`ActivityService`). What a client can read is unchanged (the same rows, under the same RLS), so nothing here widens the anonymity gap below. On a multi-choice card a tap adds or clears that option (`pollVotePayload`), the card says **Select one or more** under the question, each option's percentage is the share of voters who picked it (so the options needn't add up to 100), and the footer counts people ("3 people voted"). Mobile builds shipped before this change (through 0.10.3) draw a multi-choice card as single-choice: they count only votes whose `option_id` is one id, so their tally omits members who voted from a newer client, and a tap from one replaces that member's list with the one option. The server accepts both shapes on a multi-choice card, so nothing is refused. `/poll` posts single-choice only.
- **Expiry announcement.** It covers the REST shape only: the sweep reads `type = 'POLL'` rows, so a chat card (`type: 'TEXT'`, `kind: 'poll'`) gets no notice when its `closes_at` passes, nor when its creator closes it early, and there is nothing for an early card close to skip (checked 2026-11-09, #3794). A scheduled sweep (`ScheduledJobsService.sweepExpiredPolls`, every 5 minutes) posts a `system_audit` message — `This poll has closed.`, as a reply to the poll (`reply_to_id`) — into the channel of every poll whose `expires_at` has passed and that was not manually closed early (a manual `close` needs no announcement; the creator already knows). Like the other sweeps it claims a `scheduled_notification_dispatches` row (`entity_type: 'POLL'`, `threshold: 'EXPIRED'`) before posting, so it fires exactly once per poll across replicas and ticks. `system_audit` messages render in the channel timeline without sending a push notification (`push-rules.ts`), matching the pattern already used for invite-acceptance and chapter-welcome notices. The notice replies rather than quoting the question because the system actor cannot be blocked: `Poll "<question>" has closed.`, the text it posted until #2495, put a blocked member's question in the blocker's timeline beside the poll the block had hidden. As a reply, both clients draw the poll as the quote, and that quote is masked like any other reply to a blocked member's message. It replies in a read-only channel too: [`chat/README.md`](chat/README.md)'s no-threaded-replies rule there gates what a member sends, not what the server writes. One known cost: a client resolves the quote only from the messages it has loaded, so once the poll is further back than that the notice reads "Original message not loaded" (both clients load older pages only as the member scrolls up, #1571, #2772), and fetching the parent by id is [#2784](https://github.com/pdcarlson/Frapp/issues/2784). No notice in the old quoting form exists: when [#2681](https://github.com/pdcarlson/Frapp/issues/2681) checked on 2026-09-30, neither hosted database held one, or any poll, so there was no history to rewrite. A notice is also skipped for a poll deleted after the sweep's snapshot, which would otherwise quote `[message deleted]`.

## Anonymous polls

Anonymity is not built, and the obvious fix does not work. The design position below is **intent for unscheduled work**; the code state it rests on is an **observation**, measured against `main` on 2026-09-05 by reading the migrations, RLS policies and tally paths named inline. The negatives are the part that ages fastest — re-run them rather than trusting this paragraph:

```sh
# no sub-feature key is read anywhere — expect only comments
rg -n 'enabled_modules\.[a-z]+\.[a-z]|enabled_modules\[' apps packages
# poll_votes reaches TS only through the API repository — expect every other
# hit to be a comment, a type, or a test; a real query anywhere else falsifies
# the "client read: none" row below
rg -n 'poll_votes' --type ts apps packages
```

**No poll is anonymous today.** There is no anonymity flag in `PollMetadata`, no `anonymous` column anywhere, and no code path that treats one voter differently from another. The `polls.anonymous` entry in the module catalog (`packages/org-archetypes/src/index.ts`, `subFeatures`) is a **label with no storage**: `chapters.enabled_modules` is a flat `{module: boolean}` jsonb, no sub-feature key is written or read by anything, and the Settings Modules tab renders sub-features as read-only text under its own note that per-feature toggles are not built. Anything that reads `polls.anonymous` as configuration is reading a catalog string. This is true of every sub-feature key, not just this one (#1760).

### There are two poll systems, and they fail anonymity in opposite ways

The split is not a discovery of this section — `apps/mobile/components/chat/poll-card.tsx` already records it in its header, including the detail that keeps the two disjoint: `PollService.createPoll` leaves `kind` at its `'text'` default, so a REST-created poll never reaches the card renderer. Three things write a `kind: 'poll'` message, web's `/poll` slash command, web's New poll dialog (#3865, opened from the composer's + or by a `/poll` the parser can't read) and mobile's New poll sheet (#3701), and all three build it with `buildPollMessage` in `packages/chat-core/src/polls.ts`.

| | `/v1/polls` (REST) | Chat card (ADR-07) |
| --- | --- | --- |
| Poll body | `chat_messages.type = 'POLL'`, `metadata` | `chat_messages.payload`, `kind: "poll"` |
| Votes | `poll_votes` (`message_id`, `user_id`, `option_index`) | `chat_message_actions` (`action_type = 'vote'`, `payload.option_id`) |
| Tally computed | **Server-side** — `get_poll_vote_option_totals` / `get_poll_user_votes_for_messages` | **Client-side** — `tallyPollVotes` in `packages/chat-core/src/polls.ts` |
| Client read of vote rows | **None.** RLS on, zero policies → default-deny; only the API's `service_role` reads it | **Granted** by `chat_message_actions_select` — predicate owned by [`authorization-model.md`](../../docs/security/authorization-model.md) |
| Realtime | Not published | In the `supabase_realtime` publication |

**The REST path is already voter-private by construction.** `PollWithResults` projects per-option counts plus `userVotes` — the caller's own selections — and nothing else. No report, export or dashboard surface reads `poll_votes`. Adding anonymity there is a display concern, not a data-exposure one.

**The chat-card path cannot be made anonymous by hiding a field.** The client is the tallier: `apps/web/lib/chat/use-chat-channel.ts` selects `chat_message_actions` directly, Realtime streams row changes as they happen, and `tallyPollVotes` counts `message.actions` locally so the per-option breakdown and the viewer's own choice need no round trip. The table's read exposure is not specific to polls and is not restated here — [`authorization-model.md`](../../docs/security/authorization-model.md) owns the policy, and [`chat/catch-up.md`](chat/catch-up.md) works the same consequence for card dismissals. **What is specific to polls is that the exposed row *is the ballot*:** for a reaction, knowing who reacted is the feature; for a vote, it is the thing anonymity exists to prevent. That read is deliberate — it is what makes the card's tally instant and offline-tolerant — so anonymity here is a **direct trade against the ADR-07 hot path**, not an oversight to patch.

Making it anonymous takes two changes, not three. **The SELECT policy is the single lever for both the direct read and the live stream** — `20260816140000_realtime_carrier_repair.sql` states it outright: *"Realtime evaluates the SAME RLS policy PostgREST does."* So narrowing `chat_message_actions_select` to withhold an anonymous poll's vote rows suppresses the change events too, and the publication does not need touching. (It could not be scoped anyway: `alter publication ... add table` is table-level, so there is no per-poll exclusion to make.)

The second change is the expensive one: **the tally has to move server-side**, behind an aggregate the client can subscribe to, because withholding the rows is exactly what breaks `tallyPollVotes`. That is a re-architecture of the card's vote path, and it should be costed as one.

### Hard vs soft anonymity — the decision this rests on

**Soft anonymity** keeps `user_id` on the vote row and hides it from clients. Vote change, one-vote-per-member, and the `idx_chat_message_actions_dedupe` unique index all keep working unchanged. But the link is permanent: `service_role` sees every voter, and account deletion tombstones a user rather than removing them (`anonymize_user`), so the vote stays joined to a stable id forever. Telling a member a poll is anonymous while retaining that link is a promise the data model does not keep.

**Hard anonymity** stores no voter identity — at most a per-poll nullifier that proves "this member has voted" without revealing what for. It keeps the promise, and it costs: no vote change or retraction without a second construction, no per-member audit of who participated, and `idx_chat_message_actions_dedupe` / `poll_votes`' `unique (message_id, user_id, option_index)` both need replacing, since each is keyed on the identity being removed.

**This choice is open and is not settled here** (#1759). It is a product and trust call, and it is the one the privacy-and-minors concern raised in #382 actually turns on — a chapter running a rush ballot is exactly the case where "anonymous" being soft would matter to the people voting.

### Recommendation: anonymity is per-poll, fixed at creation

Recorded as a **recommendation for review**, not a settled decision.

Anonymity should be a property of the individual poll — set when it is created, immutable once the first vote lands — rather than a chapter-level setting:

- **A chapter is not uniformly one or the other.** The same chapter runs named quorum votes (where the record of who voted is the point) and anonymous rush ballots. A single chapter switch cannot describe both, and the driving use case in the module catalog — recruitment — is the minority case, so whichever way the switch defaulted would be wrong for real polls in the same channel.
- **Anonymity is a promise made to the voter at the moment they vote.** It has to be a visible property of the poll in front of them. A setting an officer can flip afterwards can retroactively expose votes cast under the opposite promise, which is the failure mode worth designing out rather than documenting.
- **It leaves the catalog entry meaning what every other sub-feature means.** `polls.anonymous` with `defaultOn: true` then reads as *the default for new polls in this chapter* — the same relationship `defaultOn` already implies elsewhere — rather than as a mode the chapter is in. That needs the sub-feature persistence path that does not exist yet, so an implementation that lands before it should default to named and let the creator opt in per poll.

### Surfaces that must hide voter identity

For a poll marked anonymous, every one of these is in scope. The first two are where it is currently impossible, not merely unimplemented:

1. **`chat_message_actions` SELECT policy** — the client's direct read of vote rows.
2. **The `supabase_realtime` publication** — live row events carry `user_id`.
3. **`tallyPollVotes`** (`packages/chat-core/src/polls.ts`) and both card renderers (`apps/web/components/chat/renderers/poll-card.tsx`, `apps/mobile/components/chat/poll-card.tsx`) — they must consume a server aggregate instead of raw rows.
4. **`PollWithResults.userVotes`** — correct as-is (the caller's own vote), but it must stay the caller's own and never be widened to other members.
5. **`polls:view_all`** — grants the chapter-wide list. It must not become a way to see who voted; today it does not, and that has to stay true by test rather than by accident.
6. **Any future poll export or report** — none exists today, which is the cheapest moment to write the constraint down.

Not in scope, and worth stating so it is not re-derived: `poll_votes` needs no RLS change. It has no policies, so it is already unreadable by clients.

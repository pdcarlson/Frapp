# Events & Attendance

## Event Creation

- **The maker is recorded** (2026-11-11, #3897): `events.created_by` is the member who called `POST /v1/events`, and a series' generated occurrences carry their head's. It is null on events made before then. Nothing gates on it; Activity reads it for "Made by you" ([`activity.md`](activity.md)).
- Anyone with `events:create` creates events with: name, description, location (free text), start time, end time, point value (configurable, default 10), mandatory flag, and recurrence rule (optional).
- **Who makes an event required or worth points** (2026-11-12, #3709, Paul: start from social trust). Every member holds `events:create` by default ([`rbac.md`](rbac.md#role-lifecycle)), so a member can put a study night or a pickup game on the calendar. Making anyone required, and attaching points, stay with `events:update` holders: the officers who edit any event and take attendance (in a new chapter the Exec board, so the Vice President and Secretary too, plus the Treasurer's own grant and the President's `*`). `POST /v1/events` from anyone else is stored lowered, never refused, since every client sends a point value (the forms and `/event` default to 10) and builds already installed copy a type's "required for everyone" into the form, so a refusal would leave a member retrying a save that can never succeed:
  - `is_mandatory` is stored false, and each `required_role_ids` role moves to `optional_role_ids`: still invited, never marked absent by the auto-absent sweep. `others_invited` is written out as the request meant it, so an event meant for some roles stays closed to the rest;
  - it is worth **0 points**, whatever `point_value` says;
  - it may still leave roles out or list them as optional.
  Editing already takes `events:update`, so what a create may set never exceeds what its maker could edit in later. The forms follow suit (`EventService.create` is the rule): for a member without `events:update`, web's editor and mobile's New event sheet hide the points field, a picked type fills only the name, and the Who's coming editor offers no Required answer (a row already Required keeps it, `attendanceChoices`), and a required choice that gets through anyway is stopped on the form with "Only officers who manage events can make one required" before it reaches the API. The maker can't edit or delete their own event afterwards; that is a proposal for Paul, not built.
- **Recurring events:** Whoever creates an event can set a recurrence rule (every member holds `events:create`, above), so one create can make up to 120 meetings. The system generates individual event instances according to the rule. Each instance can be individually edited or canceled. Recurrence rules can be modified (changes apply to future instances only).
  - **The rule format** (#4488, #3662; owned by `packages/validation/src/recurrence.ts`, which both the API's generator and the clients' captions read). `recurrence_rule` holds either a **legacy token** (`WEEKLY`, `BIWEEKLY`, `MONTHLY`) or a **structured rule**, a subset of iCalendar's RRULE written as `KEY=VALUE` pairs joined by `;`, for example `FREQ=WEEKLY;INTERVAL=1;BYDAY=MO,TH;COUNT=20;TZID=America/New_York`:
    - `FREQ` `DAILY`, `WEEKLY` or `MONTHLY`, and `INTERVAL` 1 to 30 (every N days, weeks or months).
    - Weekly: `BYDAY` names the days it meets (`MO,TH` is twice a week), and is required. Weeks run Sunday to Saturday.
    - Monthly: `BYDAY` with a week number meets on the nth weekday (`2TU` the second Tuesday, `-1FR` the last Friday); `BYMONTHDAY` (1 to 31, not with `BYDAY`) meets on that day of the month, falling back to a short month's last day. With neither, it meets on the first meeting's day of the month. When a series is handed to a later head, a by-date rule gains the old head's `BYMONTHDAY`, so a new head on Feb 28 doesn't move a series on the 31st.
    - Exactly one end: `COUNT` (2 to 120 meetings, the first included) or `UNTIL` (`YYYYMMDD`, the last day a meeting may fall on, inclusive). An `UNTIL` that leaves no second meeting, or makes more than 120, is a 400, on create, on an instance edit that sets the rule or moves the start of a row that carries one, and on a series edit (checked against the meeting that becomes the series' first when a started head is split off).
    - `TZID`, required: the zone whose wall clock the series keeps, so a 7 PM meeting stays at 7 PM across a DST change (a time a spring-forward change skips lands after the gap: 2:30 AM becomes 3:30 AM). Chapters keep no zone, so the clients send the creating officer's.
  - **The Repeat control** (web editor and phone sheet, one shared state in `packages/validation/src/repeat-draft.ts`): a preset row (Doesn't repeat, Daily, Weekly, Monthly), and under a picked cadence its options, shown open rather than behind a "Custom…" step (Shawn, 2026-11-12): weekday chips (the start's weekday on by default; two chips is twice a week) and Every N weeks for Weekly; Every N months and on the day of the month or the nth (or last) weekday for Monthly; and Ends, after N meetings (each cadence's default is `REPEAT_DEFAULT_COUNT`) or on a date, for every cadence, with a caption saying how many meetings and the last one's date.
    - Where a legacy token makes exactly the meetings the rule does (weekly on the first meeting's weekday or every 2 weeks, or monthly on its day of the month, at the token's own length, on a run no DST change moves) the client sends the token, because shipped phone builds read only tokens; they show any other rule raw and treat its head as one-time until they update. A token still differs on regeneration: a series edit that rebuilds it makes its run again from now.
    - On an edit, leaving Repeat untouched leaves the stored rule alone, so a legacy token isn't rewritten into a structured rule that would rebuild the series. A changed rule goes with `series` scope (`null` for Doesn't repeat, which ends the series), stepped from the meeting that is the series' first once the save lands: the head moved by the save's shift, or the next meeting when the head has started. The control shows what will be saved: weekdays left as stored move with a start moved in the same save, and on a started head a count left as stored counts the meetings left. A one-time event that has started can't begin a series (the editors say so; the API would refuse it). Neither editor sends an unchanged rule (they send only what changed). Both edit Repeat from any meeting of a series (a generated occurrence's change goes to its parent, read when the editor opens; web holds Repeat until it has it) (#3667).
  - The series head is always the first meeting; the rule makes the meetings after it. A `COUNT` counts from the head, so when the head leaves the series (an instance delete of the head, or a series edit on a started head, below) the new head's `COUNT` drops by the pattern's meetings before it, ones canceled on their own included, and a later regeneration keeps the series' length. When fewer than two meetings of the pattern would remain, by `COUNT` or `UNTIL`, the new head stands alone with no rule.
  - A series edit that moves the head and keeps the rule moves the rule's days with it: a weekly rule's days by the days the head moved, a monthly rule's day of the month or nth weekday to the new head's. An instance edit checks a rule's end only when the rule or the start changes, so a save that sends the stored rule back isn't judged on it; a start moved without the rule in the request is checked against the stored rule, since the editors send only what changed (#4515).
  - **Legacy tokens** are still accepted, because shipped phone builds send them, and still read, so no stored row is migrated. A token makes a fixed run after the first meeting (12 weekly, 6 every two weeks, 6 monthly), stepped in UTC as before, and regeneration makes that run again from now.
- **Recurrence edit and cancellation scope.** `PATCH /v1/events/:id` accepts an optional `scope` in the body and `DELETE /v1/events/:id` an optional `scope` query parameter, each one of `instance` (the default) or `series`. There is deliberately no "this and past" — the rule above allows individual edits and future-only series changes, and nothing else.
  - **The editors ask** (web and the phone alike, #3667; `event-edit.ts` in `@repo/validation`), as Google Calendar, Apple Calendar and Outlook do: saving an edit to, or deleting, a repeating event that hasn't started asks "This event only" or "All upcoming events". A Repeat change isn't asked: it is always `series`. An event already under way edits and deletes only itself, since a series write never reaches a started event. An edit from a generated occurrence waits for its parent to load (web holds Save; the phone holds Edit), and if the parent can't be read it edits only itself, since a series time change has to go through the parent; a delete needs no parent and still asks. A series time change from a generated occurrence is sent to the parent as the same shift. Only changed fields are sent, and an untouched form saves nothing: on "All upcoming events" every field sent is written onto each upcoming meeting, so sending the whole event would undo a meeting changed on its own. When the server refuses an "All upcoming events" save the officer picked, the editors say to save it to this event only or change the next event; a refused Repeat change, which can't be saved to one event, gets the plain error. A series save that rebuilds the occurrence on screen returns to the Events list rather than to that occurrence.
  - **`instance`** is what a caller that sends no `scope` gets, and is the pre-existing behavior for updates. Deletes touch one row *except* when the target is a recurring series head, where the successor promotion below also writes the new head and re-points its siblings — so a client must not assume a single-row invalidation there.
  - **`series`** resolves to the series parent first — so the operation behaves the same whichever occurrence the client happens to hold — and then applies to the parent and to every *generated* occurrence that has not yet started. **A generated occurrence whose `start_time` has passed is never deleted and never patched.** That boundary is evaluated server-side from `start_time`, never from a flag the caller sends, because `event_attendance.event_id` is `on delete cascade`: deleting a past occurrence would destroy the record of a meeting that happened and everyone marked at it.
  - **A `series` edit whose head has already started splits the series rather than rewriting the head.** The parent row is both the series *template* that regeneration reads from and the series' own *first occurrence*, so writing the patch to a started head edits a meeting that already happened. Instead the started head is retired into standalone history — its `recurrence_rule` cleared and **no other field written**, so its `event_attendance` rows keep describing the meeting as it actually was — and the earliest *upcoming* occurrence becomes the new series head, carrying the edit and the recurrence rule. Remaining future occurrences are re-pointed at it (or regenerated from it); occurrences that already happened are detached into standalone events, as everywhere else. Guarding the head instead of splitting it does not work: regeneration reads the parent as the template, so a head that stops accepting writes is rebuilt from stale values — a reschedule is silently dropped, and a later rule change reverts an earlier rename.
    - **The series head's id changes**, exactly as it already does when `instance`-scope deletion of a head promotes its successor. The old id keeps resolving to the meeting that took place, which is the right target for a chat event card, a notification deep link or a previously exported `.ics` — each was created for that occurrence, not for the series.
    - **Times are applied as a shift, not as instants.** The caller's `start_time` describes the old head and lies in the past; moving the head 18:00 → 19:00 moves every upcoming occurrence an hour later rather than anchoring the series on the head's past date. A shift that would push the next occurrence before now is a 400.
    - A `series` edit on a started head with **no upcoming occurrence** is a 400: every row it could reach is history. Edit those with `instance` scope.
    - Clearing `recurrence_rule` in the same edit ends the series; the promoted occurrence survives as a standalone event carrying the edit, rather than the edit landing nowhere.
  - A `series` edit addressed to a **generated occurrence** applies every field except `start_time` / `end_time`. Those describe the occurrence the client had open, not the series anchor — a client that round-trips the whole event object (both apps did before #3667) would otherwise turn a rename into a request to move the whole series. Move the anchor by addressing the head. An edit from a generated occurrence carrying *only* times is a 400 rather than a silent no-op.
  - On a `series` update, a change to `recurrence_rule`, `start_time` or `end_time` **regenerates** the future occurrences from the new rule; any other field is patched onto them in place. The comparison is by value, not by presence — a client that PATCHes the whole event back with an unchanged rule does not trigger a regeneration. Regeneration of a legacy token always yields a full run of *upcoming* dates: occurrences falling in the past are skipped without consuming the count, so a long-dormant series regenerates forward rather than to nothing. A structured rule's `COUNT` or `UNTIL` is fixed from the head, so regeneration makes only its meetings still to come. A `recurrence_rule` outside the format above is a 400 **before** any occurrence is deleted (`null` still clears the series).
  - **Deleting a series parent with `instance` scope promotes the next still-upcoming occurrence** into the series head and re-points its remaining future siblings at it; occurrences that already happened are detached into standalone events rather than promoted, and if none is still upcoming the series simply ends. `events.parent_event_id` is `on delete set null`, so without that promotion cancelling the first occurrence would silently strand the rest of the series as unowned rows that no later series operation could reach.
  - `series` deletion of a series whose parent has already started ends the series in place (clearing its `recurrence_rule`) rather than deleting the parent row, for the same attendance reason; surviving past occurrences are detached into standalone events.
  - Generated occurrences inherit the parent's `check_in_zone` and `check_in_zone_name` along with its other fields, so a recurring meeting's geofence applies to every date rather than only the first.
- **Attendance by role** (2026-11-06; replaces the single required-roles list): an event says, for everyone and then per role, one of three answers: **required** (counted, and marked absent if they don't check in), **optional** (can see it and check in for points, never marked absent), or **not invited** (can't see it). The default is the answer for everyone, and roles that differ from it are listed. An officer sets "Required for officers, optional for everyone else", or "Required for everyone, not new members", in one place.
  - **Columns.** `is_mandatory` and `others_invited` (boolean, nullable; see Wire) hold the default: `others_invited = false` is "not invited", otherwise `is_mandatory` picks required or optional. `required_role_ids`, `optional_role_ids` and `excluded_role_ids` (text arrays) list the roles that differ. A member's answer is the strongest their roles reach, **required > optional > not invited**, and the default only when none of their roles is listed (`eventAttendanceFor` in `@repo/validation`, which the API, web and mobile all read).
  - **Wire.** On create, omitting a list stores none; on update, omitting one leaves it and sending `[]` clears it. `others_invited` is nullable: a row written without it (before the column, or by a client or API that predates it) reads as invited unless `required_role_ids` is non-empty, the old meaning, so an older build keeps targeting during a deploy. Omitted on update, it is left as stored. The apps send it on create only when a null would read differently, so a plain event still creates against an older API. A stored `[]` is the same as `null` everywhere. The values are **RBAC role ids** (rows of `roles`, as in `member.role_ids` and `GET /v1/roles`), not `chapter_custom_roles` keys ([`rbac.md`](rbac.md)).
  - **Who is counted.** The auto-absent sweep and the attendance roster count a member whose answer is required. The mobile list's Mandatory chip is the viewer's own answer, so an event required only of officers carries it for an officer and not for anyone else.
  - **Editors.** Both show one line with the whole rule ("Officers required, everyone else optional"; `describeAttendance`), then "Everyone else" and one row per role, each with the same three answers (owner, 2026-11-07, #3706: picking Required and then a role read as contradictory). A role that only follows Everyone else holds its answer in neutral ink; a role set apart is lit, so what changed reads at a glance. Setting a role to Everyone else's answer puts it back with everyone else. At a hundred roles a search narrows the rows past eight, and the roles set apart when the editor opened lead, in an order kept for that visit (`attendanceRows`); on web the rows flow with the panel, showing the set-apart roles and the first few others with "Show all" for the rest. While the Alumni role follows Everyone else, its row says "Left out unless set here", since an alumnus is held to an event only when a role of theirs is set apart ([`alumni.md`](alumni.md)). On mobile the sheet is a step stacked over New event that closes with **Done**, a swipe or Android back, each returning to the form with the row filled in. The web panel (`apps/web/components/events/attendance-editor.tsx`) and the mobile Who's coming sheet (`apps/mobile/components/events/attendance-sheet.tsx`) share their moves from `@repo/validation`.
  - **An answer of not invited also gates read access.** A member whose answer is not invited gets nothing back from `GET /v1/events` (filtered out of the list), a `404` from `GET /v1/events/:id` (never a `403`, so the response can't be used to confirm a role-targeted event exists), no hit for it from `GET /search`, and no row for it in `GET /v1/activity-feed` or `GET /v1/activity` (each carries the event's name and location, so each resolves events through the viewer, not chapter-wide). The new-event and rescheduled pushes and in-app notifications ([`notifications.md`](notifications.md#what-a-push-says) § What a push says) are scoped the same way — only eligible members are notified, not the whole chapter. A member who holds `events:update` (or the wildcard `*` role) is exempt from all of the above and always sees every event, so an officer who can edit any event is never blocked from finding it to do so.
  - **An event that leaves anyone out cannot be created with a chat card.** `POST /v1/events` returns `400` when the event limits its audience (`others_invited = false`, or a non-empty `excluded_role_ids`) and either `channel_id` or `client_message_id` is supplied (either key alone, not just the pair), and no event row is written. The `kind:"event"` card embeds the event's name, times, location and point value in a chat message that Realtime fans out to every reader of the channel, so posting one would show an ineligible member exactly what `GET /v1/events/:id` returns `404` to hide. It is refused rather than redacted because the card is a snapshot the client renders from its own payload — it never draws from a re-read of the event: its live requests are the `events:update`-gated attendance roster, whose holders are exempt from the role gate anyway, and on mobile, while check-in is open, the event itself, read only for whether it has a check-in zone (an ineligible member's `404` shows them nothing) — so a single broadcast row cannot show different viewers different things, and channels gate on `required_permissions` (permission strings) rather than roles, so there is no channel the card could be safely confined to instead. An event that invites everyone and only sets some roles required or optional posts a card as before, since every reader may see it. The `/event` slash command is unaffected: it has no syntax for roles and always invites everyone. **Known gap:** `PATCH /v1/events/:id` can still limit the audience of an event whose card already posted, and that card is left in place — the details were chapter-visible at the moment they were broadcast, and no scrub is attempted. Deleting the card removes them from the message: a delete clears the card's `payload` and no API read serves a deleted card's data (#1575, spec/behavior/chat/README.md § Edit and delete). The in-app notification each member was sent, which quotes the card's text, is deleted with it ([#4418](https://github.com/pdcarlson/Frapp/issues/4418)); what outlives it is a push already on a phone, a notification written before #4418 reached the environment (it records no message id), and, for a card deleted before #1575, the row's `payload` until its cleanup migration runs.
- **Meeting minutes:** Events have an optional `notes` field (rich text / markdown). Editable by admins with `events:update` permission after the event. Visible to every member the event invites (attendance by role, above). While the meetings module is on, the minutes are their own record and this field is the event's notes, labeled "Notes" ([`meetings.md` § Where minutes live](meetings.md#where-minutes-live)).

## Event types

(2026-11-11, #3730 step 1.) A chapter keeps a short list of the kinds of event it holds, so the member making one picks "Chapter meeting" instead of thinking about points and attendance.

- **What a type is.** A row of `event_types`: a name (1 to 60 characters, unique in the chapter ignoring case and outer spaces), points for attending (0 to 100,000) and whether everyone must attend. `position` orders the list. A chapter holds at most 30 (`EVENT_TYPES_MAX`).
- **Seeded.** Every chapter starts with seven, by a trigger on `chapters` (existing chapters were backfilled): Chapter meeting (10 points, required), Committee meeting (5), Philanthropy (10), Community service (10), Brotherhood (5), Work party (5), Social (0). Officers rename, re-point or delete any of them.
- **Picking one fills the form, and that's all.** The New event form (web and mobile) opens with the chapter's types as a row of chips above the name, none picked. Picking one sets the points and the default attendance (required or optional for everyone; roles already set apart stay) and makes the type's name the event's name if the name is blank. Everything stays editable. The event stores `event_type_id` and keeps its own `point_value` and `is_mandatory`, so **editing a type never changes events already made**. A repeating event's occurrences carry the type.
- **Who manages them.** Anyone with `members:view` reads them (`GET /v1/event-types`). Adding, changing and deleting need `events:update` (`POST`, `PATCH`, `DELETE /v1/event-types[/:id]`): the officers who may edit any event decide what each kind is worth. A member who may only create events picks a type for its name alone: since #3709 their event carries no points and requires nobody, whatever the type says ([above](#event-creation)). On web, "Edit types" at the end of the picker opens the list; on mobile the picker only picks.
- **Deleting a type** clears `event_type_id` on its events (composite foreign key, `on delete set null (event_type_id)`); they keep their points and attendance. An event can only point at a type of its own chapter; an id that isn't the chapter's is a 400.
- **Not yet** (the rest of #3730): a points category per type, service hours on check-in, and per-type check-out, an excuse receiver per type, and RSVP (#3734, #3735, #1035).

## Check-In

- Members check in via the mobile app (self-service).
- **Rotating check-in code.** An officer with `events:update` mints a rotating code from `GET /v1/events/:eventId/attendance/check-in-token` and displays it (mobile s22); a member scans it (s18) and the token rides on the check-in request. The code is HMAC-signed over the event id and a 30-second window, and the server accepts the **current and the immediately previous** window so a scan racing a rotation still lands. A short manual code (`4KQ-88`) is minted from the same secret for members whose camera fails. Signing key: `EVENT_CHECK_IN_TOKEN_SECRET` — where it is unset the mint route returns 503 and a supplied token is rejected, while plain self check-in is unaffected.
  - **"Single-use" means once per member, not once per code.** One host code is scanned by everyone in the room inside the same window; a globally single-use token would admit exactly one member. The one-per-member guarantee is the unique `(event_id, user_id)` index enforced inside `check_in_event`, not a redemption ledger over tokens.
  - **A token is verified when supplied, and required once a screen has shown it** (#4532, Paul 2026-11-12). Until an officer's screen reports for the event (below), the chat event card checks in with no token, as it always has. From the first report until check-in closes, a check-in without a code is refused (403, "Scan the code on the check-in screen with the Frapp app to check in"), on a zoned event too, and mobile's chat card turns its Check in into Scan code, which opens s18. Web has no scanner, so its event card and event sheet show that sentence, which names the app. Who may check in, and whether they already have, is answered first: a member already checked in hears that (409), not "scan the code". A code alone is still not proof of presence, since any displayed code can be screenshotted and forwarded inside its window; the location checks below are.
- **Near the QR screen (the default presence check, #4532, Paul 2026-11-12: "within 100 yards of the person with the QR code device").** While mobile's host screen (s22) draws a code, it reports where it is with `PUT /v1/events/:eventId/attendance/check-in-screen` (`events:update`, the mint's gate): once when a code is first drawn, then every minute it stays up, never while no code is drawn (a screen that can't get a code must not make one required). The event keeps one record per officer showing the code, `event_check_in_screens` (two doors can have two phones), and each report replaces that officer's own record, location included: a phone carried to another room moves its anchor, and one that loses its fix stops anchoring its old spot.
  - **The rule.** With no drawn zone and at least one live screen location, a check-in must carry the member's coordinates (400 "This check-in needs your location…" without them) and be within **100 yards (91.44 m)** of one of those screens, plus each phone's reported accuracy up to 50 m (`accuracy_meters` on the check-in; the screen's on the record). So the furthest a check-in passes is about 210 yards, and a member 300 yards away with a fresh code is refused (403 "You need to be near the check-in screen to check in"). Owned by `apps/api/src/domain/utils/check-in-screen.ts`. Measure on real events before tightening: phones drift 15 to 50 m indoors.
  - **A screen that can't tell where it is** (location refused for Frapp, no fix, or a fix less precise than 100 m) still reports, without a location: the code is required, and when no other officer's screen has a location, distance isn't checked. It never touches another officer's record, so a laptop without a location beside a phone with one doesn't switch the check off. The host screen says which is happening in one line under the count: "Members check in within about 100 yards of this phone.", "Members check in near another officer's screen. This phone can't tell where it is.", or "Distance isn't checked." with why (and Open Settings once the OS won't ask again). The answer is the route's `check`: `screen`, `other_screen`, `no_location`, `zone`, or `not_open` / `closed`.
  - **Any officer's open screen counts.** An officer who opens s22 away from the room (to watch the count) anchors a second spot, so a member near that officer with a forwarded code would pass too. That is accepted: it takes an officer standing with the member.
  - **A drawn zone wins.** An event with `check_in_zone` is checked against it alone, and its screen's location isn't stored.
  - **Retention.** The screen's location is stored only inside the event's check-in window: a report before the window opens or after it closes stores nothing, and the record expires when the window closes (read from the event's times on every report, so an edited end time is followed from the screen's next report; a screen closed before an edit keeps the old close). Nothing reads an expired record, and a sweep (`CheckInScreenSweepService`) deletes it within 10 minutes. Members never read it: the table has row-level security on and no policies, so only the API does.
  - The member's scanner (s18) keeps a GPS fix ready while it is open, when location is already allowed (it doesn't prompt for it there), and a scan uses that fix. A scan with no fresh one asks for its own, without insisting and for at most 8 seconds, because the scanned code expires in 30 to 60: it sends the code with no position when the phone gives none, and the server says whether it needed one. A drawn zone still insists before sending.
- **Check-in geofence (drawn zone).** An event may carry `check_in_zone` — a polygon of `{lat,lng}` vertices — plus a display name in `check_in_zone_name`. When set, check-in **requires** the member's coordinates on every surface and rejects a position outside the polygon (403); a request that omits coordinates is a 400, and a malformed polygon fails closed rather than being treated as "no zone". When `check_in_zone` is null the event has no drawn geofence, and the QR screen above is the check when one reported a location. Any displayed code can be screenshotted and forwarded, so presence — not the code — is what the server actually verifies (`spec/ui/mobile/patterns.md` § QR check-in). A surface that cannot supply a location, such as the web chat event card, is told to use the mobile app (by the refusal's own sentence, through the shared error map) rather than left with a control that fails silently.
  - Zones are set through `POST /v1/events` / `PATCH /v1/events/:id` (`events:create` / `events:update`). Sending an empty array **clears** the zone, matching the role lists' wire semantics above; fewer than three points is a 400.
    - **The two verbs are deliberately asymmetric, and the asymmetry is load-bearing.** `CreateEventDto.check_in_zone` carries `@ArrayMinSize(3)`, so an empty array on create is a 400 rather than "no zone" — a zone-less create must omit the field entirely. `UpdateEventDto` drops that decorator precisely so `[]` can clear a stored zone. A client that sends `[]` on create to mean "no geofence" gets a validation error, not an un-geofenced event.
  - The **dashboard event editor** surfaces the zone as a list of coordinate rows (add / remove / reorder) plus the zone name, and rejects fewer than three points in the form before the API does. Until this shipped the fields were reachable only by hand-crafting an API request, so the geofence was enforced everywhere but creatable nowhere. Drawing a zone on a map is a later addition — it needs a mapping dependency the repo does not carry, and the coordinate rows are the interim surface, not a permanent one.
  - The **event detail view** reports zone state in three ways, not two: a named zone with its point count, no zone at all, or a warning that the stored polygon is malformed. The third case matters because a non-empty polygon with fewer than three valid points fails `isValidZone` and so rejects every check-in — showing it as "no zone" would tell an officer the opposite of what members experience.
- Check-in atomically creates an attendance record AND awards the event's point value (same database transaction), via the `check_in_event` RPC.
- Check-in is only available during the event's window: from `check_in_opens_minutes` before `start_time` (per event, 0–120, default 10; members arrive early, #3703) until 15 minutes after `end_time`. The rule is `checkInWindowBounds` in `@repo/validation`, which the API enforces and every client reads, so no surface keeps its own copy. An officer sets the lead in the mobile event sheet's More options; the chat event card carries it in its payload, and a card posted before the field existed reads as the default.
- Unique constraint: one attendance record per (event, user) — enforced inside `check_in_event` via `on conflict do nothing`, so a concurrent double check-in inserts nothing and returns 409 Conflict without a double award. See [points.md](points.md) for the atomicity invariant. Each occurrence of a recurring series is its own event row, so the pair is per occurrence. `apps/api/test/integration/check-in-once.integration-spec.ts` pins the guard against a real database. The 409 is the API's answer to a repeat, not a second record: a member's own row is readable at `GET /v1/events/:eventId/attendance/me` (`{ attendance: row | null }`; any member who may read events, `members:view` as `GET /v1/events/:id` requires, unlike the `events:update` roster; an event the caller can't see 404s by that route's rule), which is how mobile's event page shows "Checked in at 7:52 PM" in place of check-in, and how web's event sheet shows a member their own check-in ("Checked in 7:52 PM", an officer's mark such as "Marked excused", or **Check in** during the window, with the mobile app named instead for an event with a zone); the sheet mounts the roster only for `events:update` (#3855). A repeat is answered 409 by decision (owner, 2026-11-08, #3703): the clients read it as "you're in": the mobile scanner (s18) reads the member's own row and, when it is a check-in, shows its success panel ("You're already in", no points), or says the officer's mark when one replaced it; mobile's chat card shows the member checked in; web's chat card and event sheet toast that the member is already on the list (a 409 also answers an officer's mark, so neither says "checked in"), and the sheet then shows the row it re-reads.
- Only members the event invites can check in. A member whose answer is not invited receives a 403 Forbidden.
- Alumni-role members cannot check in and receive a 403 Forbidden, checked before the attendance + points write — **unless** one of the alumnus's roles is listed as required or optional, which is an explicit decision to include them (e.g. an alumni homecoming). See [alumni.md](alumni.md).

## Attendance Management

- Admins with `events:update` permission can view full attendance for any event.
- **Marking excused:** Admins mark members as EXCUSED with an optional reason string. This edits an existing `event_attendance` row — `updateStatus` 404s when the member has none. A member who knows ahead sends an excuse instead ([§ Excuses](#excuses)); approving it writes the row. Excused members are not penalized for mandatory events and do not appear as ABSENT in reports.
- Admins can also manually mark members as ABSENT or LATE after the event.
- Marking a member ABSENT who previously checked in (PRESENT) does NOT reverse the points already awarded. The admin must separately create a point adjustment if needed.
- **Auto-absent:** For mandatory or role-targeted events, members who are required to attend but did not check in, were not marked EXCUSED and hold no pending or approved excuse ([§ Excuses](#excuses)) are auto-marked ABSENT after the grace period ends. Alumni-role members are excluded on non-targeted events — they can neither check in nor send an excuse, so marking them would guarantee an ABSENT record they have no way to avoid. A role-targeted event keeps whoever it names, alumni included. This runs automatically: an hourly scheduled sweep processes every event whose grace period closed in the preceding 24 hours, so no officer action is required. The admin-triggered endpoint remains available for immediate marking. Re-running is harmless — members who already hold an attendance record are skipped.

## Excuses

(2026-11-12, #3735.) A member an event requires tells the chapter they can't make it, and the event's receiver approves or declines, in place of a text to the secretary.

- **Two picks Paul can redirect in review** (Shawn asked for it to be built with the issue's own picks, 2026-11-12): the **receiver is the event's creator**, and excuses are accepted **up to 48 hours after the event ends** (`EVENT_EXCUSE_LATE_HOURS` in `@repo/validation`). A per-type receiver (an event type naming the Secretary role, from [Event types](#event-types)) is not built yet.
- **Who can send one.** Only a member the event requires, by the rule the auto-absent sweep uses (`AttendanceService.requiresMember`, the single-member form of `resolveRequiredMembers`, sharing its helpers: required by [attendance by role](#event-creation), an alumnus only when a role of theirs is named). On an optional event there is nothing to excuse. A member already checked in (PRESENT or LATE) or already EXCUSED gets a 409, as does a second excuse for the same event, and one an officer marked ABSENT (an approval could not reverse it). One line, 1 to 500 characters (`EVENT_EXCUSE_REASON_MAX`).
- **When.** Any time before the event, and until 48 hours after its `end_time`; later is a 400.
- **Who receives it.** The event's creator (`events.created_by`) while they can act on it: still a member of the chapter and able to see the event (a creator who lost `events:update` and isn't invited to their own role-limited event would get the excuse routes' 404). Otherwise, and for the creator's own excuse, every `events:update` holder. One push per excuse, category `events`, titled "Sam can't make Chapter meeting" with the reason as its body, never to the sender. Anyone with `events:update` may also decide. A creator never decides their own excuse unless they hold `events:update`.
- **Store.** `event_excuses`, one row per `(event_id, user_id)`: `reason`, `status` (`PENDING`, `APPROVED`, `DECLINED`), `decided_by`, `decided_at`. Kept apart from `event_attendance` so it can exist before the event.
- **Approving** writes the member's attendance EXCUSED with the reason and the decider as `marked_by`, in the same transaction as the decision (`decide_event_excuse`): over an ABSENT the sweep wrote (`marked_by` null: a late excuse) or an EXCUSED, never over PRESENT, LATE or an ABSENT an officer set (the API answers those 409 first). **Declining** leaves the member required: before check-in closes the sweep marks them as usual; after it (the sweep already ran and skipped them while pending), the decline writes ABSENT itself, with the decider as `marked_by`, while the event still requires them. The member is pushed either way ("Excused", or "Excuse not accepted"). Only a pending excuse from a current member is decided; anything else is a 409. Corrections after that go through the officer's attendance edit above.
- **Checking in drops a pending excuse:** the member came after all, so it asks nothing of the receiver.
- **The sweep** skips a member with a pending or approved excuse. A pending excuse stays pending past the grace period, and the sweep sends the receivers one reminder for the event ("2 excuses for Chapter meeting still need a decision."), under the sweep's own once-per-event claim. Until someone decides it, that member has no attendance row: the roster leaves them out and the officer's attendance edit 404s for them, so the receiver's Excuses list is where they're found and decided. The 30-minute pre-event reminder skips a member whose excuse was approved; a pending one may still be declined, so it keeps the reminder.
- **Withdrawing.** The member takes back a pending or approved excuse until check-in closes. An approved one's EXCUSED row goes with it (`withdraw_event_excuse`), so they can check in after all. A declined excuse, or any excuse once check-in has closed, can't be withdrawn (409).
- **Routes** (`/v1/events/:eventId/excuses`; every route needs `members:view`, as `GET /v1/events/:id` does, and an event the caller can't see 404s by that route's rule): `POST` sends one (`{ reason }`); `GET me` returns `{ excuse, receiver }`, where `receiver` is the creator's id and name for "Excuse sent to Jake" (null when the event has no creator in the chapter or the caller made it); `DELETE me` withdraws; `GET` lists the event's excuses from current members with each sender's name, for the creator or an `events:update` holder (403 otherwise); `PATCH :userId` decides (`{ decision: "APPROVED" | "DECLINED" }`).
- **Known gap: a series edit that regenerates occurrences deletes their excuses.** Changing a series' times or rule replaces its upcoming occurrences ([Event Creation](#event-creation)), and `event_excuses` cascades with the deleted rows, as does an approved excuse's EXCUSED row, without telling the member. Tracked in [#4620](https://github.com/pdcarlson/Frapp/issues/4620).
- **Not yet:** the phone and web screens (Can't make it on the event and the chat card, the receiver's list and roster count), deciding from the push, and a per-type receiver. Those follow in their own PRs (#3735).

## Edge Cases

- Deleting a role does **not** release its holders. `RbacService.delete` calls straight through to `SupabaseRoleRepository.delete`, a bare `delete from roles`, with no cleanup of `members.role_ids` or the events' role lists, and no trigger does it either — so the dangling id still matches, and a member who held the deleted role stays required, stays able to check in, and stays eligible for the auto-absent sweep.
- If an event's point value is changed after some members have already checked in, only future check-ins use the new value. Already-awarded points are not retroactively adjusted.

## Calendar Integration

### Calendar subscription

Added 2026-11-12 (#3322, step 1). A member puts the chapter's calendar on the calendar app they already use (Apple Calendar, Google Calendar, Outlook) through a **private subscription link**. Frapp never writes to the member's calendar account; the calendar app fetches the link on its own schedule and shows what it gets.

- **Where.** A **Subscribe** menu on the web Events toolbar, and a calendar icon in the mobile Events header that opens the same choices as a sheet: Apple Calendar (web, and iPhone only on mobile, since it opens a `webcal://` link as a one-tap subscription), Google Calendar, Outlook.com and Outlook for school or work (web only: outlook.live.com is personal Microsoft accounts, outlook.office.com is Microsoft 365, the Outlook most college members have), **Copy link**, and **Reset link**. Shaped after TeamSnap's schedule Subscribe, Canvas's Calendar Feed and Heja's schedule sync, which each put this one control on the calendar screen.
- **Google Calendar adds a calendar by link only on a computer**, never in its phone app (Google's own help says so). On the web the row opens Google's add-by-URL page. On a phone it says so instead, and offers **Share link** so the member can send it to themselves and add it from a computer.
- **One link per member per chapter**, made the first time they open the menu (`POST /v1/calendar-feed`, idempotent) and the same link every time after. **Reset link** (`POST /v1/calendar-feed/reset`, behind a confirm) replaces it.
- **What it serves**, read fresh on every fetch with the app's own read rules, so an edit, a cancelled or deleted event, or a role change reaches the calendar at its next check:
  - every event the member can see ([§ Attendance by role](#event-creation)) that ends within the last 60 days or starts within the next year, one calendar item per occurrence, in UTC;
  - the member's own tasks that aren't completed or confirmed: on the due day as an all-day item, or at the due time when the task has one (a moment with no length), titled "Due: <title>";
  - nothing from a module the chapter turned off.
- **What leaves Frapp.** An event's name, time, location and description, and "Required" when the event requires this member (the push's rule, `memberAttendance`). A task's title, due date or time and description. Points, meeting notes, check-in details and who else is invited stay in Frapp.
- **Every item links back** to its Frapp page, twice: the iCalendar `URL` field, and the first line of the description ("Open in Frapp: …"), because not every calendar app shows `URL`. Events link to `/events?event=<id>` on the web app; tasks link to `/tasks`, which has no per-task web link yet.
- **The link is the credential.** Calendar apps fetch with no sign-in, so the URL carries a 256-bit random token (`GET /v1/calendar-feed/feed.ics?token=…`, no auth guard, no per-address throttle, because Google fetches every subscription from a shared pool of addresses). The token rides in the query string, which the API's request log and Sentry drop. Anyone holding the link reads what it serves, which is why the menu offers Reset link, and why Reset works even while the chapter's subscription has lapsed (`@SubscriptionExempt`, as member safety; making a first link follows the free wedge). Each link's calendar is rendered at most once every five minutes per API instance, so a link fetched in a loop costs one render, and a change can take up to five more minutes to reach the calendar.
- **When access ends, the calendar empties.** A reset link, a member who left the chapter, or one who lost `members:view` gets a valid but empty calendar rather than an error, so the calendar app clears what it holds; calendar apps keep their last copy when a fetch fails. An unknown token is a 404. A deleted account's links are deleted with it.
- **How fast changes arrive** is the calendar app's choice. The feed asks for hourly checks (`REFRESH-INTERVAL`, `X-PUBLISHED-TTL`); Apple Calendar and Outlook read one of them. Google Calendar ignores both and refreshes on its own schedule, reported as several hours up to about a day. The menu says so in one line. Instant updates in Google need a push integration through Google's Calendar API (Google sign-in, a Google app review), which #3322 keeps as a possible second step.
- **One way only.** Nothing is read back from the member's calendar.

### The withdrawn `.ics` download

- **No per-event "Add to Calendar".** Withdrawn 2026-11-08 (#3708), on the owner's call that handing a member an `.ics` file was not useful: the web downloaded one from `GET /v1/events/:id/ics` and mobile built its own and handed it to the share sheet. The route, both builders and both buttons were deleted. The subscription above replaced it (2026-11-12).
- **Files already exported stay valid.** Each mobile-built `.ics` carries `frapp://event-details?id=<event id>`, and those entries live on in members' calendars, so the route and its `id` param stay a contract ([`navigation.md` § Deep links](../ui/mobile/navigation.md#deep-links)).

## Chat Integration

The `/event "<name>" <YYYY-MM-DD> <HH:MM>-<HH:MM> [location] [points=<n>]` slash command creates an event
(`events:create` and `members:view`, re-checked on `POST /v1/events`) and posts a server-originated **event card** to the
current channel — an immutable snapshot (name, when, location, point value). Every member sees a
**Check-in** action during the event window (its lead before the start → end + grace), so the chat card is an *additional*
self-service check-in surface alongside the mobile app; the server enforces the window, the role gate, and
one-check-in-per-member regardless of surface. Once an officer's screen has shown the check-in code, the card's
plain check-in is refused and members are told to scan the code (mobile's card turns into Scan code, [§ Check-In](#check-in)). Viewers who can read attendance (`events:update`) also see a
live checked-in count read back through the attendance query (members can self-check-in but can't read the
roster, so the count is shown only to them). Recurrence, role-targeting, and the mandatory flag stay off the one-liner. On web, an `/event` the one-liner can't read opens the full event form in the chat instead, and it posts the card the same way ([`integrations.md` § Slash command catalog](chat/integrations.md#slash-command-catalog)).

Role-targeting and the card are mutually exclusive on create, and `POST /v1/events` enforces that with a `400` —
because the card is broadcast to every reader of the channel, it would undo the read gate. The rule, its reasoning
and its one known gap live with the rest of role-targeting, under
[Attendance by role](#event-creation); this section does not restate them.

Pre-event **RSVP intent** (going / maybe / not-going, ahead of the window) is not yet modelled — tracked as
a follow-up. The shared slash-command catalog, dispatch path, renderer registry, and the
server-originated-kind (anti-forgery) rules are canonical in [`integrations.md`](integrations.md) and the
chat-specific [`chat/integrations.md`](chat/integrations.md).

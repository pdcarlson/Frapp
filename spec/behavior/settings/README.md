# Chapter Settings

The settings surface is the chapter's configuration home. It is one stable layout (#3827, 2026-11-11): a **settings rail** at a fixed 200px that stays put (sticky) while the panel beside it scrolls, and a panel at one width whichever row is open. Chapter settings takes the **whole width**: side-by-side chat closes while it is open and comes back on leaving (decision 3 of [#4068](https://github.com/pdcarlson/Frapp/issues/4068); `isFullWidthToolRoute` in `apps/web/components/layout/shell-layout.ts`). The rail lists the setup rows grouped **Chapter**, **People** and **Modules**, where **Modules** is one row per module ([#4073](https://github.com/pdcarlson/Frapp/issues/4073); § Module pages below). There is no Danger zone row since the second #3827 PR: what it held moved into Plan and billing (below). The rows and their groups are `SETTINGS_TABS` in `apps/web/components/settings/settings-rail.tsx` and are not restated here: a hand-copied list of tab names is how this paragraph came to name two that no longer exist. Each row's panel is a stack of sections, each named by its section label, not a stack of cards (the page grammar, [`../../ui/web-dashboard/README.md`](../../ui/web-dashboard/README.md) § Page grammar). This file covers the cross-cutting behavior plus the **Chapter** (formerly Org), module, **Privacy**, **AI** and **Plan and billing** rows; the customization-heavy ones (Accent, Roles, Fields, Dues, and the workflows behind two module pages) are specced in [`customization.md`](customization.md).

Two renames and one split landed with the greenfield Admin lane ([#2146](https://github.com/pdcarlson/Frapp/issues/2146)), and the `?tab=` deep-link values did **not** change with the labels: **Org** is labelled "Chapter" (`?tab=org`), and Org's semester and billing/danger cards moved to their own **Semester** (`?tab=semester`) and **Danger zone** (`?tab=danger`) entries. **Accent** was its own row (`?tab=theme`) until #3827 folded it into Chapter, under the chapter mark; `?tab=theme` still opens Chapter. **Fields** is labelled "Member fields" (`?tab=fields`). **Danger zone** (`?tab=danger`) folded into **Plan and billing** (`?tab=billing`) in #3827; `?tab=danger` opens it.

Related canon lives in:

- [`../chapter-config.md`](../chapter-config.md) — `GET/PATCH /chapters/:id/config` endpoints.
- [`../rbac.md`](../rbac.md) — role lifecycle and permission catalog.
- [`../branding.md`](../branding.md) — chapter logo and accent color.
- [`../billing.md`](../billing.md) — dues invoicing.
- [`../data-retention.md`](../data-retention.md) — pseudonymous analytics + the chapter opt-out surfaced by the Privacy tab.

## Who sees what

Chapter settings is the one door to officer setup and officer tools (the web nav row was named Settings until 2026-11-10; a member's own settings are a separate page, [`../../ui/web-dashboard/README.md` § Two doors](../../ui/web-dashboard/README.md#two-doors-chapter-settings-and-your-settings)). The web nav's six-row Admin group folded into that single row so the nav fits a 1024×768 window ([#2946](https://github.com/pdcarlson/Frapp/issues/2946); [`../../ui/web-dashboard/README.md`](../../ui/web-dashboard/README.md) § Navigation map). So the page shows each viewer only what they can use. This section owns those rules. In code they live in `apps/web/components/settings/settings-access.ts`, which the nav's Settings row and the chapter switcher's "Chapter settings" link read too:

- **Tools** live on their module's page (Chat admin and Discord import on Chat, Study zones on Study zones, Reports on Reports; `page` in `SETTINGS_TOOLS`), not a rail group since [#4073](https://github.com/pdcarlson/Frapp/issues/4073). No tool leaves Chapter settings ([#3837](https://github.com/pdcarlson/Frapp/issues/3837), Paul 2026-11-12). Study zones (since [#2239](https://github.com/pdcarlson/Frapp/issues/2239)), Chat admin and Reports are **embedded** (`embedded` in `SETTINGS_TOOLS`): the zone list, the channels-to-report-queue body and the export form are their module page's own body. Discord import is a row on the Chat page that opens it in place of the page with a back arrow, and so does a channel's own settings (`?channel=`); the lit rail row also goes back. `/geofences`, `/chat-admin`, `/discord-import` and `/reports` only redirect to those pages, carrying their params. Each shows to a holder of its own permission and hides when its module is off; `SETTINGS_TOOLS` lists them with the gates each had as a nav row.
- **Module pages** need `chapter-config:view`, or a tool that lives on that page and is showing: a treasurer holding only `reports:export` gets the Reports page and nothing else, and loses it when the chapter switches Reports off. A module that is off for every chapter in the beta (`BETA_OFF_MODULES`, Dues) has no page.
- **Setup tabs** need `chapter-config:view`. They read or write chapter config, and `ChapterConfigController` guards both its read and its PATCH on `view`, so `chapter-config:manage` alone opens none of them ([`../rbac.md`](../rbac.md)).
- **Two tabs admit one more permission each.** The Roles tab admits `roles:manage`: it needs no config read ([`customization.md`](customization.md) § Roles Tab). The Semester tab admits `semester:rollover`: its rollover card is the only web surface for a rollover.
- **Plan and billing needs `billing:view` and nothing else** ([#3827](https://github.com/pdcarlson/Frapp/issues/3827), decision 8 of [#4068](https://github.com/pdcarlson/Frapp/issues/4068)). It is the gate the sidebar's Billing row had, so whoever reached billing before still does, and holding it is enough to show the Chapter settings door. It reads the billing record and invoices, not chapter config, so `chapter-config:view` alone doesn't show it. Plan actions inside it stay behind `billing:manage`.
- **The pledge class tab needs `roles:manage` and nothing else** ([#3939](https://github.com/pdcarlson/Frapp/issues/3939)). It reads no chapter config, and `roles:manage` gates every write on it, so `chapter-config:view` alone doesn't show it. The rail names it in the chapter's own word for a class, as typed ("Pledge class", "Line"). Its copy never pluralizes or lowercases a chapter's word, which is free text. What it does: [`../members.md` § Pledge class and order number](../members.md#pledge-class-and-order-number).
- **The door hides when there is nothing behind it.** The nav row and the switcher link show only when the viewer has a tab, or a tool whose module is on. Anyone reaching `/settings` with no row gets an empty state that names who can grant a role. A `?tab=` deep link to a tab the viewer doesn't get lands on the first tab they do.
- **While the permission read is in flight**, the page draws its skeleton, and the nav row and the switcher link stay hidden. Each appears only once the read has answered that this viewer has something there, so a member never sees an officer's door or rail drawn and then taken back. A failed read shows the page's error state with a Retry, not a guess. Offline with nothing cached, the read can't run, which is not a denial: the nav row and the switcher link show, and the page states the outage with its offline state (`apps/web/lib/hooks/use-nav-permissions.ts`). *Changed in #4281 by pdcarlson, 2026-11-11:* this used to fail open, every tab and tool showing until the read answered, which flashed officer entries at every member on every reload.

## Chapter Tab (`?tab=org`)

- Identity fields: name, university, Greek letters (not drawn for an organization that doesn't display them, [`../branding.md` § Chapter mark](../branding.md#chapter-mark)), designation, school short, founded year, donation URL. Emptying a branding field and saving clears it (the form sends `""`, since the config PATCH deep-merges).
- **Chapter mark** card ([`../branding.md` § Chapter mark](../branding.md#chapter-mark)): upload, replace or remove the logo, set the short name, and turn the Greek letters off, with a live preview of the nav's chapter tile. The logo routes take `CHAPTER_PROFILE_PERMISSIONS`, like the profile save; the short name and the switch go through the config PATCH, which takes `chapter-config:manage`, like the identity fields.
- **Archetype** is selectable from the eight supported archetypes. Switching archetype **resets modules and vocabulary** to the new archetype's defaults (no role changes: nothing seeds roles from the archetype); identity, branding, and custom fields are kept. The switch is confirmed before applying because of the reset.
- Archetype lookups always resolve through the `getArchetype()` helper, which falls back to the `ifc` archetype when the stored key is missing or unknown. Settings must never crash on a stale or in-flight archetype value, and must never read an archetype map directly by key without that guard.
- **Vocabulary** is configurable per chapter via four substitutable terms: pledge/aspirant/candidate, rush/recruitment/intake/induction, class/line/cohort, and (since #3939) a member's order number: fraternal order/bond number/line number/roll number. The Settings form edits all four. The config PATCH deep-merges, so the form sends a cleared field as `""`, which readers take as the archetype's word (`memberViewVocabulary`); a key left out would keep its stored word. All settings copy and downstream surfaces render the chapter's chosen term through the vocabulary helper (`vocab()` in `@repo/org-archetypes`) rather than hardcoding "rush" or "pledge."

## Plan and billing (`?tab=billing`)

Billing used to be its own route behind a sidebar row. A president checks it a few times a year, so it is a row of Chapter settings ([#3827](https://github.com/pdcarlson/Frapp/issues/3827)), the way Discord, Slack and GitHub keep billing inside server, workspace or organization settings. Top to bottom:

- **The plan**: the plan panel, with the lapse line above it when the chapter is `past_due` or `canceled`. Its rules (one reader for the status, checkout or Portal by status, the bounded webhook wait) are [`../../ui/web-dashboard/README.md` § Surviving data contracts](../../ui/web-dashboard/README.md#surviving-data-contracts). An `active` chapter with no Stripe customer is one Frapp switched on by hand: the panel says "Turned on by Frapp. No card on file and nothing to pay." and offers no Manage in Stripe, because the Portal refuses a chapter without a customer.
- **What the plan includes**: the module matrix. On a paid plan its heading says what the chapter has rather than what it could buy, and the Pro column is marked as the chapter's.
- **Member invoices**, the treasurer's list, while dues is on (it is off for the beta).
- **Cancel or close**, what Danger zone held. Cancelling is the plan panel's Manage in Stripe for a Stripe customer; a chapter Frapp switched on writes to team@frapp.live, as does anyone closing a chapter for good. A closed chapter's history is kept, locked for editing.

`/billing` redirects by what the viewer holds: Plan and billing for `billing:view`, otherwise the member's own **My invoices** in personal Settings (`/preferences?section=invoices`), or chat while dues is beta-off and there are none. Stripe's return URLs point at Plan and billing directly (`/settings?tab=billing&checkout=…`); the redirect carries `?checkout=` for a session that began before the move.

## Module pages (`?tab=<module key>`)

Each module is a row in the rail's Modules group and opens one page ([#4073](https://github.com/pdcarlson/Frapp/issues/4073), slice 11 of [#4068](https://github.com/pdcarlson/Frapp/issues/4068)), the way Discord gives each integration its own page with its switch and its "Roles & Members" list, and Slack each app its configuration. The list and the order are `MODULE_SETTINGS` in `apps/web/components/settings/settings-modules.ts`. Members, the audit log and Chapter settings are the chapter rather than modules, Billing is Plan and billing, and the catalog's prototype extras with no product behind them have no page. Top to bottom:

- **The switch**, with the plan the module belongs to (**Free**, locked on, or **Chapter Pro**). It writes `enabled_modules[key]` through the config PATCH (optimistic, rollback on error, in flight per switch through `usePendingConfigKeys()`). While a module is off, its rail row says **Off** and the page says what is hidden. Officers can still set its rules.
- **Tools**: the module's officer tools (above).
- **Rules**: only settings that are stored and read. Service hours has the point rate (`chapter_service_config.minutes_per_point`) and **Ask for proof** (`wf_hours_receipt`); Points has its two anti-fraud limits (`chapter_points_config`); Dues has its form and the grace period (`wf_dues_grace`). Every other module has no Rules block yet. Below the rules, Points has a **Goals** block for the points goal and Service hours one for the service and study hours goals: a goal for everyone (empty is none), and "Different goal for a role", a searchable list of roles, adds a role with its own (left empty, it holds that role to no goal); each measure saves on its own button through `PUT /v1/goals/:metric`, which needs `chapter-config:manage` (the rules are [`../activity.md` § Goals](../activity.md#goals), #1062). Numbers validate on save or blur and name the problem under the field.
- **Who can**: each of the module's permissions from the permission registry, with the tiers that have it, and a role only where it differs from its tier or sits outside the tiers (#3990: a chapter with a hundred roles reads its four or five tiers, not forty chips). A `roles:manage` holder edits it in place (Paul, 2026-11-11: "why would I want to go all the way back to roles for this?"): a chip's × takes the permission away and Add, a searchable list of the tiers and then the roles that lack it, grants it, each saved on click through the same `PATCH /v1/role-tiers/:id` or `PATCH /v1/roles/:id` the Roles pages use. Tiers and roles the rank rules put out of reach are not offered and keep no ×. Anyone else sees it read-only with a link to Roles. The President's wildcard is said once rather than drawn on every row. It shows to `members:view` holders. A role's own Off / Same as tier / On answers are set on its Roles page ([#4072](https://github.com/pdcarlson/Frapp/issues/4072)).

**One answer for "is it on" ([#3028](https://github.com/pdcarlson/Frapp/issues/3028)).** `GET /chapters/:id/config` reports every catalog module as `ChapterGuard` enforces it: on unless the stored column says `false`. It used to lay the archetype's seed under the column, so a module the archetype seeds off with no stored key showed off here while the guard, the nav and the slash palette treated it as on. Archetype seeds reach the column through onboarding and an archetype switch. Beta-off is applied by the clients' `isModuleEnabled`, not by this read, so a save can't store a beta-off module as off. An always-on module can't be switched off: the PATCH refuses it (`400`, `chapter.config.module_always_on`).

**Switching a module off immediately** hides its nav item, removes its slash commands from the chat palette, and keeps its data, so switching it back on restores it. Module state is read from chapter config, never from a `window.*` global.

**Old links.** `?tab=modules` opens Events, `?tab=modules&module=<key>` opens that module's page with its switch focused (chat's ops-setup nudge now links `?tab=<key>&module=<key>`), and `?tab=workflows` opens Service hours.

## Privacy Tab

- Chapter-wide data controls, gated by `chapter-config:manage`. Non-managers see the toggles read-only.
- **Analytics opt-out.** A single toggle writes the `chapters.analytics_opt_out` scalar through the config PATCH mutation (so it is audit-logged like every other config change). The switch is framed positively ("Chapter analytics" on/off) to avoid a double-negative — *checked = analytics enabled = `analytics_opt_out` false*. Default is opt-in (analytics on); onboarding discloses this. The same flag gates PostHog session replay ([`observability.md` § Privacy and replay](../observability.md#privacy-and-replay)).
- When opted out, **web and mobile** emit **zero** events for the chapter's members (enforced at each app's `AnalyticsProvider` via the shared `isAnalyticsOptedOut` gate in `@repo/validation`) and the API repeats the check server-side as defense-in-depth. Full pipeline + keying semantics live in [`../data-retention.md`](../data-retention.md) (#analytics-events-pseudonymous).

## AI Tab

The president's switch for each AI feature family ([#4308](https://github.com/pdcarlson/Frapp/issues/4308); the rules are [`../ai.md` § Consent](../ai.md#consent), gate 1). A **Chapter** row, `?tab=ai`. Implementation: `apps/web/components/settings/settings-ai-tab.tsx`; the words are `AI_SWITCHES` and `AI_SETTINGS_COPY` in `@repo/validation`, which mobile shares.

- **Only while the server has AI.** With `AI_ENABLED` off every AI route answers 404 `ai.not_available`, and the rail has no AI row, so Chapter settings is what it was. The row waits for that answer rather than flashing in and out.
- **Every config viewer sees the switches here; only the president changes them.** `GET /v1/ai/settings` answers `can_change` for the member holding the chapter's President role, and the page draws the switches read-only for everyone else with "Only the chapter president can turn these on or off." The PATCH checks again (`ai.settings.president_only`) and audits each change to `#chapter-audit`. [`../ai.md` § Consent](../ai.md#consent) says every member can see which switches are on: the API serves them to every member (`members:view`), but no web page draws them for a member without `chapter-config:view` yet ([#4376](https://github.com/pdcarlson/Frapp/issues/4376)).
- **Three switches, in this order:** Minutes from notes (the beta feature), Ask Frapp, and Include channel messages. The last changes what Ask reads and lets members summarize a channel ([`../ai.md` § Catch me up](../ai.md#catch-me-up), 2026-11-12), and neither works with Ask off, so it is drawn nested under Ask Frapp and can't be turned on while Ask is off ("Turn on Ask Frapp first."). It can still be turned off then, so a president who turned Ask off can clear what it would read. The server stores it either way. While one switch saves, all three wait, so two saves in flight can't leave one drawn wrong.
- **Every switch has its screen.** Ask Frapp's row used to carry a line saying it comes in a later update; the slice that shipped Ask on web removed it (2026-11-12, #450). Ask has no mobile screen yet, and the page does not say so: the switch governs Ask wherever it exists.
- The header names who the chapter's information goes to, from the providers Meet Frapp AI names, so the page and what the member agreed to never disagree.

- Beta preferences live in the chapter's `beta_config` object (`{ enabled, style }`), read and written through the audited config GET/PATCH like every other tab — shape in [`../chapter-config.md`](../chapter-config.md). Writes already work; nothing reads them yet.

## Audit Rules

- **Audit-write on save:** the core-profile and config PATCHes, the logo routes, custom fields and the Roles tab's role routes write a row to `chapter_audit_log` when they **change something**. Each audit row is created `member_visible = true` and is mirrored to the `#chapter-audit` channel via the audit bridge. Not every writer keeps to one row per *effective change*: the next two bullets say where they differ. The Roles tab's rows ([#2599](https://github.com/pdcarlson/Frapp/issues/2599)):
  - `POST /v1/roles`, `PATCH /v1/roles/:id` and `DELETE /v1/roles/:id` write `role_created`, `role_updated` and `role_deleted`, with `target_type` `role`. They cover the non-system roles the Manage roles section calls custom roles, and every permission switch on a role.
  - Create and delete record the role row under `role`. An update records one `from`/`to` pair per changed `name`, `color`, `display_order`, `mentionable` or `tier_id`, records `permission_overrides` as the whole map before and after, and records `permissions` as `{ added, removed }` rather than both arrays.
  - The tier routes (`/v1/role-tiers`, [#4071](https://github.com/pdcarlson/Frapp/issues/4071)) write `role_tier_created` and `role_tier_deleted` (the tier row under `tier`), `role_tier_updated` (`name` as `from`/`to`, `permissions` as `{ added, removed }`; no row when neither changed) and `role_tiers_reordered` (`order`, the tier names before and after), with `target_type` `role_tier`.
  - A Discord import that creates roles or grants them its channels' read permissions writes the same rows, as the member who started it.
  - `POST /v1/roles/transfer-presidency` writes `presidency_transferred` (`target_type` `chapter`) with `president_member_id` going from the outgoing to the incoming member.

  Not every Settings write is audited: the Semester tab's rollover (`POST /v1/chapters/current/rollover`, including any New Member promotion) writes no row ([#2596](https://github.com/pdcarlson/Frapp/issues/2596)).
- **Writers differ on a no-op save.** The core-profile `PATCH /chapters/current` writes **no** row when its diff is empty. `PATCH /chapters/:id/config` returns early only when its *update payload* is empty, which is not the same test: it assigns `branding`, `vocabulary`, `enabled_modules` and `beta_config` whenever the DTO merely carries the key, so a client that re-sends an unchanged jsonb object still gets a row whose `diff` has `from` equal to `to` (#1605). The custom-field `PATCH` route behaves like the config route: only an empty patch returns early, so re-sending an unchanged field writes an `_updated` row. The logo routes split: removing a logo that was never set writes nothing, and every confirm writes a row, `from` equal to `to` included ([`chapter-config.md` § The logo routes](../chapter-config.md#the-logo-routes) says why). `PATCH /v1/roles/:id` writes **no** row when the saved role's `name`, `color`, `display_order`, `mentionable`, `tier_id`, `permission_overrides` and `permissions` all match the old ones, with permissions compared as a set, so re-sending them in another order is no change. Do not assume a row means something changed, and do not assume a save without changes produced no row.
- **Audit writes are not transactional with the mutation they describe** (#1599). The row is inserted after the change commits, so an insert failure surfaces as a `500` on a change that persisted. Whether an identical retry then recovers the record depends on the writer. For example, on the core-profile route and a logo removal the retry changes nothing, so nothing is written and the change stays unaudited; a retried custom-field create or delete is refused (`409`, `404`) and writes nothing; on the config route a re-sent jsonb field, and on a logo confirm the retry itself, writes a row whose `from` equals its `to`; a retried custom-field update writes an `_updated` row whose snapshots differ only in `updated_at`, which a trigger sets on every update. On the Roles tab a retried role create, delete or presidency transfer is refused (`409`, `404`, `403`) and writes nothing, and a retried role update changes nothing, so it writes nothing and the change stays unaudited. A Discord import start that fails on one of these audit writes has already created the role or granted the permission, and a retried start skips a step that is already done, so that role or grant stays unaudited too. Do not build a compliance check on the assumption that every mutation has a row.
- **The Audit tab is not built, and has no rail entry.** When it lands it presents a paginated, filterable table of `chapter_audit_log` rows (filter by actor, action type, date range), with per-row expansion of the change `diff`. It rendered a coming-soon placeholder until [#2146](https://github.com/pdcarlson/Frapp/issues/2146) deleted that stub with the Beta one above. Not to be confused with the **Points** admin Audit tab, which is built and is a different surface.
- **Who sees which rows (#1773).** `GET /v1/audit-log` returns **only `member_visible` rows to every caller except the chapter's President**, who sees all of them, exec-only included. "President" is the member holding the chapter's seeded `PRESIDENT` system role — the one role that may carry the wildcard — not any permission a custom role can be minted with, so a custom role holding `chapter-config:view` + `members:view` reads the same member-visible history the `#chapter-audit` mirror shows. The filter is applied in the API (`ChapterAuditLogService.list` → the repository's `member_visible = true` predicate, which is what `idx_audit_log_chapter_visible` exists for); `chapter_audit_log` carries no SELECT policy because the service-role query is the only reader. A chapter with no President role (orphaned, or mid-transfer) has no exec-only readers until one exists.
- **`member_visible` is togglable per row, president-only.** Toggling `member_visible` **off retracts** the corresponding `#chapter-audit` message for non-president members **and** drops the row from their `GET /v1/audit-log` reads; toggling it back **on re-posts** it and restores the row. The toggle itself is not built yet; the read-side rule above is, so the toggle cannot ship visibly present and silently ineffective.

# Chapter Billing (Stripe)

## The chapter subscription

- **One flat price per chapter per month, in USD**, billed as a Stripe recurring subscription. The amount, the commercial framing and the free-tier split are in [`positioning.md` § Paid tier (Chapter Pro)](../product/positioning.md#paid-tier-chapter-pro); this section is the mechanical contract.
- **One Price, one line item, `quantity: 1`.** `StripeBillingService.createCheckoutSession` builds `line_items: [{ price: STRIPE_PRICE_ID, quantity: 1 }]` in `mode: 'subscription'`. A different `STRIPE_PRICE_ID` can therefore change **the amount and nothing else** — per-seat billing, quantity tiers, and per-chapter price variation each need a code change first, because a quantity-tiered Price would always resolve to its first tier against a hardcoded quantity of 1.
- **A 14-day trial opens at checkout**, set by `subscription_data.trial_period_days` (#913). It has to be set there: Stripe's Price object exposes no writable trial field, so a trial cannot be carried by `STRIPE_PRICE_ID` and is lost silently if that argument is dropped — the checkout would then charge on day zero while the public site still advertises a free trial. `stripe.service.spec.ts` asserts it separately for that reason.
- Stripe reports the window as `trialing`, which `mapStripeStatus` folds into `active`. No `trial` state exists in the database and none is needed — the `subscription_status` CHECK allows only `incomplete`/`active`/`past_due`/`canceled`, and a trialing chapter is deliberately a fully active one to every permission gate.
- **The whole Stripe → chapter status map** (`BillingService.mapStripeStatus`, applied by `customer.subscription.updated`): `active` and `trialing` → `active`; `past_due`, `unpaid` and `paused` → `past_due`; `canceled` and `incomplete_expired` → `canceled`; `incomplete` → `incomplete`. So an `unpaid` or `paused` subscription starts the `past_due` grace clock like any failed renewal. A status outside the map is logged at `warn` and changes nothing.
- **The trial is once per chapter, not once per checkout session.** A chapter that has ever held a subscription (`subscription_id` is set) gets no trial on a later checkout, and is charged immediately. This has to be decided by `BillingService`, which can see billing history, and is passed down as `grantTrial` — the provider adapter cannot tell a first subscription from a fifth. It is deliberately keyed on having held a subscription rather than on status, because a chapter can return to `canceled` repeatedly.
- That guard is load-bearing rather than defensive. Checkout now refuses `active` and `past_due` and reuses the chapter's stored customer (§Duplicate checkout below), so Stripe _can_ see a returning chapter's trial history — but `grantTrial` remains the boundary rather than a second line of defence, because it is keyed on our own record of having held a subscription rather than on what Stripe infers from a Customer. A `canceled` chapter still reaches checkout by design, and it is `grantTrial` alone that stops it collecting another 14 free days on every return.
- When the trial is withheld, `subscription_data` is omitted from the session entirely rather than sent with a zero-day trial. Absence is the unambiguous way to say "no trial" — a repeat checkout is then an ordinary immediate charge, with no dependence on how Stripe treats `trial_period_days: 0`.

## Webhook Reliability

- Stripe webhooks are the **source of truth** for subscription status changes.
- Every webhook event is checked for idempotency using the Stripe event ID (never process the same event twice). The check is **durable**, not per-process: the event id is claimed in `stripe_webhook_events` **before** any side effect runs, so a redelivery after a deploy, a crash, or onto a second API instance is skipped rather than re-applied. Only the event types with side effects are claimed (`HANDLED_WEBHOOK_EVENT_TYPES` in `infrastructure/billing/stripe-webhook-events.ts`); anything else is logged and dropped without touching the table. Ordering (below) and event-id dedup are orthogonal — the `last_stripe_webhook_at` mark deliberately treats a same-second redelivery as fresh, so it cannot deduplicate on its own.
- The claim is a compare-and-set (`claim_stripe_webhook_event`): of N simultaneous deliveries of one event, exactly one claims it. The losers return **503 rather than acknowledging** — acking would tell Stripe the event was delivered while the winner's outcome is still unknown, so a winner that then failed would leave the event dropped with nothing to retry it. A claim left `processing` for more than 5 minutes is treated as abandoned — the worker died mid-handler — and the next delivery takes it over, so a crash cannot wedge an event permanently.
- Processing is therefore **at-least-once**, deliberately: a handler that crashes after its side effects but before the row is marked `processed` is retried once its claim goes stale. Losing a billing event is the worse failure, so the design errs toward a rare replay rather than a rare drop.
- A handler failure stamps `status = 'failed'` with the error and the attempt count, then returns 5xx so Stripe retries; a `failed` row is immediately re-claimable. `attempts` and `last_error` are the retry forensics — a poison event shows up as a climbing attempt count rather than silence.
- Metadata-resolved handlers (`checkout.session.completed`, `payment_intent.succeeded`, `payment_intent.payment_failed`) verify that the chapter/invoice ids in the event metadata are UUIDs before touching the database. Other integrations can share a Stripe account, and a foreign event's arbitrary metadata would otherwise reach uuid-typed columns and fail the request — which Stripe would retry for days. Foreign metadata is acknowledged and logged instead.
- **`checkout.session.completed` specifically** — not the payment_intent handlers — whose `chapter_id` is a well-formed UUID that no chapter row carries is **acked, not retried**, and reported at `error` with a Sentry event tagged `billing_event: checkout_unknown_chapter`. It is terminal by construction: `createCheckoutSession` 404s unless the chapter already exists, so the row always predates the session, and there is no delete path in the product. The reachable cause is cross-environment delivery — see [`ENV_REFERENCE.md` § Core App Secrets](../../docs/internal/environment/ENV_REFERENCE.md#core-app-secrets) for the shared test-mode account — where retrying a foreign event for days would be the wrong answer. Reporting carries a **15-minute** cooldown keyed on the chapter, so routine cross-environment traffic cannot bury a real occurrence; it is in-memory, so per-instance and reset by deploys. **If chapter deletion ever ships** (`data-retention.md` § Inactive Chapter Cleanup reserves it), this stops being terminal and the decision needs re-taking.
- `payment_intent.succeeded` is **not** covered by that rule: it performs no chapter-existence check, forwarding to `FinancialInvoiceService.applyStripePaymentSuccess`, which on a missing ledger row logs at `warn` ("reconcile manually") and raises no Sentry event. A captured member payment against an unknown chapter therefore has **no alert** — only a log line.
- A **subscription-resolved** event (`customer.subscription.*`, `invoice.paid`) is matched to its chapter by `subscription_id` first and by **`stripe_customer_id` second** (#1738). The fallback exists because `subscription_id` is written by `checkout.session.completed` and Stripe guarantees no ordering between that event and the subscription events of the same checkout — while `stripe_customer_id` is written by `POST /v1/billing/checkout` _before_ the session exists, so it is populated in exactly the ordering that leaves `subscription_id` empty. An event that overtakes its own checkout therefore resolves, **claims `subscription_id`** on the chapter at once, and applies its transition; the checkout that then arrives is either applied (same-second) or dropped as stale by the ordering rule below, and in the stale case — and when a concurrent CAS lost after both handlers passed the in-memory check — it reloads the chapter and still records the `activation-checkout-completed` milestone when its subscription is the one the chapter now references. Checkout writes `subscription_id` and `stripe_customer_id` only when the session carries them: a present JSON `null` would CLEAR, and `claimSubscriptionId` does not stamp the mark. Because the overtaking event may be the checkout's own first `invoice.paid`, that handler sends `activate_if: past_due|incomplete` so the RPC activates those statuses against the row at UPDATE time — a paid invoice for the chapter's subscription means the subscription is live, and leaving activation to a checkout that will be dropped as stale would park the chapter `incomplete` under a paid subscription. A concurrent `canceled` is not overwritten, because the predicate is the live row, not the handler's snapshot. The fallback is refused **while the chapter's stored subscription is live** (`active` / `past_due` — the same statuses checkout refuses to reopen): a live chapter pointing at a _different_ subscription is the **superseded reference** — `subscription_id` is overwritten when a canceled chapter resubscribes, and the app then instructs the operator to cancel the old subscription in Stripe, which emits `customer.subscription.deleted` for the old id — and resolving that through the customer would cancel the live subscription. A chapter whose stored subscription is _not_ live (`canceled`, or an `incomplete` leftover) is the resubscribe race, one row later: the new subscription's event overwrites the stale reference and applies. What still falls through is acked at `warn` with no alert, and is one of two expected things: that superseded reference on a live chapter, or a subscription whose customer this database has never seen (cross-environment delivery on the shared test-mode account). Neither is a lost transition. The customer-fallback **claim** of `subscription_id` is itself a compare-and-set: it writes only while the stored id is still the one the handler read (null, or a non-live leftover) and the chapter is not live, so two events racing the same empty row cannot both associate it. A lost claim reloads by the incoming id and continues only when that id owns the chapter; otherwise the event is acked as superseded. Status-transition writes go through `apply_subscription_webhook`, a compare-and-set on `last_stripe_webhook_at`: the stale-event predicate and the column patch are one `UPDATE`, and a lost race returns empty so the loser does not notify. Same-second events still apply (`<=`), matching FRA-242. Event-id idempotency (`claim_stripe_webhook_event`) stays a separate claim and is not folded into this RPC.
- Timestamp-aware: an older webhook event must not overwrite a newer subscription status. The chapter row carries a `last_stripe_webhook_at` high-water mark — the `event.created` of the most recently applied webhook. Every subscription webhook (`checkout.session.completed`, `customer.subscription.updated`/`deleted`, `invoice.paid`) ignores any event older than the mark (in-memory fast path) and applies through `apply_subscription_webhook`, which stamps the mark in the same `UPDATE` that writes status — including a renewal `invoice.paid` that sends only `activate_if`, so a later out-of-order dunning event that predates the payment can't downgrade the chapter. Concurrent deliveries that both passed the in-memory check still cannot both write: the loser updates zero rows. `invoice.paid`'s `activate_if` lifts `past_due`/`incomplete` only, so a patch computed against a stale dunning snapshot cannot un-cancel. A non-null `past_due_since` in the patch is ignored when the row is already `past_due`, so two concurrent into-past_due writers cannot reset the grace clock. The handler always sends `past_due_since` on a `past_due` apply so a snapshot that still thought it was repeating cannot skip restarting the clock after a concurrent cancel cleared it. On a `customer.subscription.updated`/`deleted` event the president is notified only when the RPC returned a row **and** that row's status actually changed in the UPDATE (`previous_subscription_status` ≠ applied status) — not when the handler's pre-CAS snapshot differed from the mapped status. Two concurrent `past_due` events that both read `active` therefore produce one president notify. Sequential repeated `past_due` still does not. Lost CAS still does not.

### Duplicate checkout: how the dedup holds (#929)

Two independent mechanisms, because either alone leaves a hole.

**1. A live subscription refuses checkout.** `BillingService.createCheckoutSession` rejects `active` and `past_due` with a 400 pointing at the Customer Portal, which updates the existing subscription in place and cannot double-subscribe. `past_due` is the case that matters: the subscription is live and in dunning, so a second checkout would bill the chapter twice, indefinitely, while Stripe kept dunning the first.

`canceled` is deliberately **not** refused. A canceled subscription is terminal at Stripe — `mapStripeStatus` folds both `canceled` and `incomplete_expired` into it — and the Portal cannot resume one; it only reactivates a subscription still scheduled to cancel at period end, which Stripe still reports as `active`. Refusing `canceled` would leave the chapter with no way back into the product. Nothing live remains to orphan, and mechanism 2 keeps the returning chapter on one customer.

**2. Every session is opened against the chapter's own customer.** `CreateCheckoutParams` carries `customerId` and no email: `BillingService` resolves the customer (creating and persisting one only if the chapter has none) before calling the adapter, and `StripeBillingService` passes `customer`. Stripe mints a fresh Customer for any `customer_email` it is handed, so the old email path made a repeat checkout structurally unrecognisable as the same chapter. Removing the email field entirely — rather than preferring the id when present — is what makes that unrepresentable instead of merely guarded.

If that stored id is **unknown on the configured Stripe account** (`resource_missing` on `customer` — typically a leftover from a different Stripe account after a key mismatch), checkout clears `stripe_customer_id`, mints a replacement, and retries session create **once**. A missing Price is a different Stripe `param` and stays a 503. `active` / `past_due` still refuse before Stripe is called.

This also repairs a case that was never a duplicate at all: on a **first** checkout the customer was persisted and then dropped, so it was orphaned immediately, and permanently if the treasurer abandoned checkout — leaving `POST /v1/billing/portal` opening a portal for a customer that owned no subscription.

**Reconciliation signal.** `handleCheckoutCompleted` still stores the incoming subscription (it is the one now billing the chapter; dropping it would hide a live subscription from the app), but logs at `error` with both ids when it replaces a different stored `subscription_id`, or when the session's customer differs from the stored one. The reference is therefore never replaced _silently_.

**The refusal carries a `message` and no `code`.** It was written while `AllExceptionsFilter` dropped every `code` (#1020); giving these two refusals codes is weighed in #2995. The two refusal strings are stable and distinct so a client can map them; `apps/web/components/billing/plan-panel.tsx` routes on `subscription_status` directly rather than on the response.

**Client routing.** `past_due` → Portal. `canceled` → checkout. The web plan panel enforces this as an affordance; both are now real server boundaries as well.

## Billing Adapter Pattern

Application logic talks to an `IBillingProvider` interface, never directly to the Stripe SDK. This allows future provider changes (e.g. LemonSqueezy) without touching business logic.

## Price / account consistency at boot

`validateEnv` only requires a non-empty `STRIPE_PRICE_ID`. A Price id from another Stripe account therefore used to boot, then 503 at checkout (FRAPP-API-4). `StripePriceConsistencyService` retrieves that id with `STRIPE_SECRET_KEY` on `onModuleInit` and again from `GET /health/ready`. `resource_missing` or an inactive Price refuses boot and 503s ready (`message` includes `billing: …`) so a staging/prod deploy cannot stay healthy. `/health` liveness never calls Stripe — it is Render's `healthCheckPath` and must stay 2xx through a Stripe blip. Transient Stripe errors (network, 5xx) warn and do not refuse boot.

Placeholder secrets (`sk_test_dummy`, `sk_test_ci_not_real`, `sk_test_placeholder_cloud_sandbox`, `placeholder_value`, and other documented non-live fixtures) skip the retrieve — the same places this repo already skipped real Stripe. A real-looking `sk_test_` / `sk_live_` is validated even in development. Mocked billing unit tests cannot catch a cross-account Infisical mismatch; this runtime check is the gate. The account/price pairing itself: [`ENV_REFERENCE.md` § Core App Secrets](../../docs/internal/environment/ENV_REFERENCE.md#core-app-secrets).

## Member Invoices (Dues)

- Admins with `billing:manage` create invoices for individual members (e.g. semester dues).
- **Field bounds** (rejected with 400 at the edge, so a client form can pre-validate against them): `amount` is in cents and must be **1 – 99,999,999** — the upper bound is Stripe's own per-charge maximum for USD ($999,999.99), above which the PaymentIntent could never be created, so accepting the invoice would only defer the failure to payment time. `title` is capped at 255 characters and `description` at 2,000.
- Invoice statuses: DRAFT (not yet sent), OPEN (sent, awaiting payment), PAID, VOID.
- Payments tracked via Stripe PaymentIntents. Webhook confirms payment and moves invoice to PAID.
- Overdue invoices: an invoice counts as overdue once it is OPEN past its `due_date` **plus the chapter's dues grace period** (the `wf_dues_grace` workflow, enabled with a 7-day threshold by default — see the runtime-enforcement rules in [`settings/customization.md`](settings/customization.md)); a notification is sent to the member and the invoice is flagged as overdue in the admin dashboard.
- Invoice reminders are sent by a daily scheduled sweep: **1 day before `due_date`** while the invoice is still OPEN (matching the task reminder lead time in [`tasks.md`](tasks.md)), and again once it crosses `due_date` plus the dues grace. Each threshold notifies at most once per invoice — delivery is recorded in `scheduled_notification_dispatches`, so re-running a sweep, or running it on several API instances, cannot duplicate a reminder. An invoice that went overdue more than 7 days ago is not retro-notified. While dues is [beta-off](../product/modules.md#beta-off-modules) the sweep sends nothing.
- Financial transactions log payments with Stripe charge IDs for reconciliation. The `type` column also permits `REFUND` and `ADJUSTMENT`, but the only path that writes one today is the `apply_invoice_payment` RPC, which hardcodes `'PAYMENT'`; the repository's `create` is the sole other insert, and no production path calls it — only its own spec does, which is where the `REFUND` kind appears at all.

### Member payment flow

- A member initiates payment with `POST /v1/invoices/:id/payment-intent` — **owner-only** (the invoice's `user_id` must be the caller) and only for an `OPEN` invoice. The endpoint creates a Stripe PaymentIntent (`amount` in cents, `usd`, metadata `invoice_id`/`chapter_id`/`user_id`) and returns `{ client_secret, payment_intent_id }` for client-side confirmation.
- The stored intent is **reused** when it is still confirmable (`requires_payment_method`, `requires_confirmation`, `requires_action`, `processing`); a `succeeded` intent returns 409 (payment already completed, confirmation pending); a `canceled` intent — or one the provider no longer knows (e.g. after a key/account migration) — is replaced by a fresh one.
- Minting is idempotent per stored-intent generation: concurrent first attempts collapse into one provider-side intent, so a double-tap cannot produce two separately chargeable intents for one invoice.
- The invoice's OPEN state is re-checked **after** the provider round-trip, on both the new-intent and reuse paths, and the intent id is stamped only while it still holds; if the invoice settled or was voided in that window the request fails (409 when already paid) rather than handing out a live client secret for a non-payable invoice.
- A second request arriving while the first is still in flight at the provider gets 409 ("payment attempt already in progress"), not a 503 — the idempotency key collapses them into one intent by design.
- The route is **subscription-exempt**: dues collection must stay reachable while the chapter's own subscription is `past_due`/`canceled` — collecting dues is exactly how a chapter recovers.
- **Invoice list visibility:** `GET /v1/invoices` returns the _whole chapter's_ invoices to a `billing:view` holder; a member without that permission sees only their own rows. Payment ownership is enforced by the API (the 403 below), so a client rendering the chapter-wide list must not offer a pay affordance on an invoice whose `user_id` is not the viewer's — the client gate only avoids offering an action that cannot work; the 403 is the enforcement.
- **Failure responses** for the payment-intent endpoint, for clients mapping errors: **400** — the invoice is no longer OPEN; **403** — the caller is not the invoice's owner; **404** — no such invoice in the caller's chapter; **409** — the two cases above (payment already completed / attempt already in flight), distinguished by the server's own message; **503** — the payment provider is unavailable, or a guard could not finish verifying the caller ([`multi-tenancy.md`](multi-tenancy.md), #3143), so client copy for it names no one service.
- Only the `payment_intent.succeeded` webhook moves an invoice to PAID on the Stripe path; the pay endpoint never does.
- A `payment_intent.payment_failed` webhook notifies the invoice owner (`category: 'billing'`, NORMAL) with Stripe's decline reason when present. Invoice status stays OPEN — the pay endpoint already reuses a confirmable intent — and officers are not notified: a card decline is the payer's business. Missing or non-OPEN invoices are acknowledged without a notification.
- **A successful client-side confirmation means the money moved, not that the invoice settled.** Clients must re-read the invoice until the server reports PAID, and until then surface "payment received, confirmation pending" — never a locally-declared PAID the webhook has not written.

### Payment webhook idempotency

- `payment_intent.succeeded` and `payment_intent.payment_failed` resolve the invoice from the intent's **metadata** (written only by our server, delivered inside a signature-verified event). Events without invoice metadata (e.g. subscription checkouts), or whose metadata ids are not UUIDs (another integration sharing the Stripe account), are acknowledged and ignored — never surfaced as a 5xx, which would make Stripe retry the same event for days. The failed-intent path never calls `apply_invoice_payment`.
- Payment is applied by the `apply_invoice_payment` RPC: a compare-and-set (`status = 'OPEN'` → `PAID`, stamping `paid_at` and the succeeded intent's id) plus the `PAYMENT` transaction insert (with the Stripe charge id) in **one database transaction**. **Both** PAID writers go through it — the webhook (intent + charge ids) and the admin manual transition (nulls; any stored intent id is preserved) — so whichever side loses the race gets zero rows and writes no ledger entry. This is invoice-level idempotency, independent of the chapter-level `last_stripe_webhook_at` mark (which orders subscription state only). A manual transition that loses the race returns 400 rather than silently double-recording the payment.
- Unique partial indexes on `financial_invoices.stripe_payment_intent_id` and `financial_transactions.stripe_charge_id` (PAYMENT rows) are the durable idempotency floor beneath the CAS.
- Moving an invoice to either terminal state — **VOID or a manual PAID** — cancels its outstanding PaymentIntent, so a payment sheet the member already opened can no longer capture money (voiding would leave an unrecorded charge; a cash-marked PAID would double-charge). Cancellation is best-effort: a provider failure is logged and does not block the transition, and a refused cancel (e.g. the intent is already `processing`) is logged as a reconciliation signal rather than swallowed.
- Any `payment_intent.succeeded` that cannot be applied and whose charge has no ledger row — a VOID invoice, or a second intent on an already-PAID one — is logged as a **reconciliation warning** (money captured, nothing recorded; resolve by refund or reissue). A miss is treated as a benign redelivery **only** when its charge id is already in the ledger. An event carrying no charge id cannot be matched (a manual PAID writes a null-charge row and preserves the stored intent id, so a genuine redelivery is indistinguishable from a cash entry that raced a card capture) and is warned as ambiguous rather than assumed benign — pinning a Stripe API version that sends `latest_charge` removes the ambiguity.

### Ledger provenance invariant

- A `PAYMENT` transaction with a **non-null** `stripe_charge_id` was written by the webhook path and is Stripe-reconciled. A `PAYMENT` transaction with a **null** `stripe_charge_id` is a manual/offline record (admin `billing:manage` marked the invoice PAID — e.g. cash dues). The API surface cannot forge charge ids: invoice DTOs do not expose Stripe fields and validation rejects unknown properties.

## AI Usage Pricing

AI features ([`ai.md`](ai.md), meeting summarization in [`meetings.md`](meetings.md)) are gated behind the paid tier with an **allowance + at-cost overage** model. Two design goals: members never see a meter at point-of-use, and the chapter treasurer never gets a surprise bill.

### Monthly allowance

- The paid tier includes a monthly AI allowance, sized so that ~90% of chapters never overage. **The number is still `TBD`, and the blocker is now usage, not plumbing.** The metering ledger exists since 2026-11-12 (`ai_usage_events`, #714, below), and the AI gateway writes a row for every provider call (#4306). No feature calls the gateway yet and AI is off everywhere (`AI_ENABLED`), so there is still no usage to analyse.
- **Do not set a launch number by estimate.** An allowance is a dollar promise against provider costs that no chapter has run up yet (the providers were chosen on 2026-11-11, [ADR-28](../architecture/adr/adr-28.md); the usage is still unmeasured); a guess here converts directly into either margin loss or a treasurer's surprise bill, which is the exact failure this model exists to prevent. The allowance is also **not on the critical path for billing** — it is a future line item with no Stripe object, so `STRIPE_PRICE_ID` and the flat subscription ship without it.
- **What has to exist first, in order:** (1) the AI features and their chosen provider/model, (2) the metering row (built, below), and (3) roughly a quarter of real multi-chapter usage. The allowance is then read off the 90th percentile of observed monthly cost, not chosen. Until (3), the chapter cap below stands in for it.
- Allowance covers LLM tokens (Q&A, summarization) and transcription minutes, normalized to a dollar equivalent of upstream provider cost.
- Allowance resets on the chapter's monthly billing anniversary. **Built today on the calendar month in UTC instead** (#714, 2026-11-12): `chapters` stores no billing period yet ([#3281](https://github.com/pdcarlson/Frapp/issues/3281)), and dues and billing are off for the beta. When #3281 lands, the chapter's period replaces the calendar month in `reserve_ai_spend` and `AiSpendLedgerService.chapterUsage`.
- Unused allowance does **not** roll over.

### Caps

Built 2026-11-12 (#714). Every call is held against three caps **before** it is made ([ADR-28](../architecture/adr/adr-28.md) decision 1). The gateway works out the call's worst case (its estimated input plus its whole output ceiling, at the [model catalog](../../apps/api/src/domain/constants/ai-model-catalog.ts)'s prices) and `reserve_ai_spend` holds that amount in one transaction, under a lock per chapter and per provider, so two calls at once can't both take the last of a cap. A call that would cross a cap is not made: the gateway answers `unavailable: spend_cap`, naming the cap.

| --- | --- | --- | --- | --- |
| Chapter | calendar month, UTC | $25 | `AI_CHAPTER_MONTHLY_CAP_USD` | one chapter's AI until the month turns ("monthly cap reached — contact treasurer") |
| Member | day, UTC, in one chapter | $2 | `AI_MEMBER_DAILY_CAP_USD` | one member, or a runaway script, from spending the chapter's month |
| Platform, per provider | calendar month, UTC, every chapter | Anthropic $150, Google $50, AssemblyAI $25 | `AI_ANTHROPIC_MONTHLY_CAP_USD`, `AI_GOOGLE_MONTHLY_CAP_USD`, `AI_ASSEMBLYAI_MONTHLY_CAP_USD` | Frapp from overspending a provider account |

- The defaults are guards for the beta, not prices (`apps/api/src/config/ai-spend-config.ts`). The chapter's is the research's 90th-percentile month on Sonnet (#714, 2026-10-08); the platform's leave room under the provider credits ADR-28 plans on, after the evals' share. Each is overridable per environment; a malformed value fails boot rather than falling back.
- The chapter cap is the allowance plus the overage cap. With the overage cap at $0 (the default below), it is the allowance alone, and no chapter can run up a bill. A cap the treasurer sets per chapter (#1310) replaces the default for that chapter: it is an argument to `reserve_ai_spend`, not a new table.
- Scripted calls (local runs, tests) are held against the chapter and member caps at catalog prices, and against no platform cap, since they cost nothing.
- A hold that lands exactly on a cap is granted. A member's cap is per chapter.
- Indexing the chapter's sources for Ask (#720) is the chapter's upkeep, not a member's request, so it is held against the chapter's and the platform's caps only and recorded with no member (`chapterUpkeep` on the call, #4504). A large backfill can't use up the president's own day, whom indexing acts for. Embedding a member's question at Ask time is their own call and counts against their day as usual.
- Holds count at their full amount until settled. After the call, `settle_ai_spend` replaces the hold with the call's real cost, before the gateway returns, which frees what the call did not use.
- A hold nobody settled (the process died mid-call) expires after an hour and keeps counting at its full amount, because the call may have run and been billed. A sweep tick that expires any reports a warning to Sentry.
- Sentry hears when a provider's month reaches 50% and 75% of its platform cap (warning) and 90% (error), once per line per month from each API process, and when a call is refused at the platform cap (error). Only error-level production issues email Paul ([`alert-routing.md`](../../docs/ops/alert-routing.md)), so 90% and the refusal reach his inbox, the first time each happens or when its issue regresses; 50% and 75% are for looking up in Sentry.

### Abandoned and unanswered calls

Decided 2026-11-12 (#714): **a call that failed without the provider saying what it used is charged its whole hold, marked as an estimate** (`cost_estimated`), unless the failure proves the provider turned it away at the door.

- Charged the hold: a stream the member stopped reading before its end (the gateway records `error` / `aborted` with no counts, because counts arrive only with the stream's end), a time-out, a dropped connection, an overload and an unknown error, each with no counts. Any of them can come after the provider had already written, and billed, part of an answer, and the usage record can't tell a stream that had produced text from one that had not.
- Why the hold and not zero: zero lets a client spend without limit by closing every stream early, and the caps exist to make that impossible. The hold is the most the call could have cost, so the caps are never under-counted. The price is that a call that failed before any work also uses a cap's room for its hold.
- Charged what the provider reported, which is nothing: `rate_limited`, `auth`, `invalid_request` and `unsupported`, which the provider answers before doing any work. A failure that reported counts is charged those counts.
- One known gap: the Anthropic SDK retries a time-out or a dropped connection itself (twice, by default), so one hold can cover up to three attempts. Reconciliation against the provider's bill ([#3284](https://github.com/pdcarlson/Frapp/issues/3284)) is where that shows.
- The usage query reports estimated cost on its own (`estimated_cost_micro_usd`), so reconciliation against the provider's bill ([#3284](https://github.com/pdcarlson/Frapp/issues/3284)) can replace it, and an overage invoice can leave it out if Paul prefers.

### At-cost overage

**The caps are built; the overage charge is not.** The bullets below state the intended model, not a shipped surface.

- Usage past the monthly allowance bills the chapter at the actual upstream provider cost — zero markup.
- The treasurer sees a real-time usage dashboard per chapter: allowance used / remaining / projected overage if current pace continues ([#1310](https://github.com/pdcarlson/Frapp/issues/1310); its data is `AiSpendLedgerService.chapterUsage`).
- A configurable hard cap (default: $0 overage allowed, configurable by the treasurer) prevents runaway costs. When the cap is reached, AI features return a "monthly cap reached — contact treasurer" error rather than continuing to bill.
- Alerts fire at 75%, 90%, and 100% of allowance + at 75%, 90%, 100% of any configured overage cap (to the treasurer, with #1310; Paul's platform alerts are above).

**How overage will reach Stripe** (recorded 2026-11-12 in #714, pending Paul; nothing is built, and no Stripe object exists):

1. **Now: no Stripe mechanism.** The overage cap defaults to $0, so overage never accrues, and dues and billing are off for the beta. Nothing is charged for AI.
2. **When a treasurer first allows overage:** a Stripe Billing Meter (`sum`) with a metered Price on a second subscription item. A daily job reads each chapter's overage for its period from the ledger (spend over the allowance, never the whole usage) and sends Stripe only the change since its last report, with an idempotent identifier per chapter, period and report. Stripe never decides whether a call may go ahead: the caps above do.
3. **Rejected:** an invoice item per chapter per period (it must land while the renewal invoice is a draft, about an hour, or the overage slides to the next month), and Stripe credit grants for the allowance (Stripe would hold the allowance as a balance, which the invariant below forbids).
4. This changes "one Price, one line item" for chapters with overage on, and existing subscriptions get the metered item added once. Who absorbs Stripe's fee on overage (about 3.6%, or gross it up) is Paul's call when this is built.

### Member-facing UX

Members **never see a meter or "this costs X" prompt at the point of using an AI feature.** The allowance + overage cost is a chapter-level concern surfaced only to the treasurer (`billing:view`/`billing:manage`). Member-facing prompts about cost would create perverse incentives against using the feature that the chapter is already paying for. A member who reaches their daily cap is told the feature is not available right now, never what it cost.

### Implementation invariants

- Every AI provider call is metered: one `ai_usage_events` row per call ([`spec/architecture/README.md`](../architecture/README.md)), with the chapter, the acting member, the task (the "feature"), provider, model, prompt version, input, output and cached input tokens, and the cost in micro-USD (millionths of a dollar: a cached read costs less than a cent, so cents would round it to zero). The row is settled before the response is returned to the client, failed and refused calls included. A transcription is one row too (#712, built 2026-11-12): no tokens, `audio_seconds` as the provider measured them, and the cost at the catalog's price per hour of audio. Its hold is the longest recording the feature takes (two hours for a meeting) at that price, whatever length the upload states, and the provider is asked to stop transcribing at that length (AssemblyAI's `audio_end_at`; whether it then bills the part it transcribed or the whole file is unverified until the transcription bake-off, and the ledger records the length the provider reports either way): the stated length and size are the uploader's word, so a file that understates them must not be able to pass the caps and then settle for more (changed in #4504, 2026-11-12; the hold was the stated length before). A try that dies while the provider works is counted twice against the caps, once as its unsettled hold and once when the next try resumes the same provider job and settles: the safe side of the error.
- Allowance and overage are computed from the meter, not from a separate balance. There is no mutable "balance" column.
- The hard cap is enforced server-side; clients never compute "should this request go through" locally.
- The ledger has no text column ([`ai.md`](ai.md) § Stored AI text).

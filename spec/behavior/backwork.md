# Backwork (Academic Library)

## Rich Metadata

Every uploaded resource carries the following metadata fields. **All fields except the file and its hash are optional** to allow graceful handling of incomplete information.

| Field                 | Type               | Description                                                                         |
| --------------------- | ------------------ | ----------------------------------------------------------------------------------- |
| **Department**        | Free text          | e.g. "CS", "MATH", "ECON". Auto-vivified per chapter.                               |
| **Course number**     | Free text          | e.g. "101", "3320". Combined with department for display (e.g. "CS 101").           |
| **Course name**       | Free text (optional) | Not on the file: what the chapter calls the course, kept once per course. See § Course Names. |
| **Professor name**    | Free text          | Auto-vivified per chapter.                                                          |
| **Year**              | Integer            | e.g. 2025.                                                                          |
| **Semester**          | Enum               | Spring, Summer, Fall, Winter.                                                       |
| **Assignment type**   | Enum               | Exam, Midterm, Final Exam, Quiz, Homework, Lab, Project, Study Guide, Notes, Other. |
| **Assignment number** | Integer (optional) | For "Homework 3", "Lab 2", "Exam 1", etc.                                           |
| **Document variant**  | Enum               | Student Copy, Blank Copy (professor-released), Answer Key.                          |
| **Tags**              | Text array         | Free-form for additional categorization.                                            |
| **File hash**         | String             | SHA-256 of the uploaded file. Used for duplicate detection.                         |

## Auto-Vivification

When a member provides a department or professor name that does not exist in the chapter's dictionary, the system automatically creates the corresponding record.

- Lookup is scoped to the chapter. "CS" in Chapter A is independent of "CS" in Chapter B.
- Auto-vivification is **not** transactional: `confirmUpload` resolves-or-creates the department, then the professor, then inserts the resource as three independent writes. A failed resource insert leaves the new department and professor rows behind, which the next upload reuses rather than duplicating.
- Department records store the short code (e.g. "CS") and an optional full name (e.g. "Computer Science") that admins can fill in later.
- **A department code matches trimmed and in any case** (#3918, 2026-11-12): an upload typed "math" files under the chapter's existing "MATH", which keeps its stored spelling. A new department's code is stored trimmed and upper-cased ("math" creates "MATH"), the way course codes are written. One rule, `findDepartmentByCode` in `@repo/validation` (`backwork-courses.ts`), serves the API's resolve-or-create and the web upload sheet's course-name lookup, so the sheet names the course the upload will file under. Departments that already exist as case variants of each other (filed before this rule) are merged into one by a one-time migration (#4491, `20261112153000`); until it runs, an upload picks among them by the exact trimmed spelling first, then the first code in code-unit order.
- Filling in that name (`PATCH /v1/backwork/departments/:id`, requires `backwork:admin`) is scoped to the caller's active chapter: a department ID belonging to another chapter matches no row and returns **404 Not Found** instead of being renamed.

## Course Names

A file stores its department and course number, never the course's name. What members call a course ("Calculus I", "Calc 1", "Orgo") lives in a per-chapter dictionary, `backwork_courses` (#3848): one row per chapter, department and course number, with an optional display `name` (up to 255 characters) and up to 20 `nicknames` (60 characters each). A file belongs to a course by its department and its course number compared trimmed and case-insensitively (the table's generated `course_key`; upload stores the number trimmed too); a course row exists only once someone names it.

- **Who may edit (2026-11-09, the social-trust default of #3709).** Anyone with `backwork:upload` may name a course that has no name yet and add nicknames. Changing a name that is set, removing a nickname, and deleting a course's entry need `backwork:admin`; the API answers **403** otherwise. The rule is one function, `courseEditRefusal` in `apps/api/src/domain/utils/backwork-course-rules.ts`, which the service applies against the stored row.
- **API.** `GET /v1/backwork/courses` lists the chapter's courses (the library's any-of read gate). `PUT /v1/backwork/courses` takes `{ department_id, course_number, name?, add_nicknames?, remove_nicknames? }` and creates the entry on first write. An omitted `name` keeps the stored one. Each write is one SQL statement (`backwork_course_write`), an insert-or-update applied to the row as it is when the statement runs: nicknames are the stored ones minus `remove_nicknames` (case-insensitive), then `add_nicknames`, de-duplicated case-insensitively (so replacing "orgo" with "Orgo" is remove "orgo", add "Orgo"). A name is replaced only for an admin; for anyone else, and for an upload, it only fills an empty name. So no edit drops a nickname saved by someone else since, and two first writes don't collide. A list past 20 nicknames, a name over 255 characters or a nickname over 60 (counted in code points, as Postgres counts them) is a **400**. `DELETE /v1/backwork/courses/:id` removes the entry (`backwork:admin`); its files keep their course number. A department or course id from another chapter is **404**. Both writes are paid-ops: a lapsed chapter can't send them.
- **On upload.** `POST /v1/backwork` takes an optional `course_name`, saved only when the course has no name yet, so an upload never renames a course. Naming is best effort, after the file is filed: if it fails the API logs it and the upload still succeeds, and the course can be named from the row's menu. The web upload sheet shows a named course under Course number ("MATH 1010 · **Calculus I**"), and for a course no file has yet offers "Course name (optional)". Bulk upload (`/backwork/upload`) does not ask.
- **Web.** The row's course line reads "MATH 1010 · Calculus I", or the department's name when the course has none; when a search matched only a nickname, the nickname follows in parentheses ("CHEM 2250 · Organic Chemistry I (Orgo)"). The Course filter labels a course the same way. A row's menu offers every uploader and `backwork:admin` holder one course entry beside "Name the {CODE} department…": "Name the {CODE NUMBER} course…" while the course has no name; once it has one, "Rename the … course…" for an admin and "Add a nickname for {CODE NUMBER}…" for anyone else. None is offered until the course list has loaded. All three open one dialog that takes the name and nicknames ("Also called"; Enter adds one) and sends only what changed. It shows a non-admin a set name read-only, and offers a remove button only on nicknames added in that dialog, unless the viewer is an admin.
- **Taxonomy cleanup keeps names.** A department merge folds the source's courses into the target first (§ Taxonomy Admin). Deleting a department deletes its course entries (`on delete cascade`); the API only deletes a department no file uses.

## Taxonomy Admin

Uploads accumulate junk departments and professors — typos, duplicate spellings, one-off OCR misreads — that manual admin cleanup fixes. `backwork:admin` gets rename, delete, and merge for both, mirroring each other: `PATCH /v1/backwork/{departments,professors}/:id` (rename), `DELETE /v1/backwork/{departments,professors}/:id`, `POST /v1/backwork/{departments,professors}/:id/merge`.

- **Delete blocks rather than orphaning.** `department_id`/`professor_id` on `backwork_resources` are `on delete set null`, so a bare delete would silently blank the field on every resource still tagged with it. The API instead counts referencing resources first and returns **400** naming the count when it's nonzero — merge is the guided path to clear that.
- **Merge reassigns then deletes.** `POST .../:id/merge` with `{ target_id }` moves every resource tagged with the source to the target, then deletes the source, returning `{ reassigned: <count> }`. Not wrapped in a database transaction: the only failure window is a resource created between the reassign and the delete, which the same `on delete set null` FK degrades to a blank field on that one row rather than an orphaned reference — self-healing on the next re-tag, unlike the ledger-touching operations elsewhere in this codebase that do need an atomic RPC. The course fold has a window of the same kind: each source course is folded into the target, then deleted, in two statements, so a nickname or name saved to a source course between its fold and its delete is lost with the source entry. Merges are rare officer cleanup, so this is accepted rather than guarded.
- **A department merge carries its courses.** Before the files move, each of the source's course entries is folded into the target department's entry for the same course number (trimmed, case-insensitive), then deleted. The fold is one `backwork_course_write`, fill-only, so it creates the target's entry or merges into one that exists, including one created a moment earlier: the target's name stays (the source's when the target has none), and the source's nicknames and name join the target's nicknames, de-duplicated, without one that repeats the resulting name. A fold never fails on the table's limits: it drops a nickname over 60 characters (a long losing name) and keeps the first 20, the target's own first. The fold runs before the source entry is deleted, so a failed fold leaves it in place.
- Both operations 404 when the source or target id belongs to another chapter, and 400 when merging an entry into itself.
- Rename, delete, and merge all require `backwork:admin`. Browsing needs either `backwork:upload` or `backwork:admin` (the controller's class-level any-of gate); uploading needs `backwork:upload` specifically, so `backwork:admin` alone does not grant it.
- **Web, where officers find these (2026-11-05 redesign).** No taxonomy control sits on the page by default. A row's menu (right-click, long-press, the keyboard menu key, or the row's ⋯ button, one shared list in `apps/web/components/shared/row-menu.tsx`) offers `backwork:admin` holders "Rename {professor}…", "Merge {professor} into…", "Name the {CODE} department…" (a department's `PATCH` sets its full name; the code stays as it was filed (trimmed and upper-cased since #3918)) and "Merge {CODE} into…". Delete is not on the row, since that row still references the entry and the API would refuse it. The full list with delete lives in the clean-up drawer (`backwork-taxonomy-drawer.tsx`), opened from the toolbar's More menu ("Clean up professors and departments"). Both paths share the merge dialog (`backwork-taxonomy-actions.tsx`); the drawer keeps its own inline rename, and the row menu opens that file's rename dialog.

## Duplicate Prevention

Unique constraint on (chapter_id, file_hash). If the exact same file (by hash) has already been uploaded to the chapter, the API returns 409 Conflict with a reference to the existing resource.

A flattened file is hashed as uploaded, after flattening (§ PDF Redaction). The PDF assembly adds nothing that varies (no timestamps or IDs), but the page images come from the browser's renderer and JPEG encoder, which differ between browsers and devices. So the same PDF flattened twice on the same browser is usually caught; the same PDF flattened on two different browsers, or boxed differently, is a different file and is not, and a flattened copy never matches an earlier as-is upload of the same original. Bulk upload also refuses a file already in the same batch, by the original's hash: of two copies loaded together, the later one in the batch is refused and the earlier one stays, however long each takes to hash (#3665). A copy retried after a failed read joins behind the copy already in the batch, so the retried one is refused.

## Storage

Files are stored in Supabase Storage under `chapters/{chapter_id}/backwork/{resource_id}/{filename}`. The upload-URL step generates this chapter-scoped path server-side. On confirm, the API rejects any `storage_path` that does not start with `chapters/{chapter_id}/backwork/` (the caller's active chapter) so a client cannot register metadata that points outside its own chapter folder. Signed download URLs are only issued for resources already scoped to the active chapter.

As with chapter documents, the signed URL comes back on `GET /v1/backwork/{id}` under the key **`downloadUrl`**, and clients read it through `selectDownloadUrl` in `@repo/hooks` rather than naming a spelling at the call site — see [`chapter-docs.md`](./chapter-docs.md) § Storage for why (#1040). The link is a forced download (#3867, 2026-11-12): it is signed with a `download` parameter naming the stored filename (the storage key's last segment, encoded once: storage-js's own `download` option encodes it twice, which saved `Q&A (draft).pdf` as `Q%26A %28draft%29.pdf`), so storage serves it with `Content-Disposition: attachment` and following it saves the file under that name. Nothing on `/backwork` previews a file, so unlike Documents there is no inline link, and the app never opens a member's file as a page. That is how the app behaves, not a boundary: as with Documents' `forcedDownloadUrl` (`chapter-docs.md` § Two links), the `download` parameter sits outside the signature, so anyone holding the link can drop it. What gates content is the bucket's allowed types ([`chat/README.md`](./chat/README.md) § File and image uploads). The web Download opens the link in a new tab, which saves the file; a server from before this change, or a storage error, then shows in that tab rather than replacing the library. The zip's batch links are forced downloads too (§ Browsing and Search).

Backwork's size ceiling is its own: **100 MB per file** (`MAX_BACKWORK_UPLOAD_BYTES`), above the 25 MB every other member upload keeps, because scanned exams run large (#3487). It equals the hosted projects' global storage limit, which caps every bucket, so raising it also means raising that limit in the Supabase dashboard. The `backwork` bucket's `file_size_limit` mirrors it.

The file-type allowlist is the `document` kind in `@repo/validation`, shared with chapter documents and chat — including `image/gif` and legacy Office (`.doc` / `.xls` / `.ppt`). Membership and the rationale: [`content-validation.md`](../../docs/security/content-validation.md) § Validations Required.

## Browsing and Search

- Resources are browsable by department, course, professor, semester/year, assignment type, and tags.
- Full-text search across title, tags, course (number, department, and the course's name and nicknames, § Course Names), and professor name. The library's own `GET /v1/backwork?search=` still matches `title` and `course_number` only, as a case-insensitive substring (#1357); no client sends it. Global search covers every field listed here and forgives typos since #585 (2026-11-06, [`search.md` § Global search](search.md#global-search)).
- Results are always scoped to the user's active chapter.
- **Web library search runs on the client (2026-11-05).** `GET /v1/backwork` returns the library in one unpaginated response, so `/backwork` searches and filters it in memory (`apps/web/components/backwork/backwork-library.ts`) instead of calling `?search=`. It matches title, department code and name, course number (also joined, "cogs2120"), the course's name and nicknames, professor, term, type, number, copy, tags and "redacted"; it forgives one typo in a word of 4 to 6 letters and two in a longer one, never fuzzes a word with a digit in it, matches a one- or two-digit number or a Roman numeral from I to X only as a whole word (so "i" never finds "II" or "Integral" in a title), and expands shorthand (hw, mt, ans, sg, proj). In a course's name and nicknames, Roman numerals I to X and the numbers 1 to 10 are the same word, so "Calc 1", "Calc I", "Calculus 1" and "Calculus I" all find "Calculus I"; elsewhere ("v" in a title) they stay as typed. Against a course's name and nicknames, any query word with a digit in it, and a Roman numeral from I to X, counts only beside a non-numeric query word that matched the same name or nickname, so a bare "1" or "i", or "hw 1", never reaches Calculus I's files through the course name, and "200" alone never reaches a course nicknamed "Stat 200" while "stat 200" does. A number from 1 to 10 in either spelling ("1", "i") counts there only exactly ("I" never finds "II" or "Integral"). Against the rest of a row, such as its title, a Roman numeral from I to X follows the rule for a one- or two-digit number: a whole word only, so "Calc I" does not find a Calculus II file titled "Calculus II Midterm", just as "Calc 1" does not. A file whose course's name or one nickname matches more of the query ranks above one that only shares words with it, so "Calc 1" puts Calculus I's files above "Calculus II — Midterm 1". **Known gap:** that response is capped at PostgREST's `max_rows` (1000), newest first, with no `.range()`; a longer library is truncated, and the page then says it is showing only the newest 1,000 files (pagination: [#3525](https://github.com/pdcarlson/Frapp/issues/3525)). Filters for course, professor, term, type and copy offer only values some file has; the Course filter also offers a whole department ("COGS · all courses") when it has more than one course, and a term is a semester with its year (search "fall" finds every Fall). A redacted file is marked with a lock icon beside its copy type, not a text badge: Paul's 2026-11-05 call ("with the copy, keep the icons consistent"), with "Redacted" as its accessible name and hover title. Without a query the list is newest term first (Fall, Summer, Spring, Winter inside a year), undated files last. The server search above, and global search, are unchanged by this.
- **Zip download, capped (2026-11-06).** Paul's rule: a member can't pull the whole archive at once. `/backwork` offers a zip only once a search or filter has narrowed the list, and only for 50 files or fewer (`MAX_BACKWORK_ZIP_FILES`; above that the button is disabled and its label says to narrow further). `GET /v1/backwork/download-urls?ids=` signs up to 50 files in one call (ids lowercased and de-duplicated): chapter-scoped, forced downloads, in the order asked, leaving out any id it can't sign. It is a GET, so a lapsed chapter can still zip, as it can still download one file. The browser fetches the files one at a time and zips them (`apps/web/lib/backwork-zip.ts`), so the API never carries the bytes, and it stops before the total passes 250 MB (`MAX_BACKWORK_ZIP_BYTES`), checking each file's `Content-Length` before reading it and counting its body as it streams in. The size cap lives only in the browser, because nothing records a file's size at upload. Files it couldn't fetch are left out, and the page says how many.
- **Every row deletes for `backwork:admin`** through `DELETE /v1/backwork/:id`, behind a confirm. Rename, merge and delete on a row are paid-ops writes and are disabled on a lapsed chapter, like upload.
- **Dashboard `/backwork`:** `useBackworkResources` is `enabled: !!chapterId`. With no chapter selected the page shows "No chapter selected", never a loading state. The resource list gates its loading skeleton on `isLoading` or `fetchStatus === "paused"` (offline, no data), and also waits for the department and professor reads its rows join on. It does not wait on course names: rows show the department's name until they arrive, and a failed course-name read leaves them that way rather than failing the page; a disabled TanStack Query v5 stays `isPending` with `fetchStatus: "idle"` and must not be treated as in-flight or as an empty library.

## PDF Redaction

Redaction ships with web bulk upload (`/backwork/upload`, #3499). PDFs only. PDFs dropped or picked on `/backwork`'s drop strip go to bulk upload too. The single-file upload sheet on `/backwork` uploads as-is, so it never uploads a Student Copy (#3509). It requires a document variant, since a blank one could be an unmarked Student Copy; a Student Copy PDF is sent on to bulk upload, where its form opens with the fields typed in the sheet, title and Student Copy mark included, however much of a batch is ahead of it, and a Student Copy in any other format is refused, since only a PDF can be flattened in the browser. No path on web uploads a Student Copy's original bytes.

1. The person drops PDFs, or folders of PDFs, and works through them one at a time. The next two documents load in the background while they work on the current one, and finished ones flatten and upload behind them, so moving to the next document never waits. The batch lasts as long as the browser tab: leaving the page doesn't cancel what was already submitted, it keeps uploading, and coming back to Bulk upload shows the same list, so a failure (shown as a toast while the page is closed) can be retried from its row without redacting again. While anything in the batch isn't uploaded yet, the browser asks before the tab closes or reloads. A batch belongs to one account and one chapter. A chapter switch, a sign-out, or another account signing in ends it: nothing more from it is uploaded or shown, so it is never filed in the wrong chapter or under, or seen by, the next account. The chapter switcher and Sign out ask first when that would drop documents not uploaded yet.
2. The editor renders each page. The person drags opaque black boxes over a name, student ID, or handwriting, and can move, resize, delete, undo, or copy one page's boxes to every page.
3. A person reviews every document before it uploads. Nothing is submitted without them.
4. A **Student Copy is always flattened**, and so is any document with a box on it. Flattening happens on the person's device: each page is rendered to an image with the boxes burned in, and a new PDF is built from those images, with no metadata and no form fields. Only the flattened file is uploaded; the original's bytes never leave the browser, and the stored file is named after the confirmed title rather than the original filename (which for a Student Copy is often the student's name). The title starts as the filename, so the person checks it. A Blank Copy or Answer Key with no boxes uploads as the original file.
5. Text outside the boxes is kept as an invisible, searchable layer over the image. Any text item that touches a box (within 2 points) is dropped whole, so a box that clips part of a name drops the whole name. Text the rendered page doesn't show is dropped too: before the boxes go on, the middle of each text item's area is checked for ink, so text under an earlier tool's black bar or a covering image, white-on-white text, and text off the page never reach the layer. Rotated text and text on rotated pages is filtered the same way but not redrawn.
6. The storage record is flagged `is_redacted: true` whenever the file was flattened.

**Rationale:** Overlaying black boxes on an existing PDF does not prevent text selection of the underlying content. Rendering to images ensures true redaction; the rebuilt text layer comes only from text the boxes don't touch, so search keeps working without carrying a redacted word.

**Limits:** The ink check looks for contrast, so hidden text over a busy background (a photo, a pattern) still reads as visible and is kept; it is only as hidden as the page made it. Very faint visible text (a light watermark) can read as invisible and drop out of search. A scanned page has no text to keep, so it stays image-only.

## AI Metadata Extraction (Phase: v3+)

On upload, an optional AI step parses the PDF and pre-fills metadata fields (department, course number, professor, assignment type, etc.). The user reviews and corrects before confirming. The data model and upload flow must not block this future capability (all metadata fields are optional; the upload endpoint accepts partial metadata).

## Chat Integration

Backwork has no slash command and no rich renderer, by design: nothing it produces belongs in a message ([`integrations.md` § Integration Pattern](integrations.md#integration-pattern), #2468).

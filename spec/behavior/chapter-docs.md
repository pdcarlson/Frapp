# Chapter Documents

A "Chapter Files" storage area for organizational documents (bylaws, constitutions, meeting agendas, etc.), separate from Backwork which is strictly for academic materials.

## Permissions

- `chapter_docs:upload` — Upload new documents.
- `chapter_docs:manage` — Delete documents, create/rename/delete folders, add, rename and delete document types, and connect or disconnect the chapter's Google Drive folder.
- Reads are gated on `members:view`, which every seeded role holds (the President holds it from its starting tier, beside the `*` wildcard) — so every member can open Documents, but the controller's class-level gate is a permission rather than an all-members bypass. Upload and management need their own `chapter_docs:*` permissions.
- Inside Documents, a folder or file can be limited to some tiers, roles and groups ([§ Who can see](#who-can-see)). `chapter_docs:manage` is not a way past that: a manager sees only what a list lets them see.

## Who can see

*(Added 2026-11-16, #3642 piece 1; Paul asked to set folder and file permissions by role, and approved all five recommended picks on the [proposal page](https://claude.ai/artifact/Sjvz2GH9DUMzecPhXpJF15): "Plan looks good. Recommendations are solid.")* A folder, and a single file, can be limited to some of the chapter. It is the same answer a chat channel gives ([chat](chat/README.md), `packages/validation/src/channel-access-lists.ts`), so officers learn it once. Comparable apps: Google Drive's and SharePoint's folder sharing, where a file inherits its folder's access until it is given its own, and Slack's private channels.

- **The answer.** `who_can_see` on a folder is `null` (everyone who can open Documents) or a list of `tier:<id>`, `role:<id>` and `group:<id>` entries (Paul's pick 1), checked by `chat_access_list_valid` in the database and, on a write, as a channel's list is: every entry is this chapter's, a class-year group is refused, and the list is not empty. A member on any entry passes.
- **A file follows its folder.** A file's `null` reads "Same as folder". A file given its own list narrows its folder's: a member must pass both, so a file is never open to more people than its folder. A file at the top level (no folder) has only its own list.
- **Who always sees.** A member holding `*` (the President) passes every list, so a chapter can't lock itself out. A file's uploader always sees that file, except a Google Drive copy: copies are filed as uploaded by whoever connected the folder, which gives them no way past a list. Holding `chapter_docs:manage` passes nothing (Paul's pick 2): a chair who runs the library doesn't see the exec board's files.
- **Rank** (Paul's pick 3, as invites keep to rank, #4546). A list someone sets always keeps their own tier and every tier above it, added on save, so a chair can hide a file from members but never from the exec board, or from themselves. `*` adds none. A member with no role in any tier can't set a list (403).
- **Who sets it** (Paul's pick 5). A folder's list is set with the folder, by `chapter_docs:manage` (`POST /v1/documents/folders`, `PATCH /v1/documents/folders/{id}`, field `who_can_see`). A file's list is set at upload (`POST /v1/documents` and each item of `POST /v1/documents/batch`, field `who_can_see`) or later by its uploader (not a Drive copy's) or a `chapter_docs:manage` holder who sees it (`PUT /v1/documents/{id}/access`, `{ who_can_see }`, `null` going back to Same as folder). `GET /v1/documents/access-options`, behind `chapter_docs:upload` or `chapter_docs:manage`, returns the entries a list may hold (`options`, as a channel's picker gets them) and the tier entries the caller's lists always keep (`always`, `null` for a caller outside every tier).
- **On the web** (#5216). The folder dialog (Edit in the rail, and New folder) holds the folder's name and its Who can see: Everyone or Chosen roles, with the channel picker's chips and Add menu. The upload panel has the same field under Folder, reading Same as folder (Everyone when no folder is picked) until the uploader chooses roles. A file's own Who can see control sits with Star, Pin and Download, for its uploader (not on a Drive copy) and whoever manages documents, and opens the same field with Same as folder. The tiers a list always keeps join the list at its first edit, as the API adds them on save, and are drawn as chips without a remove; a stored list is shown as it is until then, and a dialog opened only to look saves nothing. Save waits while Chosen roles holds nothing, since the API refuses an empty list. A member outside every tier is offered no list: the upload panel and New folder leave the field out, a file's dialog says why, and on a folder or file that already has a list they can only switch it back to Everyone or Same as folder, which the API takes from them. A folder or file not everyone can see carries a lock beside its name, the way Slack marks a private channel; a file in a limited folder carries it too, and so does one in a folder the member can't see (their own upload, which they always see; `limitedDocumentCheck` in `packages/hooks/src/document-library.ts`, which the phone shares). The folder import panel's per-file field comes next (#5216).
- **On the phone** (#5216). The upload sheet has a Who can see row under Folder, reading Same as folder (Everyone with no folder); it opens the channel picker's step (`channel-access-sheet.tsx`), where the uploader's own tier and those above are ticked and fixed, and Upload waits while Chosen roles holds nothing. A member outside every tier gets no row. A lock marks a limited folder's chip and a file row, tile or Pinned and Starred card not everyone can see, and the row says so to a screen reader. Setting a folder's list or an existing file's is web-only for now.
- **Hidden means absent.** A folder or file a member can't see is left out of every read: the list, folders, previews, stars and pins (a starred or pinned item they can't open isn't shown), and Ask, whose answers quote only files the member could open (`ChapterDocumentCorpusSource.readableBy`). Posting an Ask answer to a channel lists, for the asker to acknowledge first, every file it drew on that some reader of the channel can't open (`AskPostService`). Reading, previewing, pinning, starring, deleting or changing one by id answers 404, as one never there does, so a hidden file's existence doesn't leak. Filing an upload into an existing folder the uploader can't see is a 403. Every one of these asks `apps/api/src/domain/utils/document-access.ts`, so no two paths decide differently. A read with no list on any folder or file in play reads no viewer at all. Both tables stay API-only (RLS on, no client policies).
- **Moving.** A file on Same as folder takes its new folder's answer when it moves; a file with its own list keeps it (Paul's pick 4). Renaming a folder re-files its documents and renames it in one transaction (`rename_document_folder`), and deleting one moves its documents to the top level and deletes it in one (`delete_document_folder`), so a restricted folder's files are never left under a name no folder claims. Deleting a restricted folder gives its list to the files on Same as folder, and a file with its own list keeps only the entries both lists held, so none is opened by the move (one may narrow: someone who passed both lists through different entries no longer does, and its uploader or a manager can widen it again).
- **Deleted entries.** Deleting a role, tier or group takes its entry off every folder and file list (`document_access_strip_entry`), as it does for channels. A list left empty admits only `*` and, for a file, its uploader.
- **Google Drive copies** ([#5220](https://github.com/frapplive/Frapp/issues/5220), Paul's approved rules). Drive's own sharing isn't mirrored: a copy is seen by whoever its Documents folder admits, and a synced folder's list is set like any folder's. Sync keeps lists as § Google Drive folder describes: it starts a folder's list once, never writes one after, and never moves a copy where more people may see it. A single copy can be given its own list, which sync never changes.
- **Event attachments.** An event can still hold a file some of its readers can't see; opening it reads the file itself, which answers 404 to them. Showing such an attachment as "a file you can't open" rather than by its title, and refusing to attach a file you can't see, is [#5217](https://github.com/frapplive/Frapp/issues/5217).

## Structure

- Documents are organized into an optional flat folder structure (one level deep). A document belongs to zero or one folder.
- Folders have a name and a sort order. Documents without a folder are filed at the root; the dashboard rail surfaces them under a **No folder** view, alongside an **All files** view that ignores the folder filter entirely.
- A folder's name is unique within a chapter. Two chapters may each have a folder of the same name.
- A folder exists independently of its contents: it can be created empty, and it survives having its last document removed.

## Folder management

Officers with `chapter_docs:manage` create, rename, reorder, and delete folders; every member can list them.

- **Create** — names are trimmed, and a name that is empty (or only whitespace) is rejected. A new folder is appended to the end of the display order unless an explicit position is given.
- **Rename** — documents record their folder by *name*, so renaming a folder re-files every document in it. Renaming onto a name already used in the chapter is rejected.
- **Reorder** — folders are listed by sort order, then by name as a tiebreak.
- **Delete** — see Edge Cases below.
- **Uploading into an unknown folder still works.** Naming a folder that does not exist on upload registers it, which is how folders came into being before they were manageable. It is not an error.

## Document types

*(Added 2026-11-13, #3642 piece 4; Shawn's go on the folder-import plan, 2026-11-12.)* Each chapter has its own ordered list of document types (`chapter_document_types`), so the library stops filling with near-duplicates ("Bylaws", "bylaws", "By-laws") and filters and suggestions have a fixed list to aim at. Comparable apps: Linear's labels and Notion's select options, edited from the menu that applies them.

- **One type per key.** Two names are the same type when they match ignoring case and everything but letters and digits (`documentTypeKey`; the database's `document_type_key`), so "Bylaws", "by-laws" and " BYLAWS " are one type. The unique index, uploads, rename and delete all match this way; nothing matches by pattern, so `*` or `%` in a name is just a character.
- **Starting list.** Every chapter starts with Bylaws, Minutes, Agenda, Budget, Policy, Form and Other (#3642's list, plus Agenda, which the upload form already offered), from a trigger on new chapters. A chapter that had documents before the list existed keeps every type they used, once per key, in the spelling most of them used, with inner whitespace collapsed, and a default it already spells its own way ("By-Laws") isn't added again.
- **Names** are trimmed, inner whitespace collapsed, 1 to 100 characters, and must hold a letter or digit. A chapter adds at most 50 (`DOCUMENT_TYPES_MAX`): past that, adding a type or uploading with a new one is refused. A chapter that brought more from before the list keeps them, and officers delete down from there.
- **A document stores its type's name**, as it stores its folder's. Uploading with a type stores the list's spelling of it, so "bylaws" files as "Bylaws". A name the chapter doesn't have yet is added to the list, as uploading into an unknown folder registers the folder; with a full list it is refused, before any folder the upload names is registered. The web panel hides New type once the list is full.
- **Managing.** Officers with `chapter_docs:manage` add, rename, reorder and delete types; every member can list them (`GET /v1/documents/types`). Renaming a type renames it on every document of that type, and deleting one leaves its documents with no type and nothing else changed. Each is one transaction: a rename onto a name another type took in the meantime changes nothing and answers 409.
- **Web.** The upload panel's Type chips are the chapter's list, in its order, with "New type" for a name not on it (uploading adds it). A file's name only ever suggests one of the chapter's own types, so a type the chapter deleted is never guessed back, and a picked chip that leaves the list (renamed or deleted meanwhile) is let go rather than re-added. Officers who can manage see "Edit types" at the end of the row: rename, add and delete inline. Until the list loads, or when it can't be read, the chips fall back to the starting types plus the types the documents in hand use.

## Folder import

*(Added 2026-11-13, #2242; step 4 of the plan in #3642, Shawn's go 2026-11-12.)* On web, officers with `chapter_docs:upload` choose **Import a folder** beside Upload document: they drop a folder (or pick one, or pick many files), check what Frapp suggests for each file, and import them in one go. Comparable apps: Google Drive's and Dropbox's folder upload, which keep a dropped folder's structure; the grouped review follows M-Files and Box, which have an officer check suggestions in sets rather than one value at a time.

- **Nothing uploads before Import.** The device walks the folder and checks every file first. Operating-system files (`.DS_Store`, `._*`, `Thumbs.db`, `desktop.ini`) are dropped unseen. Files of a type Documents doesn't take, or over the upload cap, are **left out** and listed with the reason. Two files with the same bytes in one import (SHA-256, hashed on the device two files at a time) and a file with the same name and size as a document already in Documents are **possible copies**: listed apart and left out unless the officer ticks them. Documents keep no content hash, so the library match is a likeness, never a refusal.
- **Suggestions, with no AI.** Each file's title comes from its name and its type from its name or a folder on its path, from the chapter's type list ([§ Document types](#document-types)), as the single upload panel does. Its folder is the deepest folder on its path the chapter already has (ignoring case and punctuation), else the deepest whose name holds every word of a folder on the path ("Minutes" files into "Meeting Minutes"), else the first folder under the one dropped, as a new folder, else, for a file directly in the dropped folder, that folder; a loose file goes where the chapter files its type, or nowhere. Folders are one level deep, so a tree becomes these suggestions rather than nested folders, and the folders below the one a file lands in go into its title instead ("Rush/2025/flyer.pdf" becomes "Flyer (2025)" in Rush), so files the tree kept apart still read apart.
- **Review in groups.** Files are grouped by the folder they'll land in; a group's folder changes for the whole group at once, and each file's title, type and whether it's imported change on its row. A new folder is labelled as new.
- **Import** mints the kept files' upload links ahead, 25 a call (`POST /v1/documents/upload-urls`), uploads them through the signed uploads six at a time, and files each document once its file is stored, gathering the filings for a few seconds into calls of up to 25 (`POST /v1/documents/batch`). Both routes allow 10 calls a minute, so an import tops out near 250 files a minute; a rate-limited call waits and retries on its own. A document exists only once its file does. A file that couldn't be read leaves the import at Import. A file the server refuses is listed with the reason and a Retry; a retry keeps the file's link and stored copy, so it re-files the same object, which the API answers with the document if it was already filed, and never files a file twice. Nothing files once the chapter or the signed-in account has changed since the import began. The library refreshes once when the import finishes. The import outlives the page: leaving Documents keeps it uploading and its progress is there on return, and while anything is uploading the browser asks before the tab closes; closing it anyway keeps what was filed and loses the rest.
- **Visibility.** An imported file is filed on Same as folder, so it takes the answer of the folder it lands in ([§ Who can see](#who-can-see)); a new folder an import makes is open to everyone. Drafts that survive a closed tab, undoing an import, and AI suggestions are later steps of #3642 that wait on Paul's decisions.

## Pinned and starred

*(Added 2026-11-11, #3934; Shawn's idea, and his picks of where they show, what can be marked and who pins.)* Documents lists folders and files in three tiers: what officers **pinned** for the whole chapter, then what this member **starred** for themselves, then everything else. Both folders and single files can be pinned and starred. Comparable apps: Google Drive's Starred, Slack's pinned and starred sidebar sections, Microsoft Teams' pinned channels.

- **Pin** is chapter-wide. A member holding `chapter_docs:manage`, the permission that already creates, renames and reorders folders, pins or unpins a folder or a file, and every member sees it at the top. A pin is `pinned_at` on the folder or document row; pinning something already pinned keeps its first pin time.
- **Star** is personal. Every member who can read the library stars or unstars any folder or file for themselves; nobody else, officers included, can see who starred what. A star is a row in `chapter_document_stars`, which has RLS on and no policies, so only the API reads it, filtering on the member.
- **Order inside a tier.** The tiers sit on top of the existing orders rather than replacing them: pinned folders keep the officers' folder order among themselves (§ Folder management's Reorder still applies), and pinned or starred files keep the list's chosen sort (§ Search). Something both pinned and starred shows once, under Pinned, still wearing the member's star.
- **Search and filters** narrow every tier the same way: the tiers order whatever the folder, search and filters leave.
- **Stars that can't be read** say so in a line above the list ("Couldn't load your stars.", with Try again on web and pull-to-refresh on the phone), rather than every star vanishing silently. Pins arrive with the folders and files themselves.
- **Deleting** a folder or a file removes its pin and every member's star on it. Renaming a folder keeps both, since a star points at the folder's record, not its name. Deleting an account removes that member's stars (`anonymize_user`).
- **Who sees a pinned folder.** A pinned or starred folder or file a member cannot open is not shown to that member ([§ Who can see](#who-can-see)), and pinning one they can't see is a 404, managers included.
- **Routes.** `GET /v1/documents/stars` returns the caller's own `{ folder_ids, document_ids }`. `PUT` stars and `DELETE` unstars `/v1/documents/folders/{id}/star` and `/v1/documents/{id}/star`, each idempotent and answering 204. `PUT` pins and `DELETE` unpins `/v1/documents/folders/{id}/pin` and `/v1/documents/{id}/pin`, behind `chapter_docs:manage`, each idempotent and answering the updated row. Starring something outside the caller's chapter is a 404.

**Web `/documents`** *(2026-11-11, #3934)*:

- **Cards on top of All files.** On All files with no search or filter, a **Pinned** group of cards, then a **Starred** group, sits above the list, folders and files together (as Google Drive's top row and mobile s12's PINNED draw them). A folder card names how many files it holds and opens the folder; a file card opens the viewer. Pinned cards take the chapter accent on their glyph, starred ones the neutral glyph. The list below keeps its own order, each row's Star and Pin lit where they apply. Inside a folder, or with a search or filter, there are no cards: pinned files, then starred files, lead the list instead, each tier in the chosen sort.
- **The folder rail is grouped** under **Pinned**, **Starred** and **Other folders**, below All files and No folder; with nothing pinned or starred it is one plain list, as before. A star sits beside each folder, drawn on hover or focus (always under a finger) and kept drawn while starred.
- **Each file row** carries a Star for everyone and, for `chapter_docs:manage`, a Pin, both lit while on. In the Grid layout (#4175, [web README § Resources](../ui/web-dashboard/README.md#resources-documents-and-backwork)) each tile carries the row's Star, Pin, Download and Delete. A member who can't pin sees a pinned file's pin as a mark only.
- **Pinning a folder is an Edit control.** Edit adds Pin to each folder's move, rename and delete controls, and shows the chapter's arrangement, pinned then the rest, without the officer's own stars. Move up and Move down move a folder within its tier and save the arrangement pinned-first, so the stored order and what everyone sees agree.
- A star failing, or a pin, says so in a toast; a star moves on the tap and settles on what the server holds.
- The cards, their file counts and the tiers come from the library the page has loaded, so they share § Search's cap: past 1,000 documents, a pinned or starred file older than the newest 1,000 is missing from them, and a folder card counts only the files loaded.

**Mobile s12** *(2026-11-11, #3934)*:

- **PINNED and STARRED cards** sit above the list on All with no search or filter, folders and files together, as the design board draws PINNED (`canvas-screens.dc.html` s12) and as web's cards do. A tap opens the folder or the file; a starred card wears a star. Inside a folder chip, or with a search or filter, there are no cards and the tiers lead the list.
- **Folder chips** run pinned, then starred, then the rest, a pinned chip wearing a pin and a starred one a star (both, on a folder pinned and starred). A file being deleted takes no press, as card, row or grid tile.
- **A long press** on a folder chip, a card, a file row or its grid tile (or its screen-reader action, named for what the viewer may do) opens one action menu, headed by the folder's or file's name with no title or Cancel: **Star** or **Unstar** for everyone, **Pin for the chapter** or **Unpin for the chapter** for `chapter_docs:manage`, and on a file **Delete document** for `chapter_docs:manage`. The phone doesn't reorder folders, so pinning there leaves the officers' order as it is.
- A file in the Grid layout (#4175, [`screens.md`](../ui/mobile/screens.md) s12) is the same file row drawn as a tile: the same tap, long press, screen-reader action and marks.
- A file row wears its pin and star at its end, and a screen reader hears "Pinned for the chapter" and "Starred" as the row's value. A star or a pin that fails says so in a line above the list.

## Search

Document listing accepts an optional case-insensitive substring match on the title, combinable with the folder filter. Search is scoped to the caller's active chapter. `%` and `_` in a query are matched literally, not as wildcards.

**Both apps search, filters and sort on the client** *(2026-11-09, #3852; Shawn's idea. Mobile too since #3938, Shawn's ask)*. Web `/documents` and mobile's Documents screen (s12) each read the chapter's whole library once (`GET /v1/documents` with no `search` or `folder`) and do the rest in memory, as `/backwork` does, through one shared implementation (`packages/hooks/src/document-library.ts`, reusing `packages/hooks/src/fuzzy-match.ts`, and the `useDocumentLibrary` hook beside it for the roster, the semester window and the clock). Where mobile differs, the bullet says so:

- **Search** matches the title, description, uploader's name, folder and document type: every query word must match a word, a word's start, or a near miss (backwork's typo tolerance), or the query must appear anywhere in that text, as the server's title search matched ("laws" finds "bylaws", and `%` or `_` is just a character). A query word also matches the file's format group by its words (`FILE_KIND_WORDS` in `document-library.ts`: "pdf"; "word", "doc", "docx"; "slides", "slide", "powerpoint", "presentation", "deck"; "spreadsheet", "excel", "sheet", "sheets", "csv"; "image", "photo", "picture"), exactly or by their start from three letters, never as a near miss, so "work" doesn't find Word files. It works offline over the library already loaded.
- **File type** *(2026-11-09, #3938; Shawn's addition, after Google Drive's Type filter)* groups each file as PDF, Word (doc, docx, odt, rtf), Slides (ppt, pptx, key, odp), Spreadsheet (xls, xlsx, csv, ods), Image, or Other, read from its declared `content_type`, or, when that is null (rows filed before 2026-08-31), the generic `application/octet-stream`, or a type it doesn't recognise, from the extension of the stored filename in `storage_path`. One classifier decides this for the filter, search and the web viewer (`classifyFile` in `@repo/hooks/document-library`, #3959); its extension table is the upload allowlist's plus the legacy formats below. The groups name more formats than the upload allowlist (`packages/validation/src/upload-allowlists.ts`) accepts today: odt, rtf, key, odp and ods can't be uploaded, and are grouped only so a file that arrives some other way still lands in the right place; an allowed `txt` file is Other. It offers only the groups some file is in, in that order, plus a picked group whose last file has gone, so the list says nothing matches.
- **Uploaded by** offers only people the chapter roster can name who have uploaded something. A departed member's files keep showing, just without a name, and a filter on someone who has since left the roster is dropped. Someone still on the roster stays picked after their last file goes, and the list says nothing matches.
- **Pinned and Starred** *(2026-11-11, #4290; Shawn's ask, after Google Drive's Starred filter)* are two on/off filters: Pinned keeps files an officer pinned for the chapter, Starred keeps files this member starred. With both on, a file that is either shows (once), so the pair means "what's been marked". They combine with the search, the folder and every other filter, for example starred PDFs from the last 30 days, and the tiers (§ Pinned and starred) still lead what's left. They match files only: a pinned or starred folder is found through the rail or the folder chips, and a file inside one is not matched unless it is marked itself. A file the member stars, unstars, pins or unpins while one of them is on stays listed until the Pinned or Starred filter changes, as Gmail's Starred view keeps a row you just unstarred, so it doesn't vanish under the cursor (or, on web, close the viewer open on it; the open file is kept the same way). Starred reads the stars the app holds: before the first read lands it matches nothing, and when a later read fails it keeps matching the stars last read, while the "Couldn't load your stars" line shows. On web they are two toggle chips beside File type; on mobile, two toggles in the Sort & filter panel, each counted as one filter on its chip.
- **Date added** offers any time; this semester, which is the chapter's own window from [semester-rollover.md](semester-rollover.md) (after the end of the most recently created archive's `end_date` day, or everything before a first rollover), the archive picked and the day read as the API's points window picks and reads them (`findLatestByChapter`, `resolveWindowSince('semester')`), and offered only once the archives have loaded; the last 30 days; or, on web only, a custom from and to range, inclusive and read in the viewer's timezone (mobile waits on a native date picker, which needs a store build). A custom range with no dates set filters nothing. The windows move while the page stays open.
- **Sort** orders by name A to Z (the default, and the order before #3852), newest first, oldest first, or uploader A to Z. The chosen order applies whether or not a search is typed.
- **Rows** read "Uploaded Sep 26 by Ryan Castellano · …" when the roster can name the uploader. Mobile's line stops before the effective date and description, which it searches but has no room to draw.
- **Delete** is offered to `chapter_docs:manage` holders and asks first: a button on each web row, and on mobile the Delete document row of the long-press sheet (the row's long press, or its screen-reader action; the sheet holds Star and Pin too since #3934, § Pinned and starred), which opens a system confirm.
- **Cap.** A response at PostgREST's 1,000-row `max_rows` is treated as truncated, and a status line above the list says it is showing only the newest, whether the list shows rows or a search that matched nothing (not above the error or offline states). Backwork hit this cap (#3525); a chapter's documents are far fewer.

The server's `search` parameter has no client caller since #3938; it stays for API consumers and the contract.

## Metadata

Each document has: a system-generated `id` (UUID, primary key — **not** the `{document_id}` in the storage path below: that is a separate UUID minted by the upload-URL step and returned as `documentId`, so no storage path can be derived from a document's `id`), title, description (optional), folder (optional), storage path, uploaded_by (FK users), and created_at. No academic metadata (no department, professor, assignment type, etc.).

Four additional fields, all optional and populated at confirm-upload time: `content_type` (MIME type, client-declared), `byte_size`, `document_type` (the name of one of the chapter's document types, [§ Document types](#document-types); free text before 2026-11-13), and `effective_date` (the date the document took effect, distinct from `created_at` which is upload time). The web upload panel shows it and starts it on Today, which the officer changes or clears; the phone sheet has no date row and sends the upload day; Drive copies carry none (Paul, 2026-11-16; before then it was never filled unless typed). A file row leaves out "Effective" when it is the upload day, and Ask reads the date at noon UTC so it lands on that day in the chapter's zone. These exist for the AI corpus retrieval design ([`spec/architecture/README.md`](../architecture/README.md) § 13 AI Corpus Architecture — **not** [ADR-13](../architecture/adr/adr-13.md), which is Repository visibility), which needs a currency signal distinct from upload time and provenance metadata beyond a title.

## Storage

Files are stored in Supabase Storage under `chapters/{chapter_id}/documents/{document_id}/{filename}`. The upload-URL step generates this chapter-scoped path server-side. On confirm, the API rejects any `storage_path` that does not start with `chapters/{chapter_id}/documents/` (the caller's active chapter) so a client cannot register metadata that points outside its own chapter folder, and any whose rest is not the `{document_id}/{filename}` shape the mint builds with `safeObjectFilename` (its kept characters, no trailing space), since a `?`, `#`, `%` or trailing-space spelling of a filed path names the same object under another string (#3399). Confirm is idempotent on the stored object: one row per `storage_path` (`chapter_documents_storage_path_key`), so a confirm retried after its response was lost returns the row it already filed, unchanged, to the member who filed it, and refuses anyone else with a 409 (#3399). Both answers come from a read made before the confirm's folder is registered, so neither leaves an empty folder behind; only two confirms racing past that read can, since the loser registers its folder before the index refuses its row. Two rows on one object would break delete, which removes the object. Because a replay changes nothing, a client retrying a confirm resends the title, folder and Who can see list it first sent; how s21 does that is in [`../ui/mobile/screens.md`](../ui/mobile/screens.md) (s21). Signed download URLs are only issued for documents already scoped to the active chapter.

There is no separate download endpoint: `GET /v1/documents/{id}` returns the document *with* a freshly signed URL, on the key **`downloadUrl`**. No case-transforming interceptor exists anywhere in the stack, so a client that reads `download_url` gets `undefined` — which is exactly what both web call sites did until #1040. Clients resolve it through `selectDownloadUrl` (`packages/hooks/src/document-download.ts`), a deliberately pure module — no `"use client"`, no react-query — so mobile's plain-node selectors and any server component can import it. It accepts either spelling so a server-side rename cannot break a client, and is the only place either spelling appears **for a document or backwork download**. Scope that carefully before any cleanup: `download_url` is the correct, live key for **chat attachments** — a different endpoint, which emits it at `chat-attachment.service.ts` and declares it on `ChatMessageAttachmentWithUrl`, the subtype that adds the key — so converging those onto `downloadUrl`, or routing them through this selector, breaks every attachment link and inline image. Nothing typed enforces any of this: none of these endpoints declares an OpenAPI response schema, so the SDK infers the body as `never` and any property access compiles.

### Two links: inline and saved

`GET /v1/documents/{id}` returns two signed links to the file from one signing call, each good for an hour (#3849):

- **`downloadUrl`** serves the file inline, with no `Content-Disposition`, so a browser shows a PDF or image in place. The web viewer (§ Preview) reads the file through it and never loads it as a page, which keeps chat's trust rule that nothing member-uploaded is served inline as a document. On the phone only Ask's document source chips still read it, opening it in the in-app browser, until [#5175](https://github.com/pdcarlson/Frapp/issues/5175). Backwork has no viewer, so its `GET /v1/backwork/{id}` link is a forced download only ([`backwork.md`](./backwork.md) § Storage, #3867).
- **`forcedDownloadUrl`** is the same signed link with a `download` query parameter naming the stored filename (the storage key's last segment, encoded once by `SupabaseStorageService`; storage-js's own `download` option encodes it twice, and until #3867's fix on 2026-11-12 a name like `Q&A (draft).pdf` saved as `Q%26A %28draft%29.pdf`), so storage serves it with `Content-Disposition: attachment` and following it saves the file. The parameter sits outside the signature, so anyone holding `downloadUrl` can turn it into a download; nothing is protected by the difference. Web's Download controls follow it (`selectForcedDownloadUrl`), and fall back to opening `downloadUrl` in a new tab when a server predates it.

**Mobile's Documents screen (s12) never opens either link as a page** (owner's decision 2026-11-16, [#4409](https://github.com/pdcarlson/Frapp/issues/4409), option B). A tap on a document downloads `forcedDownloadUrl` into the phone's cache and presents the system share sheet (iOS's share sheet; Android's chooser of apps that accept the type), where the member saves it to Files or opens it in an app that reads it. Slack, Google Drive, Dropbox and Teams likewise never open a member's upload as a web page on the phone (`shareDocumentFile`, `apps/mobile/lib/more/document-file.ts`). Neither sheet is itself a viewer: reading a document on the phone goes through the app the member picks. The row's spinner runs from the tap until the sheet closes, one sheet shows at a time, and a file that lands after the member has left s12 presents nothing. The saved file's type is the one the library files it under (§ Search's File type: the declared type, or the stored extension's when the declared one is absent or unrecognised). Its extension only ever names a type on the `document` upload list (§ Upload allowlist), because the app receiving the file types it by its extension; a document whose type isn't on the list doesn't open and says so. A server that predates `forcedDownloadUrl` is downloaded from `downloadUrl` instead, which is just as safe, since a download writes the bytes to disk whatever the header says. Until 2026-11-16 s12 opened `downloadUrl` in the in-app browser, the one place a member's file was served inline as a page. The rejected alternative was keeping that, with a dated exception to the trust rule on the grounds that the `document` list admits no HTML or SVG type; the bucket gates the declared type, never the bytes, so s12 now keeps the rule with no exception. Ask's document source chips don't yet ([#5175](https://github.com/pdcarlson/Frapp/issues/5175)).

### Grid preview links

*(Added 2026-11-13, #4647.)* The web Grid's previews ([§ Preview](#preview)) don't call `GET /v1/documents/{id}` per tile. `GET /v1/documents/previews?ids=<id>&ids=<id>…` (or one comma-separated `ids`) signs inline links for up to 100 of the chapter's documents in one storage call, each good for an hour, and returns `[{ id, url }]`; an id outside the caller's chapter, or one storage couldn't sign, is left out, and more than 100 ids, or one that isn't a document id, is a 400. It needs the same `members:view` as the rest of the library. It records **no** `document-viewed` event, because a tile coming into view isn't a member opening a file ([`observability.md`](observability.md)); opening the viewer still records one. The grid asks once per hundred previewable files (`useDocumentPreviews`), so browsing a large library spends one or two reads of the member's per-minute read budget rather than one per tile, and keeps the links for 50 minutes without refetching on focus or after an upload or delete, so a photo isn't downloaded again.

## Preview

*(Added 2026-11-09, #3849; Shawn's idea, his pick of the full-screen option.)* On web `/documents`, clicking a row's name opens the document full screen, in the viewer chat's images open in (`apps/web/components/shared/media-viewer.tsx`, [chat § File and image uploads](chat/README.md)): a dim backdrop over the whole window, icon-only Download and Close in the top-right corner, step arrows at the sides that walk the list as it is shown (folder, search, filters and sort applied, [§ Search](#search)), wrapping at the ends, and Esc, the backdrop or Close to dismiss. Unlike chat's, it draws the document's title and a meta line (type, upload date, folder) top-left, because a document's title is the one its uploader typed. Stepping keeps one dialog open and swaps the file inside it. Closing returns focus to the row of the document it was showing, which may not be the one that opened it, as chat's viewer returns to the image it was showing.

What previews (`previewKind` in `apps/web/components/documents/document-viewer.tsx`) is decided by the type `classifyFile` gives the file, the same classifier the File type filter groups by ([§ Search](#search)): the declared type, or the stored extension's when no useful type was recorded. A declared type the classifier doesn't recognise still previews only as itself, so it gets the card. The viewer's name for the type ("Excel spreadsheet", "Photo", "HEIC photo") comes from there too. *(2026-11-12, #3959: this replaced "when no type was recorded, a stored `.pdf` extension still counts as a PDF; nothing else is guessed from a name", which let a row the filter called an Image open as a bare File. Guessing is safe because neither preview path loads the file as a page.)*

- **PDFs** are drawn page by page with pdf.js in the member's own browser (`apps/web/lib/backwork-bulk/pdf.ts`, the loader Backwork's bulk upload uses), into images in a column that scrolls. The first page is readable while the rest draw; at most 50 pages are drawn, and a longer file says so and offers the download.
- **Images** on chat's viewable list (JPEG, PNG, GIF, WebP, BMP) draw in an `<img>`.
- **Everything else**, Office files, text and CSV included, shows a card naming the type ("Excel spreadsheets can't be previewed yet") with a Download button. Previewing Office files needs a converter or an outside viewer; which one is a privacy decision for the owner, tracked in [#3889](https://github.com/pdcarlson/Frapp/issues/3889).

Neither path loads the member's file as a document, which keeps the trust rule chat states for member uploads: pdf.js parses the bytes and paints a canvas, and an `<img>` decodes or fails. The file is fetched from our own storage only. A load that fails (the link, the bytes, or an image that doesn't decode) says so with Try again, which fetches fresh links first; Download stays in the corner throughout. A file that doesn't preview fetches no links until Download is pressed, and Download reuses the links the viewer already holds while they're fresh.

Mobile has no viewer: s12 hands the file to the system share sheet (§ Two links).

## Google Drive folder

*(Added 2026-11-16, #5157; Paul picked "Connect a chapter folder" over linking single files or a web-only Drive picker.)* A chapter that keeps its files in Google Drive connects one Drive folder, and Documents holds a copy of every file in it, kept matching the folder. Comparable apps: Notion's and Slack's Google Drive connections, and Dropbox shared folders.

- **Connecting.** An officer with `chapter_docs:manage` shares the folder in Google Drive with Frapp's address (a Google service account, one per environment; `GET /v1/google-drive` names it) as a Viewer, then pastes the folder's link in Documents (`PUT /v1/google-drive`), with who should see what it brings in (`who_can_see`, checked as a folder's list is, § Who can see; left out, everyone who can open Documents). The link is checked with Google at once: a link that isn't a Drive folder, a link to a file, or a folder not shared with Frapp is refused with what to do, and nothing is saved. One folder per chapter; connecting another means disconnecting first, and waiting the minute it takes the last folder's copies to leave. A folder feeds one chapter at a time: a folder another chapter has connected is refused.
- **Why a service account.** Frapp reads only what a chapter explicitly shared with it, and no member signs in to Google. Reading a folder through a member's own Google sign-in would need the `drive.readonly` permission, which Google classes as restricted and audits yearly, because the narrower `drive.file` does not reliably reach a picked folder's contents.
- **Copies, not links.** Each file is copied into the documents bucket and filed as an ordinary document (`drive_file_id`, `drive_modified_at` and `drive_url` set), so members who can't open the Drive folder still open, preview, star and search it, on the web and the phone, and Ask reads it. Copies are filed as uploaded by the officer who connected the folder. Google Docs and Slides are copied as PDF and Sheets as Excel (`.xlsx`); other files keep their type when it is on the upload allowlist below and are at most `MAX_UPLOAD_BYTES`. Forms, shortcuts and Google's other types, other file types, larger files and files past the 500th are left out and counted.
- **Folders** *(changed 2026-11-16, #5220; until then top-level files had no folder and subfolders were matched by name)*. The connected folder becomes a Documents folder of its name, holding the files at its top. A subfolder at any level becomes a folder named by its path ("Chapter files / Rush", then "Chapter files / Rush / Flyers"), since Documents folders don't nest; a path too long for a folder name (100 characters) keeps its first folder and as many of its last as fit, with "…" between ("Chapter files / … / 2025 / Flyers"). *(Changed 2026-11-17, #5331, Shawn's report that a real chapter drive came in only two levels deep: until then three levels were read, the folder and two below it, and deeper files were left out without a word.)* Ten levels are read, the folder and nine below it, and at most 300 folders a pass, shallow levels first; each folder read is one Drive list call, so a pass makes at most 300 before copying anything. Folders past either cap aren't read, and the pass counts them (`folders_left_out`), so the Google Drive panel says how many and that their files aren't in Documents, rather than leaving them out silently. A pass that stops at the folder cap is a read in part: it removes no copies or synced folders (below). Each synced folder is tied to its Drive folder (`drive_folder_id`), so a rename in Drive renames the same folder and keeps who can see it; a name another folder already has gets a number ("Rush (2)"). A synced folder's name and existence follow Drive, so renaming or deleting one in Frapp is refused (409, "Rename or delete it in Drive"); its list is set in Frapp like any folder's. A folder that leaves Drive is deleted once a full read shows it gone, and anything else filed in it moves to the top level, keeping who could see it (as deleting a folder does).
- **Who sees the copies.** The connected folder's Documents folder starts with the connection's list, and each new subfolder with its parent's, so a folder made under a limited one is never wider. After that the list is the folder's own, and sync never changes it. When Drive moves a file into a folder more people may see, sync leaves the copy where it is, at its old reach, and marks it (`drive_held_folder_id`, the folder Drive put it in) until a member with `chapter_docs:manage` who sees that folder opens it up (`POST /v1/google-drive/copies/{id}/open-up`). "More people" is judged by entries: a list is no wider only when every entry it holds is in the current one, so a move a person might call safe can still be held, and none that widens is let through. A move Drive undoes lets go of the hold. On the web, the Google Drive panel lists held copies under Held back, each with the folder Drive put it in and an Open it up control that confirms who will see it first; a copy held for a folder the officer can't see isn't listed. The connect panel asks who should see the folder (step 3) for an officer who may set a list, and Edit folder on a synced folder offers who can see it but not its name, with no Delete in the folder rail.
- **Keeping in sync.** Every 15 minutes, or at once after Connect or **Sync now** (`POST /v1/google-drive/sync`), a pass reads the folder: new files are filed, files whose Drive modified time changed are copied again in place (the document keeps its pins and stars), renamed or moved files are renamed and refiled without copying, and copies of files that left the folder are removed. A pass copies at most 20 files and the rest follow at once, so a large first connect takes a few minutes.
- **Drive owns a copy.** Deleting one in Frapp is refused ("Remove it in Google Drive"), since the next pass would bring it back. Renaming one in Frapp lasts until the next pass puts back Drive's name. Refiling one in Frapp lasts until the next pass puts it back in Drive's folder, unless that folder is open to someone the copy's current folder isn't: then the copy stays where it is and is held, as for a move in Drive (below). Synced folders themselves are renamed and deleted only in Drive (the API answers 409).
- **Lost access.** When Google answers that Frapp can no longer see the folder (unshared or deleted), the connection shows that, with the address to share it with again, and the copies stay as they were; sharing it again resumes syncing at the next pass.
- **Disconnecting** (`DELETE /v1/google-drive`) removes every copy and synced folder from Documents (anything else filed in one moves to the top level, keeping who could see it); nothing in Drive changes. It works while the chapter's subscription is locked.
- **Who sees what.** Every member who can read Documents sees where a copy came from on its row. Only `chapter_docs:manage` sees the Google Drive panel: when the folder last synced, its counts (files in Documents, files left out, and folders not read past a cap), Connect, Sync now and Disconnect.

## Upload allowlist

Chapter documents share the `document` kind in `@repo/validation` (`packages/validation/src/upload-allowlists.ts`) with Backwork and chat attachments. That single list is what the API, the web Documents page, mobile's upload sheet (s21), the Backwork page, the chat composer, and the `documents` / `backwork` / `chat` buckets must agree on. The membership of that list, the `MAX_UPLOAD_BYTES` cap, the never-SVG rule, and why `image/gif` and legacy `.doc` / `.xls` / `.ppt` are on it are owned by [`docs/security/content-validation.md`](../../docs/security/content-validation.md) § Validations Required — do not restate them here.

Clients check type and size via `inspectUploadFile` before requesting a signed URL. `POST /v1/documents/upload-url` also accepts an optional `size_bytes`, checked with `isWithinUploadSizeLimit` before the URL is issued; because that field is optional and client-declared, the bucket `file_size_limit` stays the only server-side size gate.

## Edge Cases

- Deleting a folder moves its documents to the root level (no cascading delete of files), in the same transaction that deletes the folder, so a failure part-way leaves the folder and its documents as they were. A restricted folder's list goes with its files ([§ Who can see](#who-can-see)).
- Document titles do not need to be unique. Duplicate file content (same hash) is allowed since organizational documents may be legitimately duplicated (e.g. updated versions).

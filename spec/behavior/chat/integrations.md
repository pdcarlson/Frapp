# Chat Integrations — Slash Commands, Renderers, and System Channel

Chat is the spine; an ops module with a message-shaped action is a **chat integration** (see [README.md](./README.md) → *Chat is the spine*; which modules have none, by design: [`../integrations.md` § Integration Pattern](../integrations.md#integration-pattern)). This file specifies the slash-command catalog, the dispatch path, the rich-message renderer registry, and the `#chapter-audit` system-channel bridge. Push-notification rules for chat live in [../notifications.md](../notifications.md).

## Slash command catalog

Slash commands turn chat into the dispatcher for the ops modules that have a message-shaped action. The catalog is filtered by the chapter's `enabled_modules` so disabling a paid module hides its command from the palette without UI churn, and the composer refuses the same command typed out in full. Commands marked `implemented: true` post a rich message; `implemented: false` commands surface a "coming soon" toast as modules ship. **Server-side authorization is independent of the client gate** — the server re-checks permission for every send; the client gate is UX only, the server is the trust boundary.

Opt1 Opt2 [closes=<mins>]` | yes | `polls` | chapter member; `ChatService.sendMessage` refuses `kind: "poll"` with `403 chapter.module.disabled` while `polls` is off, and so does a card vote ([`../../product/modules.md` § Module disabling behavior](../../product/modules.md#module-disabling-behavior)) | current channel |
| `/announce <message>` | yes | always-on | an entry on `#announcements`' who-can-post list (or `*`) via `canAccessChannel({ operation:'post' })` | `#announcements` |

Parsing rules live in `packages/chat-core/src/integrations/parsers.ts` (`parsePollArgs`, `parseAnnounceArgs`, `parsePointsArgs`, `parseTaskArgs`, `parseEventArgs`, `parseHoursArgs`, `parseRushArgs`) so web and any future heavy-command RPC share one source of truth. Mobile is not a consumer and is not planned as one: slash commands are not a mobile surface. Poll arguments tokenize on whitespace but respect double-quoted spans for the question; unterminated quotes return a specific error rather than silently truncating. Polls require at least two distinct options (case-insensitive dedup) and at most ten; an optional trailing `closes=<minutes>` overrides the 24-hour default. `/points` parses `grant`/`deduct`, an `@member` token (resolved to a user id at dispatch from the chapter directory), a positive whole amount, and the reason after the literal `for`; the reason is capped at `POINTS_REASON_MAX_LENGTH` from `@repo/validation` (the same 500-character bound as `AdjustPointsDto`), not a package-local copy; `grant` maps to a `+amount` `MANUAL` adjustment and `deduct` to a `−amount` `FINE`. `/task` parses a double-quoted title (titles routinely contain spaces), an `@assignee` token (resolved to a user id at dispatch), a required due date, and an optional trailing non-negative whole-number point reward. The due date is read as the task forms read it (`parseDateEntryWithTime` in `@repo/formatting`, leaning ahead, #3928): `11/14`, `Nov 14`, `Friday` or `tomorrow`, the year being the next time the date comes round, or a full `YYYY-MM-DD`. Everything after the `@assignee` must be that date, or the date and then the points; a run that is neither is refused, and opens the form without a due date. `/event` parses a double-quoted name, a `YYYY-MM-DD` date, and a 24-hour `HH:MM-HH:MM` time range (end strictly after start, same day); a trailing `points=<n>` overrides the default point value (10), kept only when the maker holds `events:update` (a member's event is stored worth 0, [`events.md` § Event Creation](../events.md#event-creation), #3709), and any other trailing tokens join as the free-text location. The parser is timezone-pure — the date+time → ISO conversion happens at dispatch in the client's local timezone — and recurrence, role-targeting, and the mandatory flag stay off the one-liner. On web, an `/event` the parser refuses (typed bare, or with details it can't read; typing after `/` goes into the palette's search box, and a pick hands the command whatever followed its word there, `paletteCommandArgs`) does not toast the usage string: it opens the + card's Event form (below), filled in by the lenient `eventFormPrefill` with whatever parts were readable, and that form makes the one-liner's write (`postEvent` in `@repo/chat-core/dispatch`), posting the card in the channel the command came from with the same placeholder and `recorded`-row bookkeeping ([#3773](https://github.com/pdcarlson/Frapp/issues/3773), [#3983](https://github.com/pdcarlson/Frapp/issues/3983)). Its More options opens the Events page's full editor with what was typed carried over, which can set recurrence, role-targeting and the mandatory flag, and posts its card through `trackEventCard`, unless the event keeps anyone out, which it creates without a card and says so. A one-liner the parser accepts still dispatches directly. `/poll` does the same on web ([#3865](https://github.com/pdcarlson/Frapp/issues/3865), #3773 step 2): a `/poll` the parser refuses opens the + card's Poll form (`apps/web/components/chat/poll-form.tsx`), filled in by `pollDraftFromArgs` with the question and any options typed, on the draft model mobile's New poll sheet uses (`@repo/chat-core/poll-draft`), where the form, unlike the one-liner, can also post a poll that doesn't close ([`../polls.md`](../polls.md), #3896), and it posts the same `buildPollMessage` card through the outbox (`postPoll` in `@repo/chat-core/dispatch`), so it works offline. Because `/poll` and `/announce` queue, the composer doesn't refuse them offline as it does the queueless commands. `/hours` parses a `log` action, a duration (`2h` / `2.5h` hours, `90m`/`90min` minutes, or a bare number of hours), and a required description (max 2000, matching `CreateServiceEntryDto`); the date is stamped at dispatch as today's local `YYYY-MM-DD`. Unknown actions (including `review`) return usage. The one-liner cannot attach proof (the + menu's Service hours form can): when `wf_hours_receipt` is enabled the API 400s with its existing receipt message — that is the correct UX, not a bypass of the seed-default-on workflow. `/<vocab>` (`parseRushArgs`) parses `add` (a name: `@token`, a quoted span, or the rest of the line, max 200), `vote` (a candidate UUID or a name resolved at dispatch), and `bid` (a name or UUID). Errors omit a hardcoded `/rush` so a chapter whose term is Intake is not toasted "rush".

## The composer's + menu

Every slash command also has a button and a visual form; typing the command stays the shortcut (Shawn's rule, [#3865](https://github.com/pdcarlson/Frapp/issues/3865), layout A picked 2026-11-09). The web composer's toolbar is **+ · emoji · help**: one **+** replaced the paperclip and the slash-palette button, and typing `/` in the message box (or Cmd/Ctrl+/) still opens the palette. The **+** opens one card (`apps/web/components/chat/composer-plus-card.tsx`, [#3983](https://github.com/pdcarlson/Frapp/issues/3983)) whose first view is a menu: Attach a file, then one row per command that has a form, each showing its shortcut in mono. The rows are Poll (`/poll`), Sign-up sheet (no shortcut, [#3926](https://github.com/pdcarlson/Frapp/issues/3926); [§ Sign-up sheet cards](#sign-up-sheet-cards)), Event (`/event`), Task (`/task`), Service hours (`/hours`) and Points (`/points`). Picking a row turns the card into that form in place, above the +, with no dialog and no scrim, so the chat stays readable and live behind it (Paul, 2026-11-10; the card's size and step are [`components.md`](../../ui/design-system/components.md) § Surface size). Its header has a back arrow to the menu, the form's title and an X; Escape steps back to the menu once, then closes, and focus goes to the form's first field on open and back to the + on close. A typed command that opens a form (below) opens the same card on that form.

Each form posts its card into the channel it was opened in through the same chat-core call the one-liner makes (`postPoll`, `postEvent`, `postTask`, `postHours`, `postPointsAdjustment` in `@repo/chat-core/dispatch`), so the placeholder, the `recorded` row, and for points the `unconfirmed` row and its Retry behave the same either way. A lost card gets the typed command's notice, titled for what was made rather than the command ("Task not confirmed", not "/task not confirmed"; [#3913](https://github.com/pdcarlson/Frapp/issues/3913)). Poll is `poll-form.tsx`. Event (`apps/web/components/chat/event-quick-form.tsx`) holds the four fields every event needs, name, date, start and end, starting at the next whole hour for an hour, and creates it as the one-liner does (10 points unless typed, not required, everyone invited; a member without `events:update` gets 0 points whatever is typed, #3709); More options opens the full editor with the draft carried over. Task (`apps/web/components/tasks/task-form.tsx`) is Title, Assignee and Due date, with Points and Description behind More options (Repeat and role assignees are [#3661](https://github.com/pdcarlson/Frapp/issues/3661)). Service hours and Points are the bodies the Service page's Log service hours dialog and the Points page's Adjust points dialog also host (`apps/web/components/service/log-hours-form.tsx`, `apps/web/components/points/points-adjustment-form.tsx`), so the two never drift; Service hours, unlike `/hours log`, can attach proof, and Points lists members by name (a shared name gets its email, never a user id), picks nobody until asked, and leaves out the officer's own row, which the API refuses. Every form names a missing or invalid field under it, outlined, and focuses it on submit; only a write the server refuses toasts.

**Drafts.** Closing the card never loses what was typed: a click away, Escape, the X, Back and a channel switch keep each form's draft, one per form per channel, until it is posted or discarded with the trash icon in the form's footer (`apps/web/components/chat/use-plus-drafts.ts`). The menu marks a row that holds one with "Draft", and picking the row or typing its bare command picks it back up. A typed command with details replaces that form's draft with what was typed. Drafts live for the page's session; a reload drops them.

A `/task` the parser refuses opens the Task form, filled in by the lenient `taskFormPrefill` with the title, a resolved `@member`, the due date and the points ([#3773](https://github.com/pdcarlson/Frapp/issues/3773) step 3). `/hours` and `/points` open their forms only when picked from the palette or typed bare; a half-typed one keeps the parser's refusal, since neither form has a field for what was wrong. A footer always reads "Tip: type / in the message box for shortcuts."

What a row does follows [`README.md` §5](../../ui/design-system/README.md#5-entitlement-gating-standard-fail-fast) (`plusMenuModel` in `@repo/chat-core/plus-menu`, which web and the phone share, with each form's grants in `PLUS_MENU_PERMISSIONS`):

- **The role can't:** left out, with one footer line naming what ("Your role can't create polls or events."), never a permission key. Poll needs `polls:create`, the phone's rule; `/poll` typed still lets any member post one, and whether the server should enforce it is #3007. Event needs `EVENT_CREATE_PERMISSIONS`. Task needs `tasks:manage` and `members:view`, Service hours `service:log`, and Points `points:adjust` and `members:view`, each its route's guard (the task and points forms also list members). A typed `/task`, or `/hours` or `/points` picked bare, by a role without them is refused with a toast before the form opens, as `/event` is. While permissions load, a row is left out without the line; if that read fails, the footer says the role couldn't be checked.
- **No grant and no module:** Sign-up sheet needs neither (`PLUS_MENU_PERMISSIONS.signup` is empty, and it has no slash command to name a module), so it is offered as soon as the menu opens, before the permissions or module reads answer, and works offline because it queues like a poll.
- **The chapter turned the module off:** left out, with "Polls are turned off in this chapter's Settings."
- **It can't work this second:** shown greyed with the reason beside it and its shortcut still shown, the typed command's refusals: "Reconnect first" offline (not Poll, which queues, unless the module read has nothing cached), "Send the file first" with a file staged, "Not while replying" with a reply staged, and "Still loading" or "Couldn't check Settings" while the module read hasn't answered.
- The menu always opens, even when Attach a file is all it holds, so the footer can say why.

**The phone** ([#3865](https://github.com/pdcarlson/Frapp/issues/3865), s05 in [`screens.md`](../../ui/mobile/screens.md)): the composer's **+** opens a bottom sheet on the New poll sheet's chrome (`apps/mobile/components/chat/composer-plus-sheet.tsx`, "Add to the conversation") with **Photo**, then Poll, Sign-up sheet, Event, Task and Service hours, in web's order and by the same model and footer lines. Points waits for a phone form, and the phone has no slash commands, so rows show no shortcut and there is no tip line. The phone's words differ in three places: "Send the photo first" with a photo staged, Photo greyed "Reconnect first" offline (an upload has no outbox) or "Up to 10 photos" with the tray full, and "Close this and try again." when the role couldn't be checked. The sheet always opens, even with Photo alone, so the line can show; the + is held dark only in a channel the member can't post in, and is absent while an edit is staged. A row runs once the sheet has finished closing. Each row opens the phone's existing sheet for it, posting into the channel it was opened from (`apps/mobile/components/chat/use-composer-plus.tsx`): Poll is the New poll sheet through `postPoll`; Event is the New event sheet, whose create asks for the card with `trackEventCard`'s placeholder (none for an event that keeps anyone out, which it says); Task and Service hours are the quick actions' New task and Log hours sheets through `postTask` and `postHours`, Log hours with its proof photo. A refusal keeps the sheet's draft and its own refusal copy. A lost answer, or a write whose card didn't post, closes the sheet and says so in an alert, since neither route dedupes.

## Slash command dispatch

- **Simple commands** (`/poll`, `/announce`) parse on the client and post via `POST /v1/channels/:id/messages` (`ChatService.sendMessage`) with the appropriate `kind` (`poll` | `announcement`) and parsed args in `payload`. One round-trip.
- **Heavy commands** (`/points grant`, `/task`, `/event`, `/hours log`) render a `kind="loading"` placeholder card optimistically (cache-only, with a `client_message_id`), then call a NestJS RPC; the server performs the side effect and posts the rich card itself carrying the **same `client_message_id`**, so the Realtime echo reconciles the placeholder in place via `mergeServerRow`. `/points` calls `POST /v1/points/adjust` with the active `channel_id` + `client_message_id`; on a committed ledger row the service posts the `kind="points"` card. `/task` calls `POST /v1/tasks` the same way; on a committed task row `TaskService.create` posts the `kind="task"` card (see *Server-originated kinds* below). `/event` calls `POST /v1/events` the same way; on a committed event row `EventService.create` posts the `kind="event"` card (through `EventAnnouncementService`). `/hours log` calls `POST /v1/service-entries` the same way; on a committed service-entry row `ServiceEntryService.create` posts the `kind="hours"` card. The committed row is the source of truth — a failed card post is logged, never rolled back. `/task`, `/event` and `/hours` drop the placeholder on any HTTP error. **`/points` no longer does, and it is the only one of the four that may not**: it drops the placeholder on a *definitive* refusal — a 409 on any attempt, or, on a first attempt only, a 4xx the **origin** produced, meaning the request was validated and rejected and nothing was written. Everything else leaves the row in place as `unconfirmed`: a 5xx, a transport failure, any refusal of a retry, and the 4xx statuses an intermediary emits after the origin may already have committed (`408`, nginx `499`, ALB `460`) — those look like refusals and are really lost responses, carrying the original `client_message_id`, with a Retry that replays that same request rather than minting a new one ([#1733](https://github.com/pdcarlson/Frapp/issues/1733)). The `unconfirmed` row and its replay handle persist on the dispatching browser, in the store `recorded` rows use (`packages/chat-core/src/heavy-command-notices.ts`), so a reconnect's refetch, a reload or a cache eviction restores them. The store is keyed by the member who dispatched, so a row is restored only into that member's view: the dedupe index is per chapter, not per member, and another officer's Retry of a never-committed original would write a fresh grant under their name. An entry leaves the store when its card arrives (the Realtime echo, a backfill, or a load that already carries it), or when a retry resolves or answers `409`. An `unconfirmed` entry more than a day old is pruned rather than restored the next time its member loads the channel. A retry that comes back `card_posted: false` turns the entry into a `recorded` one, which stays until its card arrives (for a card that never posts, indefinitely), and a retry that is refused again leaves it `unconfirmed`. Nothing prunes the entries of a member who does not come back. Where storage is blocked or full a write may not land, and the next rebuild (usually the reconnect that follows the outage) restores at most what an earlier write left; where the entry is within an hour of that day, or past it, a rebuild after the day is up prunes it instead of restoring it. In both cases the notice keeps its "check the ledger" fallback instead of promising the Retry will be there ([#1909](https://github.com/pdcarlson/Frapp/issues/1909)). The difference is not a style choice: only `/points` has a server-side dedupe index, so only there is a replay safe. The placeholder is only ever reconciled by the Realtime echo of the server's card, so a failed post means no echo arrives and the placeholder would otherwise sit on its loading copy permanently — indistinguishable from a lost write, which invites a retry that would double the side effect. **That hazard is general to every heavy command.** All four POST routes report it with `card_posted`. `POST /v1/points/adjust` returns `card_posted: boolean` whenever it actually attempted a card — `channel_id` + `client_message_id` supplied on a first write, or a replay whose stored origin channel lets it re-attempt the post. On `false` the client keeps the placeholder as a durable, non-retryable `_status: "recorded"` timeline row and surfaces a **non-destructive** notice: the ledger row committed, so it must not read as a failure, and Retry must not appear — a replay (or a re-typed command) would double an append-only write. The toast is secondary and evictable (`TOAST_LIMIT = 1`); the row is the trace that survives the next toast and a reload. Only an explicit `false` counts. The field is **absent** when the server reported no outcome — a dashboard adjustment (no card is due), or a replay of a row with no stored origin channel (legacy chat adjustments from before `channel_id` was recorded, and any dashboard-keyed row). A replay whose stored origin is set reports `card_posted` like a first attempt: `true` when the heal (or the idempotent re-send) lands, `false` when it still fails. **What an absent field means to the client depends on whether the client is replaying, and it must branch on that**: on a *first* attempt it leaves the placeholder for the echo, exactly as before; on a *replay* it removes the row and reports the points as recorded with the card's fate unknown — the replay proves the ledger row exists while proving nothing about a card that this request did not attempt, and leaving the placeholder up would strand it on its loading copy forever. The copy says *unknown*, never *failed*. The client needs no help from the server to tell these apart, since it knows which of its own requests carries a reused key. `POST /v1/tasks`, `POST /v1/events` and `POST /v1/service-entries` report the same flag under the same three-way contract (present only when `channel_id` + `client_message_id` were supplied; only an explicit `false` is actionable). On `false`, `/task`, `/event` and `/hours` keep the placeholder as the same `recorded` row and return `{ ok: true, warning }` — never `ok: false`, which would toast destructively and invite a duplicating retry. They have no replay path and drop the placeholder on any HTTP error. `/event` reports every one as a failure, including an empty-body gateway 5xx. `/task` and `/hours` report only a definitive refusal (a 4xx from the origin, `isDefinitiveClientError`) as one; a transport failure, a 5xx, or a 408/499/460 reads as unconfirmed (`ok: true, unconfirmed`, with a "check before you do it again" notice), because neither route dedupes and the + menu's form keeps its draft, so a "failed" there is one click from a duplicate ([#3865](https://github.com/pdcarlson/Frapp/issues/3865)).
  - **Only `/points` is retry-safe on the server.** The four heavy commands share a dispatch shape but no longer share a retry contract: `POST /v1/points/adjust` dedupes on `client_message_id` against a partial unique index ([`points.md`](../points.md) § Anti-Fraud), while `POST /v1/tasks`, `POST /v1/events` and `POST /v1/service-entries` have **no** server-side dedupe at all, so a replay there creates a duplicate task, event, or service entry. Do not add retry — or an outbox path — to the shared dispatcher on the strength of the paragraph above; `/task`, `/event` and `/hours` need their own idempotency first. Note that `/points` now *does* reuse its id on an explicit retry (#1733), so its dedupe path is live in the product and must not be treated as dead code; `/task`, `/event` and `/hours` still mint a fresh id per dispatch, which is the only thing making their lack of dedupe safe.
- A plain text message (no leading slash) goes through the same `POST /v1/channels/:id/messages` as `kind="text"`.
- **`/<vocab> add`** is a fifth heavy command with the same `card_posted` three-way contract as `/hours` (`POST /v1/rush/candidates`, no server-side dedupe, drop the placeholder on any HTTP error), except that every HTTP error reads as a failure, as `/event`'s do. **`vote` and `bid` are not heavy** — they POST with no placeholder; the existing candidate card live-updates via GET. Actor identity is the session (`viewer.id`), never a client-supplied id.

## Server-originated kinds (anti-forgery)

A `points`, `task`, `event`, `hours`, `rush`, or `system_audit` card asserts that a server-side side effect happened (a committed ledger row, a created task, event, service entry, or rush candidate, an audit entry). A client therefore **cannot** post these kinds directly: `chat.service.sendMessage` rejects any send whose `kind` is in `SERVER_ONLY_KINDS` (`event`, `points`, `task`, `hours`, `rush`, `system_audit`, `imported`) unless the trusted internal caller sets `system_originated: true` (never exposed on `SendMessageDto`). `PointsService.adjustPoints` is the only writer of `points` cards; `TaskService.create` is the only writer of `task` cards; `EventService.create` is the only writer of `event` cards (it posts through `EventAnnouncementService.postEventCard`); `ServiceEntryService.create` is the only writer of `hours` cards; `RushService.create` is the only writer of `rush` cards; `system_audit` has four server-side writers — the `#chapter-audit` bridge worker, plus `PollService` (expiry notices, into the poll's own channel), `InviteService` (acceptance notices, into the DM between the inviter and the new member) and `ChapterOnboardingService` (the one-time welcome message, whose channel [`onboarding.md` § First-Officer Onboarding Wizard](../onboarding.md#first-officer-onboarding-wizard) owns). **None of the four goes through `sendMessage`** — each writes on the service-role path instead (`PollService` and `InviteService` say why in comments). So `SERVER_ONLY_KINDS` is what stops a *client* posting the kind; it is not what gates these four. The optimistic `loading` placeholder stays client-postable — it carries no assertion until the server's real card replaces it.

## Announcement gating

`/announce` is exec-only and posts to the current chapter's `#announcements`. The gate is the `operation: 'read' | 'post'` parameter on the shared `canAccessChannel` predicate (default `'read'`): for `operation:'post'`, after the read check passes, the predicate denies when the channel has a who-can-post list and the caller holds no entry on it and not `*` (#3722) (and denies everyone in the audit log, [README § The audit log is system-write only](README.md#the-audit-log-is-system-write-only)). Enforced server-side in `ChatService.sendMessage`, which asserts channel access on every send. The `system_audit` writers listed above, and the Discord importer, write on the service-role path instead and never reach it. The client hides the disallowed command for UX, but the server is the trust boundary.

## Vote-change (UPSERT semantics)

Poll votes are written to `chat_message_actions` via `POST /v1/channels/messages/:messageId/actions` (`ChatReactionService.recordMessageAction`). Every user has **at most one** row with `action_type='vote'` per poll message (the dedupe unique index `(message_id, user_id, action_type)` is retained). Switching options is an upsert in effect, not in SQL: the insert raises the dedupe unique violation, which `recordMessageAction` catches and turns into an update of `payload.option_id` (and `created_at`) in place and returns a distinct response shape (`updated: true`) so the optimistic client can replay the tally. Emoji reactions (`action_type='reaction:<emoji>'`) keep the unique-violation → dedup path unchanged (one reaction per user per emoji, toggle to remove).

## Sign-up sheet cards

A **sign-up sheet** ([#3926](https://github.com/pdcarlson/Frapp/issues/3926), Shawn, 2026-11-09 and 2026-11-12) replaces the Google Form or Sheet link a chapter posts for "sober drivers Friday: 2, Saturday: 2", so Frapp knows who signed up and nobody marks anything Done by hand. It is the first of a series on the issue: headcount, closing and an end time, short forms, and Activity's Needs you with CSV export follow in their own PRs.

- **The card.** A `kind: "signup"` chat message whose `content` is the title and whose `payload` is `{ title, note?, slots: [{ id, label, capacity }] }`, `capacity` a whole number from 1 to `SIGNUP_SLOT_CAPACITY_MAX` (100) or `null` for no limit, at most `SIGNUP_SLOTS_MAX` (20) slots (bounds in `@repo/validation`'s `field-limits.ts`). Both forms build it with `buildSignupMessage` in `@repo/chat-core/signups` and post it through the outbox (`postSignup` in `@repo/chat-core/dispatch`), so it is optimistic and survives going offline, like a poll. Anyone who can post in the channel may post one: no permission and no module (Shawn's chat, 2026-11-12). Access follows the channel, as for every card.
- **Checked on send.** Unlike a poll card, whose payload is stored as sent, `ChatService.sendMessage` checks a sign-up card and stores it rebuilt from its known fields (`normalizeSignupCard` in `apps/api/src/domain/utils/signup-card-rules.ts`): a title, unique slot ids, named slots, limits in range. Anything else is a 400 before anything is written. It must be, because the claim below trusts the stored slots.
- **A claim.** A member's slots are their one `chat_message_actions` row with `action_type: "signup"` and `payload.slot_ids`, the whole list, sent through `POST /v1/channels/messages/:messageId/actions` like a vote. A tap adds or drops one slot and sends the list (`signupClaimPayload`); an empty list gives up every slot and keeps the row, as an emptied multi-choice vote does. A member may hold several slots. `ChatReactionService.recordMessageAction` hands a `signup` action to `claimSignupSlots` rather than the plain insert: the `claim_signup_slots` RPC (`20261112170000_signup_card_claims.sql`) locks the card's message row, counts every other member's claim on each slot asked for, refuses a full one, and inserts or updates the row in place (ADR-07's one row per member). So two members tapping the last spot at once can't both get it: the second gets a **409** ("That slot is full. Someone took the last spot just before you."), which each client's card-action error path shows in those words (`SERVER_MESSAGE_COPY` in `@repo/validation`). The card doesn't hear about the refusal, so it leaves a slot it now draws full of other members out of the member's next tap (`castSignupClaim`); otherwise the refused slot would ride along on every tap for ten seconds and have each refused in turn. A slot the member already holds is never full to them. A `signup` action on any other kind of message is a 400. Changing the row is a Realtime INSERT or UPDATE, which every open card already takes for votes. Unlike a vote change, it keeps the row's `created_at`, so it records when the member first signed up on the card.
- **What the card shows** (`apps/web/components/chat/renderers/signup-card.tsx`, `apps/mobile/components/chat/signup-card.tsx`, both drawing from `@repo/chat-core/signups`): an eyebrow ("Sign-up · 3 of 4 spots taken", "Sign-up · Full", or plain "Sign-up" when a slot has no limit), the title and details, then each slot with its count ("1/2", or "3" with no limit), a **Sign up** button (Secondary), **Signed up ✓** (Primary, the viewer's own, as a voted option is) or a disabled **Full**, and the names of who holds it in the order they first signed up on the card, the viewer as "You". The footer names the viewer's slots ("You're signed up for Friday") or counts people. Names are shown on purpose: unlike a poll, a sign-up is never anonymous. A blocked member's claim is shown to the blocker like anyone's: the `chat_message_actions` SELECT policy hides only a blocked member's reactions (#2494), and a card that hid their spot would draw a full slot as open. A pending card takes no tap.
- **Why not a poll variant.** A poll counts and a sign-up names; polls have an anonymity decision pending ([`../polls.md` § Anonymous polls](../polls.md#anonymous-polls)) that must not reach sign-ups; a limit has to be checked one claim at a time under a lock, which the vote rules don't do; and switching Polls off shouldn't take sign-ups with it. It reuses the poll card's mechanism instead: a chat message, one action row per member, the + menu and the outbox. Comparable apps: SignUpGenius (named slots with a quantity, names on each, several slots per person), GroupMe and Microsoft Teams sign-up lists and polls with capacity, Slack Workflow forms (short forms, step 3).
- **Older clients.** A client from before this change doesn't know the kind and draws the card as its `content`, the title, as text. An API from before it refuses to post one (`kind` is validated).
- **Reports.** A reported sign-up card keeps its title, details and slot names in the report's snapshot (`reportedContentSnapshot`), as a poll keeps its options, since all of them are member-written and a delete clears the card.

## Rich-message renderer registry

The payload shapes in `@repo/chat-core/integrations` (`packages/chat-core/src/integrations/payloads.ts`) are the wire contract; web maps a message `kind` → a React component via `apps/web/components/chat/renderers/index.tsx`'s `MessageRenderer` switch. **Mobile has no registry**: `cardFor` in `apps/mobile/components/chat/thread-message-row.tsx` picks a card by kind, and the cards share one frame, `ChatCardShell` in `chat-card.tsx` (long-press actions, delivery status, reactions). The poll card reads the poll shapes and tally logic from `@repo/chat-core/polls`, which re-exports them from `./integrations`, and dispatches through the platform-neutral `actOnCard`/`react`/`unreact` functions in `@repo/chat-core/chat-client` directly. The `event`, `task`, `points`, `hours`, `rush` and `system_audit` payloads are read on both surfaces by the readers in `@repo/chat-core/cards` (`readEventPayload`, `readTaskPayload`, `readPointsPayload`, `readHoursPayload`, `readRushPayload`, `readSystemAuditPayload`, and `readAnnouncementBody` for an announcement's text), and the task card's rules (who may read the live task, which controls to offer, the status label) by `taskCardControls` and its neighbours in `@repo/hooks` (`packages/hooks/src/task-card.ts`), the hours card's by `packages/hooks/src/service-entry-card.ts`, and the rush card's by `packages/hooks/src/rush-card.ts`, so the two surfaces' cards can't disagree (#3185, #3383). (Until #3228 the shapes lived in a separate `@repo/chat-integrations` package whose `require` condition pointed at an unbuilt `dist/`, #989, so `chat-core/polls` redeclared them and mobile read them from there.) The two surfaces also style differently — web with Tailwind, mobile with the typed `StyleSheet` token factories required by [`../../ui/mobile/README.md`](../../ui/mobile/README.md) § Styling. (This line previously said mobile used NativeWind; NativeWind was removed from `apps/mobile` entirely in S1 of #937 and is now banned there.) On web, concrete renderers exist for `text` (default), `poll`, `signup` ([§ Sign-up sheet cards](#sign-up-sheet-cards)), `announcement`, `system_audit`, `loading` (placeholder while a heavy command computes), `points` (read-only ledger card: `actor → recipient`, signed amount, reason — append-only, no actions), `task` (interactive assignment card), `event` (interactive event card), `hours` (read-only service-entry log: member, duration, date, description — append-only, no actions; the snapshot's status is the creation-time `PENDING` forever, so the badge is the entry's **live** review status, Pending review / Approved / Rejected, read back through `GET /v1/service-entries/:id`, which needs `members:view` and the Hours module and then answers only the member who logged it and a `service:approve` holder, so nobody else asks (until the viewer's permissions are read, only the member who logged it does); anyone else, anyone before the read lands, and anyone the route answers with a 404 or its own 403 (a deleted entry, a lost permission) sees no badge, #3383), and `rush` (candidate card: the chapter's word for recruitment as its eyebrow, `vocab("recruitment", …)` from `@repo/org-archetypes`; the candidate's name and who added them; then, from the live candidate, whether a bid is out (Open / Bid extended) and the vote count with "you voted". The live candidate is read back through `GET /v1/rush/candidates/:id`, which needs `members:view` and nothing else, so nobody known to lack it asks (a viewer whose permissions haven't been read yet asks anyway, since every seeded role holds it), and a 404 or the route's own 403 clears the tally. Both card reads tell those answers from `ChapterGuard`'s `chapter.context.mismatch` with `isCardReadMiss` in `@repo/hooks`: a session whose token hasn't caught up with a chapter switch is retried, not read as a miss. Nothing live is drawn and no control is offered before that read lands, because the snapshot has no votes and its bid is `none` forever. Every member may Vote (then a disabled Voted, since there is no unvote) and Extend bid (gone once a bid is out); while Recruitment is known to be off the card offers neither, and keeps its tally, since the reads still answer. A gate's refusal of either write is told in a member's words, `rushCardGateRefusal`, never the guard's officer-addressed message. Voter names are never shown); mobile draws `poll`, `signup`, `event`, `task`, `points`, `hours`, `rush`, `announcement` and `system_audit` as cards in the same row frame (`apps/mobile/components/chat/`), and `dues` and `loading` as text via `message-item.tsx`; a card whose payload doesn't read is drawn as its `content` text, as on web. The `announcement` card draws the message's `content` through the message markdown, and `payload.body` only when `content` is empty: `content` is what the push and the channel preview showed, and `announcement` is not a server-only kind, so a client could send a body that says something else. The `system_audit` card names its actor through `actorLabel` (`@repo/hooks`): the roster's name, "Frapp" for the system, or the member fallback, never a bare id prefix. Only the `#chapter-audit` mirror writes that payload; the server's own notices (a poll closing, an invite accepted, the chapter welcome) are `system_audit` rows without one, whose `content` is the whole sentence: mobile draws them as text, and web as that sentence in a muted card frame, because the renderer registry keeps every card kind out of the text body. The `task` card is an immutable creation-time snapshot (`assigner → assignee`, title, due date, point reward) whose **live** status is read back through the task query — the chat message row is never mutated — and carries inline lifecycle actions: the assignee can Start / Mark done and a `tasks:manage` admin can Confirm / Reject, gated client-side for UX with the existing task REST endpoints as the trust boundary. No control and no status badge is drawn until the live task is read, because the payload's status is the creation-time `TODO` forever (#2065); a viewer who can't read the task sees the snapshot without a live status ([`../tasks.md` § Chat Integration](../tasks.md#chat-integration)). The `event` card mirrors that shape: an immutable creation-time snapshot (name, when, location, point value); a Check-in action is gated client-side to the event window for every member (on mobile it also reads the event while the window is open, to learn whether a check-in zone needs the member's position), and the **live** checked-in count is read back through the attendance query only for viewers who can read attendance (`events:update`) — the server enforces the window, the role gate, and one-check-in-per-member. The remaining ops kind (`dues`) has a stub renderer that shows a "renderer coming soon" card, so modules can drop in a concrete renderer without UI-plumbing work. Card action buttons (Vote, RSVP, Pay, Confirm, Submit) fire through the chat hot path via `actOnCard` (`@repo/chat-core/chat-client`) — idempotent (ADR-07's UPSERT semantics for a vote-change), but **not optimistic**: unlike `react`/`unreact`, which patch the cache before the request and roll back on failure, `actOnCard` only patches the cache after a successful response, and neither it nor a card that calls it (the poll card, on either surface) drops a second tap while the first request is still in flight (#1499 tracks adding both). The mobile event, task and rush cards write through the attendance, task and rush REST hooks rather than `actOnCard`, and each drops a second tap with a ref set before its first await (#3185, #3383); web's event, task and rush cards still rely on the mutation's `isPending`, which reaches the button a render late.

See [README.md](./README.md) → *Message Kinds and Actions* for the canonical `kind` table.

## `#chapter-audit` system-channel bridge

Member-visible officer changes (dues, modules, roles) surface in chat as a system-written audit feed. The bridge worker subscribes (service-role) to `chapter_audit_log` INSERT via Supabase Realtime and posts a `kind='system_audit'` message into the chapter's `#chapter-audit` channel as the system sender (`00000000-0000-0000-0000-000000000000`). This is a server-originated insert that bypasses the client send path and goes direct via service role; it has a single owner (no inline audit-post in writing services).

- Rows with `member_visible=false` are skipped — internal-scope rows stay out of the channel.
- Message shape: `sender_id` = system sender; `content` = human summary (`"<action>: <diff keys>"`); `kind` = `system_audit`; `payload` = `{ action, actor_user_id, diff }`. The renderer reads from `payload`, not the prose `content`.
- Chapters that pre-date the `#chapter-audit` channel have no mirror; the bridge logs and continues. The audit row itself is always the source of truth.

The same `system_audit` message pattern is reused, targeted to a DM, for the invite-accept notification (see [README.md](./README.md) → *Direct Messages*).

## The team's Dev log channel

The Frapp team's own chapter has a channel where GitHub Actions posts what is being worked on and what shipped ([#4145](https://github.com/pdcarlson/Frapp/issues/4145), asked for by Shawn, built on Paul's go, 2026-11-11). It is a tool for the people who build Frapp, not a product feature: no chapter can turn it on, and a deployment without the token's hash answers `404` on the route.

- **Four posts.** An issue gets the `in-progress` label ("<who> started: <title>", with the issue's area labels and the other in-progress issues that share one, so someone starting work sees who is already there). A pull request merges to `main`. Once a day: how many pull requests merged in the last day, per person, and what is in progress now. A Deploy production run ships: "Update pushed: please update", with the newest What's new entry of the API that just went live (`RELEASE_NOTES` in `@repo/validation`, the list the apps show), so the channel and the app can't differ.
- **One route, facts only.** `POST /v1/integrations/dev-log` takes an event name and its facts (a number, a title, a name). The API writes the sentence and builds every link from the number, to this repository only, as `<url>`, the one bare form both clients link. The body cannot name a channel, a chapter, a sender, or a URL; an unknown key is a `400`.
- **Titles and names cannot carry a link.** The message is parsed as markdown, and an issue title in a public repository is anyone's text. So every title, name and label has its square and angle brackets replaced and any `http(s)://` removed before it is written (`plainText` in `dev-log.service.ts`): nothing the caller sends can become a link or an image under Frapp's name. Bold or italic in a title is left alone.
- **Message shape.** `sender_id` = system sender, `kind` = `text`, no payload. `text`, not `system_audit`: a `system_audit` notice draws its words as plain text with no links and defaults push to off. As a `text` row it draws as Frapp's (the crest, the name) with working links, and follows the channel's notification level like any message.
- **Nothing posts twice.** Each event has a `client_message_id`, so the dedupe index drops a re-run and the route answers `duplicate`: `devlog:pr_merged:<pull request>`, `devlog:daily_summary:<day>`, `devlog:work_started:<issue>:<workflow run>` (an issue released and taken again posts again), and `devlog:update_pushed:<deploy run>:<what it shipped>` (re-running a deploy's failed app jobs posts once more, with the build).
- **What counts as shipped.** A Deploy production run whose deploy job succeeded and that was neither a dry run nor migrations-only, whether or not its tag was minted afterwards. The phone-app lines are added only for a store build its confirm job saw uploaded, and an over-the-air update its publish job sent. The post is written when the whole run ends, so on a run that also builds for the stores it arrives when that build is confirmed, which can be hours after the web went live.
- **What's new on an update.** The newest entry in full when it is at most a few days old. When the update shipped no new entry, one line naming the latest, so an old entry is not announced again as news.
- **Skipped.** Anything a bot account did (Dependabot, an App), an issue or pull request labelled `routine-state` or `incident`, a summary with nothing in it, and a Deploy production run that did not ship.
- **Who.** The account that added the label or opened the pull request, by its GitHub profile name, or its login when it has none. Agent sessions act under their user's account, so that is whose chat it was.

The credential, where it lives and how it is revoked: [`authorization-model.md`](../../../docs/security/authorization-model.md) (the route's row) and [`ENV_REFERENCE.md` § Dev log channel](../../../docs/internal/environment/ENV_REFERENCE.md#dev-log-channel). The workflow: `.github/workflows/dev-log.yml`.

# Onboarding and Invites

This file covers the in-app onboarding behavior: the first-officer wizard, invite tokens, what a new member sees after joining (their name and photo, then the welcome card), and chapter-directory search. The signup/payment flow and chapter lifecycle are specced in [`../product/onboarding.md`](../product/onboarding.md) — cross-reference, not duplicated here.

## First-Officer Onboarding Wizard

- Fires on first sign-in when the authenticated user has **no chapter memberships** (`GET /v1/chapters` returns empty). **Web** mounts it as a full-screen overlay. **Mobile** is a deliberate route (`apps/mobile/app/(auth)/create-chapter.tsx`) reached from join's "Starting a chapter? Create a chapter" line (the chapter-picker empty state's button opens join), and from the You tab when the account has zero memberships — so the wizard can own its lifecycle after submit flips the membership count to 1. `(auth)/_layout.tsx` exempts `/create-chapter` from the post-auth bounce into the tabs for that reason. Both surfaces read the archetype catalog from `@repo/org-archetypes` (`ARCHETYPES`). Web maps a directory row's archetype through `getArchetype`, which falls back to IFC; mobile asks instead when the row's archetype isn't one it knows (below); mobile declares that workspace package in `apps/mobile/package.json` rather than keeping a local catalog.
- **Web zero-membership is not create-only.** The overlay still opens (same trigger), but the find step's **I have an invite** control goes to `/join`. The dialog stays non-dismissable via Escape so a first officer cannot abandon mid-create by accident; `/join` is outside `DashboardShell`, so the overlay does not remount there. `/join` offers **Create a chapter** back to `/chat?setup=chapter`, which remounts the wizard. An account with an invite emailed to it (`GET /v1/invites/mine`, below) is sent to `/join` instead of the wizard, where it is offered as a one-tap Join; the wizard opens only once that read finds none or fails, or when the visit came from **Create a chapter** (#5077: signing in with the invited address used to land on Set up your chapter). Mobile already routes zero memberships to s02, which offers each emailed invite, Paste for an invite link, and a Create a chapter line (#3350, #5626).
- **Web `/join` for a member who already has a chapter (#3850).** The page doesn't redirect members away in general: an invite link may be for a second chapter, the chapter switcher's **Join another chapter** opens it, and `/no-access` sends a member with no role here, who would loop back to `/no-access` from `/chat`. Instead it leads with **You're already in <chapter>** and **Open chat**, and keeps the invite form as the secondary action. A member `/no-access` would send back (no role in their only chapter, `isLockedOutOfChapter` in `apps/web/lib/auth/no-access.ts`) doesn't see it. The one exception is the sign-in footer's **Join your chapter**, which signs in toward `/join?from=sign-in`. A member who arrives that way with no invite in the URL, no invite emailed to them, and not locked out by that rule goes straight to `/chat`. The page decides once, on arrival, so a join made there never triggers it (`shouldSkipJoinForMember` in `apps/web/lib/auth/join-visit.ts`).
- **"No chapter memberships" is the only robust (re-)trigger signal.** A wizard-created membership is written with `has_completed_onboarding=true`, and the chapters-list response does not expose `enabled_modules`, so a client cannot detect "chapter still at the default seed" from it. Once opened, the wizard owns its own lifecycle — the membership count flipping to 1 mid-flow does not auto-close it.
- **Mobile's steps (#3351):** **Find** the chapter in the directory, **Confirm** the match (a card, its fields behind `Edit details`) or describe it by hand, then pick its **Color** and accept the Terms. The archetype comes from the directory match; it is asked only on manual entry, or when the match's archetype is unknown to the app, with nothing preselected. For an organization that doesn't display its Greek letters (Phi Gamma Delta), neither the letters nor their switch appear in setup, the directory results leave them off, and the chapter is sent with the switch off. Both wizards decide it the same way: by the picked directory row's organization, which holds whatever the name field says later, else by the name as typed, alone or with more ("FIJI", "Phi Gamma Delta Tau Nu", `orgHidingGreekLettersIn`). Naming such an organization, by its row or by hand, turns the switch off and fills the short name only when the founder left it empty (`orgMarkFieldsFor`). Either way the letters are still stored, hidden ([`branding.md`](branding.md) § Chapter mark: the switch hides, it doesn't delete). Create opens `<name> is live` with the seeded channels and an optional logo upload, then `Pick your chat display` (#4056: the founder's own display, as s03 asks a joining member), then the `Turn on notifications` step (only when the build can push and push is off), then the invite step (only when the new chapter is active), then chat. The invite step never shows a token: each press of **Share invite** mints one invite (`POST /v1/invites`, the chapter's Everyone role, which is no role a member sees) and opens the platform share sheet with its join link, so one press sends one person one link. Nothing is minted before a press, so skipping the step leaves no invite. On iOS a sheet closed without sending keeps its link for the next press; Android can't report that, so there every opened chooser counts as sent. Links sent are listed with whether each has been used, read by polling `GET /v1/invites` every 15 seconds while the step is open and a link is out. A link counts as used when its row's `status` is `joined`; a revoked one also carries `used_at`, so `used_at` is read only from a row with no `status` (an API before #3652). The logo and invite routes act on the active chapter, so when the new chapter couldn't be made active the live step names no channels and offers no logo, and setup ends at chat with no invite step. All of it is one route, because the gates exempt `/create-chapter` by exact path.
- Submit calls `POST /v1/chapters/onboard` on the **cold path** (NestJS + service-role Supabase), not the chat hot path. `ChapterOnboardingService.onboard`:
  1. Materializes the chapter config from the chosen archetype, **deep-copying the archetype seed** so per-chapter edits never mutate the shared reference. Sets `org_archetype`, `enabled_modules`, `vocabulary`, and a derived `theme_palette`. The client never supplies the module map — it is resolved server-side from the archetype.
  2. Creates the chapter with branding + `directory_id` (when matched in the directory), default roles, the creator's President membership, and the default channels seeded from `DEFAULT_CHANNELS` (the set, and each channel's type and gating: [`chat/README.md` § Channels](chat/README.md#channels)). The no-channels empty state names no seeded channel (web `Onboarding seeds them. Ask an admin.`, mobile `Ask an admin to add one.`), so it never lists `#alumni` to someone who can't see it. Copy that lists channels by name, such as mobile chapter setup's live step, names only the three public ones.
  3. Seeds the archetype's default custom fields into `chapter_custom_fields`, so Settings → Fields opens populated rather than empty. Best-effort and idempotent; the key derivation and skip rules live with the rest of the Fields-tab behavior in [`settings/customization.md`](settings/customization.md#fields-tab), not here.
  4. Posts a one-time welcome `system_audit` message into `#general` (resolved by name; skipped if absent): `"Welcome to the <designation> chapter of <name>. Invite your chapter to get the conversation started."` (for example "Welcome to the Tau Nu chapter of FIJI."). With only one of the two it reads `"Welcome to the <designation> chapter."` or `"Welcome to <name>."`, and with neither, `"Welcome to your chapter."`; the second sentence is the same in every case. A designation that ends in the word "chapter" drops it, so the sentence never says "chapter" twice. `<name>` is the short name the wizard set, else the chapter's name field (the organization's name on the directory path, free text on manual entry). It is never Greek letters, whatever the chapter's letters setting, because some organizations (Phi Gamma Delta among them) don't allow their letters to be shown: a name or designation with any Greek letter in it is left out. A name that repeats the designation ("FIJI Tau Nu") drops it, and one that is only the designation is left out (`welcomeGreeting`). Sent by the system user (drawn with the Frapp crest, [`chat/README.md`](chat/README.md#hot-path-client-behavior)); best-effort (a failure does not roll back chapter creation).
  5. Navigates the client. **Web goes to `/billing`**, not chat (#2297); mobile goes to `/` — chat home. While chapter billing is off for the beta, web goes to `/chat` as well (below).
- **While chapter billing is off for the beta, a new chapter starts `active` (Paul, 2026-11-15).** `CHAPTER_BILLING_BETA_OFF` in `@repo/validation` (beside `BETA_OFF_MODULES`) is one switch, the same in every environment: `ChapterService.create` writes `subscription_status: 'active'` over the schema default, and the web wizard ends on `/chat` instead of Plan and billing. The chapter has no Stripe customer, which Plan and billing draws as complimentary ("Turned on by Frapp. No card on file and nothing to pay."). The `incomplete` state below stays unreachable on the normal path, which is what the 2026-09-18 decision asks; the free tier is not widened. Setting the switch to `false` brings back everything this section describes for chapters created after that; the beta's chapters stay `active` with no `stripe_customer_id` until someone decides what they get when billing returns. That pair alone doesn't find them: the App Store demo chapter and chapters Frapp switched on by hand (Paul's own) look the same, so pick them by `created_at` between this change and the flip, minus those. The rest of this section is the behavior with billing on.
- **With billing on, web lands a new founder on checkout, because the chapter it just made cannot write anything.** `subscription_status` defaults to `'incomplete'` (`00000000000000_initial_schema.sql:34-35`) and `ChapterService.create` has no billing dependency, so a brand-new chapter is in the one state where every screen loads and every paid-ops **write** is refused. Landing on chat left the founder there with no explanation — the Guideline 2.1 finding in #2297.
  - **The gate is writes-only.** `ChapterGuard.enforceSubscription` returns before any status branch for `GET`/`HEAD`/`OPTIONS`, so reads are never refused and a lapsed or incomplete chapter can still see everything. Do not describe this gate as blocking events/tasks/points wholesale — it blocks *changing* them. Matrix: [`docs/guides/api-architecture.md`](../../docs/guides/api-architecture.md) § Subscription enforcement; read access is also stated in [`billing.md`](billing.md).
  - **Recorded decision (2026-09-18, owner):** make the `incomplete` state unreachable on the normal path rather than widen the free tier. `@FreeTier()` is **not** added to the paid-ops controllers — the boundary below stands as written. The founder is put in front of checkout instead, which costs nothing on day zero because #913's trial (`grantTrial: !chapter.subscription_id`) makes Stripe report `trialing`, which `mapStripeStatus` folds to `active`.
  - **A landing, not a gate.** Nothing blocks navigating away from `/billing`; the dashboard shell and its nav are fully available. That is what keeps this consistent with [`../product/positioning.md`](../product/positioning.md) § Officer onboarding, which requires ops setup to be an inline nudge rather than a mandatory gate.
  - **Checkout is web-only, and that is a store commitment, not a preference.** `apps/mobile/store/README.md` § Identity (the Price row) and § Review notes carry the submitted App Store Connect answers: the app has no in-app purchases and chapter subscriptions "are not offered, linked or mentioned in the app". Mobile's half of #2297 is therefore copy only — a refusal is explained and the retry withdrawn, naming no price, plan, purchase path or link. Adding one trades a 2.1 finding for a 3.1.1 one.
- **Manual-entry path:** when the officer's chapter is not in the directory, the wizard submits with no `directory_id`. The service writes a `chapter_directory_requests` row (status `pending`) so the curated directory seed can be backfilled later. The row is RLS-enabled and API-only (no client policies), like `chapter_directory`.
- **Actor identity** for the chapter, membership, welcome message, and directory request is **always resolved from the authenticated session**, never from the request payload. The `requested_by` on a directory request comes from the session.

## Invite Token Rules

- Tokens **expire after 7 days** (`INVITE_DAYS`; Paul 2026-11-19, #5625: a link texted on a Friday night was dead by Sunday at 24 hours).
- A token can be used **only once** (`used_at` is set on redemption).
- **The chapter link is the exception to both (#3353, Paul 2026-11-19: "One chapter link, 7 days"; per role since #5633, Paul 2026-11-19: "Officer picks it per link").** An officer with `members:invite` makes a shareable link (`POST /v1/invites/chapter-link`, body `{ role? }`) to post where everyone will see it, such as the chapter's Discord. It lasts **7 days**, grants the role the officer picked, or the chapter's default invite role when none is named (the rule below for a token with no role named), and any number of people join with it at once, with no approval: a redeem leaves its `used_at` null (`invites.reusable`). A chapter has at most one per role that no officer has turned off (`invites_one_chapter_link_per_role` on `(chapter_id, role)`), so a pledge class link and a brothers link can be out together; making a new one for a role turns off only that role's link before it, and turning one off is the ordinary revoke (`DELETE /v1/invites/:id`), after which it answers 410 like any revoked token. `GET /v1/invites/chapter-link` returns `{ links, default_role, link }`: every role's link the caller may see, newest first, expired or not (both apps list an expired one as expired, so an officer sees why a posted link is dead); `default_role`, the role a link with no role named gets for this caller, which both apps' pickers start on (the chapter's configured default is an officer-only read the client may lack); and `link`, that role's link, for phone builds from before #5633, whose Make a new link posts no role and so replaces exactly it. A link whose role is no longer one the officer may hand out (renamed, deleted or ranked up) offers only Turn off. They stay out of `GET /v1/invites`, which lists who was asked. Like any invite a link is shown, made and replaced only by an officer who could invite someone into its role (#4546): one ranked above the caller isn't listed, and making one for that role answers 403. The roles offered are the personal invite's (`useInviteRoleChoices`). Its sender is told of each join by a notification, `<name> joined with your chapter link` (#5625; it was a Frapp line in a DM with the new member until Paul's 2026-11-19 "not the biggest fan of these DMs").
- An expired or already-used token returns **410 Gone**.
- Each token carries a `role` that determines the joining member's initial role. If that role was deleted between creation and redemption, the user is assigned the chapter's Everyone role (`system_key` `MEMBER`, once called Member; [`rbac.md` § The Everyone role](rbac.md#the-everyone-role)) instead. A chapter with no such role, a rare legacy case ([`rbac.md`](rbac.md)), gets a member with no role, and the preview below reports its role as `null`. When the token's role is not a seeded one (`is_system` false: a role the chapter made, or one a Discord import brought over) and grants neither `members:view` nor `*`, the member also gets the chapter's Everyone role, listed after the token's role: such a role usually carries nothing but a channel read permission, and without `members:view` the member is refused on every screen. A chapter with no Everyone role grants the token's role alone. Every other role is granted alone.
- Only users with the `members:invite` permission can generate tokens. Multiple tokens can be generated at once (batch invite), or one per address via a bulk email send (`POST /v1/invites/email`) that mints a token per address and emails each a join link. Email delivery is best-effort per address — a send failure never invalidates the token, it is only reported back so the caller can retry or share the link manually.
- **Minting an invite is part of the free-tier wedge, but it is not ungated.** `InviteService.create` / `createBatch` / `createWithEmails` never check `subscription_status` themselves — the gate lives in `ChapterGuard`, via `@FreeTier()` on the controller class plus `@GraceBlocked()` on those three creating routes. So a brand-new `incomplete` chapter from the onboarding wizard (with chapter billing on) **can** mint tokens, but a `past_due` chapter **cannot**: creation is refused with **403** (code `chapter.subscription.invite_blocked` in the response body) even inside the 3-day grace window that still permits its other free-tier writes, and a null `past_due_since` counts as within grace. A `canceled` chapter cannot mint either. Billing gates the paid ops modules more broadly than it gates chat/members/invites, but "free-tier" never means "always allowed". Full matrix: [`docs/guides/api-architecture.md`](../../docs/guides/api-architecture.md) § Subscription enforcement (ChapterGuard).
- **Redeeming is subscription-gated in the service, not the guard (#1546).** `POST /v1/invites/redeem` carries no `ChapterGuard`: `InviteController` applies `ChapterGuard`/`PermissionsGuard` per route and `redeem` declares neither. It is still authenticated — `SupabaseAuthGuard` is class-level. It _cannot_ simply be guarded, and not because the caller lacks chapter context (`ChapterGuard` resolves one per [`multi-tenancy.md`](multi-tenancy.md)) but because the chapter which matters here is `invite.chapter_id`, which the guard never sees — adding the guard would gate the redeemer's _current_ chapter instead, and 400 a brand-new user who has none. So `InviteService.redeem` loads `invite.chapter_id` and applies the guard's own hard-lock rule to it (`isSubscriptionHardLocked` in `#domain/constants/subscription-grace`): a `canceled` chapter, or a `past_due` one past the 3-day grace window, is refused with **403** and the token is **not** consumed — the same link works once the chapter recovers. This closed the one-day tail in which a token minted before a lapse could still add a member; a `past_due` chapter inside grace still admits, matching the guard. Minting stays gated at the guard (`@GraceBlocked`).
- Email delivery itself is optional infrastructure: with no `RESEND_API_KEY` configured, the API logs invite emails instead of sending them rather than failing the request — tokens are still created and can be shared as links. See `docs/internal/environment/ENV_REFERENCE.md` § Invite Email.
- If a user is already a member of the chapter and attempts to use an invite token for it, the API returns **409 Conflict**.
- **Redeem re-checks the invite's role against its sender (#1830).** An invite never makes anyone President, and grants only a role ranked below whoever sent it, judged by the sender's roles at redeem time ([`rbac.md` § Rank](rbac.md#rank)). One that fails (a `*` role, a sender since demoted, or a sender who has left the chapter or lost `members:invite`) is refused with **403** (code `invite.role_out_of_reach`) before the token is claimed, so an officer can still revoke it; the join screens show the server's message. The preview answers such an invite with the same 403, and `GET /v1/invites/mine` leaves it out, so an older invite that works is offered instead.
- **Redeeming needs the current Terms (#2302).** A user who hasn't accepted the Terms version the API enforces must send `accept_terms_privacy: true`. Every join from a join screen sends it (`joinRedeemBody`): the screens show the Terms line under the button instead of a checkbox (Paul's pick 2026-11-19, #5625), so the tap is the acceptance, and the server records it only when the user hasn't accepted the current version already. Without it the join is refused with **403** and the token is **not** consumed. The client recognises the refusal by its code, `legal.acceptance_required`, falling back to its message, `LEGAL_ACCEPTANCE_REQUIRED_MESSAGE`, for an API that predates #1020 and sends no code. The check runs after the 410, 409 and subscription-lock checks, so a dead link or a locked chapter says what is actually wrong. A user who already accepted joins without it. Rule and record: [`legal.md` § Acceptance record](legal.md#acceptance-record).
- **An invite link opened on a phone leads only to the app (#4002; app only since Paul's pick, 2026-11-21).** On an iPhone or an Android phone (`phonePlatform` in `@repo/validation`; iPads and Android tablets get the web as before), web `/join` with an invite in its query offers the app first (its strings: [`writing.md` § Join chapter (pre-auth)](../ui/design-system/writing.md#join-chapter-pre-auth)): open it in the app (`frapp://join?token=…` on iOS; on Android a Chrome `intent:` link naming `live.frapp.mobile`, which opens Play when the app is missing) or get the app. There is no way on in the browser on a phone: until 2026-11-21 a `Join on the web instead` link went on to the page as on a desktop, and a new member on staging took it while the app was already signing him in and joining him, so he signed in twice and was asked his name twice. When the environment has an install link for its app (`NEXT_PUBLIC_IOS_INSTALL_URL` / `NEXT_PUBLIC_ANDROID_INSTALL_URL`: the TestFlight external group's public link and Play's tester link during the beta, the store listing for the store app when unset; `apps/web/lib/app-install.ts`), the page is two numbered steps, Get the app and then Paste your invite, so on an iPhone one texted invite link is all a beta tester needs and nobody is added to TestFlight by Apple ID (2026-11-19, Paul); tapping Get copies the invite (below). Play's tester link opens only for accounts on the track's tester list, so an Android tester is added there first and the hint says so. Without an install link (Frapp Staging before its links are set) the page offers Open in the app alone, with a note to ask the officer how to get the app. The scheme and package are the environment's own app's (`nativeAppForOrigin`): `frapp-staging://` and `live.frapp.mobile.staging` on staging. It shows signed in or out, member or not (`proxy.ts` lets a signed-out phone visitor carrying an invite reach `/join` instead of bouncing to `/sign-in`): from #4341 (2026-11-20) the app joins a second chapter itself (`(auth)/join-another`, [`navigation.md` § Deep links](../ui/mobile/navigation.md#deep-links)). The one phone visit that goes on in the browser is a URL marked `web=1`, which app builds before #4341 add when they hand a member's second-chapter invite to the web in an in-app browser; offering the app there would send it straight back (`JOIN_IN_BROWSER_KEY`, `apps/web/lib/auth/join-visit.ts`). Joining on the web and then signing in to the app again is the double sign-in this removes. The clipboard carries the invite through the install (next rule). Once app links are live, the link opens an installed app before the page loads. That needs both halves: the dashboard origin publishes `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` for `/join` only (`apps/web/lib/app-links.ts`), from two values set in `prod` and `staging` ([`ENV_REFERENCE.md` § References](../../docs/internal/environment/ENV_REFERENCE.md#references--framework-specific-names)), and the installed build claims the same path. Store builds claim it from 0.11.0 ([`navigation.md` § Deep links](../ui/mobile/navigation.md#deep-links)); production's dashboard doesn't publish the two files yet, because their values aren't set ([#4336](https://github.com/frapplive/Frapp/issues/4336), Paul's), so today every invite link opens the web. (Corrected 2026-11-20, #5628: this said no store build claimed it.) Only an invite is handed over: no other page, chapter creation included, sends a phone visitor to the app. The phone dashboard does suggest the app, with a card its member can close and that blocks nothing ([`web-dashboard/README.md` § Get the app (phones)](../ui/web-dashboard/README.md#get-the-app-phones)); changed in the #4002 slice that added it, 2026-11-11.
- **The invite survives installing the app (#5626, Paul's pick 2026-11-19: "Copy on install, Paste fallback").** iOS can't hand a link to an app that wasn't installed when it was tapped, short of a third-party link service (Branch and the like, which send device data to a third party), and Android's Play install referrer hands the invite to Google and needs a native change. So the clipboard carries it: on web `/join`'s two steps, the tap on Get copies the invite's join link (`navigator.clipboard.writeText` inside the click, as browsers require) and opens the store or TestFlight in a new tab, so the page stays to come back to; step 1's line then says `Invite copied. When <app> opens, tap Paste.` (or, where the browser refused, to come back and use Open in the app). The app's first screens offer Paste: sign-in's `Joining a chapter?` strip, before any account, and s02's question for an account with no chapter. On iOS 16 and later it is the system Paste button (`UIPasteControl` through `expo-clipboard`), which reads the clipboard with no prompt and no "pasted from" banner; elsewhere it is Frapp's own button, which reads it on the tap. Nothing reads the clipboard without a tap. A paste opens the invite card when it holds an invite, a join link or the bare invite, and only one shaped like the invites the API mints (`pastedInviteToken` in `@repo/validation`, a UUID), so a tracking number left on the clipboard says `That isn't a Frapp invite` on the screen instead of opening a card that says the link doesn't work. A pasted invite is remembered as an opened link's is, so the card's sign-in and join carry on through the sign-in leaving the app. An invite emailed to the member's address is offered on s02 after sign-in either way (`GET /v1/invites/mine`, below).
- **An invite can be read before it is used (#3352).** `POST /v1/invites/preview` takes the token in the body, like redeem, and returns the chapter's name and school, its text mark (resolved as [`branding.md` § Chapter mark](branding.md#chapter-mark) says, so never letters the chapter or its organization hides), its accent color, the inviter's display name, the token's role (the Everyone role the redeem may add beside it, as above, is not reported, and an invite granting only Everyone reports `null`) and the expiry. It uses nothing up and answers only the 410s; the subscription lock, the Terms and an existing membership stay the redeem's to refuse. It is signed-in only. No current screen reads it: the invite card reads the details below instead, and the route stays for phone builds already in people's hands, which read it on their confirm step.
- **The invite card reads an invite before anyone signs in (#5625).** `POST /v1/invites/details` needs no account (its own controller, `InviteDetailsController`, so no class-level guard covers it by accident) and returns the preview's fields plus the link's `state` (`live`, `expired`, `used`, `off` for one revoked or one its sender can no longer grant, or `locked` for a live link whose chapter's subscription is hard-locked, so joining would be refused until it is restored), the `chapter_id`, the chapter's `member_count` and `sent_at`. It answers for a dead link too, so the card still names the chapter and the sender to ask, but leaves out what only a member needs (`member_count` is 0 and `role` null), and only for 30 days after the link stopped working (`DEAD_INVITE_DETAILS_DAYS`). It 404s a token that never existed, whose chapter is gone, or that has been dead longer than that. The token is the credential: whoever holds a live one could join with it, so the card tells them nothing joining wouldn't. It is counted per address (`ThrottlePublicTokenRead`), generously, because a pledge class opens the chapter link together on one campus network. Web `/join` and the phone's join screen show the same card from it, state for state:
  - **Signed out, live link:** the card, Continue with Apple, Google or email, and the Terms line. A sign-in started there comes back marked to join, and that mark is what joins, once: a sign-in from anywhere else never joins on its own. On web the mark is two halves that must agree: `then=join` on the `/join` URL and the same token and action stored in the browser when the button was tapped (`frapp.join-then`, `rememberJoinMark` in `apps/web/lib/auth/join-visit.ts`), so a link crafted with `then=join` and sent to a signed-in member only shows them the card. On the phone it is the remembered invite's mark. The email way is a six-digit code typed in place (`verifyOtp`), with the email's link still working on another device or until the Auth templates print `{{ .Token }}`. The phone remembers the invite on the device (`invite-token.ts`) until it is joined or declined, so a sign-in that leaves the app, or a relaunch, comes back to it; the join mark lapses after 30 minutes.
  - **Signed in:** the card and one Join. Someone already in the chapter is told so and offered it; a join that answers 409 opens it.
  - **Dead link:** the card with `<sender> sent it on <date>`, and **Ask for a new link**: `POST /v1/invites/ask-for-new-link` (signed-in, so the sender sees a real name) notifies the invite's sender by name, in the app and by push. For a `locked` chapter the notice says the caller tried to join and the subscription is inactive, since a new link wouldn't help. 409 when the link still works (`invite.still_live`) or the caller is already in the chapter (`invite.already_member`); a sender who has left the chapter isn't told, and the caller hears it as sent. It is limited to 3 an hour per account (`ThrottlePersonalNudge`), because each one pages a person who never asked to hear from the caller. Signed out, the button opens the ways in, marked to ask.
  - **Measured.** Each step of the card (viewed, a way in tapped, the email code sent and verified, a failed join, an ask) and the join itself are recorded in the invite card funnel through `POST /v1/invites/funnel`, which also needs no account and applies the invite's chapter's analytics opt-out ([`observability.md` § Invite Card Funnel](observability.md#invite-card-funnel), #5663).
  - **Not an invite** (404): says so, and takes another link.
- **Invites waiting for the account's verified address are offered without the link (#3776).** `GET /v1/invites/mine` (signed-in, no chapter needed) returns every invite emailed to the caller's address that is still pending (not used, revoked or expired), matched case-insensitively against `invites.email`, minus chapters the caller already belongs to, one per chapter (the newest), each with the preview's fields and its token. The address is the one Supabase Auth verified for the account (`email_confirmed_at` set, on the user `SupabaseAuthGuard` fetched with the caller's token), never one the client sends; an account without one gets an empty list. Returning the token to whoever proved they read that inbox reveals nothing the invite email didn't, and hosted projects require email confirmation ([`supabase.md` § Auth settings](../../docs/ops/deployment/supabase.md#auth-settings-hosted-dashboard-or-management-api)), asserted daily on both as `auth-email-confirm`. Joining one still goes through `POST /v1/invites/redeem` with its token, so every rule above applies. Matching is exact in the API, never a SQL `like`, where PostgREST reads `*` as a wildcard. Web `/join` offers them in place of the field, which waits behind **Have a different invite?** so the invite's own Join is the one to press, with the Terms line under the offers; the page holds the field until that read settles (#5076, 2026-11-15), and mobile s02 on its question ([#3782](https://github.com/pdcarlson/Frapp/issues/3782)), each only when not opened with an invite link.
- **Redeem binds the signed-in user id, not the invite email.** `InviteService.redeem` takes the current `users.id` and the token. It does not require `users.email` to equal the address the invite was mailed to. Apple Hide My Email (`privaterelay.appleid.com`) therefore still joins when the member opens the invite after signing in.
- **The chapter hears who joined once they've named themselves (Paul, 2026-11-19, #5627).** Redeem keeps the invite on the membership (`members.joined_via_invite_id`) and sends nothing. The first `PATCH /v1/members/me/onboarding` that turns `has_completed_onboarding` on, which leaving the name and photo screen does (web `/welcome`, phone s03), sends the inviter's "accepted your invite" (only while the inviter is still in the chapter: removing a member leaves their invites working) and the officers' "<name> joined" ([`notifications.md`](notifications.md)), with the name just given. Before #5627 both went out at redeem, often as "A new member joined" or an email's first half. A member who never finishes isn't announced; a founder, and a member who joined another way, has no invite to announce.
- Clients redeem the opaque token, not the URL. Web `/join`'s field accepts a pasted raw token, a full join URL (`…/join?token=…`, `frapp://join?token=…`), or the bare join URL the web Members invite panel's `Copy link` puts on the clipboard (until 2026-11-06 it was wrapped in role and expiry lines, which the parser still accepts) and extracts via `extractInviteToken` in `@repo/validation` before `POST /v1/invites/redeem`. The phone has no field: its Paste (#5626) takes the same link or bare token through `pastedInviteToken`, which accepts only a UUID, the shape every minted invite has, so anything else on the clipboard is "That isn't a Frapp invite" rather than a dead card. Opening `/join?token=`, `/join?invite=`, or `/join?code=` opens that invite (`extractInviteTokenFromQuery`; first non-empty key wins). Officers mint `?token=` (`mintJoinUrl` in `@repo/validation`, wrapped by the web/API/mobile `buildJoinUrl` / `webJoinUrl` helpers and the Members invite panel). Minted join URLs use `https:` — a public `http:` origin throws rather than putting the token on the wire (`assertHttpsJoinOrigin`). Loopback `http:` is allowed so local Infisical `APP_URL` still works. A production process must also mint/forward `https://app.frapp.live` (`assertProductionAppOrigin`): API boot when `SUPABASE_URL` is the `frapp-prod` project, landing `/join` and CTAs when `VERCEL_ENV=production`, and a set `EXPO_PUBLIC_APP_URL` on EAS production builds. Unset production `APP_URL` / `EXPO_PUBLIC_APP_URL` still falls back to that origin. The landing `/join` redirect uses the same origin rules ([`../product/surfaces.md`](../product/surfaces.md)).

## Chapter Directory Search

`GET /chapter-directory/search?q=...&university=...` returns up to 20 matching directory entries, used by the onboarding autocomplete wizard.

- `q`: matched against the organization's name, letters and nicknames (`org_aliases`: "FIJI"), the chapter's designation, and the school's full name, short name and nicknames (`aliases`: "RPI", "Rensselaer"). Both sides are normalized alike: case and accents aside ("manoa" finds Mānoa), apostrophes dropped ("st johns"), "&" read as "and" and "A&M" as "am" too. Every word of the query must start a word of the row, so a half-typed last word still matches ("phi gamma del"); joining words (and, at, of, the, in, for) are skipped ("sigma chi at ohio state"). A word of four or more letters that starts no word anywhere in the directory may instead be a close misspelling ("renselaer"); one that starts some word is taken as typed. Only the first eight words count, and a query with more than two words that start nothing finds nothing.
- Ranking: rows that matched every word as typed come first; then rows by how much the query names outright, the organization counted double, then the chapter, then the school, where a name (or any of its nicknames) counts when it is a phrase of the query or the query is the start of it, and a one-word chapter only in the second way; then closeness; then organization, school and chapter name. `search_chapter_directory` in `20261107043000_chapter_directory_search.sql` owns the details.
- `university`: narrows to rows where a word of the school's name, short name or a nickname starts with it ("rens", "RPI"). With `university` and no `q`, the call lists that school's chapters; with neither, it returns nothing.
- A directory row a chapter links but the seed no longer lists is retired: it keeps the link and is never returned.
- Response rows: `{ id, org_letters, org_name, archetype, chapter_designation, university, university_short, founded_year, default_colors, website }`.

## After joining

When a new member joins a chapter (via invite token), two short screens come first, then the chapter itself.

### Behavior

- **After a join, two screens (Paul, 2026-11-19, #5627: "Two: name, then notifications").** First, on web (`/welcome`, `apps/web/components/onboarding/welcome-you.tsx`) and the phone (s03) alike: `How the chapter sees you`, an optional photo and the member's name. The name is pre-filled when sign-in carried a real one (Apple or Google). It starts empty when it is only the API's `Member` stand-in (stored when sign-in carried no name, as an Apple sign-up that hides its email does, and swapped for the name Apple sends once it reaches the auth metadata) or the email before the `@`, which is what an email sign-up is stored as (`displayNameForSync` in `apps/api/src/application/services/auth.service.ts`; `needsName` in `@repo/validation`), and Go to chat needs a typed name (`typedNameMissing`): any name the member types counts, even one that matches their email, since "Evan" typed by evan@ is their name. Second, on the phone only, `Turn on notifications` when the build can push and push is off ([`../ui/mobile/patterns.md`](../ui/mobile/patterns.md#push-notifications) § Push notifications). Then chat. Web goes there from a fresh join; an "already in" join and **Open chat** go straight to chat. There is no separate Skip: `Not now` and `Go to chat` are how it is skipped (#3352). Leaving `/welcome` on web PATCHes `has_completed_onboarding: true`, as leaving s03 does, so a member who joined on web skips s03 on the phone, whose chat home asks about notifications once instead (`usePushReminder` offers to a member never asked).
- What else s03 asked waits until the member wants it (#5627): the chat display in Settings → Chat density, roles in the Directory's **Add roles** and web Profile's **Your roles**, and `Meet Frapp AI` at the first use of an AI feature ([`ai.md` § Consent](ai.md#consent)). Until #5627 s03 asked the photo and name only when missing, then `Pick your chat display` (#3787), `Pick your roles` (#4958) and `Meet Frapp AI` (#4790) before notifications. Canvas s03 is the drawing.
- **Landing: the chapter's default channel, with a welcome card (Paul, 2026-11-19, #5627: "welcome card, no tour").** Chat opens on the chapter's default channel (`landingChannelId` in `@repo/hooks`: the member's last channel, else the default, else `#general`, else the first channel they can post in), on web and now the phone, whose chat home stayed on the channel list when it remembered no channel until #5627. In that channel only, never every channel the member opens, sits the welcome card (`welcome-card.tsx` on each app, copy in `WELCOME_CARD_COPY`): `Welcome to <chapter>, <first name>`, the chapter's next two events with their days written out (each opens the event), and **Finish your profile**, which opens the photo, the roles the member can join (only when there is one) and the chat display, the same controls as Profile, the Directory's Add roles and Settings. Its X closes it for good. Leaving `/welcome` or s03 marks it due for that member and chapter on that device (`lib/onboarding/welcome-due.ts` on each app) for a week (`WELCOME_CARD_DAYS`), after which it lapses unclosed; What's new sits out while it is due, so the week also bounds how long a member who never closes it misses What's new.
- **The first-run tours are gone (#5627).** Web had a spotlight tour over Chat (#5080: channels, the chat display, roles, the Chapter group, Direct messages and the avatar, revisitable from Settings → Account's **Replay tour**), and the phone a four-stop tour over chat home after s03 (2026-11-07: the top channel section, the Messages tab, the + and the You tab). Paul picked the welcome card over keeping either: the card says what's next in the chapter rather than where the controls are, and the display and roles the web tour asked now wait in Finish your profile.
- A `has_completed_onboarding` flag on the member record says whether the member has been through the screens after joining; the Directory lists a member without it as pending. On mobile the auth gate reads it from `GET /v1/chapters` and routes to s03 when the active membership's flag is false (`apps/mobile/lib/auth-gate.ts`). Leaving s03, by Go to chat or by either answer on the notifications screen, PATCHes `PATCH /v1/members/me/onboarding`. On web the dashboard sends a member whose active membership's flag is false back to `/welcome` (`WelcomeGate`, `apps/web/components/onboarding/welcome-gate.tsx`; not on Chapter settings, and not while the Terms prompt is up), as the phone's gate re-offers s03, so a member who closed the tab there, or whose finish never landed, still names themselves and is announced; the first-run tour was that net on web until #5627. Finishing is one-way: `false` is accepted and changes nothing since #5627 (its only caller, web's Replay tour, went with the tours), because a reset would let the next `true` announce the join again. Wizard-created memberships are written with the flag already true, so first officers skip s03. On mobile, setup itself carries what s03 would have: after create it shows the chapter's seeded public channels, then `Pick your chat display`, then `Meet Frapp AI` when the server has AI on and the founder has not answered it (#4790; until #5294, 2026-11-17, also when the new chapter's AI switches were never set, which no longer happens since they start on), then the `Turn on notifications` step when the build can push and push is off, then the invite step (#3351). Both setups ask the founder for their chat display once the chapter exists (#4056), with the same three cards and the device's current display preselected (Cozy on a device that never picked one), so moving on keeps it: mobile as the step after the live moment, web as the wizard's `Pick your chat display` step between create and the invite step. Neither has a way back from it to before the chapter was made.
- An authenticated mobile session with **zero** memberships is routed to s02 (`(auth)/join.tsx`), which asks **Joining a chapter?** (#3350; Paste since #5626, [§ Invite Token Rules](#invite-token-rules), the invite through an install). **Paste** opens the invite card on the invite copied before the install; **Create a chapter** opens first-officer chapter creation, `(auth)/create-chapter` (#1102). An opened invite link skips the question.

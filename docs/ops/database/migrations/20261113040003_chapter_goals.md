Adds `public.chapter_goals`, the goals officers set for points, service hours and study hours, so Activity's "This semester" block can draw each member a bar toward theirs (#1062).

## Promotion

- **Purpose**: One row per chapter and measure (`points`, `service`, `study`), holding `goals jsonb` (`{everyone, roles: [{role_id, target}]}`) plus `updated_at` and `updated_by`. Officers set them on the Points and Service hours module pages through `PUT /v1/goals/:metric`, and `GET /v1/activity/standing` reads them. Row level security is on with no policies: only the API reads or writes the table.
- **Checks**: After `db push`, `select count(*) from information_schema.tables where table_name = 'chapter_goals';` returns `1`, `select relrowsecurity from pg_class where relname = 'chapter_goals';` returns `true`, and `select count(*) from chapter_goals;` returns `0` until an officer saves a goal.
- **Promoter notes**: Ship it before, or with, the API from the same PR; a deploy applies migrations first. The older API never reads the table. The newer API against an unmigrated database fails `GET` and `PUT /v1/goals`, and the standing read reports the failure and draws no goals, so Activity still loads. It writes no data: every chapter starts with no goals.

## Rollback

A code revert needs no SQL: the API from before #1062 never reads the table, and the goals come back when the API does. Drop the table only to remove the feature for good, after reverting the API, because it loses every goal officers have set ([§ 3) Undo one migration](../../db-rollback-playbook.md#3-undo-one-migration)).

```sql
drop table if exists public.chapter_goals;
```

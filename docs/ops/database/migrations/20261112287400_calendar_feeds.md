Adds `calendar_feeds`, the private calendar subscription links members put in Apple Calendar, Google Calendar or Outlook (#3322). The rule is [`spec/behavior/events.md` § Calendar subscription](../../../../spec/behavior/events.md#calendar-subscription).

## Promotion

- **Purpose**: One row per calendar subscription link (`id`, `user_id`, `chapter_id`, `token`, `created_at`, `revoked_at`; `token` unique and at least 32 characters; at most one row with `revoked_at` null per `(chapter_id, user_id)`), cascading with the user and the chapter. RLS on, no policies (API only, service role). Adds `calendar_feeds_drop_for_deleted_user()` and the trigger `users_drop_calendar_feeds` (after `deleted_at` is first set on `users`, which `anonymize_user` does), which deletes the account's links; `anonymize_user` is not redefined. No existing row changes.
- **Checks**: After `db push`, `select relrowsecurity from pg_class where relname = 'calendar_feeds';` returns `true`, `select count(*) from pg_policies where tablename = 'calendar_feeds';` returns `0`, `select count(*) from pg_indexes where indexname in ('calendar_feeds_token_key', 'calendar_feeds_one_live_per_member');` returns `2`, and `select count(*) from pg_trigger where tgname = 'users_drop_calendar_feeds';` returns `1`.
- **Promoter notes**: Ship it before, or with, the API from the same PR; a deploy applies migrations first. The older API never reads the table. The newer API against an unmigrated database fails the three `/v1/calendar-feed` routes (500), so the Subscribe menu says it couldn't get a link; nothing else is affected. The two foreign keys and the trigger take `SHARE ROW EXCLUSIVE` on `users` and `chapters` until commit, for a few catalog statements that touch no rows. `if not exists`, `create or replace` and `drop trigger if exists` make re-applying idempotent. No data written, nothing by hand.

## Rollback

Revert the API forward and keep the migration file ([§ 3) Undo one migration](../../db-rollback-playbook.md#3-undo-one-migration)). The reverted API has no `/v1/calendar-feed` routes, so every member's subscribed calendar fails its next fetch with a 404 and keeps the last events it fetched, frozen, until the API ships again (calendar apps keep their copy when a fetch fails). Rows written before the revert stay, so the same links work again once the API is back. The trigger keeps deleting a deleted account's links, which is harmless.

Keep the table unless it is itself the problem. Dropping it ends every member's subscription for good: their links answer 404 even once the API ships again, and each member has to subscribe anew. To remove it, after the code revert has shipped, in a later forward migration:

```sql
drop trigger if exists users_drop_calendar_feeds on public.users;
drop function if exists public.calendar_feeds_drop_for_deleted_user();
drop table if exists public.calendar_feeds;
```

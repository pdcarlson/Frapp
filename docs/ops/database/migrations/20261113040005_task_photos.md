Adds task photos (#4565): three columns on `tasks` and the private `tasks` storage bucket. The rule is [`spec/behavior/tasks.md` § Photos](../../../../spec/behavior/tasks.md#photos).

## Promotion

- **Purpose**: `tasks` gains `reference_photo_path text` (null), `proof_photo_path text` (null) and `photo_required boolean not null default false`; every existing row reads as no photos and no requirement. Two partial unique indexes, `tasks_reference_photo_path_key` and `tasks_proof_photo_path_key` (each `where … is not null`), hold one stored object to one task. Declares the private `tasks` bucket: `public = false`, `allowed_mime_types` JPEG, PNG, GIF and WebP, `file_size_limit` 26214400 (25MB). No storage policies: reads and writes go through API-signed URLs.
- **Checks**: After `db push`, `select count(*) from information_schema.columns where table_name = 'tasks' and column_name in ('reference_photo_path', 'proof_photo_path', 'photo_required');` returns `3`, and `select public, allowed_mime_types, file_size_limit from storage.buckets where id = 'tasks';` returns `false`, the four image types and `26214400`, and `select count(*) from pg_indexes where indexname in ('tasks_reference_photo_path_key', 'tasks_proof_photo_path_key');` returns `2`.
- **Promoter notes**: Ship it before, or with, the API from the same PR; a deploy applies migrations first. The older API reads `select *` and ignores the new columns. The newer API against an unmigrated database fails task writes that name the new columns and every photo route. Adding a nullable column and a column with a constant default is a catalog change in Postgres 11+ and rewrites no rows; the `ALTER` takes `ACCESS EXCLUSIVE` on `tasks` for that instant. The two indexes are built plainly (not `concurrently`), which holds `SHARE` on `tasks` while they scan the table; every value is null, so they index nothing. `if not exists` and the bucket's `on conflict` update make re-applying idempotent. No data written, nothing by hand.

## Rollback

Revert the API forward and keep the migration ([§ 3) Undo one migration](../../db-rollback-playbook.md#3-undo-one-migration)). The reverted API ignores the columns, so tasks lose their photos and the "Photo required" switch stops being enforced until the API ships again; the rows and objects stay and come back with it.

Keep the columns and the bucket unless they are themselves the problem. Dropping them loses every task photo for good. To remove them, after the code revert has shipped, in a later forward migration:

```sql
drop index if exists public.tasks_reference_photo_path_key;
drop index if exists public.tasks_proof_photo_path_key;
alter table public.tasks
  drop column if exists reference_photo_path,
  drop column if exists proof_photo_path,
  drop column if exists photo_required;
```

Then empty and remove the `tasks` bucket through the Storage API or the dashboard, not in SQL: a raw `delete from storage.buckets` is refused by `protect_buckets_delete` (42501) and would abort the migration with it, as the [playbook](../../db-rollback-playbook.md) records for `chat-archive` and `meeting-audio`.

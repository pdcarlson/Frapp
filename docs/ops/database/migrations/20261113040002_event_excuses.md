Adds `event_excuses`, members' requests to be excused from an event that requires them, and the two functions that decide and withdraw one atomically with the attendance it implies (#3735). The rule is [`spec/behavior/events.md` § Excuses](../../../../spec/behavior/events.md#excuses).

## Promotion

- **Purpose**: One row per `(event_id, user_id)`: `reason` (1 to 500 characters), `status` (`PENDING`, `APPROVED`, `DECLINED`), `decided_by`, `decided_at`, cascading with the chapter, the event and the user. RLS on, no policies (API only, service role). `decide_event_excuse(uuid, uuid, text, uuid, boolean)` moves a pending excuse to a decision and, in the same transaction, writes `event_attendance` `EXCUSED` on approval (over `ABSENT` or `EXCUSED` only) or `ABSENT` on a late decline when asked. `withdraw_event_excuse(uuid, uuid, uuid)` deletes a pending or approved excuse, and an approved one's `EXCUSED` attendance row. Both are executable by the service role only. No existing row changes.
- **Checks**: After `db push`, `select relrowsecurity from pg_class where relname = 'event_excuses';` returns `true`, `select count(*) from pg_policies where tablename = 'event_excuses';` returns `0`, and `select count(*) from pg_proc where proname in ('decide_event_excuse', 'withdraw_event_excuse');` returns `2`.
- **Promoter notes**: Ship it before, or with, the API from the same PR; a deploy applies migrations first. The older API never reads the table. The newer API against an unmigrated database fails the `/v1/events/:eventId/excuses` routes (500), and the hourly auto-absent sweep fails its excuse read for each event and releases its claim to retry the next hour, so nobody is marked absent until the migration lands. The foreign keys take `SHARE ROW EXCLUSIVE` on `chapters`, `events` and `users` until commit, for a few catalog statements that touch no rows. `if not exists`, `create or replace` and `drop trigger if exists` make re-applying idempotent. No data written, nothing by hand.

## Rollback

Revert the API forward and keep the migration file ([§ 3) Undo one migration](../../db-rollback-playbook.md#3-undo-one-migration)). The reverted API has no excuse routes and its sweep marks every required member without a row absent again, including anyone whose excuse was still pending; approved excuses already wrote their `EXCUSED` attendance rows, which stay. Rows written before the revert stay, so pending excuses come back if the API ships again.

Keep the table unless it is itself the problem. Dropping it loses every pending and decided excuse (the `EXCUSED` attendance rows from approvals stay). To remove it, after the code revert has shipped, in a later forward migration:

```sql
drop function if exists public.withdraw_event_excuse(uuid, uuid, uuid);
drop function if exists public.decide_event_excuse(uuid, uuid, text, uuid, boolean);
drop table if exists public.event_excuses;
```

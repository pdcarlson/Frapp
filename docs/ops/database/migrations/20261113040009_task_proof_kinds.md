Task proof kinds and several photos (#4635): `tasks.proof_kind` replaces #4565's `photo_required`, photos move from two single-path columns into a `task_photos` table, and `tasks` gains `proof_link`, `sent_back_reason` and `completion_note`. The rule is [`spec/behavior/tasks.md` § Photos](../../../../spec/behavior/tasks.md#photos).

## Promotion

- **Purpose**: `tasks` gains `proof_kind text not null default 'none'` (check `none|photo|link`), `proof_link text` (http/https, at most 2048 characters), `sent_back_reason text` (at most 200) and `completion_note text` (at most 500). New table `task_photos` (`id`, `task_id`, `chapter_id`, `kind` `reference|proof`, `storage_path` unique, `position`, `created_by`, `created_at`), RLS on with no policies. Every `reference_photo_path` and `proof_photo_path` is copied into it at position 0, every `photo_required = true` becomes `proof_kind = 'photo'`, every completion still waiting with no points and no proof is signed off (`confirmed_at = completed_at`, `points_awarded = true`, nothing paid: decision C applied to what's already waiting), and then the two indexes `tasks_reference_photo_path_key` and `tasks_proof_photo_path_key` and the three columns `reference_photo_path`, `proof_photo_path`, `photo_required` are dropped.
- **Checks**: After `db push`, `select count(*) from information_schema.columns where table_name = 'tasks' and column_name in ('reference_photo_path', 'proof_photo_path', 'photo_required');` returns `0`; `select count(*) from information_schema.columns where table_name = 'tasks' and column_name in ('proof_kind', 'proof_link', 'sent_back_reason', 'completion_note');` returns `4`; and `select kind, count(*) from public.task_photos group by kind;` matches how many tasks had each photo before the push (take that count first: `select count(reference_photo_path), count(proof_photo_path), count(*) filter (where photo_required) from public.tasks;`).
- **Promoter notes**: Ship it with the API from the same PR; a deploy applies migrations first. Between the migration and the new API going live, the older API's task create and edit fail (they name `photo_required` and `reference_photo_path`), and its task reads still work (`select *`), so keep that window short. It writes data: one insert per photo, one update per photo-required task, and one per waiting completion with no points and no proof, all small (task photos shipped on 2026-11-12). The `ALTER`s take `ACCESS EXCLUSIVE` on `tasks` briefly; the check constraints scan `tasks` once to validate. `if not exists`, `drop … if exists` and the guarded backfill make re-applying idempotent. Nothing by hand.

## Rollback

Revert the API forward and keep the migration ([§ 3) Undo one migration](../../db-rollback-playbook.md#3-undo-one-migration)). A reverted API still names the dropped columns, so reverting the code alone needs the columns back first. In a later forward migration:

```sql
alter table public.tasks
  add column if not exists reference_photo_path text,
  add column if not exists proof_photo_path text,
  add column if not exists photo_required boolean not null default false;
update public.tasks t set reference_photo_path = p.storage_path
  from public.task_photos p
  where p.task_id = t.id and p.kind = 'reference' and p.position = 0;
update public.tasks t set proof_photo_path = p.storage_path
  from public.task_photos p
  where p.task_id = t.id and p.kind = 'proof' and p.position = 0;
update public.tasks set photo_required = true where proof_kind = 'photo';
create unique index if not exists tasks_reference_photo_path_key
  on public.tasks (reference_photo_path) where reference_photo_path is not null;
create unique index if not exists tasks_proof_photo_path_key
  on public.tasks (proof_photo_path) where proof_photo_path is not null;
```

Completions it signed off stay Done; the old API reads them as confirmed. Photos past the first of each kind, link proof, send-back reasons and replies have no home in the old shape; keep `task_photos` and the new columns so they come back when the API ships again.

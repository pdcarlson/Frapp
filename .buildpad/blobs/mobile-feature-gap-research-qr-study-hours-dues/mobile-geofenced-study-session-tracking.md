# Geofenced study-session tracking on Expo: build it foreground-only, verify-on-tap, and never touch background location

**Recommendation up front: build this as a foreground-only feature.** When a member starts a study session, request *foreground* ("When In Use") location permission, do a one-shot location check against the chapter's defined zones to gate the session start, then poll every few minutes with `watchPositionAsync`/`getCurrentPositionAsync` *only while the app is open and the session is active*. Do **not** use `startGeofencingAsync`, do **not** request background/"Always" location, and do **not** add the background-location config flags. This mirrors your web heartbeat model almost exactly, avoids the single most common location-related App Store/Play Store rejection path, and is precisely how comparable geofenced attendance and workout apps actually work. Every piece of the research — Expo's own documentation, Apple and Google policy, and real deployed apps — independently supports this same conclusion.

## Why background geofencing is the wrong tool here

The command asks whether true OS-level geofencing (`startGeofencingAsync`, region enter/exit callbacks that fire while backgrounded) is necessary. It is not, and adopting it would actively hurt you on three fronts.

**It doesn't reliably do what you'd want anyway.** OS geofencing is documented as unreliable for the exact event you'd care about — a student leaving the zone. Practitioners measure "less than 50% of zone exits detected on average," with zone-exit less reliable than zone-enter [stackoverflow](https://stackoverflow.com/questions/59502937/will-geofence-reduce-power-consumption-vs-just-checking-location-every-x-seconds). Android's geofencing is widely reported as flaky, degrading under power-saving mode and depending on Wi-Fi being on [simpleinout](https://simpleinout.helpscoutdocs.com/article/232-my-geofences-arent-working-android). Expo's own GitHub issues report geofencing failing when the app is killed [github](https://github.com/expo/expo/issues/5383) and stopping when the app crashes or is force-quit [github](https://github.com/expo/expo/issues/20252). And there are hard platform limits: **iOS monitors at most 20 regions simultaneously** [apple](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/RegionMonitoring/RegionMonitoring.html), with a practical minimum radius near 200m on iOS [apple](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/RegionMonitoring/RegionMonitoring.html) and ~100m recommended on Android [android](https://developer.android.com/develop/sensors-and-location/location/geofencing).

**The terminated-app behavior is worse than the web.** Expo documents that "background location will stop if the user terminates the app," and on **Android a terminated app will not automatically restart** when a geofence event occurs [expo](https://docs.expo.dev/versions/latest/sdk/location/). So background geofencing wouldn't even give you robust "left the zone" detection when a student swipes the app away — the failure mode you'd be adding complexity to solve.

**It triggers the review scrutiny you want to avoid** (next section). For a "verify presence during an active, user-initiated session" use case, background execution is both unnecessary and a liability. Every comparable app category studied reached the same verdict — see the validation section.

## The permission model and the exact config difference between the two approaches

Expo's permission model is a two-step ladder. `requestForegroundPermissionsAsync()` asks for access "while the app is in the foreground" and maps to iOS **"When In Use"**; `requestBackgroundPermissionsAsync()` maps to iOS **"Always"** [expo](https://docs.expo.dev/versions/latest/sdk/location/). Foreground must be granted first — "your app can't obtain background permission without foreground permission" [expo](https://docs.expo.dev/versions/latest/sdk/location/). Critically, `watchPositionAsync` **"updates will only occur while the application is in the foreground"** [expo](https://docs.expo.dev/versions/latest/sdk/location/) — which is exactly the behavior you want, and it means the foreground-only approach needs only foreground permission.

The config difference is the whole point. **The foreground approach requires none of the background machinery:**

| Config artifact | Foreground-only (recommended) | Background geofencing (avoid) |
|---|---|---|
| iOS purpose string | `locationWhenInUsePermission` → `NSLocationWhenInUseUsageDescription` [expo](https://docs.expo.dev/versions/latest/sdk/location/) | Also needs `locationAlwaysAndWhenInUsePermission` → `NSLocationAlwaysAndWhenInUseUsageDescription` [expo](https://docs.expo.dev/versions/latest/sdk/location/) |
| iOS background mode | Not needed | `isIosBackgroundLocationEnabled: true` adds `location` to `UIBackgroundModes` [expo](https://docs.expo.dev/versions/latest/sdk/location/) |
| Android permissions | `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` (added automatically by the module) [expo](https://docs.expo.dev/versions/latest/sdk/location/) | Also `isAndroidBackgroundLocationEnabled: true` → `ACCESS_BACKGROUND_LOCATION`, which also defaults a foreground service on [expo](https://docs.expo.dev/versions/latest/sdk/location/) |
| Permission function | `requestForegroundPermissionsAsync()` only | Also `requestBackgroundPermissionsAsync()` |
| TaskManager | Not needed | Required — task must be defined in global scope via `TaskManager.defineTask` [expo](https://docs.expo.dev/versions/latest/sdk/task-manager/) |

The foreground-only path leaves off every background flag, keeps you to a single "While Using the App" prompt, and never opens the Play Console background-location declaration process.

## Why background/"Always" location is the rejection minefield — and foreground-only sidesteps it entirely

This is the highest-stakes part of the decision, and the asymmetry is stark.

**Google Play imposes a formal gauntlet on background location.** If background location "is not important to the app's core functionality," Google requires you to remove it or "implement location access in the foreground" [google](https://support.google.com/googleplay/android-developer/answer/9799150?hl=en). Background access requires a permission-declaration review that includes **a demonstration video (≤30s) showing the prominent-disclosure dialog and the runtime prompt**, evaluates **only one feature at a time**, and mandates a prominent disclosure — appearing *before* the runtime prompt — that includes the word "location," a background phrase ("when the app is closed"/"always in use"), and the template sentence *"This app collects location data to enable [feature]… even when the app is closed or not in use"* [google](https://support.google.com/googleplay/android-developer/answer/9799150?hl=en). Developer accounts describe repeated rejections: "Prominent disclosure not found," "does not meet requirements for background location access," and rejections even after removing the permission because a library re-added it in the merged manifest [stackoverflow](https://stackoverflow.com/questions/79087290/background-location-enabled-for-my-app-play-store-rejected-my-app-update-how-t) [github](https://github.com/transistorsoft/react-native-background-geolocation/issues/1149) [stackoverflow](https://stackoverflow.com/questions/66796529/android-app-is-rejected-by-google-because-of-background-location). The recurring resolution in these threads is to drop background location and refactor to foreground-only.

**Apple's guidelines cut the same way.** Guideline **5.1.1(iii) Data Minimization** says apps should "only request access to data relevant to the core functionality" and "only collect and use data required" [apple](https://developer.apple.com/app-store/review/guidelines/), and **5.1.5** says to use Location Services "only when directly relevant to the features… provided" [apple](https://developer.apple.com/app-store/review/guidelines/). Requesting "Always" for a feature that only operates during an active, foregrounded session is exactly the over-collection reviewers flag. Additionally, iOS periodically re-notifies users when an app accesses location in the background under "Always" [apple](https://www.apple.com/privacy/docs/Location_Services_White_Paper_Nov_2019.pdf) — a recurring friction and trust hit even if approved. (Note: Apple's public guidelines don't spell out an explicit "Always is reviewed more strictly than When In Use" rule; the elevated scrutiny is indirect, flowing from minimization plus the extra user-facing background notifications [apple](https://developer.apple.com/app-store/review/guidelines/).)

**Foreground-only avoids all of it.** No Play declaration form, no demo video, no prominent-disclosure dialog requirement, no Apple minimization argument to win, no periodic background-tracking notifications. You request a single "While Using the App" permission tied to a visible user action.

### Permission copy and timing (hand this verbatim to the coding agent)

Both platforms want **contextual, incremental** requests. Android explicitly says to "wait until the user interacts with the feature" and to request foreground first [android](https://developer.android.com/develop/sensors-and-location/location/permissions/runtime); Apple's minimization stance rewards the same [apple](https://developer.apple.com/app-store/review/guidelines/). Apple's own guidance on purpose strings: state *specifically how* the data is used and give *an example*; "To use location" is called out as too vague [apple](https://developer.apple.com/videos/play/tech-talks/110152/). A developer who was rejected under 5.1.1 for vague copy got approved after rewriting it to be specific with concrete examples [reddit](https://www.reddit.com/r/iOSProgramming/comments/1s0nb97/got_rejected_by_the_app_store_5_times_before/).

Concrete copy for Signet:
- **iOS `NSLocationWhenInUseUsageDescription`:** *"Signet uses your location while you have a study session open to confirm you're studying inside one of your chapter's study zones and to credit your study hours. Location is only checked while the app is open and a session is active."*
- **Timing:** Do not prompt on app launch or on the study screen render. Prompt only when the member taps **"Start study session,"** after a brief in-app primer sheet ("To verify you're in a study zone, Signet needs your location while a session is running."). Then call `requestForegroundPermissionsAsync()`. This in-context primer both raises grant rates and satisfies the "relevant to core functionality" test.
- On iOS, note the "Allow Once" quirk: it grants When-In-Use for the session and cannot be distinguished from "While Using" [expo](https://docs.expo.dev/versions/latest/sdk/location/) — which is fine for a session-scoped feature.

## Session pause/resume/end on backgrounding — the fair-to-students design

This is the mobile equivalent of your web "pause on tab hidden, resume on visible," and the honest behavior matters. Use React Native's `AppState`, which exposes `active`, `background`, and (iOS-only) `inactive` [reactnative](https://reactnative.dev/docs/appstate). Subscribe with `AppState.addEventListener('change', handler)`; the canonical "returned to foreground" detection is a transition from `inactive`/`background` to `active` [reactnative](https://reactnative.dev/docs/appstate).

**Two hard constraints from the platform shape the design:**

1. **JS timers and location watchers stop in the background.** `setInterval` is paused/suspended when the app is backgrounded or the screen is locked on iOS [stackoverflow](https://stackoverflow.com/questions/53275004/javascript-setinterval-paused-when-screen-is-locked-ios) [github](https://github.com/facebook/react-native/issues/38711), and `watchPositionAsync` explicitly only fires in the foreground [expo](https://docs.expo.dev/versions/latest/sdk/location/). So you **cannot** count elapsed time by ticking a counter. **Persist a wall-clock start timestamp** (`Date.now()`) and compute `elapsed = now − start` (minus paused intervals) whenever the app returns to `active` [medium](https://aloukissas.medium.com/how-to-build-a-background-timer-in-expo-react-native-without-ejecting-ea7d67478408). This also makes the timer robust across the background gap.

2. **Force-quit is not reliably detectable.** iOS treats force-quit as user intent and won't relaunch your app in the background; a suspended app gets no termination callback [apple](https://developer.apple.com/forums/thread/685525). So you cannot rely on catching an "app killed" event to close a session cleanly.

**Recommended session state machine (fair, not punitive):**

- **On background / lock:** Do *not* immediately end the session. Record a `backgroundedAt` timestamp and **pause the accrual clock**. A student checking a notification for 20 seconds should not lose their session — this is the core fairness requirement in the command.
- **On return to `active`:** If the gap was under a **grace threshold (e.g., 3–5 minutes)**, silently resume and continue accruing. If the gap exceeded the threshold, **re-verify location** with a one-shot `getCurrentPositionAsync`: if still in a zone, resume; if not, end the session at `backgroundedAt` (credit time up to when they left, not beyond).
- **On force-quit / never-returns:** Because you can't catch termination, cap credited time server-side. Persist the last confirmed in-zone timestamp; on the next app open (or via a server-side stale-session sweep), **close any dangling session at the last confirmed-present heartbeat**, not at the current time. This mirrors your web heartbeat's implicit "no ping = session ended" logic and prevents inflated hours from an app left running.
- **While foreground + active:** Poll on your heartbeat cadence (match the web's 5-minute interval) with `getCurrentPositionAsync` at `Accuracy.Balanced`. Each successful in-zone ping updates "last confirmed present." An out-of-zone ping triggers a grace check before ending.

This gives you honest accounting (time credited only while confirmed present) without falsely ending sessions for brief phone glances.

## Battery and OS-throttling: foreground polling is cheap; background is where the drain lives

Battery cost is driven by accuracy, frequency, and latency [android](https://developer.android.com/develop/sensors-and-location/location/battery). Your design minimizes all three: it only runs in the foreground, polls on a multi-minute interval, and needs only `Accuracy.Balanced` (~100m, typically Wi-Fi/cell rather than continuous GPS) [expo](https://docs.expo.dev/versions/latest/sdk/location/) — study zones are building-sized, so you don't need `High`/`BestForNavigation`. Apple's own energy guidance is "reduce accuracy whenever possible" [apple](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/LocationBestPractices.html). The heavy drain reports in the wild are all from *background* geofencing running continuously — e.g., users reporting 20% in 4 hours and 35% over 10 hours, resolved by disabling geofencing [arlo](https://community.arlo.com/t5/Arlo-Pro-2/Arlo-Android-amp-IOS-App-drains-phone-battery-when-in-geofencing/m-p/1690488) [reddit](https://www.reddit.com/r/EufyCam/comments/16jim7f/geofencing_is_a_terrible_mobile_battery_drain/). Foreground-only, session-scoped polling never incurs that class of cost.

On throttling: you also dodge Android 14's foreground-service-type requirements, since a location foreground service targeting Android 14+ must declare `foregroundServiceType="location"` and satisfy runtime prerequisites, and cannot even be started from the background without `ACCESS_BACKGROUND_LOCATION` [android](https://developer.android.com/develop/background-work/services/fgs/service-types). None of that applies to foreground-only watching. (I couldn't find a discrete "iOS 18 / Android 15 changed location behavior in X way" document; but because your approach never runs in the background, these deltas don't affect the recommendation — moderate confidence on the absence of a material 2025-2026 change for foreground use.)

## Comparable apps validate this exactly

The strongest external confirmation is that the apps most similar to your use case — geofenced attendance/clock-in — overwhelmingly **verify location at the moment of the punch (a foreground one-shot), not via continuous background monitoring.** TimeClick checks GPS only at clock-in and "does not monitor employee location between punches" [timeclick](https://timeclick.com/geofencing-time-clock-software/). ClockIt captures location "only at the time of clock in and clock out," with continuous tracking optional and off by default [clockit](https://get.clockit.io/features/location-tracking). Open Time Clock "verif[ies] the location of an employee when they attempt to clock in" [opentimeclock](https://www.opentimeclock.com/docs/blog2/november-2025/geofencing-time-clock-app-prevent-time-fraud-with-location-tracking). An attendance-app best-practices guide explicitly recommends "check location only at clock-in and clock-out unless there is a clear business reason" [dayoff](https://day-off.app/geofenced-time-attendance-app/).

For a study session — which *is* a duration, unlike a punch — the right adaptation is: verify at start (gate), then confirm on a foreground heartbeat while active, then close on the last confirmed heartbeat. Fitness apps that do track continuously during a session keep a **foreground service running for the duration of the workout** rather than relying on background geofencing [android](https://developer.android.com/health-and-fitness/health-services/active-data), and even Google Fit offers "only while using the app" as a valid mode . The permission-friction lesson is real too: forcing "Always" background location generates strong negative user sentiment even when justified (Fitbit users called it "spyware") [fitbit](https://community.fitbit.com/t5/Product-Feedback/Remove-requirement-to-allow-Background-Location-Permission/idi-p/5460783) — a reputational cost for a small chapter app you don't want.

## Concrete build spec for the AI coding agent

New Expo screen (`StudySessionScreen`), reusing the officer-defined zones already available from the admin feature:

1. **Dependencies/config:** Add `expo-location`. In app config, set only `locationWhenInUsePermission` (iOS) with the copy above. **Do not** set `isIosBackgroundLocationEnabled` or `isAndroidBackgroundLocationEnabled`. No `TaskManager`, no `startGeofencingAsync`.
2. **Start flow:** Tap "Start" → show primer sheet → `requestForegroundPermissionsAsync()` → if granted, `getCurrentPositionAsync({accuracy: Balanced})` → run the existing point-in-zone check against the chapter's geofence definitions (reuse the same logic/shape the web uses). In-zone → create session with server `startedAt` timestamp. Out-of-zone → block with "You need to be inside a study zone to start" (mirror Item.com's relocate prompt pattern ).
3. **Active loop:** While `AppState === 'active'` and session open, poll every 5 min (match web) via `getCurrentPositionAsync`; each in-zone ping POSTs a heartbeat updating "last confirmed present"; out-of-zone ping starts the grace check.
4. **AppState handler:** On `background`/`inactive`→ store `backgroundedAt`, pause accrual. On →`active`, compute gap: <5min silent resume; ≥5min re-verify location and resume or end at `backgroundedAt`.
5. **Duration:** Wall-clock (`serverStartedAt` → last confirmed heartbeat), never a JS tick counter.
6. **Server safety net:** A stale-session sweep closes any session with no heartbeat for >2 intervals at its last heartbeat time — handling force-quit, which is undetectable client-side [apple](https://developer.apple.com/forums/thread/685525).
7. **Points/requirements:** Feed the computed confirmed-present duration into the **existing web points-award and requirement-tracking logic** unchanged — the mobile screen only produces the same "verified minutes in zone" input the web already consumes.

## Where more research would sharpen this

Two areas could refine (but not overturn) the plan. First, **the exact anti-spoofing posture**: this design verifies GPS presence but doesn't address GPS spoofing/mock-location — if study-hour integrity becomes contested, investigate `expo-location`'s `mocked` flag and Android mock-location detection as a follow-up. Second, **the grace-threshold and heartbeat-cadence values** (5-min interval, 3-5 min grace) are reasoned from the web mirror and fairness, not from tested student behavior; a short beta with your own chapter would calibrate whether students routinely background the app longer than the grace window (e.g., during long library sessions where the phone locks), which might argue for a longer grace period or a foreground-service-backed "keep session alive while locked" mode — the one scenario that could justly reconsider (Android-only) foreground-service location later, without ever touching background geofencing.

# Rotating-QR event check-in for Signet: mechanism, library, UX, and an end-to-end build spec

**Build the rotating code as a short-lived server-signed token, not a client-side TOTP: the Signet API mints a fresh signed token every ~30 seconds, the organizer's phone/screen polls and displays it as a standard dark-on-light QR, and the member's Expo app scans it and POSTs the token plus the device's current GPS coordinates back to the API, which verifies the signature, the expiry window, single-use, chapter/event membership, and — the real anti-proxy backstop — that the scan happened inside the event's geofence.** Rotation alone stops a screenshot from being reused later; geofencing is what stops a member from texting a live code to an absent brother in his dorm. On the client side, use `expo-camera`'s built-in `CameraView` barcode scanner — the old `expo-barcode-scanner` package was deprecated in SDK 50 and removed in SDK 51, so it is not an option [expo](https://expo.dev/changelog/2024-11-12-sdk-52). This maps cleanly onto Signet's existing stack: a Supabase RPC/NestJS endpoint pair (you already have geofence infrastructure from study hours), a Next.js "present the QR" screen, and an Expo scan sheet.

Note on current state: the older Claude-Code codebase summary claims QR attendance is already built (`attendance.service.ts`, RPC `check_in_event`), but the newer grounded audit says it "does not exist anywhere." Treat QR check-in as greenfield, but **have the agent first grep for `check_in_event` and `attendance.service`** — if a stub RPC or a `check_in_event` signature already exists, extend it rather than duplicating, since the event and points modules it would write into are real.

## The rotation mechanism: interval and TOTP-vs-server-push

**Real systems rotate fast — between 10 and 30 seconds for anti-sharing use cases.** Ticketmaster's SafeTix rotating barcode "automatically refreshes every 15 seconds," and screenshots/printouts are explicitly rejected at the gate [mlb](https://www.mlb.com/padres/tickets/safetix) [ticketmaster](https://www.ticketmaster.com/safetix); an engineering teardown confirms "it updates the PDF417 barcode every 15 seconds, so even if you take a screenshot… it will immediately become invalid" [gigazine](https://gigazine.net/gsc_news/en/20240710-ticketmaster-safetix-ticket/). In the academic attendance literature, one dynamic-QR-plus-geofence system refreshes every 20 seconds [thesai](https://thesai.org/Downloads/Volume14No4/Paper_104-Fraud_Mitigation_in_Attendance_Monitoring_Systems.pdf), a commercial dynamic-QR attendance product rotates every 10 seconds [palgeo](https://palgeo.com/dynamic-secured-qr-code-linked-geofencing-attendance-system/), and a multi-factor QR+OTP system refreshes every 60–90 seconds [ijert](https://www.ijert.org/attendify-a-cloud-based-multi-factor-attendance-system-using-qr-code-facial-recognition-and-geofencing-ijertv15is040611). **Recommend ~30 seconds for Signet**: fast enough that a photo shared to a group chat is dead before an absent member can act on it, slow enough that a member fumbling to open the app still catches a live code. Because geofencing is your true anti-proxy layer, you don't need SafeTix's aggressive 15s.

**Two implementation models exist; use the server-signed-token model, not true TOTP.** SafeTix is effectively TOTP: its barcode carries a static bearer token plus two 6-digit values that "behave a lot like Time-based One-Time Passwords… generated from a shared secret and a timestamp" on a 15-second step, validated server-side against secrets (`eventKey`, `customerKey`) stored in Ticketmaster's database [conduition](https://conduition.io/coding/ticketmaster/). True TOTP's advantage is offline generation, but it requires distributing a per-event shared secret to the organizer's device and tolerating clock drift. RFC 6238 requires the verifier to allow a bounded number of time-step drifts and — critically — "MUST NOT accept the second attempt of the OTP after the successful validation has been issued for the first OTP" [datatracker](https://datatracker.ietf.org/doc/html/rfc6238). For an app that is online at the event, the simpler and safer pattern is a **server-signed, short-TTL token**: mint a token with an HMAC-SHA256 signature, an issued-at, and a TTL, then `verify()` the signature + expiry + optional single-use on scan — exactly the pattern the AdmitiQ token library documents ("The first scan succeeds; every repeat fails") [admitiq](https://admitiq.logiclitz.org/). The organizer's phone simply polls the API for the current token every 30s (a developer's own summary of "automatic refresh for QR code" is that you "need a server-side solution to generate a new QR code every few seconds while making previous ones invalid" [reddit](https://www.reddit.com/r/webdev/comments/1j50v10/automatic_refresh_for_qr_code/)). This keeps all secrets server-side, needs no client clock sync, and reuses your existing NestJS/Supabase auth.

**Server-side validation checklist** (mirrors what the academic system checks before approval — that the "QR code ID has expired" and that "the student has already marked attendance" [thesai](https://thesai.org/Downloads/Volume14No4/Paper_104-Fraud_Mitigation_in_Attendance_Monitoring_Systems.pdf)): valid HMAC signature → token not expired (with a small grace window for the rotation boundary, e.g. accept the current and immediately-previous token) → token belongs to this event → scanning user is a chapter member eligible for this event → user has not already checked in → scan coordinates fall inside the event geofence. Reject with a specific reason for each failure.

## Anti-proxy: stopping check-in on behalf of an absent member

The rotating code and the geofence attack different halves of the proxy problem, and you need both. **Rotation invalidates a shared/photographed code**: the academic system notes that "in the unlikely event that geofencing functions are circumvented, the time-sensitive QR serves to invalidate any shared QR code" [thesai](https://thesai.org/Downloads/Volume14No4/Paper_104-Fraud_Mitigation_in_Attendance_Monitoring_Systems.pdf). **Geofencing enforces physical presence**: registration is "available only within a defined geofenced area" [thesai](https://thesai.org/Downloads/Volume14No4/Paper_104-Fraud_Mitigation_in_Attendance_Monitoring_Systems.pdf), and you already have geofence setup (`study-geofence.repository.ts`) and location-permission handling from the study-hours module — reuse it. Send the member's `expo-location` coordinates in the check-in POST and validate server-side against the event's geofence polygon/radius. Best practice is to read location only at the moment of the scan, not continuously in the background, matching how geofenced attendance tools scope location to "only while using the app… during clock events or on entering a geofencing zone" [calamari](https://www.calamari.io/attendance-tracking/geofencing).

Two more controls, one usable and one not:

- **Rotation-window requirement (use it):** because you validate expiry server-side, the scan must complete within the ~30s window — a code photographed and sent to a friend is likely dead on arrival, and combined with geofence the friend is out of range anyway. This is free once rotation + expiry are implemented.
- **Device/IMEI binding (do not use it):** the academic system binds attendance to a stored device IMEI [thesai](https://thesai.org/Downloads/Volume14No4/Paper_104-Fraud_Mitigation_in_Attendance_Monitoring_Systems.pdf), but modern iOS and Android no longer expose IMEI to third-party apps, so this is not implementable in Expo. The closest safe substitute is binding the check-in to the authenticated Signet session (the token is redeemed against the logged-in user's JWT), which you get for free — a member would have to hand their unlocked, logged-in phone to a proxy, which defeats the casual "text me the code" attack.

No source established a hard requirement that the app be *foregrounded* specifically; in practice the Expo camera can only scan while the scanner screen is mounted and focused, so foreground scanning is enforced structurally rather than as an explicit check.

## Scanning library and camera permissions (Expo, 2025–2026)

**Definitive: use `expo-camera`'s `CameraView`. `expo-barcode-scanner` is gone** — "deprecated in SDK 50 and slated for removal in SDK 51," with the official migration guide stating it "is deprecated in favor of using the built in scanner in `expo-camera`" [expo](https://expo.dev/changelog/2024-11-12-sdk-52) [github](https://github.com/expo/fyi/blob/main/barcode-scanner-to-expo-camera.md). Configure QR-only scanning with `barcodeScannerSettings={{ barcodeTypes: ['qr'] }}` and handle results via `onBarcodeScanned={(result) => …}`, where `result` carries `type` and `data` [expo](https://docs.expo.dev/versions/latest/sdk/camera/).

**Critical gotcha — the callback fires repeatedly.** Developers report the scan callback firing "3–5 codes… at once in a millisecond" [github](https://github.com/expo/expo/issues/25160). The official mitigation is to gate the callback on a `scanned` state flag: `onBarcodeScanned={scanned ? undefined : handleBarcodeScanned}`, flip `scanned = true` on first read, and re-enable after handling [github](https://github.com/expo/fyi/blob/main/barcode-scanner-to-expo-camera.md). Also unmount or set `active={false}` on `CameraView` when the screen loses focus — "only one Camera preview can be active at any given time" [expo](https://docs.expo.dev/versions/latest/sdk/camera/). Minor platform gotchas: iOS sometimes needs the barcode type spelled carefully [stackoverflow](https://stackoverflow.com/questions/78845383/expo-camera-onbarcodescanned-doesnt-work-with-ios-devices), and the callback was renamed from `onBarCodeScanned` to `onBarcodeScanned` in SDK 51 [stackoverflow](https://stackoverflow.com/questions/78759848/qr-code-scanning-with-expo-v-51-is-not-working).

**Permissions and priming.** Use the `useCameraPermissions()` hook, which returns a permission object with `granted`, `status`, and `canAskAgain` [expo](https://docs.expo.dev/versions/latest/sdk/camera/). Configure the `expo-camera` config plugin with a `cameraPermission` string (this becomes iOS `NSCameraUsageDescription`; iOS crashes if you request the camera without it) [expo](https://docs.expo.dev/versions/latest/sdk/camera/) [expo](https://expo-expo.mintlify.app/guides/permissions). Follow Expo's own priming guidance: **request in context** (when the member taps "Check in," not on app launch) and **explain why first** with an in-app screen — Expo's example literally shows "We need access to your camera to… Scan QR codes" above the grant button [expo](https://expo-expo.mintlify.app/guides/permissions). When permission is permanently denied (`canAskAgain === false`), route the user to system settings via `Linking.openSettings()` [expo](https://expo-expo.mintlify.app/guides/permissions). This priming pattern fits Signet's onboarding philosophy of "permission priming in-context, not on launch" already recorded in the onboarding research.

## Organizer display UX and QR technicals (hard requirements)

**Organizer side (phone or projected screen).** Present the QR full-screen and force screen brightness to maximum — low brightness is a leading cause of on-screen QR failures [qrlynx](https://qrlynx.com/blog/qr-code-attendance-check-in-guide) [qrscannerai](https://qrscannerai.com/blog/why-qr-codes-are-not-scanning-common-problems-and-fixes). Show a **visible countdown/refresh indicator** so the organizer and members can see the code is live; rotating-QR classroom tools like Qwickly display a timer alongside a QR that "refreshes constantly" [goqwickly](https://www.goqwickly.com/attendance/modes/) . Give the code a generous quiet-zone margin and don't crowd it with UI [eventmobi](https://www.eventmobi.com/blog/qr-check-in/). If projected, test at real display size/brightness and reduce size if it pixelates [coursekey](https://support.coursekeyeducation.com/hc/en-us/articles/360000081654-Student-QR-Code-Attendance-Mobile) [ezqr](https://ezqr.ca/test-qr-code).

**QR encoding constraints (non-negotiable):** quiet zone ≥ 4 modules on all sides [freeqr](https://support.freeqr.com/hc/en-us/articles/15101916370703-QR-code-size-guide) [pageloot](https://pageloot.com/blog/best-practices-for-qr-code-readability/); size follows the 10:1 rule (minimum width ≈ scanning distance ÷ 10), with ~2 cm absolute minimum for arm's-length [freeqr](https://support.freeqr.com/hc/en-us/articles/15101916370703-QR-code-size-guide); contrast ≥ ~4.5:1 ; keep the payload short (a token string, not a long URL) to reduce density [ezqr](https://ezqr.ca/test-qr-code).

**Dark-theme caveat — this is the one place Signet's aesthetic must yield.** The safest, most universally scannable code is **dark modules on a light background**; inverted/light-on-dark QR support is device- and decoder-dependent and "can fail on many devices/older phones" [pageloot](https://pageloot.com/blog/qr-code-color-contrast-best-practices/) [generateonlineqr](https://www.generateonlineqr.com/blog/qr-code-color-combinations.php). Given the unknown device diversity in a fraternity chapter (including old phones), **render the QR itself on a solid white card even inside Signet's dark UI** — dark chrome around it is fine, but the code and its quiet zone must be dark-on-white. (White-on-dark can work with strong contrast on a controlled device set [uniqode](https://www.uniqode.com/blog/qr-code-customization/white-qr-code), but that's a risk you don't need to take.)

## Member scan UX and fallbacks

**Member scan flow.** Open the scanner from the event screen (post-priming), show a framing reticle with "point the square over the QR code" guidance [tickettailor](https://help.tickettailor.com/en/articles/5151698-how-to-check-in-your-attendees-with-the-check-in-app-at-your-event), always include a **Cancel** exit [blackthorn](https://docs.blackthorn.io/docs/mobile-check-in-attendee-listing), and on success show an instant confirmation state [ticketfalcon](https://support.ticketfalcon.com/article/251-how-to-check-in-attendees-with-a-qr-code-scanning-device). Map server rejections to distinct, human-readable states rather than a generic error — the mature apps all do this with a color/message taxonomy: valid→green, already-checked-in→red with details, invalid/wrong-event→red [tickettailor](https://help.tickettailor.com/en/articles/5151698-how-to-check-in-your-attendees-with-the-check-in-app-at-your-event), and CourseKey specifically distinguishes "No Active Attendance" (outside the window) from "Code Mismatch" (stale code) [coursekey](https://support.coursekeyeducation.com/hc/en-us/articles/360000081654-Student-QR-Code-Attendance-Mobile). For Signet's rotating model, your key error states are: **expired code** ("code refreshed — scan again"), **outside geofence** ("you must be at the event to check in"), **already checked in**, and **camera permission missing** (route to the priming/settings screen — a black camera screen otherwise reads as a bug [urbansports](https://urbansports.zendesk.com/hc/en-us/articles/360021026059-I-can-t-check-In)). This slots into the existing "pessimistic-lite" decision already recorded for QR check-in: spinner scoped to the check-in button, not a full-page gray-out.

**Fallbacks (build at least manual entry + officer override).**
1. **Manual code entry:** display a short human-typable code beneath the QR that rotates on the same schedule, and give members a "can't scan? enter code" input — CourseKey supports exactly this alphanumeric fallback for students who can't use the camera path [coursekey](https://support.coursekeyeducation.com/hc/en-us/articles/360015630553-How-to-Configure-Your-Roster-Settings) [coursekey](https://support.coursekeyeducation.com/hc/en-us/articles/360042476454-Attendance-with-the-Alphanumeric-Code). Validate it through the same token endpoint plus geofence, so it inherits the same anti-proxy protection.
2. **Officer manual override:** from the event's attendance roster, let an officer mark a member present by tapping their name — the standard "search by name / tap the circle to check in" pattern in event tools [eventmobi](https://www.eventmobi.com/blog/qr-check-in/) [wildapricot](https://gethelp.wildapricot.com/en/articles/1690-using-qr-codes-to-check-in-registrants). Because this bypasses the geofence, gate it behind an attendance-manage permission and log which officer did it (fits your existing RBAC + audit-reason conventions from the points module).
3. **Two-attempt rule:** if a scan fails twice, surface the manual-entry option automatically to keep the line moving [eventmobi](https://www.eventmobi.com/blog/event-badges-with-qr-codes/).

## Concrete end-to-end flow for the coding agent

**Data model (Supabase migration).** Extend the event schema with attendance config: `attendance_mode` (already surfaced as a ToggleGroup in the event-modal spec), `geofence` (reuse study-hours geofence shape), `rotation_seconds` (default 30), `token_secret` (per-event HMAC secret, server-only). Add `event_checkin` rows: `event_id`, `user_id`, `checked_in_at`, `method` (`scan` | `manual_code` | `officer_override`), `lat`/`lng`, `overridden_by` (nullable officer id). Enforce a unique `(event_id, user_id)` constraint for single-use.

**NestJS API.**
- `GET /events/:id/attendance-token` (organizer, permission-gated) → returns `{ token, expiresAt, displayCode }` where `token = base64(payload).hmacSHA256(secret)`, payload = `{eventId, iat, exp}` with `exp = iat + rotation_seconds`. Organizer app re-fetches every `rotation_seconds`.
- `POST /events/:id/checkin` (member) with `{ token OR displayCode, lat, lng }` → the validation checklist above (signature → not expired, accept current+previous token for the rotation-boundary grace → event match → membership → not already checked in → inside geofence), then insert `event_checkin`, award the event's configured points, return a typed result (`success` | `expired` | `outside_geofence` | `already_checked_in` | `not_eligible`). Prefer this as the primary path; if a `check_in_event` RPC already exists, wrap/extend it here rather than duplicating.
- `POST /events/:id/checkin/manual` (officer, permission-gated) with `{ userId }` → inserts with `method='officer_override'`, `overridden_by`, no geofence check, logged.

**Next.js web (organizer "Present code" screen).** Full-screen route that polls `attendance-token` every `rotation_seconds`, renders the token as a **dark-on-white QR** (short payload) with a visible countdown ring and the human-readable `displayCode` beneath it, forces max brightness where possible, and shows a live count of checked-in members. Also expose the roster with per-member officer-override toggles.

**Expo mobile (member scan sheet).** From the event screen, a "Check in" action opens (per the mobile creation-flow spec, a full-screen Expo Router modal route, not a bottom sheet, since it's camera-first). Flow: priming screen → `useCameraPermissions()` request → `CameraView` with `barcodeTypes:['qr']` and the `scanned`-flag debounce → on read, capture current `expo-location` coordinates → POST to `/checkin` → render the typed result state with haptic/visual success and specific error messaging → offer manual-code entry after two failures. Unmount the camera on blur.

**Rotation/expiry summary:** 30-second server-signed tokens, single-use, geofence-validated, with a one-interval grace window on the server to avoid boundary false-negatives, and a parallel rotating human-readable code as the no-camera fallback.

## Where more research would most change the recommendation

Two areas are worth a follow-up before locking the spec. First, **GPS geofence reliability indoors** — fraternity events happen inside chapter houses where GPS accuracy degrades, which could make the geofence check either too strict (false rejections) or too loose (large radius that a nearby dorm falls inside); Signet should empirically test accuracy in its actual event spaces and decide the radius, and consider whether a looser geofence plus the rotating code is sufficient. Second, **the exact grace-window and clock-handling behavior** for the boundary between rotations is under-specified in public sources (SafeTix's internals are only known via reverse-engineering); the safe default is server-authoritative expiry with a one-interval acceptance window, but this should be validated against real scan-latency measurements once the feature is in a member's hands.

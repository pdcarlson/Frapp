# Wiring Signet's push notification client: a hand-to-agent implementation spec (Expo SDK 52/53)

Signet's server-side push infrastructure is complete but unreachable because no device has ever registered a token. Closing the loop requires five client-side pieces, and the correct build order is not the order the command lists them. **Build the Android channel and `projectId` config first (a token cannot even be obtained without them), then the token-registration lifecycle, then wire the four-destination deep-link router, and treat the iOS badge as a last polish step.** The single most important product decision — permission timing — is already settled by your own onboarding research and confirmed by the broader evidence: **never request on launch; show a Signet-styled primer screen at a contextual value moment, and only trigger the one-shot OS prompt for users who tap "Allow" on your screen.** Contextual priming roughly **doubles-to-triples opt-in** versus a cold prompt [clevertap](https://docs.clevertap.com/docs/register-for-push), and because iOS gives you exactly one system prompt ever, the primer is the only layer you can iterate on [onesignal](https://documentation.onesignal.com/docs/en/prompt-for-push-permissions).

## The permission flow and why timing is the whole game

The technical flow is short and stable across SDK 52/53. Check the existing grant first, only request if not granted, and only proceed on a granted result: call `Notifications.getPermissionsAsync()`, and if `existingStatus !== 'granted'` call `Notifications.requestPermissionsAsync()` [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/). The returned `PermissionResponse` exposes `{ canAskAgain, expires, granted, status }`, and on iOS you should read `settings.ios?.status` against the `IosAuthorizationStatus` enum (`NOT_DETERMINED`, `DENIED`, `AUTHORIZED`, `PROVISIONAL`, `EPHEMERAL`) rather than the root `status` [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). Request iOS badge capability explicitly via `requestPermissionsAsync({ ios: { allowBadge: true, allowAlert: true, allowSound: true } })` — badge updates silently fail later if you skip this [expo](https://docs.expo.dev/versions/latest/sdk/notifications/).

The evidence for **contextual priming over launch-time requests is unanimous and quantified**. Prompting on first launch, before the user understands the app, is named the single biggest cause of low opt-in rates [onesignal](https://documentation.onesignal.com/docs/en/prompt-for-push-permissions), because first-time users have zero context and default to "no" [semnexus](https://semnexus.com/push-notification-timing-data-opt-in-rates). The winning pattern is a **soft ask / primer**: a custom in-app screen that explains the specific value and offers "Allow" and "Not now," where dismissing your screen does *not* consume the OS prompt attempt, so declining users can be re-asked later [clevertap](https://docs.clevertap.com/docs/register-for-push) [onesignal](https://documentation.onesignal.com/docs/en/prompt-for-push-permissions). Only tapping "Allow" fires `requestPermissionsAsync()` and burns the irreversible OS prompt [airship](https://www.airship.com/blog/mobile-app-marketing-how-to-series-getting-the-opt-in/).

Quantified uplift, by source:

| Source | Claim |
|---|---|
| CleverTap [clevertap](https://docs.clevertap.com/docs/register-for-push) | Contextual timing can "almost triple" opt-ins vs first-launch; +45% when shown after the 3rd session |
| Airship (NHL case) [airship](https://www.airship.com/blog/mobile-app-marketing-how-to-series-getting-the-opt-in/) | Adding a soft ask raised opt-ins 36% |
| Pushwoosh via VMobify [vmobify](https://vmobify.com/blog/push-notification-strategy) | Soft-ask 55–70% vs direct prompt 30–40% on iOS |
| Plotline [plotline](https://www.plotline.so/blog/how-to-improve-push-notification-opt-in-rates) | Pre-permission priming 2–3x uplift |

These are vendor/marketing sources and the exact percentages should be read as directional, not precise, but the direction is consistent across every independent source — **moderate-to-high confidence that priming materially outperforms cold asks**.

Copy guidance that recurs across sources: lead with **one specific benefit, not a feature list**; use user-controlled framing ("Get notified when…"); avoid vague lines like "Enable notifications to stay updated"; include a non-coercive "Not now"; and show it once at a strategic moment, not repeatedly [clevertap](https://docs.clevertap.com/docs/register-for-push) [semnexus](https://semnexus.com/push-notification-timing-data-opt-in-rates). NN/g adds that system-initiated modal requests interrupting a task flow "irritate users and are quickly dismissed" [nngroup](https://www.nngroup.com/articles/permission-requests/).

**Applied to Signet:** your onboarding research already locked "permission priming in-context (not on launch)," so this is a confirmation, not a change. Do not show the primer during the first-run tour (that would block onboarding, an anti-pattern). Trigger it at the first genuine chapter-value moment — the strongest candidate is **immediately after the member's first event RSVP or the first time they open Chat post-onboarding**, since those are the moments where "you'll miss chapter business without this" becomes self-evidently true. Because Signet's four notification types are known, name them concretely. Suggested dark-first primer copy:

> **Never miss chapter business**
> Signet can ping you when an event is posted, someone replies in chat, you're assigned points or a task, or an officer drops an announcement.
> **[ Turn on notifications ]  [ Not now ]**

"Not now" keeps the member on Signet's own screen (no OS dialog fires), so you can re-surface the primer on a later session [clearview](https://blog.clearview.team/2026/notification-permission-priming/).

## The registration lifecycle: where it triggers and how tokens stay fresh

Your `useRegisterPushToken` mutation already exists and is unconsumed — the work is calling it in the right order at the right moments. The correct ordering is **auth → (contextual primer) → permission grant → obtain token → upsert to backend**, and this is the same sequence the official sample and practitioner guidance describe [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/) [sashido](https://www.sashido.io/en/blog/expo-push-notifications-setup-caveats-troubleshooting).

Concrete lifecycle triggers to hand the agent:

- **On sign-in / app start (if already granted):** check permission; if granted, fetch the token and upsert it for this user+device. Practitioner guidance: "On sign-in, upsert the current token for that user + device"; "On app start, refresh token if needed and update last seen" [sashido](https://www.sashido.io/en/blog/expo-push-notifications-setup-caveats-troubleshooting). Wrap `getExpoPushTokenAsync()` in try/catch with retry — it hits Expo's servers and can reject [expo](https://docs.expo.dev/versions/latest/sdk/notifications/).
- **On primer "Allow":** run the permission request, and on grant immediately fetch + register.
- **On token rotation:** register `Notifications.addPushTokenListener(registerFn)` once; it fires whenever the push token changes, and you must re-register the new token with the backend right away because the old one becomes invalid [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). Critical guardrail for the agent: **do not call `getDevicePushTokenAsync` inside this listener — it re-triggers the listener and causes an infinite loop** [expo](https://docs.expo.dev/versions/latest/sdk/notifications/).
- **On sign-out:** delete/deactivate the token row for this device [sashido](https://www.sashido.io/en/blog/expo-push-notifications-setup-caveats-troubleshooting). There is no client-side token "revoke" API — deletion from your database is the only mechanism [stackoverflow](https://stackoverflow.com/questions/72138647/remove-push-notifications-token-from-expo-server).
- **Stale/uninstalled devices:** these can only be detected server-side. Expo push *receipts* return `details.error === 'DeviceNotRegistered'`, at which point you stop sending to that token; receipts should be checked ~15 minutes after send and are cleared after 24 hours [expo](https://docs.expo.dev/push-notifications/sending-notifications/). Signet's server already does "ticket classification," so confirm that path maps `DeviceNotRegistered` tickets to a `push_tokens` row deletion — if it doesn't, that's the one server gap to close.

**Dedup strategy for the `push_tokens` table:** enforce one-device-one-row by upserting on the token (ideally keyed by `user_id` + `device_id`), which prevents the duplicate-send problem caused by multiple stale tokens accumulating per user [sashido](https://www.sashido.io/en/blog/expo-push-notifications-setup-caveats-troubleshooting). Since your columns are already designed, verify they include a device identifier and a `last_seen`/`updated_at` to support the "update last seen on app start" step.

## Token acquisition and the projectId requirement

Obtain the token with `Notifications.getExpoPushTokenAsync({ projectId })`, and read the string off `.data` [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/). The `projectId` requirement is the most common failure point for EAS builds. Resolve it from config with the documented fallback chain: `Constants?.expoConfig?.extra?.eas?.projectId ?? Constants?.easConfig?.projectId` [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/); internally the library resolves `options.projectId || Constants.easConfig?.projectId || Constants.expoConfig?.extra?.eas?.projectId` [unpkg](https://app.unpkg.com/expo-notifications@55.0.20/files/src/getExpoPushTokenAsync.ts). If it can't be inferred, the call throws `CodedError('ERR_NOTIFICATIONS_NO_EXPERIENCE_ID', 'No "projectId" found…')` [unpkg](https://app.unpkg.com/expo-notifications@55.0.20/files/src/getExpoPushTokenAsync.ts). EAS Build sets it automatically, but Expo explicitly **recommends passing it manually via `expo-constants`** [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/).

**SDK 53 gotcha the agent must know:** remote push notifications are **no longer supported in Expo Go on Android as of SDK 53** (deprecated in SDK 52) — a development build is mandatory to test Signet's registration end-to-end [expo](https://expo.dev/changelog/sdk-53) [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). iOS push can still work in Expo Go, but you should test on a dev build for parity. A frequently-reported iOS failure is a missing `expo-notifications` config plugin entry — the token silently won't work until the plugin is added to `plugins` in app config [github](https://github.com/expo/expo/issues/38893).

## Android channels and the Android 13 permission

On Android 8+ (API 26) every notification must belong to a channel, created via `Notifications.setNotificationChannelAsync(channelId, channel)` [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). This is not optional and has a **hard ordering dependency**: the channel must be created **before** `getExpoPushTokenAsync`, and — critically — on **Android 13+ (API 33) the POST_NOTIFICATIONS runtime prompt will not appear until at least one channel exists** [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). Multiple practitioners hit "permission always denied / prompt never shows" precisely because they called `requestPermissionsAsync` before creating a channel; the fix is to call `setNotificationChannelAsync` first [github](https://github.com/expo/expo/discussions/17550) [stackoverflow](https://stackoverflow.com/questions/74064903/expo-notifications-requestpermissionsasync-always-return-status-denied). So the real init order is **create channel → request permission → get token**.

Use the documented channel shape as the baseline: `setNotificationChannelAsync('default', { name: 'default', importance: Notifications.AndroidImportance.MAX, vibrationPattern: [0, 250, 250, 250], lightColor: '#FF231F7C' })` [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/). For Signet, consider one channel per notification category (events, chat, points/tasks, announcements) so members can mute chat chatter without losing officer announcements — `NotificationChannelInput` supports per-channel `importance`, `sound`, `showBadge`, and `lockscreenVisibility` [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). The `expo-notifications` changelog confirms a fix for "POST_NOTIFICATIONS runtime permission integration when targetSdkVersion is 33" [github](https://github.com/expo/expo/blob/main/packages/expo-notifications/CHANGELOG.md), so ensure the library is current. **One unverified detail:** the retrieved docs did not explicitly confirm whether the config plugin auto-injects the `POST_NOTIFICATIONS` manifest permission — have the agent verify the generated `AndroidManifest.xml` contains it after a prebuild (low risk, but worth a one-line check).

## Wiring the four-destination router across kill/background/foreground

Signet's `notification-targets.tsx` routing contract (event, chat, points/task, announcement) needs a client that reads the notification's data payload and calls Expo Router. Expo Router's official pattern is **manual routing** — there is no automatic linking-config bridge for Expo Router; you read `notification.request.content.data` and call `router.push()` (or `router.replace()`) yourself [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). Design your server payloads to include a discriminator (e.g., `data.type` = `event | chat | points | announcement` plus the target id) and map it in one `redirect()` function:

| `data.type` | Signet destination |
|---|---|
| `event` | event detail screen (by event id) |
| `chat` | channel/thread screen (by channel + message id) |
| `points` / `task` | points or task board (by task id) |
| `announcement` | announcement screen |

**Handling all three app states correctly is where most implementations break.** The behavior differs by state: foreground and background taps both fire `addNotificationResponseReceivedListener`, while a **terminated (killed) app** launched by a tap is delivered via a JS task on Android and the response listener on iOS [expo](https://docs.expo.dev/push-notifications/what-you-need-to-know/). The robust pattern is to handle both channels: read the launch notification once at startup via `getLastNotificationResponseAsync()` (or the `useLastNotificationResponse()` hook), **and** subscribe to `addNotificationResponseReceivedListener` for live taps [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). Register the listener as early as possible (module top-level) so an iOS cold-start tap isn't missed [expo](https://docs.expo.dev/push-notifications/what-you-need-to-know/).

Two specific bugs the agent must defend against:

1. **Double-routing on cold start.** `useLastNotificationResponse` can emit the same notification twice when the app is killed then opened, running your navigation twice [github](https://github.com/expo/expo/issues/30649). Mitigate by calling `Notifications.clearLastNotificationResponseAsync()` immediately after you route [expo](https://docs.expo.dev/versions/latest/sdk/notifications/) [reddit](https://www.reddit.com/r/expo/comments/1dglanv/expo_notification_expo_router/).
2. **Navigating before the router is mounted.** On cold start the notification response is often available before Expo Router's navigation tree is ready. Guard the `router.replace()` call until the root navigation state is ready (practitioners gate on `rootNavigationState?.key != null`) [reddit](https://www.reddit.com/r/expo/comments/1dglanv/expo_notification_expo_router/). A body tap (vs an action button) is identified by `response.actionIdentifier === Notifications.DEFAULT_ACTION_IDENTIFIER` [expo](https://docs.expo.dev/versions/latest/sdk/notifications/).

## iOS badge management

Manage the badge with `Notifications.setBadgeCountAsync(n)` and clear it with `setBadgeCountAsync(0)`; read the current value with `getBadgeCountAsync()` [expo](https://docs.expo.dev/versions/latest/sdk/notifications/). On iOS this only works if `allowBadge` was granted in your permission request, otherwise the call returns `false` silently [expo](https://docs.expo.dev/versions/latest/sdk/notifications/) — another reason to request `allowBadge` up front. For Signet, reset the badge on app foreground and/or when the member views the relevant surface (e.g., zero it when they open Chat). **One caveat to flag:** there are reports that `setBadgeCountAsync(0)` can also dismiss notifications sitting in the iOS Notification Center [github](https://github.com/expo/expo/issues/28641), so if you want unread items to persist in the tray, clear the badge selectively rather than aggressively on every foreground.

## Concrete build sequence to hand the coding agent

1. **Config:** confirm `expo-notifications` is in `plugins` and `extra.eas.projectId` is set; resolve `projectId` in code via the `Constants` fallback chain [expo](https://docs.expo.dev/push-notifications/push-notifications-setup/).
2. **App init (once):** create Android channel(s) via `setNotificationChannelAsync` **before** any permission/token call [expo](https://docs.expo.dev/versions/latest/sdk/notifications/); set a notification handler.
3. **Root `_layout` (top-level):** register `addNotificationResponseReceivedListener` + read `getLastNotificationResponseAsync()` at startup; both funnel into one `redirect()` that maps `data.type` to the four destinations, guarded by navigation-readiness and followed by `clearLastNotificationResponseAsync()`.
4. **Primer component (Signet dark-first):** shown once at the first value moment (post-first-RSVP or first Chat open), with the copy above and a non-consuming "Not now."
5. **On "Allow":** `requestPermissionsAsync({ ios:{ allowBadge, allowAlert, allowSound } })` → if granted, `getExpoPushTokenAsync({ projectId })` → call the existing `useRegisterPushToken` mutation (upsert on user+device).
6. **On sign-in / app start:** if already granted, refresh + upsert token; update `last_seen`.
7. **Rotation:** `addPushTokenListener` → re-register (never call `getDevicePushTokenAsync` inside it).
8. **Sign-out:** delete the device's `push_tokens` row.
9. **Badge:** zero it on foreground/surface-view.
10. **Server check:** confirm the existing receipt/ticket pipeline deletes `push_tokens` rows on `DeviceNotRegistered`.
11. **Test on a development build** (not Expo Go on Android) [expo](https://expo.dev/changelog/sdk-53).

## Where more research would most change the plan

Two areas would sharpen this. First, **your server's receipt handling for `DeviceNotRegistered`** — I've assumed your "ticket classification" already prunes dead tokens, but if it doesn't, stale tokens will accumulate and silently degrade deliverability; a quick audit of that server path is higher-leverage than any client tweak. Second, the exact **grant-rate uplift numbers are all from push-vendor marketing sources** and should be treated as directional; if you want a defensible internal benchmark, instrument your own primer-accept and OS-grant rates from day one rather than relying on the cited percentages. Neither gap blocks the build — the client wiring above is complete and current for SDK 52/53.

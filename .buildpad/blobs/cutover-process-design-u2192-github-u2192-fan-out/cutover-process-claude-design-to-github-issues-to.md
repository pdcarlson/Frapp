# Executing Signet's UI/UX rebuild with Claude Design, GitHub Issues, and a fan-out of Opus-class coding agents

**Bottom line:** This tool chain is real and coheres into a workable pipeline, with one important correction. Claude Design is a genuine Anthropic Labs product (launched April 2026) whose native output is a *deployable code bundle plus an MCP handoff into Claude Code* — not machine-readable design tokens — so for Signet the right capture format is a rewritten written spec plus exported HTML/screenshots committed to the repo, because your design system already lives in `packages/theme`. "Claude Opus 5" is a real, shipped frontier coding model (July 24, 2026). But "Fable" and "Ultracode" as *a board-drafting product on a platform* do not exist publicly; the names map to an Anthropic frontier model (Claude Fable 5), a Claude Code effort/orchestration mode (`ultracode`), and a Claude Code "GitHub Project Planning" skill — i.e., your "planning agent" is almost certainly a Claude Code configuration, not a separate SaaS. The safe fan-out pattern is well-documented by Anthropic: one git worktree per issue, one PR per issue, a CI-gated merge queue, dependency-ordered merges, and a realistic ceiling of **3–5 parallel agents for a solo reviewer** because review bandwidth — not agent capacity — is what breaks first.

## Claude Design: what it is and how work actually reaches the codebase

Claude Design is a distinct **Anthropic Labs product** launched April 17, 2026, at `claude.ai/design`, available on Pro/Max/Team/Enterprise as a research preview. [anthropic](https://www.anthropic.com/news/claude-design-anthropic-labs) It is a separate workspace, not a mode inside normal Claude chat: a chat pane on the left and a generative **canvas** on the right where Claude produces a working design you refine via chat, inline comments, direct edits, and adjustment sliders. [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)

On the core question — inspectable specs/tokens versus visual mockups — the answer is **neither pure image nor a token exporter, but a code/web artifact**. Official docs list export as *standalone HTML*, a downloadable `.zip`, plus PDF/PPTX/Canva. [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design) Critically, **the docs do not describe any export of design tokens as machine-readable JSON or CSS variables** (e.g., W3C DTCG format); the official export list is HTML/zip/PDF/PPTX/Canva only, and the docs don't specify whether the HTML bundle is vanilla HTML/CSS or React. [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design) So it is **not** a Figma-Dev-Mode-style structured-token handoff. For contrast, that structured path is what Figma MCP now offers coding agents — exposing `get_variable_defs`, `get_code_connect_map`, variables, tokens, components — which Claude Design does not replicate. [logrocket](https://blog.logrocket.com/ux-design/design-to-code-with-figma-mcp/)

The documented handoff path is instead **agent-to-agent, not asset-export**:

- **"Handoff to Claude Code"** — Claude packages the design into a handoff bundle you pass to Claude Code with one instruction, with options *"Send to local coding agent"* and *"Send to Claude Code Web."* [anthropic](https://www.anthropic.com/news/claude-design-anthropic-labs) [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)
- **`/design-sync`** pulls your existing design system *into* Claude Design so its output aligns with your components, and the handoff "continues from your existing work instead of starting over from a screenshot." [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)
- **A Claude Design MCP server** (`claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp`, then `/design-login`) lets Claude Code "import a design into your codebase" and "export your code as a live prototype." [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)

Practitioners confirm the lower-tech version too: download the ZIP and prompt Claude Code with something like *"Make a real website from this Claude Design,"* with results improving markedly when a style guide/brand guide exists first. [reddit](https://www.reddit.com/r/ClaudeAI/comments/1tflhrt/claude_design_to_code/)

**What this means for Signet specifically:** your codebase audit shows `packages/theme` already ships a Tailwind preset, CSS variables, typed JS tokens, and a WCAG accent validator, and `packages/chat-theme` derives per-chapter palettes — this is a refactor, not a bootstrap. Because Claude Design won't hand you clean token JSON to drop into `packages/theme`, and because `/design-sync` works best when it can read your *existing* system, the highest-leverage use of Claude Design here is **visual exploration and finalization** (final hex/warmth, font selection, logo, key surface layouts) whose output you translate into your **written `spec/ui/brand-identity.md`** as the durable artifact, with exported HTML/screenshots committed as reference. You are not migrating into an empty repo where a Claude Design HTML bundle could become the app; you are retinting an existing token system, so the spec-and-tokens are the source of truth, and Claude Design is upstream inspiration plus optional per-screen reference.

[anthropic](https://www.anthropic.com/news/claude-opus-5) [claude](https://platform.claude.com/docs/en/about-claude/models/whats-new-opus-5) Using it as your fan-out coding model is well-founded.

**"Fable" — not a board-drafting product; it's a model name.** There is **no public product literally named "Fable" that drafts GitHub project boards/epics from specs on a platform.** What exists is **Claude Fable 5**, Anthropic's top-tier ("Mythos-level") frontier model that sits *above* Opus 5 in the lineup (Fable 5, Opus 5, Sonnet 5, Haiku 4.5). [anthropic](https://www.anthropic.com/claude/fable) [claude](https://platform.claude.com/docs/en/about-claude/models/overview) The *capability* you described — drafting an epic with native sub-issues and a Projects v2 board with automation — matches a **Claude Code skill called "GitHub Project Planning"** (`github-planning`), whose description is literally "Use when creating GitHub Issues, making an epic, creating sub-issues, setting up a project board, or converting plans into GitHub artifacts." [mcpmarket](https://mcpmarket.com/tools/skills/github-project-planning)

**"Ultracode" — not a platform; it's a Claude Code mode.** `ultracode` is a documented Claude Code setting that "combines `xhigh` reasoning effort with automatic workflow orchestration," and `/effort ultracode` makes Claude plan multi-step workflows (understand → change → verify) for the session. [claude](https://code.claude.com/docs/en/workflows) [claude](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (Unrelated open-source projects and an interview-prep site also use the name, none matching "a platform hosting planning agents." [github](https://github.com/KangarooKi/Ultracode))

**The reconciliation (inference, flagged as such):** your "planning/coordinator agent, Fable on Ultracode" is most plausibly *Claude Code running the Fable 5 model in `ultracode` orchestration mode with the `github-planning` skill*, and your "Opus 5 coding agents" are Claude Code sessions on `claude-opus-5`. That is a coherent, real configuration — just not three separate products. This matters because it means the planning step is a **prompt-and-skill configuration you control**, not a black-box SaaS, which is good: you can steer exactly how it converts your specs into a board.

## Running many Opus agents against one repo without collisions

Anthropic's own Claude Code documentation now covers this directly, and it lines up with independent practitioner experience.

**Worktree-per-task is the isolation primitive.** `claude --worktree <name>` starts an isolated session in a git worktree under `.claude/worktrees/<name>/` on a new branch; run it again with a different name in another terminal to parallelize, and "edits in one session never touch files in another." [claude](https://code.claude.com/docs/en/worktrees) Claude *enforces* this — it blocks `Edit`/`Write` targeting the main checkout and blocks git redirects into main while inside a worktree. [claude](https://code.claude.com/docs/en/worktrees) Practical gotchas: each worktree is a fresh checkout so you must install deps inside it; add `.claude/worktrees/` to `.gitignore`; use `.worktreeinclude` to copy `.env` into each; and non-interactive `-p` runs won't auto-clean, so `git worktree remove` manually. [claude](https://code.claude.com/docs/en/worktrees) A separate but real limit: worktrees isolate *files and branches*, **not runtime resources** — ports, databases, dev servers must be namespaced per agent yourself. [penligent](https://www.penligent.ai/hackinglabs/git-worktrees-need-runtime-isolation-for-parallel-ai-agent-development/)

**File ownership is the real conflict-avoidance rule, and worktrees don't make it optional.** The hard constraint from practitioners: "each parallel agent owns a disjoint set of files… shared files are edited by the PARENT after the fan-out, never by an agent," and "NEVER parallelize work that writes the same file from two agents." [claudify](https://claudify.tech/blog/claude-code-parallel-agents) Even with clean worktree isolation, *logical* conflicts still surface at merge time when two branches touch the same feature. [aakashx](https://www.aakashx.com/blog/parallel-claude-code-agents/) A known mitigation is to refactor "hotspot" files that every task tends to edit (route indexes, registries) toward auto-discovery so agents *add new files* instead of editing a shared index. [github](https://github.com/drjc1001/parallel-dev)

**PR-per-issue plus a merge queue serializes integration.** Anthropic's `/batch` skill itself splits a large change into "5 to 30 worktree-isolated subagents," each opening a pull request. [claude](https://code.claude.com/docs/en/agents) GitHub's **merge queue** then guarantees the target branch is "never broken by incompatible changes": it builds temporary branches stacking base + your PR + earlier-queued PRs, runs required checks (wired via the `merge_group` event in Actions), and automatically ejects any PR that conflicts or fails. [github](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) GitHub reports this ships hundreds of PRs/day and cut average time-to-ship by 33%. [github](https://github.blog/engineering/engineering-principles/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/)

**Dependency ordering gates what can go parallel.** Claude Code's Agent Teams model this natively: a task with unresolved dependencies "cannot be claimed until those dependencies are completed," with file-locking to prevent two teammates claiming the same task. [claude](https://code.claude.com/docs/en/agent-teams) The practitioner merge discipline is to merge in dependency order — foundational change first (shared types/refactor/API), then rebase dependents on the updated base — with a canonical ordering like "contracts/shared types → backend logic → frontend integration → tests → docs → refactors." [davidloor](https://davidloor.com/en/blog/how-to-keep-multiple-coding-agents-from-overwriting-each-other) [mindstudio](https://www.mindstudio.ai/blog/git-worktrees-parallel-ai-coding-agents) The planning move is to build a DAG of tasks and only assign *unblocked* work, keeping tasks that touch the same files or depend on the same decision off the parallel track. [davidwells](https://davidwells.io/blog/multi-agent-coding-without-worktree-chaos)

**The realistic ceiling is your review bandwidth, ~3–8 agents.** Anthropic warns running many sessions "multiplies token usage" and hits rate limits, and that Agent Teams add coordination overhead and are *less* effective for sequential/same-file/high-dependency work than a single session or plain subagents. [claude](https://code.claude.com/docs/en/agents) [claude](https://code.claude.com/docs/en/agent-teams) Practitioners converge on **5–8 as an upper bound** because review/merge overhead — not agent capacity — becomes the bottleneck, and advise "start with two or three… increase concurrency only when your review process can keep up." [mindstudio](https://www.mindstudio.ai/blog/parallel-agentic-development-claude-code-worktrees) [aakashx](https://www.aakashx.com/blog/parallel-claude-code-agents/)

## Structuring the GitHub board and a solo reviewer's cadence

**Epic = parent issue; leaf = sub-issue.** GitHub's native sub-issues support 100 children per parent and 8 nesting levels, roll child completion up to the parent automatically, and expose a **"Parent issue"** grouping field and **"Sub-issue progress"** field in Projects. [github](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues) [github](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields/about-parent-issue-and-sub-issue-progress-fields) Model it as: **epic (parent) = a migration slice/surface** carrying the spanning context, acceptance criteria for the whole slice, and links to the relevant spec docs; **leaf (sub-issue) = one PR-sized unit of work** an agent executes end-to-end. An epic holds *why and the shared context*; a leaf holds *one concrete change with a testable done-state*.

**A leaf issue for an autonomous agent is a contract, and under-specifying it is the main failure mode.** GitHub Copilot's own guidance says a well-scoped agent task needs (1) a clear problem description, (2) **complete acceptance criteria**, and (3) directions on **which files to change**, treating the issue as the prompt. [github](https://docs.github.com/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks) Empirical research on agent-ready issues found higher merge rates for issues that are well-scoped, self-contained, ambiguity-free, name the relevant artifacts, and specify expected *plus edge* behavior. [arxiv](https://arxiv.org/html/2512.21426v1) Acceptance criteria should be written in a **verifiable Given/When/Then form** — vague words like "properly" or "gracefully" aren't things an agent can test, and the criteria become the effective spec because the agent "cannot self-correct toward a target it was never given." [braingrid](https://www.braingrid.ai/blog/how-to-write-acceptance-criteria-ai-agent-can-verify) Pair task-specific criteria with a standing **Definition of Done** (tests that fail without the change and pass with it, no regressions, ship-readiness) [github](https://github.com/addyosmani/agent-skills/blob/main/references/definition-of-done.md) and a **completion bar** stating a measurable end state, a runnable check, and required evidence. [digitalapplied](https://www.digitalapplied.com/blog/define-done-acceptance-criteria-agent-prompts-2026) Include explicit **boundaries — what the agent must not touch.** [addyosmani](https://addyosmani.com/blog/good-spec/)

**Size each leaf to one reviewable PR.** Agent PRs are commonly rejected for being **too large** or bundling multiple purposes, not just for code quality. [arxiv](https://arxiv.org/html/2509.14745v3) Keep PRs under ~400 lines and limit WIP in review. [graphite](https://graphite.com/blog/code-review-best-practices) If a leaf can't be verified with a concrete check, it's too big or under-specified. [digitalapplied](https://www.digitalapplied.com/blog/define-done-acceptance-criteria-agent-prompts-2026) When an agent does produce a giant change, GitHub's new **stacked PRs** (public preview, July 2026) let you decompose it into dependency-ordered, independently reviewable layers. [github](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/)

**Solo-reviewer cadence: batch, time-box, and let CI carry the low-risk merges.** Check PRs on a fixed rhythm — twice a day (e.g., morning and after lunch) minimizes context switching. [gustavwengel](https://www.gustavwengel.dk/pr-sizes) Enforce a **WIP limit on a dedicated "In Review" column** so unreviewed work can't pile up (the column visibly blocks when full), which is the standard fix for review becoming the bottleneck. [atlassian](https://www.atlassian.com/agile/kanban/wip-limits) [gitscrum](https://gitscrum.com/en/solutions/pains/reducing-code-review-bottleneck-delays) To avoid being the bottleneck without losing control, adopt a single-maintainer policy pattern: **merge low-risk changes on green CI (including static analysis and visual-regression checks) and audit periodically** — a documented approach is merging maintainer/critical changes when all CI passes, then doing scheduled triage review of unreviewed merges later. [hexatomic](https://hexatomic.github.io/unreviewed-code-triage.html) Time-box your own feedback to a max window (~4 hours) so agents aren't idle. [graphite](https://graphite.com/blog/code-review-best-practices)

## Concrete end-to-end sequence for Signet

Here is the applied plan, tuned to the facts already established in your canvas: `packages/theme` and `packages/chapter-theme` already exist (refactor, not bootstrap); mobile is a prototype (19/23 screens hardcoded, zero modals); several UI capabilities are misrepresented (QR check-in, mobile study hours, mobile push); `spec/ui/brand-identity.md` still encodes the *old* light-first direction and misguides agents until rewritten; two real query bugs exist (`/polls`, `/backwork`); and you already run tech-debt-as-GitHub-issues.

### Step 1 — What goes through Claude Design first, and how to capture it

Run through Claude Design **only the things that are genuinely visual-exploration questions**, because it won't hand you drop-in tokens for `packages/theme`:

- Final base palette warmth + exact hex (your spec currently marks these "open"), the humanist rounded-sans font choice, the Signet "S"-seal logo/mark, and 2–3 anchor screen layouts (chat, the AI "Ask" answer card, the redesigned event modal).
- First run `/design-sync` against your existing design system so Claude Design outputs align to your shadcn/`packages/theme` component vocabulary rather than inventing a parallel one. [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)

**Capture format (this is the decision point):** do **not** treat the Claude Design HTML bundle as the thing agents implement. Instead, translate its outcomes into a **rewritten `spec/ui/brand-identity.md`** (dark-first, warm/gold, the finalized token values, font, radius, accent-generation rules) as the authoritative artifact, and commit the **exported HTML/screenshots into `docs/internal/design-reference/`** as visual reference only. Rationale: every other UI spec already references `brand-identity.md`, your tokens live in `packages/theme`, and Claude Code's handoff "continues from existing work" rather than replacing it. [claude](https://support.claude.com/en/articles/14604416-get-started-with-claude-design) The written spec is what stops agents building on the stale light-first direction (already flagged as an action item on your canvas).

### Step 2 — How to prompt the planning/coordinator agent

Configure the planner as **Claude Code running Fable 5 in `ultracode` mode with the `github-planning` skill** (its documented job is exactly "converting plans into GitHub artifacts" — epics, native sub-issues, a Projects v2 board). [mcpmarket](https://mcpmarket.com/tools/skills/github-project-planning) [claude](https://code.claude.com/docs/en/workflows) Feed it three inputs and constrain its output:

**Inputs:** (1) the rewritten `brand-identity.md` + design reference; (2) your ~10 existing spec docs (event-modal redesign, optimistic-update/mutation audit, mobile creation-flow, navigation/IA restructure, chat-core extraction decision, QR spec, mobile study-hours/dues/push specs); (3) the codebase-status audit with its exact `file:line` inventory.

**Instruct it to produce:**
- **Epics = surfaces/slices**, one per module (Chat, Events, Tasks/Points, Study/Geofences, Dues/Billing, Backwork/Documents, Settings, Navigation/Shell, Mobile-parity, plus a Foundation epic and an AI-Ask-stub epic). Each epic links its governing spec doc and states slice-level acceptance criteria.
- **Leaf sub-issues = one-PR units**, each an "Agent brief" containing: problem/goal; **Given/When/Then acceptance criteria** [braingrid](https://www.braingrid.ai/blog/how-to-write-acceptance-criteria-ai-agent-can-verify); **exact file paths pulled from the audit** (e.g., `components/events/event-editor-dialog.tsx:423`); the standing Definition of Done; a runnable completion check (lint, typecheck, the relevant Playwright visual snapshot); and an explicit **"do not touch" boundary list** naming the shared hotspot files. [github](https://docs.github.com/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks) [addyosmani](https://addyosmani.com/blog/good-spec/)
- **`Blocked by` edges** for every leaf that depends on a Foundation item, plus your existing priority/area labels.
- **Flag misrepresented-capability items as their own issues** (QR check-in, mobile study hours, mobile push) so agents build them rather than reskinning a false affordance.

Have the planner deliver the board as a **plan you approve before any issue is created** — this is your first human checkpoint and it's cheap. Anthropic's Agent Teams explicitly support requiring plan approval and keeping agents in read-only plan mode until the lead approves. [claude](https://code.claude.com/docs/en/agent-teams)

### Step 3 — The safe multi-agent fan-out

Sequence the work in waves gated by file ownership and dependencies. The governing rule: **shared/hotspot files are serialized and founder-owned; disjoint per-surface files fan out in parallel.** [claudify](https://claudify.tech/blog/claude-code-parallel-agents)

**Wave 0 — Foundation, serialized, one agent, merged before any fan-out.** These touch the shared files every other task depends on, so they must land first: rewrite `brand-identity.md`; rename/fix the mislabeled token keys in `packages/theme` (the `brand.navy`/`royalBlue` lies); the **navigation/IA restructure** in `nav-config.ts` (single source for sidebar, command palette, breadcrumbs — a classic hotspot); add the missing `alert-dialog.tsx` primitive and the shared `table-controls.ts` restyle; the `packages/chat-core` extraction (foundational for mobile chat); and the two real bug fixes (`/polls`, `/backwork` disabled-query hangs). Merge these before opening the gate — this is dependency-ordered merging (shared contracts first). [davidloor](https://davidloor.com/en/blog/how-to-keep-multiple-coding-agents-from-overwriting-each-other)

**Wave 1 — Per-surface reskins, parallel, one worktree per surface.** Once the token rename and `nav-config.ts` are merged, each module's page/component tree is a **disjoint file set**: Events (incl. the 423-line modal redesign), Tasks/Points, Service, Documents/Backwork, Billing, Study, Settings tabs, Chat. Assign **one Opus 5 agent per surface** via `claude --worktree <surface>`, each opening one PR, with the "do not touch: `packages/theme`, `nav-config.ts`, `table-controls.ts`, `globals.css`" boundary in every brief. [claude](https://code.claude.com/docs/en/worktrees) Replacing the 11 `window.confirm()` calls with the new AlertDialog can ride along inside each surface's issue since each call site lives in that surface's files.

**Wave 2 — Mobile net-new build.** Mobile modals, study-hours, dues (Stripe PaymentSheet), and push registration are net-new and depend on `chat-core` (chat) and on your NativeWind-vs-typed-tokens decision — resolve that decision in Wave 0, then fan these out as their own epic. Keep them out of Wave 1 because they're larger and higher-risk.

**Parallelism count and review checkpoints:**
- **Run 3 agents to start, cap at 5.** You are a solo reviewer; review bandwidth is the true ceiling, and the guidance is to start at 2–3 and only scale when your merge process keeps up. [aakashx](https://www.aakashx.com/blog/parallel-claude-code-agents/) [mindstudio](https://www.mindstudio.ai/blog/parallel-agentic-development-claude-code-worktrees)
- **Enable GitHub merge queue** with required CI (typecheck, lint, unit, and the existing Playwright visual snapshots — which you'll rebaseline anyway across all 16 dashboard routes). The queue serializes integration and auto-ejects any conflicting/failing PR so parallel work can't break `main`. [github](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- **Human checkpoints:** (1) approve the board plan before issues are created; (2) review PRs in **two batched windows/day** with a WIP limit on the "In Review" column [gustavwengel](https://www.gustavwengel.dk/pr-sizes) [atlassian](https://www.atlassian.com/agile/kanban/wip-limits); (3) **manually review Foundation PRs and any change touching shared files or auth/billing**, but **let visually-scoped reskin PRs merge on green CI + passing visual regression**, auditing them in a periodic sweep — the documented solo-maintainer pattern for not being the bottleneck while keeping control. [hexatomic](https://hexatomic.github.io/unreviewed-code-triage.html)
- **Namespace runtime resources** per worktree (dev-server ports, any local DB) — worktrees don't isolate these and port collisions will otherwise stall parallel agents. [penligent](https://www.penligent.ai/hackinglabs/git-worktrees-need-runtime-isolation-for-parallel-ai-agent-development/)

This gives you parallel throughput where it's safe (independent surface reskins), hard serialization where it isn't (shared tokens, nav, chat-core), CI-enforced integration safety, and a review rhythm that keeps one person in control of a fast rollout.

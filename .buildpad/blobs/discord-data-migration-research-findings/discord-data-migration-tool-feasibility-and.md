# Discord migration tool for Signet: feasible, but build a read-only archive via bot token, not a live sync

**Bottom line: this tool is buildable by a solo developer with Claude Code, and the founder's requirement ("the chapter doesn't lose their data") is satisfiable with a substantially simpler and more legally defensible approach than live bidirectional sync.** A Discord bot *can* read a channel's full message history retroactively (history access is governed by the `READ_MESSAGE_HISTORY` permission, not by when the bot was installed) [discord](https://discord.com/developers/docs/resources/channel#get-channel-messages), and the entire export of a mid-size chapter server (~80–150 members, a handful of channels, plausibly 100k–300k messages) is a matter of minutes-to-hours of compute, not a heroic engineering effort [github](https://github.com/Tyrrrz/DiscordChatExporter/issues/749). The right MVP is a **one-time, bot-authorized bulk export into a read-only, searchable Signet archive** — capturing messages, attachments (downloaded and rehosted), channel/category structure, and the role list as reference data — rather than reconstructing live threads or syncing bidirectionally. This is simpler to build, avoids the highest-risk legal ground, and directly meets the "don't lose our history" bar.

The most important strategic decision is **use a properly-added bot token, never a user token / self-bot.** That single choice moves the project from "high, actively-enforced legal risk" to "gray-area but defensible," and the rest of the recommendation follows from it.

## What's actually extractable, and how

**Full historical read is possible with a bot.** The `GET /channels/{channel.id}/messages` endpoint returns messages newest-to-oldest and paginates via snowflake-based `before`/`after`/`around` cursors with a `limit` of 1–100 (default 50) [discord](https://discord.com/developers/docs/resources/channel#get-channel-messages). There is no "install-forward only" cutoff for REST history reads — the bot can walk backward through years of messages as long as it holds `VIEW_CHANNEL` + `READ_MESSAGE_HISTORY` on each channel [discord](https://discord.com/developers/docs/resources/channel#get-channel-messages). This is the critical enabling fact: the founder's chapter does not need to have had a bot running for the last three years.

**Message bodies require the MESSAGE_CONTENT privileged intent.** Without it, the `content`, `embeds`, `attachments`, and `components` fields come back empty [discord](https://docs.discord.com/developers/resources/message). This intent must be toggled on in the Developer Portal (and requires Discord approval once a bot is in 100+ servers, which won't apply to a single chapter's private export bot). Message objects otherwise expose everything needed for a faithful archive: `author`, `timestamp`, nullable `edited_timestamp`, `attachments` (with `id`, `filename`, `size`, signed `url`), `embeds`, and `reactions` (emoji + count) [discord](https://docs.discord.com/developers/resources/message).

**Data type accessibility (what maps cleanly to a Signet import):**

| Data type | Accessible via bot API | Notes for import |
|---|---|---|
| Messages (author, timestamps, edits, content) | Yes | Requires MESSAGE_CONTENT intent [discord](https://docs.discord.com/developers/resources/message) |
| Attachments/files | Yes (metadata + signed URL) | Must download+rehost; URLs expire (see below) [discord](https://docs.discord.com/developers/reference) |
| Reactions | Yes | Count + emoji; author lists need extra calls [discord](https://docs.discord.com/developers/resources/message) |
| Threads | Yes | Message object carries `thread`; forum-thread export is weaker in tooling [bellingcat](https://bellingcat.gitbook.io/toolkit/more/all-tools/discord-chat-exporter) |
| Channel structure/categories | Yes | `parent_id` gives category; `Get Guild Channels` excludes threads [discord](https://docs.discord.com/developers/resources/guild) |
| Roles + per-member assignments + join dates | Yes | Member list needs GUILD_MEMBERS privileged intent; member `roles` + `joined_at` [discord](https://docs.discord.com/developers/resources/guild) |

**Rate limits are not a blocker.** Discord's global bot limit is **50 requests/second** [discord](https://docs.discord.com/developers/topics/rate-limits). The message-fetch endpoint has a per-route bucket, but Discord deliberately does **not** publish a fixed numeric limit for it — the documentation explicitly tells you not to hardcode values and instead parse `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset-After`, and `X-RateLimit-Bucket` headers at runtime, backing off on `429` using the `retry_after` field [discord](https://docs.discord.com/developers/topics/rate-limits). This means any well-behaved exporter that respects headers will not get throttled hard on a single small server.

**The three export paths are very different in scope:**
- **Bot-based export (recommended):** server-wide, admin-authorized, full channel history — but requires the admin to add a bot with the right permissions/intents [discord](https://discord.com/developers/docs/resources/channel#get-channel-messages).
- **Discord's official "Request my Data" package:** **user-only, not server-wide.** It contains only "all the messages that *you* have sent," scoped to servers you're currently a member of [discord](https://support.discord.com/hc/en-us/articles/360004957991-Your-Discord-Data-Package). This cannot reconstruct a chapter's shared history and is therefore not viable as the migration mechanism, though it's a useful fallback for an individual member who wants their own record.
- **Third-party scraping via user tokens:** highest legal risk (see below); avoid entirely.

**The single biggest technical gotcha: attachment CDN links expire.** Since Discord's 2023 authentication-enforcement rollout, attachment URLs are **signed with a preset expiry** — the URL carries `ex` (expiry), `is` (issued), and `hm` (signature) parameters, and the signature is only valid until `ex` [discord](https://docs.discord.com/developers/reference). External reporting puts the practical window at **~24 hours** [bleepingcomputer](https://www.bleepingcomputer.com/news/security/discord-will-switch-to-temporary-file-links-to-block-malware-delivery/). The consequence for Signet is decisive: **storing the message JSON alone will silently lose every file within a day.** The export must download-and-rehost every attachment in the same job that reads the messages. This is not optional and shapes the architecture.

## Legal and ToS assessment: gray-area but defensible with a bot, high-risk with a user token

**The bot-vs-self-bot line is the whole ballgame.** Discord's support documentation states plainly that "automating normal user accounts (generally called 'self-bots') outside of the OAuth2/bot API is forbidden, and can result in an account termination" [discord](https://support.discord.com/hc/en-us/articles/115002192352-Automated-User-Accounts-Self-Bots). Enforcement here is real and demonstrated: when the scraping site Spy.pet surfaced, a Discord spokesperson said "scraping our services and self-botting are violations of our Terms of Service," that Discord was "banning the affiliated accounts," and was "considering appropriate legal action" [pcmag](https://www.pcmag.com/news/discord-users-are-being-tracked-through-data-scraping-site) [arstechnica](https://arstechnica.com/tech-policy/2024/04/message-scraping-user-tracking-service-spy-pet-shut-down-by-discord/). Practitioner reports mirror this split: DiscordChatExporter's own community consensus is that user-token use "is not technically ToS compliant" and "accounts have been shut down," whereas "using a token from a bot account… is compliant and perfectly okay" and is "strongly encouraged" [github](https://github.com/Tyrrrz/DiscordChatExporter/discussions/889). There are also recent reports of a Discord crackdown where users get community-guidelines notices "as soon as they run an export with their token" [reddit](https://www.reddit.com/r/BannedFromDiscord/comments/1r2qsz2/have_any_of_you_been_banned_for_using_a_chat/) — again, concentrated on token-based (user-account) automation.

**Even with a bot, the Developer Policy imposes real constraints Signet must design around.** The 2022 Developer Policy says "you may not mine or scrape any data" and, crucially, "do not use API Data for any purpose outside of what is necessary to provide your stated functionality" [discord](https://support-dev.discord.com/hc/en-us/articles/25280499088279-2022-Discord-Developer-Policy). The Developer Terms require you to "promptly delete the API Data" when retention "is no longer necessary" for the app's stated functionality, and to delete it on user request [discord](https://support-dev.discord.com/hc/en-us/articles/25280523748759-2022-Discord-Developer-Terms-of-Service). The 2017 terms add that offering an API that lets you "reproduce or display End User message content is not… a license to such content" and that you "shall not sell, license or otherwise commercialize any End User Data" [discord](https://support-dev.discord.com/hc/en-us/articles/25280443568791-2017-Discord-Developer-Terms-of-Service).

How this nets out for Signet's specific use case (a chapter admin exporting *their own* server's history *at their own direction* to keep it):
- **Bulk export is not prohibited merely for being bulk.** The compliance gate is *purpose and retention*, not volume [discord](https://support-dev.discord.com/hc/en-us/articles/25280499088279-2022-Discord-Developer-Policy). A one-time migration the server owner explicitly initiates is a defensible "stated functionality."
- **"Using data to compete" is the sharpest edge.** The policy prohibits commercializing API Data and using it "outside stated functionality" [discord](https://support-dev.discord.com/hc/en-us/articles/25280443568791-2017-Discord-Developer-Terms-of-Service). Signet is a paid competing platform, so framing matters: the tool should be positioned and built as a *data-portability / user-owned-export* feature that the chapter owner triggers to move *their own* records — not as a growth-hacking pipe that harvests Discord data. The "contact users outside Discord without explicit consent" clause [discord](https://support-dev.discord.com/hc/en-us/articles/25280499088279-2022-Discord-Developer-Policy) means Signet must not, for example, scrape the member list to cold-invite people.
- **Retention hygiene is a contractual obligation.** If Signet stores imported content, it must offer a deletion path and a privacy policy — the Developer Terms mandate "an easily accessible way for users to ask for their API Data to be modified and deleted" and compliance with GDPR/CCPA [discord](https://support-dev.discord.com/hc/en-us/articles/25280523748759-2022-Discord-Developer-Terms-of-Service). This dovetails with Signet's existing tenant model.

**Confidence:** *High* that user-token/self-bot export is prohibited and enforced; *Moderate* that bot-authorized, owner-directed, one-time export for data portability is defensible (this is an interpretation of policy language, not a Discord ruling, and enforcement of bot-based export is reportedly non-uniform [github](https://github.com/Tyrrrz/DiscordChatExporter/discussions/889)).

**Consent norms are an unresolved gap — treat as product design, not compliance blocker.** There is no Discord-authored guidance instructing admins to individually notify every member before a server-wide export; the Developer Policy speaks only to "obtain consent before initiating processes on a user or server's behalf" and respecting members' ability to remove the app [discord](https://support-dev.discord.com/hc/en-us/articles/25280499088279-2022-Discord-Developer-Policy). The practical, defensible norm to adopt: post an in-channel notice before running the export, since the president/admin is authorizing it on behalf of a private membership org they already govern. This mirrors how the Developer Policy treats an admin-initiated command as a valid consent instance [discord](https://support-dev.discord.com/hc/en-us/articles/25280499088279-2022-Discord-Developer-Policy).

## Technical approach: build on DiscordChatExporter's proven output, not raw API calls

**Do not write the exporter from scratch.** DiscordChatExporter (Tyrrrz) is the mature, battle-tested tool and — critically — it supports **bot-token authentication**, exports to **JSON/HTML/TXT/CSV**, and handles attachments, embeds, reactions, and threads . Its JSON export is the natural machine-readable input for a Signet importer, and multiple existing migration pipelines already treat it as the interchange format (Discord→Matrix and Discord→Slack tools both consume DCE JSON) [github](https://github.com/macdows/import-discord-to-matrix) [github](https://github.com/egorkhmelev/discord-slack-toolkit). The realistic architecture is therefore two decoupled stages: **(1) DCE (bot token) produces JSON + downloaded media; (2) a Signet importer (the part Claude Code writes) parses that JSON into Signet's schema.** This halves the build.

**Attachment handling is a solved pattern — copy it.** DCE's `--media` flag downloads all assets locally (default is *off*, so it must be explicitly enabled) into an `_Files/` directory [deepwiki](https://deepwiki.com/Tyrrrz/DiscordChatExporter/3.1-command-reference), and companion tools like `DiscordChatExporter-MediaDownloader` and `Dimport` exist precisely to download CDN attachments and "replace expired attachment links with local media files" [github](https://github.com/Marcelektro/DiscordChatExporter-MediaDownloader) [github](https://github.com/Inc44/Dimport). Signet's importer should run DCE with `--media`, then rehost those files into Signet's own file storage and rewrite the links — a one-time bulk download-and-rehost is confirmed as the only reliable approach given the ~24h signed-URL expiry [github](https://github.com/Marcelektro/DiscordChatExporter-MediaDownloader).

**Throughput is comfortable for a chapter server.** A DCE user reports exporting **~400,000 messages in 10–15 minutes** when the content lacked `@mentions` [github](https://github.com/Tyrrrz/DiscordChatExporter/issues/749); another reports a full guild export finishing in "about 20 minutes" [alon-alush](https://alon-alush.github.io/scraping/scrapingdiscordmessages/). A chapter's 100k–300k messages should export in **minutes to low tens of minutes**. The one documented pathology: messages heavy with `@user` mentions can slow exports dramatically (one user saw a 400k-message window barely progress after 4–5 hours) because of per-mention user lookups [github](https://github.com/Tyrrrz/DiscordChatExporter/issues/749). Plan for a background job with progress reporting rather than a synchronous request, and prefer CSV/simplified output if mention-resolution proves slow.

**Role/permission mapping should be manual/config-based, not automated.** Every real migration precedent treats this as a non-automatable step: the Discord→Slack playbook lists "roles, permissions, and community moderation" as **manual** because "Discord role hierarchy and moderation tools do not map cleanly" [migratingto](https://migratingto.dev/guides/discord-to-slack/); Guilded's template import brings channels/categories/roles but is capped at "one template import per server" [guilded](https://support.guilded.gg/hc/en-us/articles/360058767274-Importing-Discord-Server-Templates); Matrix's importer maps *identities*, not roles, and auto-creates ghost users for unmapped authors [github](https://github.com/macdows/import-discord-to-matrix). For Signet, the pragmatic pattern is: **import the Discord role list as reference data, then present the admin a mapping UI** ("Discord 'Exec' role → Signet 'Officer' permission set") during onboarding, defaulting everyone to Member and letting the admin promote — which aligns exactly with Signet's already-decided onboarding model (everyone joins as Member, officers promoted after). Identity mapping (Discord author → Signet member) will similarly need an admin-assisted match step, since Discord usernames won't automatically equal Signet accounts.

## Recommended MVP: a read-only searchable archive, not live thread reconstruction

**Yes — a read-only searchable archive fully satisfies "the chapter doesn't lose their data," and it is dramatically simpler and safer than live sync.** The founder's stated requirement is preservation, not continuity of the live chat surface (which Signet's own chat replaces going forward). The MVP:

1. **Admin adds a Signet bot** to the Discord server with `READ_MESSAGE_HISTORY` + `VIEW_CHANNEL` and the MESSAGE_CONTENT + GUILD_MEMBERS intents; a one-time authorization the president can do [discord](https://discord.com/developers/docs/resources/channel#get-channel-messages).
2. **DCE (bot token) exports** all channels to JSON with `--media` on .
3. **Signet importer** ingests the JSON, rehosts attachments into Signet storage, and stores messages as an **immutable, per-channel, searchable archive** tied to the chapter tenant — with author, timestamp, and reactions preserved for readability, but no attempt to make old threads "live" or writable.
4. **Admin-assisted mapping** for roles (→ Signet permission sets) and, optionally, member identities.
5. **Notice + deletion hygiene:** an in-channel notice before export, a privacy note, and a tenant-level delete path to satisfy Developer Terms retention/deletion obligations [discord](https://support-dev.discord.com/hc/en-us/articles/25280523748759-2022-Discord-Developer-Terms-of-Service).

**Why this is the right scope for a solo dev with Claude Code:**
- **Legally more defensible** — a one-time, owner-directed, read-only export for data portability sits far better against the "stated functionality / not commercialize / not competing-use" tests than an ongoing sync that continuously mines a live server [discord](https://support-dev.discord.com/hc/en-us/articles/25280499088279-2022-Discord-Developer-Policy).
- **Sidesteps the hardest technical problem** — the CDN expiry window makes any *ongoing* link-based approach fragile; a one-time rehost is the clean solution [discord](https://docs.discord.com/developers/reference).
- **Reuses an existing tool** for the risky/fiddly half (rate-limit-respecting pagination, format handling), leaving Claude Code to build only the importer against a stable JSON schema .
- **Fits Signet's RAG roadmap** — a searchable message archive is exactly the kind of corpus Signet's "Ask your chapter anything" AI is meant to index later, so this MVP doubles as RAG-ready input rather than throwaway migration plumbing.

Live bidirectional sync should be explicitly deferred or dropped: it multiplies engineering (realtime gateway listening, dedup, conflict handling), continuously re-triggers the "mining API data" concern, and delivers value the chapter doesn't actually need once it has switched.

## Where more research would change the conclusion

Two areas carry the most residual uncertainty. First, **the current enforcement climate for bot-token bulk export specifically** — reports of a 2025 crackdown exist but are concentrated on user-token use [reddit](https://www.reddit.com/r/BannedFromDiscord/comments/1r2qsz2/have_any_of_you_been_banned_for_using_a_chat/); confirming whether Discord has recently flagged *bot-authorized* exports would sharpen the risk estimate, and a brief consultation with someone versed in platform ToS / a review of Discord's most recent Developer Policy revisions would be worthwhile before making this a marketed feature. Second, **whether to run DCE as a bundled dependency vs. reimplementing its core fetch loop in Signet's own bot** — bundling is faster to ship but ties Signet to a third-party tool's licensing and update cadence; if that coupling is unacceptable, the discord.js/discord.py pagination patterns are simple enough to reimplement [stackoverflow](https://stackoverflow.com/questions/66281939/discordjs-fetching-more-then-100-messages), but that shifts rate-limit-handling responsibility back onto the build. Neither uncertainty changes the core recommendation — bot token, one-time export, read-only archive — only its packaging and go-to-market framing.

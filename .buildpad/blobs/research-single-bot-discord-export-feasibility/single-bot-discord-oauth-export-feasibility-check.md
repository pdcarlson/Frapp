# Rebuilding the Discord importer: the three infra blockers dissolve, but a single Signet-owned bot trades them for one harder external blocker — Discord's Message Content Intent approval at scale

**The proposed architecture — one Signet-owned bot + native Node/TypeScript REST export + no DiscordChatExporter + no local admin tooling — is genuinely buildable, and all three of the original infra objections evaporate under the single-bot model.** Global credential storage is the same problem as your existing Stripe keys (blocker 1 gone), a native paginated REST fetch in Node is a well-trodden, low-risk pattern with automatic rate-limit handling built into `@discordjs/rest` (blocker 2 gone), and a chunked streaming job fits the resource envelope — though not on Render's free tier, which is the one real cost the rebuild adds (blocker 3 is a plan change, not a wall). The UX win is real: the admin clicks an "Add to Server" link, picks their server, clicks Authorize, and never sees a token.

**But the single-bot model introduces a new blocker the per-chapter design never had, and it's harder because it's external and not fixable with engineering.** A single application that reads message content must be Discord-verified once it reaches **100 servers**, and must pass a **Message Content Intent review** once it reaches **~10,000 unique users** — and without approved Message Content Intent, Discord returns *empty* `content`, `attachments`, and `embeds` fields, which makes the export return nothing. This gate is a single point of failure across every tenant, and a bot whose entire stated purpose is bulk-extracting members' messages to a paid competitor is squarely the profile Discord's review is most skeptical of. The per-chapter-bot model quietly sidestepped all of this by keeping each chapter's private bot far below both thresholds. **Net recommendation: build the simpler architecture — it works with zero approval friction up to ~100 chapters / 10k users — but treat Discord platform approval as a known scaling cliff, apply for verification early, and keep the admin-owned-bot/DCE path alive as a fallback for the day the shared bot is throttled or denied.**

## The three original blockers, re-checked against the single-bot model

**Blocker 1 (no per-tenant encrypted credential store) — your reasoning is sound; it no longer applies.** A single application-level bot token is one global secret, not a per-tenant credential, so it needs exactly the same secret storage you already use for Stripe keys — no pgsodium, no Vault, no `integrations` table. Discord's Developer Terms do require that developer credentials be "kept encrypted" and treated as confidential [discord](https://support-dev.discord.com/hc/en-us/articles/8562894815383-Discord-Developer-Terms-of-Service), which your existing Infisical-based secret handling already satisfies. The confirmation: yes, this blocker is dissolved by collapsing N tenant credentials into 1.

**Blocker 2 (no .NET runtime for DCE) — dissolves entirely with a native implementation.** You do not need DiscordChatExporter or .NET. The paginated fetch is `GET /channels/{id}/messages` with `limit` up to 100 and mutually-exclusive `before`/`after`/`around` snowflake cursors, returning newest-to-oldest [discord](https://discord.com/developers/docs/resources/message). The standard Node pattern is a loop of `channel.messages.fetch({ limit: 100, before: lastMessageId })` until a page returns fewer than 100 [stackoverflow](https://stackoverflow.com/questions/63322284/discord-js-get-an-array-of-all-messages-in-a-channel). This is low-risk — details in the engineering section below.

**Blocker 3 (Render web-only, 512MB, ephemeral disk) — feasible, but requires a paid Background Worker, not the free tier.** A chunked page-by-page job that streams to the database works within these constraints, but the free tier cannot host it (details in the Render section). This is the one place the rebuild costs you something real: roughly **$7/month** for a Starter Background Worker.

## OAuth mechanics confirmed — and the scaling cliff that is the actual new blocker

**The "Add to Server" flow works exactly as you hope: no token ever touches the admin.** Discord's bot-authorization OAuth2 flow is deliberately "server-less and callback-less" — it uses `scope=bot` with a `permissions=` integer (a bitfield including `READ_MESSAGE_HISTORY`, `1 << 16`) and does *not* return a user access token, because "there's no need to retrieve the user's access token." The admin is simply "prompted to add the bot to a guild in which they have proper permissions," and "on acceptance, the bot will be added" [discord](https://docs.discord.com/developers/topics/oauth2). The bot authenticates using "the bot token found in your app's settings" [discord](https://docs.discord.com/developers/topics/oauth2) — i.e., Signet holds one application-level token and reuses it to act in every server that installs the bot. Confirmed: the admin handles nothing.

**Retroactive full history holds under the single-app-multi-guild model.** History access is gated purely by the `READ_MESSAGE_HISTORY` permission, not by when the bot joined — Discord documents no "install-forward only" cutoff, only the permission requirement and the `before`/`after`/`around` cursor semantics [discord](https://docs.discord.com/developers/resources/message). This is a per-guild, per-channel permission property, so it applies identically whether the app is in 1 guild or 500.

**The new blocker: two scaling thresholds, both fatal to the feature if crossed unapproved.**

| Gate | Trigger | Consequence if unmet |
|---|---|---|
| **Bot verification** | **100 servers** (can apply from 75) | Bot "will not be able to grow past 100 servers"; if already past, "will not be able to join any more" [discord](https://support.discord.com/hc/en-us/community/posts/360050817314-Discord-Bots-Info) |
| **Message Content Intent review** | **~10,000 unique users** across all servers | Without approval, `content`/`embeds`/`attachments`/`components` return **empty** [discord](https://docs.discord.com/developers/resources/message) — export yields nothing |

Verification requires identity verification (via Stripe as Discord's provider) plus a questionnaire asking "which Intents you're applying for," "your use case for those Intents," and "data security and privacy questions," reviewed by a human [discord](https://support.discord.com/hc/en-us/community/posts/360050817314-Discord-Bots-Info). The current (as of June 2026) Message Content Intent Review Policy sets the privileged-intent trigger at **10,000 unique users** who can see the app across all its servers, and — importantly — the app "may continue to grow and join new servers" while review is pending [discord](https://support-dev.discord.com/hc/en-us/articles/5324827539479-Message-Content-Intent-Review-Policy). Verified bots have no maximum guild count [discord](https://docs.discord.com/developers/topics/oauth2).

**Why this is the crux of your decision.** Below ~100 servers / 10k users, you can simply toggle Message Content Intent *on* in the portal with no review — so the single-bot feature is fully functional and blocker-free through beta and early growth (dozens of chapters at ~100–150 members each). But the moment the product succeeds — roughly 70–100 chapters — the app hits both gates at once, and continued operation depends on Discord approving an application whose sole function is reading and permanently storing members' message content to move it onto a paid competing platform. That approval is (a) outside your control, (b) a single point of failure that breaks *every* chapter's import simultaneously if denied or revoked, and (c) faces the elevated risk profile detailed below. The per-chapter-bot design never crossed either threshold because each private bot stayed small — it distributed the risk instead of centralizing it.

## Native REST export: low-risk, ~100 lines, rate-limiting handled for you

**This is a well-trodden pattern, and the strongest single reason not to lean on DiscordChatExporter is that `@discordjs/rest` already solves the hard part — rate limiting — automatically.** Its `RequestHandler` uses an internal async queue, models both global and per-route buckets, and on a `429` "delays (`await Util.delayFor(this.retryAfter)`) and re-executes the request" [github](https://github.com/discordjs/discord.js/pull/4711/files). Global pacing defaults to Discord's documented 50 requests/second and is configurable via `globalRequestsPerSecond` [discordjs](https://discord.js.org/docs/packages/rest/main/RESTOptions:Interface). You do not hand-roll header parsing or backoff. You can also run **REST-only with no gateway/websocket** — `@discordjs/core` documents "Independent REST API Usage" (`new REST({version:'10'}).setToken(token)`) and gateway connection is a separate, optional step [discordjs](https://discordjs.dev/docs/packages/core/0.5.0). A batch export job needs no persistent bot process.

**Scope is genuinely small: ~20–40 LOC for the message loop, ~20–50 more for attachment rehosting** [stackoverflow](https://stackoverflow.com/questions/63322284/discord-js-get-an-array-of-all-messages-in-a-channel). The one real edge case is **threads**: active threads sync via the gateway but "archived threads are not synced up-front," so a complete export must enumerate archived public/private threads via separate HTTP endpoints (requiring `READ_MESSAGE_HISTORY`, plus `MANAGE_THREADS` for private archived threads) [discord](https://discord.com/developers/docs/topics/threads). This is modest extra code, not a reason to keep DCE.

**Attachment rehosting works server-side, same job run, memory-safe via streaming.** CDN URLs carry `ex`/`is`/`hm` signed-expiry params, but a freshly-fetched message object contains a currently-valid `url`, and Discord "automatically refreshes attachment CDN URLs" in returned payloads [discord](https://docs.discord.com/developers/reference). Supabase Storage's `upload` accepts `NodeJS.ReadableStream`/`ReadableStream` bodies [supabase](https://supabase.com/docs/reference/javascript/storage-from-upload), so the pattern is download-stream → upload-stream with no full-file buffering [github](https://gist.github.com/danalloway/d839a6ca18fd8878936c40f8470002cf). One honest gap: Discord does not publish CDN *download* bandwidth/rate caps, so at 100k–300k messages with video attachments, throttle downloads conservatively rather than assuming unlimited pull [discord](https://docs.discord.com/developers/topics/rate-limits). At chapter scale this is not expected to bite, but it's untested. (Your Phase-1 audit already built the `chat-archive` bucket at 100MB with a wide MIME list and a server-side `IStorageProvider.uploadFile()` path, so this half is largely in place.)

## Render feasibility: works, but needs a paid Background Worker and disciplined streaming

**The chunked-incremental pattern is the right one, but it cannot run on the free tier.** Render's free instances support only "Static Site, Web Service, Postgres, or Key Value" — "other service types don't support Free instances," and Render states plainly it "does not provide a free instance type for background workers" [render](https://render.com/docs/free) [render](https://render.com/articles/cron-jobs-vs-background-workers-vs-durable-workflows-picking-the-right-async-pri). A free web service also spins down after 15 minutes of no inbound traffic and "might restart at any time" [render](https://render.com/docs/free) — either event would kill a mid-run export. So a background export must live on a paid service.

**Recommended primitive: a paid Background Worker (Starter, 512MB, ~$7/mo).** The service-type choices are Web Service, Background Worker (continuous, no inbound URL, queue-driven), and Cron Job (run-and-exit on schedule) [render](https://render.com/docs/service-types). Render's own guidance for long multi-step jobs is to "acknowledge the incoming event quickly and offload the heavy reasoning to a background worker" [render](https://render.com/articles/best-cloud-platform-to-run-agents). Notably, Render web requests can run up to **100 minutes** [render](https://render.com/docs/render-vs-vercel-comparison), so a synchronous export isn't *forced* off the web service by a short timeout — but the free-tier spin-down/restart behavior and the memory contention with live request handling make a dedicated worker the correct choice. A Cron Job is also viable (hard-stopped at 12 hours per run [render](https://render.com/docs/cronjobs)) if you prefer triggered-and-exit over always-on.

**512MB is tight but workable — if, and only if, you stream.** RAM per tier: Free and Starter = 512MB, Standard = 2GB [render](https://render.com/pricing). Practitioners report container OOM kills at 512MB for memory-heavy Node workloads ("Out of memory (used over 512Mi)"), resolved by moving to the 2GB Standard plan [github](https://github.com/openclaw/openclaw/issues/5966). The implication for your job: writing messages to the database per-page (not accumulating) and streaming attachments (never buffering a full video in memory) keeps you within 512MB; buffering will OOM. If large video attachments prove problematic, the escape hatch is the 2GB Standard tier, not a redesign. Ephemeral disk is wiped on every deploy/restart [render](https://render.com/docs/disks.md), which reinforces stream-through-to-storage rather than staging files on local disk.

## Legal/ToS re-check: the single-bot commercial model sharpens every edge the prior research flagged

**No policy clause names "competitors" — but the single-bot-as-product model makes the clauses that already exist far more likely to apply.** The Developer Policy requires that you "may not request, access, or use API Data for any purpose other than as necessary to provide your Application's stated (and approved through App Review, as applicable) functionality," prohibits "sell[ing], licens[ing], or otherwise commercializ[ing] API Data," and prohibits "min[ing] or scrap[ing] any data" [discord](https://discord.com/developers/docs/policies-and-agreements/developer-policy/). The prior research judged a *one-off, owner-directed* export defensible against these. The shift to a repeatable product where Signet holds one token and processes every tenant's message content pushes toward the "commercializing End User Data / operating outside Discord's stated functionality" reading — precisely because Signet is a paid platform ingesting that content as a product input. There's no explicit competitor rule, but the commercialization and stated-functionality clauses are the ones a reviewer would reach for.

**The App Review clause is the sharpest new exposure.** Once approved through App Review, you "will not materially change your Application's functionality (including the scope of API Data you collect or how you use or share it) beyond its reviewed stated purpose, unless you first re-submit… and receive our approval" [discord](https://support-dev.discord.com/hc/en-us/articles/8562894815383-Discord-Developer-Terms-of-Service). This means at the 100-server / 10k-user gate you must *truthfully state* the purpose — "export server message history into our platform" — in the intent application. That is the exact framing most likely to draw scrutiny.

**Calibration on approval odds is mixed-to-cautionary.** The review guide warns that "'my bot needs message content' is not a justification," denies requests that "can be accomplished through interactions or other means without privileged intents," and pushes slash-command alternatives [discord](https://support-dev.discord.com/hc/en-us/articles/5324827539479-Message-Content-Intent-Review-Policy). A bulk historical export is a *stronger* necessity case than moderation bots — there is genuinely no slash-command way to read years of past message content. But the store-heavy profile is a headwind: the guide explicitly asks storage-based apps to justify "retention policy and security measures" [discord](https://support-dev.discord.com/hc/en-us/articles/5324827539479-Message-Content-Intent-Review-Policy), and a developer reported being **denied Message Content Intent twice for a ticket-transcript bot**, quoting Discord as saying "we don't want any ticket bots with Message Content Intent — no matter how advanced your implementation is" [reddit](https://www.reddit.com/r/Discord_Bots/comments/1jxyxo7/denied_discord_privileged_intent_twice_feels_like/). That is a category-level rejection of a store-message-content use case — a warning sign for an export bot. On the enforcement side, no official action against *bot-authorized* export/migration tools was found; documented account blocks remain concentrated on token-based/self-bot use, though one recent DiscordChatExporter GitHub report cites an account block for "platform abuse" without clearly specifying bot vs user token [github](https://github.com/Tyrrrz/DiscordChatExporter/issues/1497).

**The single shared token raises Signet's own contractual exposure — manageable, not a blocker.** Discord's Terms define "API Data" to explicitly include "your developer credentials and access tokens," require encryption and confidential handling, and impose retention/deletion duties — "promptly delete the API Data when… no longer necessary," on Discord's request, or on the user's request, plus deletion on termination [discord](https://support-dev.discord.com/hc/en-us/articles/8562894815383-Discord-Developer-Terms-of-Service). Centralizing into one Signet-operated app makes Signet unambiguously the responsible party for all of this across every tenant. Your Phase-2 per-import purge and deletion promise already move toward compliance; the gap the audit flagged (no chapter-level deletion path anywhere in the product, issue #1246) becomes more pressing under a model where Signet is the sole data operator.

## Bottom line and recommended shape

**The architecture is sound and buildable, and it does not reintroduce any *engineering* blocker — but it converts three solvable in-house infra problems into one external, uncontrollable dependency: Discord's approval to keep operating a content-reading bot past ~100 servers / 10k users.** That dependency is a single point of failure across all tenants and faces a plausibly high denial risk given the commercial-competitor, store-everything profile. It does *not* bite in beta or early growth, where the single bot works with zero friction.

Recommended path:
1. **Build the single-Signet-bot + native REST export** — the UX win is real and the sub-threshold window (up to ~100 chapters) is genuinely blocker-free. Use `@discordjs/rest` REST-only (no gateway), the `before`-cursor page loop, and stream attachments directly into the existing `chat-archive` Supabase bucket.
2. **Host the job on a paid Render Background Worker (Starter, 512MB, ~$7/mo)**, with strict per-page DB writes and streamed (never buffered) attachment rehosting; keep the 2GB Standard tier as the escape hatch if video attachments OOM.
3. **Treat Discord approval as a first-class product risk, not an afterthought.** Apply for verification early (allowed from 75 servers) and frame the Message Content Intent application honestly around user-directed data portability, emphasizing that historical export cannot be done via interactions. Assume it may be denied.
4. **Keep the already-shipped admin-owned-bot / DCE path as a documented fallback.** Because Phases 1–2 already built the schema, importer, and mapping UI against an upload flow, the fallback is nearly free to retain: if the shared bot is throttled or the intent is denied at scale, chapters revert to the (more technical, but always-available and per-tenant-risk-isolated) self-export path. This hedges the one blocker you cannot engineer around.
5. **Close the data-governance gap (#1246)** — a real chapter/tenant deletion path — before Signet becomes the sole operator of every chapter's Discord content, since the Developer Terms make deletion-on-request a contractual obligation you'd own centrally.

## Where more research would most change the conclusion

Two uncertainties carry the most weight. First, **the real-world approval rate for content-reading bots whose purpose is export/archival rather than moderation** — the one concrete data point found (a ticket-transcript bot denied twice, with a category-level "we don't want ticket bots with message content" rejection) is suggestive but not dispositive; a direct read from Discord's developer support, or an actual test submission of Signet's own intent application once near 75 servers, would resolve whether the scaling cliff is a real wall or a manageable hurdle. Second, **Discord CDN download rate/bandwidth limits at 100k–300k-message scale with video attachments** — undocumented publicly, and your feature has never run against real Discord (sandbox blocks the CDN), so the first supervised live import against your own chapter's data is the fastest way to convert that unknown into a measured fact.
